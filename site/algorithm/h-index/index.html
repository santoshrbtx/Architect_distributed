📊 H-Index

One number that balances how much you've produced against how much it mattered: you have index h if h of your items each got at least h "votes."

🧒 Explain it like I'm 10

The simple story

Imagine you draw lots of pictures, and people give each picture stars if they like it. Some pictures get tons of stars, some get only one or two.

Now you want one number that shows you're both a busy artist and a good one. Just counting pictures isn't fair (you could scribble 100 bad ones). Just looking at your single best picture isn't fair either (one lucky hit). So we play a game.

Here's the game: "What is the biggest number h where I have at least h pictures that each got h or more stars?"

  • If you have 3 pictures with 3 or more stars each → your number is at least 3.
  • Do you also have 4 pictures with 4 or more stars? If not, then 4 is too big.
  • So your magic number — your h-index — is 3.

It's a "best of both worlds" score. To make it bigger you need more pictures and each of them needs more stars. One amazing picture can't carry you, and a pile of ignored pictures can't either.

The rule a kid can follow

  1. Line up your pictures from most stars to fewest.
  2. Walk down the line counting: 1st, 2nd, 3rd…
  3. Keep going as long as the picture you're standing on has at least as many stars as your count.
  4. The last count that still works is your h-index!

The engineer's view

The h-index (Hirsch index, 2005) is a single scalar that summarizes a distribution. Formally: given an array citations[] of size n, the h-index is the maximum value h such that at least h elements are ≥ h (and the remaining n − h are ≤ h). It is exactly LeetCode #274 "H-Index". It's a robust order-statistic: insensitive to a single huge outlier and to a long tail of zeros, which is why it's used as a balanced productivity-vs-impact measure.

Two canonical solutions: a sort-based one (O(n log n)) and a counting-sort / bucket one (O(n) time, O(n) space). If the input is already sorted, a third binary-search approach gives O(log n) — that's LeetCode #275 "H-Index II".

Invariants, preconditions & edge cases

  • Bounded answer: 0 ≤ h ≤ n. The h-index can never exceed the number of papers, no matter how high any single citation count is.
  • Counting-sort key insight: citations larger than n contribute nothing extra — clamp them into a bucket at index n. That keeps the bucket array size n+1.
  • Monotonic suffix sum: scanning buckets from high to low, once the running count of papers with ≥ i citations reaches i, that i is achievable — return the largest such i.
  • Edge cases: all zeros → h = 0; single paper with many citations → h = 1; [n, n, … n] → h = n; empty array → 0.
  • Ties are handled naturally by the ≥ comparison.

Trade-offs & when NOT to use it

  • Sort vs counting: sorting is shorter and cache-friendly; counting sort wins only when n is large and you need guaranteed linear time. For typical inputs the constant factors make sorting competitive.
  • As a metric (not the algorithm): the h-index under-rewards a few blockbuster hits, can't decrease over time, is field-dependent (biology vs math cite at very different rates), and is gameable via self-citation. Don't use it to compare across disciplines or seniority without normalization.

Reference implementation (C#)

public class Solution
{
    // ---- Approach 1: counting sort — O(n) time, O(n) space ----
    public int HIndex(int[] citations)
    {
        int n = citations.Length;
        int[] buckets = new int[n + 1];      // buckets[i] = #papers with exactly i citations

        foreach (int c in citations)
            buckets[Math.Min(c, n)]++;        // clamp: anything > n lands in bucket n

        int count = 0;                         // running #papers with >= i citations
        for (int i = n; i >= 0; i--)        // scan from high citations down
        {
            count += buckets[i];
            if (count >= i) return i;          // h papers each with >= h citations
        }
        return 0;
    }

    // ---- Approach 2: sort + scan — O(n log n) time, O(1) extra ----
    public int HIndexSort(int[] citations)
    {
        Array.Sort(citations);                // ascending
        int n = citations.Length;
        for (int i = 0; i < n; i++)
        {
            int h = n - i;                     // #papers from index i to end
            if (citations[i] >= h) return h;     // these h papers all have >= h citations
        }
        return 0;
    }
}

🔁 How it works, step by step

Take the classic example citations = [3, 0, 6, 1, 5] (5 papers). The answer is h = 3. Let's see why with the sort & scan method.

  1. Sort descending: [6, 5, 3, 1, 0]. (We line papers up from most-cited to least.)
  2. Position 1 (count = 1): paper has 6 citations. Is 6 ≥ 1? Yes → h could be 1.
  3. Position 2 (count = 2): paper has 5. Is 5 ≥ 2? Yes → h could be 2.
  4. Position 3 (count = 3): paper has 3. Is 3 ≥ 3? Yes → h could be 3.
  5. Position 4 (count = 4): paper has 1. Is 1 ≥ 4? No → stop. The last value that worked was 3.

🌍 Real-world scenarios where the h-index pattern is used

The core idea — "the largest h where at least h items clear a threshold of h" — shows up far beyond academia, anywhere you want a single balanced score of volume × quality that resists outliers:

  • Academia & research (original use): Google Scholar, Scopus, and Web of Science show every researcher's h-index from their papers' citation counts to balance productivity against impact.
  • Open source & developer reputation: rank a maintainer by repos with at least h stars each, or a contributor by PRs with at least h reviews — a few viral repos or a pile of ignored ones don't dominate.
  • Content platforms & creators: a YouTuber/blogger "h-index" = h videos each with ≥ h thousand views; rewards consistent reach over a single viral fluke.
  • E-commerce & product ranking: score a seller by products that each have ≥ h positive reviews — filters out one-hit products and long tails of dead listings.
  • App stores / marketplaces: rank a developer by apps with at least h thousand downloads each.
  • Influencer / hiring analytics: a robust "track record" metric that's hard to game with a single spike, used to shortlist candidates or partners.
  • Algorithmically: the underlying technique — counting sort + suffix-count threshold — is a reusable trick for "find the largest k satisfying a monotonic count condition" problems in O(n).

📌 Cheat sheet

  • Definition: max h such that at least h items each have value ≥ h.
  • Bound: always 0 ≤ h ≤ n.
  • Sort method: sort, then find largest h = n − i with citations[i] ≥ h → O(n log n).
  • Counting method: bucket counts (clamp > n into bucket n), scan high→low, return first i where running count ≥ i → O(n).
  • Pre-sorted input: binary search → O(log n) (LeetCode #275).
  • Key trick: citations above n are wasted — clamp them.
  • Meaning: a balanced volume × quality score that ignores single outliers.
  • Watch out: field-dependent, can't decrease, gameable via self-citation — don't compare across domains blindly.
