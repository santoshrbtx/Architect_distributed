🌸 Bloom Filter

A tiny, super-fast memory that can say "definitely not here" or "probably here" — and never the other way around.

🧒 Explain it like I'm 10

The simple story

Imagine you have a huge box of toys — thousands of them. A friend keeps asking, "Do you have THIS exact toy?" Digging through the whole box every single time would take forever.

So you make a clever little trick. You put a row of light switches on the wall — all switched OFF to start. Every time you put a toy in the box, you look at the toy's name and follow a fixed rule to pick a few switches to flip ON (say "the 2nd, the 5th, and the 9th").

Now when your friend asks about a toy, you don't dig in the box. You just check the switches that toy's name points to:

  • If any of those switches is still OFF → you say "Nope, definitely don't have it!" — and you're 100% right, no digging needed. 🎉
  • If all of them are ON → you say "I probably have it," and only THEN do you dig to make sure.

Why only "probably"? Because two different toys might happen to flip some of the same switches. So the switches being ON could be a lucky coincidence. The wall of switches is tiny and super fast, and it saves you from digging through the giant box almost every time someone asks about a toy you don't have.

The rule a kid can follow

  1. Start with all switches OFF.
  2. Add a toy: use its name to pick a few switches, flip them ON.
  3. Asked about a toy: check its switches. Any one OFF → "No!" All ON → "Maybe — go check the box."

The engineer's view

A Bloom filter is a space-efficient probabilistic set membership data structure. It answers "is element x in the set?" with two possible answers: "definitely not" or "possibly yes." It allows false positives but never false negatives. It stores no elements themselves — only a bit array — so it cannot enumerate or delete members (in the classic form), and it trades a small, tunable error rate for enormous memory savings.

It consists of an m-bit array (all zero initially) and k independent hash functions, each mapping an element uniformly to [0, m). Insert: set the k bits at the hashed positions to 1. Query: if all k bits are 1 → "possibly present"; if any is 0 → "definitely absent."

Memory: roughly m ≈ -(n · ln p) / (ln 2)² bits for n items at false-positive rate p, and the optimal k = (m/n) · ln 2. In practice that's about 9.6 bits per element for 1% FP, and ~14.4 bits/element for 0.1% — independent of how big each element actually is. A set of 1 billion URLs at 1% FP needs only ~1.2 GB, versus storing the URLs themselves which would be hundreds of GB.

Invariants, preconditions & edge cases

  • No false negatives — ever. If query says "absent," it is truly absent. This is the property the whole design rests on.
  • False positives rise as the filter fills. Size m and k must be chosen up front for the expected n; exceeding n degrades p sharply.
  • No deletion in the standard form (clearing bits could create false negatives for other elements). Use a Counting Bloom filter (counters instead of bits) if you must delete, at higher memory cost.
  • Hash quality matters. k truly-independent hashes are emulated cheaply with double hashing: g_i(x) = h1(x) + i·h2(x).
  • Not enumerable — you cannot list the members; it only answers membership probabilistically.

Trade-offs vs. alternatives & when NOT to use it

  • vs. HashSet: a hash set is exact and supports deletion, but stores the full elements (huge memory) — use it when the set fits comfortably in RAM and you need exactness/enumeration.
  • vs. Cuckoo filter: cuckoo filters support deletion and often better space at low FP rates — prefer when deletes are required.
  • Don't use a Bloom filter when: you need exact answers, must delete frequently (without a counting variant), need to enumerate members, or the set is small enough that a plain hash set is simpler.
  • Best when: the set is huge, memory is precious, and a cheap "definitely not" answer lets you skip an expensive lookup (disk/network/DB).

Reference implementation (C#)

using System;
using System.Collections;

/// A classic Bloom filter: add + probabilistic membership test.
public class BloomFilter
{
    private readonly BitArray _bits;   // the m-bit array
    private readonly int _m;            // number of bits
    private readonly int _k;            // number of hash functions

    // n = expected item count, p = desired false-positive probability.
    public BloomFilter(int n, double p)
    {
        _m = (int)Math.Ceiling(-(n * Math.Log(p)) / (Math.Log(2) * Math.Log(2)));
        _k = Math.Max(1, (int)Math.Round((double)_m / n * Math.Log(2)));
        _bits = new BitArray(_m);
    }

    // Two base hashes → k positions via double hashing: h1 + i*h2.
    private (int h1, int h2) Hashes(string item)
    {
        int h1 = item.GetHashCode();
        int h2 = Fnv1a(item);
        return (h1 & 0x7fffffff, h2 & 0x7fffffff); // keep non-negative
    }

    public void Add(string item)
    {
        var (h1, h2) = Hashes(item);
        for (int i = 0; i < _k; i++)
            _bits[((h1 + i * h2) & 0x7fffffff) % _m] = true;
    }

    // false  => DEFINITELY not present.  true => PROBABLY present.
    public bool MightContain(string item)
    {
        var (h1, h2) = Hashes(item);
        for (int i = 0; i < _k; i++)
            if (!_bits[((h1 + i * h2) & 0x7fffffff) % _m])
                return false;          // any 0 bit ⇒ certainly absent
        return true;                   // all 1s ⇒ possibly present
    }

    private static int Fnv1a(string s)
    {
        uint hash = 2166136261;
        foreach (char c in s) { hash ^= c; hash *= 16777619; }
        return (int)hash;
    }
}

🔁 How it works, step by step

Let's use a tiny filter with m = 10 bits and k = 3 hash functions. We add "cat" and "dog", then query "cow" and "dog".

  1. Start empty. All 10 bits are 0.
  2. Add "cat". The 3 hashes give positions 1, 4, 7. Flip those bits to 1.
  3. Add "dog". The 3 hashes give positions 4, 6, 9. Flip those to 1 (position 4 was already on — fine).
  4. Query "cow". Its hashes give 2, 4, 7. Check them: bit 2 is 0 → stop → "DEFINITELY NOT present." No false negative possible.
  5. Query "dog". Its hashes give 4, 6, 9 — all 1 → "PROBABLY present." (Here it's truly present.)

🌍 Where Bloom filters are used in the real world

The pattern is always the same: a "definitely not" answer lets you skip an expensive operation (a disk read, a network call, a database hit). The filter lives in cheap RAM and filters out the easy "no" cases.

  • Databases (LSM-trees) — Cassandra, RocksDB, LevelDB, HBase, Bigtable: each on-disk SSTable carries a Bloom filter of its keys. Before a costly disk seek, the engine asks the filter "could this key be here?" — a "no" skips the disk read entirely. This is the textbook production use.
  • URL Shortener / web crawlers: "have we already generated this short code / crawled this URL?" A Bloom filter answers in O(1) from memory and avoids hitting the database for the overwhelmingly common "never seen it" case. (See the URL-shortener system-design page.)
  • CDNs & caches (e.g. Akamai, Redis-adjacent layers): the "one-hit-wonder" problem — only cache an object on its second request. A Bloom filter tracks "have we seen this URL before?" so single-access objects never pollute the cache.
  • Chrome Safe Browsing (historically): the browser kept a local Bloom filter of malicious URLs. Most sites are safe → filter says "not malicious" instantly; only on a "maybe" does it make the expensive server check.
  • Bitcoin / SPV wallets (BIP 37): lightweight clients used Bloom filters to ask peers only for transactions relevant to their addresses without revealing exactly which addresses.
  • Spam / duplicate detection & recommendation: "has this user already seen this article/ad?" — filter out already-shown items cheaply at huge scale.
  • Networking: packet routing/forwarding tables and distributed cache coordination (e.g. summary cache for proxy cooperation).

📌 Cheat sheet

  • What: probabilistic set membership — "definitely not" or "probably yes."
  • Guarantee: NO false negatives; false positives are possible and tunable.
  • How: m-bit array + k hash functions. Insert = set k bits. Query = all k bits set?
  • Cost: O(k) insert & query; ~9.6 bits/element for 1% FP — independent of element size.
  • Tuning: m ≈ -(n·ln p)/(ln2)², optimal k = (m/n)·ln2.
  • Can't: delete (use Counting Bloom filter), enumerate members, give exact answers.
  • Use when: a cheap "no" lets you skip a costly disk/network/DB lookup at scale.
  • Star use case: LSM-tree databases skipping disk reads; crawlers/URL shorteners skipping "seen it?" DB hits.
