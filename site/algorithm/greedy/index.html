Greedy Algorithm

Always grab the best-looking choice right now, and hope those local wins add up to the overall best answer.

The simple story

Imagine you have a piggy bank to break open, and you want to give your friend ₹63 using the fewest coins. You have coins of ₹20, ₹10, ₹5, and ₹1.

A "greedy" person doesn't think too hard about the future. They just say:

"What's the biggest coin I can grab right now that still fits?" — and they grab it. Then they ask the same question again, and again, until they reach ₹63.

  • Grab a ₹20 → you've given 20. (Need 43 more)
  • Grab another ₹20 → now 40. (Need 23 more)
  • Grab another ₹20 → now 60. (Need 3 more)
  • ₹20 is too big now, so grab ₹1, ₹1, ₹1 → now 63. Done! 🎉

That's 6 coins, and you never had to undo or rethink a choice. Greedy = grab the biggest helpful thing every time, and never look back.

⚠️ But be careful! Sometimes grabbing the biggest thing first leads you to a worse answer. A greedy kid grabbing the biggest slice of pizza first might end up with less total pizza if the slices are tricky sizes. Greedy is fast and easy, but it's not always the smartest.

The engineer's view

A greedy algorithm is an algorithmic paradigm (not a single algorithm) that builds a solution incrementally, at each step committing to the choice that looks locally optimal under a fixed selection heuristic, and never revisiting that choice (no backtracking). It produces a globally optimal result only when the problem exhibits two structural properties:

  • Greedy-choice property: a globally optimal solution can be reached by making locally optimal choices — the future decision space never needs a choice already discarded.
  • Optimal substructure: an optimal solution to the problem contains optimal solutions to its subproblems (shared with DP).

When the greedy-choice property does not hold, greedy yields a heuristic/approximate answer — sometimes with a provable approximation ratio (e.g., set cover ≈ ln n).

Where it shows up in real systems

  • Dijkstra / Prim / Kruskal — shortest paths and minimum spanning trees (routing, network design).
  • Huffman coding — optimal prefix-free compression (ZIP, JPEG, MP3 entropy stage).
  • Interval scheduling / activity selection — CPU job scheduling, meeting-room allocation, bandwidth reservation.
  • Load balancers & caches — heuristics like "send to least-loaded node now"; LRU-style eviction.
  • Fractional knapsack — optimal via greedy (unlike 0/1 knapsack, which needs DP).

Complexity

There is no single complexity — it's dominated by the selection step. The canonical pattern is "sort, then one linear pass":

PhaseCostNote
Sort by greedy keyO(n log n)most common bottleneck
Single greedy passO(n)one decision per element
With a priority queueO(n log n)e.g. Dijkstra/Huffman, n extract-min ops
SpaceO(1) – O(n)O(1) if in-place; O(n) if a heap/result set is kept

Contrast with dynamic programming, which explores/combines subproblems (often O(n·W) or O(n²)). Greedy is faster precisely because it commits without exploring alternatives.

Edge cases & traps

  • 0/1 Knapsack: greedy by value/weight ratio is wrong — items are indivisible, so you can get stuck. Needs DP.
  • Coin change with arbitrary denominations: greedy fails for sets like {1, 3, 4} making 6 → greedy gives 4+1+1 (3 coins) but optimal is 3+3 (2 coins). It only works for "canonical" systems (e.g. standard currency).
  • Negative edge weights: Dijkstra's greedy assumption breaks; use Bellman-Ford.
  • Proof obligation: never ship a greedy solution to an optimization problem without an exchange-argument or matroid proof that the greedy choice is safe.

Reference implementation — Activity Selection (provably optimal greedy)

Pick the maximum number of non-overlapping activities. The safe greedy choice: always take the activity that finishes earliest, because it leaves the most room for the rest.

def max_activities(activities):
    # activities: list of (start, finish) tuples
    # Greedy key: sort by finish time ascending — the heart of the algorithm.
    activities.sort(key=lambda a: a[1])

    selected = []
    last_finish = float('-inf')

    for start, finish in activities:
        # Greedy choice: take it iff it doesn't overlap what we've kept.
        if start >= last_finish:
            selected.append((start, finish))
            last_finish = finish      # commit, never reconsider

    return selected

# O(n log n) for the sort, O(n) for the pass → O(n log n) total, O(n) space.
Why it's provably optimal: exchange argument — if any optimal solution doesn't start with the earliest-finishing activity, you can swap that activity in without reducing the count. Hence the greedy choice is always "safe."

  2. Take A(1–4) — earliest finish. last_finish = 4.
  3. B(3–5)? starts at 3 < 4 → overlaps. Skip.
  4. C(0–6)? starts at 0 < 4 → overlaps. Skip.
  5. Take D(5–7) — starts at 5 ≥ 4. last_finish = 7.
  6. E(5–9)? starts at 5 < 7 → overlaps. Skip.
  7. Take F(8–9) — starts at 8 ≥ 7. last_finish = 9. Result: {A, D, F} = 3 meetings.

📌 Cheat sheet

  • Idea: at each step take the locally best option; never undo.
  • Use when: problem has greedy-choice property + optimal substructure.
  • Typical shape: sort by a clever key → single linear pass → O(n log n).
  • Wins: Dijkstra, Prim, Kruskal, Huffman, activity selection, fractional knapsack.
  • Fails: 0/1 knapsack, arbitrary-coin change, graphs with negative edges → use DP / Bellman-Ford.
  • Golden rule: greedy is fast and simple, but prove the greedy choice is safe before trusting it for optimization.
