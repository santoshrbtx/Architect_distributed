⏱️ Big O Notation (Time Complexity)

A way to describe how the work an algorithm does grows as the input grows — ignoring the small stuff, so you can compare algorithms at a glance.

🧒 Explain it like I'm 10

The simple story

Imagine your teacher gives you a stack of homework sheets and asks, "How long will this take?" You don't answer in exact minutes — you answer with the pattern: "It depends on how many sheets there are."

Big O is just that: a way to say "if the pile gets bigger, how much MORE work do I have to do?" Let's say you have N sheets.

  • If you just grab the top sheet and read its title — that's always one action, no matter how big the pile is. We call that O(1). Super fast. 🎉
  • If you have to read every sheet once — 10 sheets = 10 reads, 100 sheets = 100 reads. The work grows in step with the pile. That's O(N).
  • If for every sheet you must compare it to every other sheet (like checking everyone shook hands with everyone) — that explodes fast. 10 sheets = 100 checks, 100 sheets = 10,000 checks. That's O(N²). Yikes. 😅
  • If you can throw away half the pile every time (like a guessing game: "higher or lower?") you finish in just a few steps even for a huge pile. That's O(log N). Magic. ✨

The big idea: Big O doesn't care about the exact number of minutes — it cares about the shape of how the work grows when things get bigger.

💡 Your question: why is O(2N) still O(N)?

Why O(N), O(2N), and O(N + 100) are all just O(N)

This is the heart of Big O, and you already spotted it. Big O answers only one question: how does the work grow as N gets HUGE? It throws away two things on purpose:

  • Constant multipliers (the "2" in 2N) — because doing the loop twice is still a straight line shape, just a slightly steeper one. Whether you read the pile once or twice, doubling the pile still doubles your work. The growth pattern is identical.
  • Lower-order / smaller terms (the "+100", or the "+N" next to an "N²") — because once N is gigantic, the biggest term completely drowns out the rest.
Think about N = 1,000,000 (one million): O(N) → 1,000,000 steps O(2N) → 2,000,000 steps ← only 2× bigger, SAME straight-line shape O(N + 100) → 1,000,100 steps ← the +100 is invisible at this scale O(N²) → 1,000,000,000,000 steps ← a MILLION times worse! The gap between O(N) and O(2N) is tiny and fixed (×2). The gap between O(N) and O(N²) grows without limit. Big O only cares about that second kind of gap.

The rule in plain words: "Keep only the fastest-growing term, and drop any number multiplied in front of it." So 3N² + 5N + 800 becomes O(N²). 2N becomes O(N). We don't write O(2N) because the 2 doesn't change the category — and Big O is about categories of growth, not exact step counts.

Why ignore the constant in practice? A "2×" difference can be wiped out by a faster CPU, a better compiler, or a different language. But a difference in shape — O(N) vs O(N²) — can never be fixed by faster hardware once N is big enough. That's the difference Big O is built to capture.

The engineer's view

Big O gives an asymptotic upper bound on the growth rate of an algorithm's running time as input size n → ∞. Formally, f(n) = O(g(n)) iff there exist constants c > 0 and n₀ such that 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀. That definition is precisely why constant factors and lower-order terms vanish: they're absorbed into c and become irrelevant past n₀.

Big O is the upper bound; its siblings are Ω (omega) for the lower bound and Θ (theta) for a tight bound (when upper and lower match). In interviews "Big O" is used loosely to mean the tight worst-case bound. We also distinguish best / average / worst case, and amortized cost (average over a sequence of operations, e.g. dynamic-array append is amortized O(1) despite occasional O(n) resizes).

Why we drop constants & lower-order terms

  • Constant factors (the c) are platform-dependent — CPU, cache, language, compiler — and not a property of the algorithm. Asymptotic analysis deliberately abstracts them away.
  • Lower-order terms are dominated: limn→∞ (3n² + 5n + 800)/n² = 3, a constant, so the function is Θ(n²).
  • Caveat: constants do matter in the real world for small/medium n. An O(n²) algorithm can beat an O(n log n) one for tiny inputs (why hybrid sorts like introsort/Timsort switch to insertion sort under ~16 elements).

How to derive it (rules of thumb)

  • Sequential blocks add: O(a) then O(b) → O(a + b) → keep the bigger.
  • Nested loops multiply: a loop inside a loop over n → O(n²).
  • Halving the problem each step → a log n factor.
  • Drop constants and non-dominant terms at the end.

Quick reference: code → complexity (C#)

// O(1) — one operation regardless of n
int First(int[] a) => a[0];

// O(n) — one pass. (Two separate passes = O(2n) = O(n).)
int Sum(int[] a) {
    int s = 0;
    foreach (var x in a) s += x;   // n steps
    foreach (var x in a) s += x;   // + n steps  → still O(n)
    return s;
}

// O(n²) — nested loop over the same input
bool HasDuplicate(int[] a) {
    for (int i = 0; i < a.Length; i++)
        for (int j = i + 1; j < a.Length; j++)
            if (a[i] == a[j]) return true;  // ~n²/2 pairs → O(n²)
    return false;
}

// O(log n) — halve the search space each step (binary search)
int BinarySearch(int[] a, int target) {
    int lo = 0, hi = a.Length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;   // throw away half each loop
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}

🔁 How to find the Big O of a piece of code

Walk this recipe on the example below.

  1. Count the work in terms of n for each part of the code.
  2. Loops add or multiply: sequential loops add; nested loops multiply.
  3. Drop the constant multipliers (the 2 in 2n, the ½ in n²/2).
  4. Drop the lower-order terms (keep only the biggest).
  5. What remains is your Big O.
void Example(int[] a) {
    Console.WriteLine(a[0]);            // (A) O(1)

    foreach (var x in a)                // (B) O(n)
        Console.WriteLine(x);

    for (int i = 0; i < a.Length; i++)   // (C) nested → O(n²)
        for (int j = 0; j < a.Length; j++)
            Console.WriteLine(a[i] + a[j]);
}
Total = (A) + (B) + (C) = O(1) + O(n) + O(n²) = 1 + n + n² Step 3 — drop constants: nothing to drop here. Step 4 — keep the biggest term: n² dominates n and 1. ⇒ O(n²) (Same logic turns 2n + 100 into O(n): drop the 2, drop the 100.)

📌 Cheat sheet

  • What it is: how an algorithm's work grows as input n grows — not exact time.
  • Golden rule: keep the biggest term, drop constants & smaller terms. So 2n → O(n), 3n²+5n+9 → O(n²).
  • Why drop the 2? It's a fixed multiplier (and hardware/compiler-dependent); it never changes the growth shape. Big O compares shapes.
  • Order (best→worst): O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!).
  • Loops: sequential add, nested multiply, halving adds a log n.
  • O / Ω / Θ: upper bound / lower bound / tight bound.
  • Reality check: constants matter for small n — that's why real sorts switch to insertion sort on tiny chunks.
❓ FAQ — your follow-up questions

Questions asked about this algorithm

If O(n) and O(2n) are the same, is it fair to also consider O(100n) as O(n)?

Yes — completely correct. O(n), O(2n), O(100n), even O(1,000,000n) are all the same class: O(n). Big O drops any constant multiplier because it's a fixed number that doesn't change as n grows — so the growth shape (a straight line) stays the same; only its steepness changes. The mental test: "does the multiplier stay constant as n changes?" If yes (2, 100, …) drop it → O(n); if it depends on n (like n·n or n·log n) keep it, because then it changes the category. Real-world caveat: in theory O(100n)=O(n), but for a given input a 100-pass algorithm really is 100× slower — Big O measures scalability/growth, not raw speed on one machine.
