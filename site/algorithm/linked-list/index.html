🔗 Linked List

A chain of little boxes where each box holds a value and a note pointing to the next box — cheap inserts, no shuffling, at the cost of random access.

🧒 Explain it like I'm 10

The treasure hunt story

Imagine you and your friends are playing a treasure hunt. There is no big map. Instead, the first clue is in your pocket. That clue says:

"Look under the red flowerpot."

You run to the red flowerpot. Under it, you find a small toy… and a new clue. The new clue says:

"Look behind the swing."

Behind the swing there's another toy… and another clue. And on and on, until one clue says "That's it, you're done!"

That is a linked list. Each hiding spot has two things:

  • 🎁 a toy (the actual thing you care about)
  • 👉 a note that tells you where to look next

Why is this cool?

Say your friend wants to add a new hiding spot in the middle. They don't have to move all the toys around. They just:

  1. Pick a new spot (say, "the mailbox").
  2. Hide a toy there.
  3. Change one clue to point to the mailbox first, and write a new clue at the mailbox that points to whatever came next.

Two little changes — done! Nobody had to run around moving anything else. That's the superpower of a linked list: adding and removing is easy, because everything is tied together by little clues instead of being crammed into fixed spots.

The downside

Want the 7th toy? You can't just jump to it. You have to start at clue #1 and follow, follow, follow, follow, follow, follow, follow. Six hops to get to the seventh spot. There's no shortcut.

🧑‍🎓 In laymen terms — for a curious beginner

What it is and why anyone should care

A linked list is a way of storing a bunch of items — a to-do list, a queue of songs, a browser's history — where the items are not sitting next to each other in memory. Each item carries a little arrow that says "the next item lives over there."

To picture it, think of a train. A train is a bunch of carriages coupled one to the next. You can walk from the front carriage to the back only by going through each one in order. But adding a new carriage in the middle of the train just means unhook, insert, re-hook — you don't have to move every carriage after it.

The problem it solves

Computers usually store lists in an array (a long shelf where item #1 is right next to item #2, item #2 is right next to item #3, and so on). Arrays are great for reading — "give me item #5" is instant. But inserting or removing an item in the middle is painful: everything after it has to physically shift one spot to fill the gap or make room.

A linked list fixes exactly that pain. You pay more to look things up, and less to change the list.

A tiny concrete example

Say your favourite songs are in this order:

Bohemian Rhapsody → Hotel California → Imagine → ⛔ (end)

Each song is a little box. Each box has (1) the song name and (2) an arrow that says "next song is here." The last box has an arrow pointing to nothing — that means "end of the list."

Now you want to add "Yesterday" between Hotel California and Imagine. Here's what happens:

  1. Make a new box for "Yesterday."
  2. Copy Hotel California's arrow into Yesterday's arrow (so Yesterday now points to Imagine).
  3. Change Hotel California's arrow to point to Yesterday.

Two arrows changed. That's it. Nothing else moved. In an array, you'd have to shove Imagine and everything after it one slot down to make room.

How fast/slow does it feel?

  • Add a song at the front? Instant. (One arrow flip.)
  • Add or remove one you already have a hold of? Instant.
  • "Give me the 100th song"? Slow — you have to walk from song 1, following arrows, 99 times. Twice as many songs → twice as long to find one in the middle.

The rule of thumb: a linked list is great when you're always inserting/removing and rarely jumping to a specific position; an array is the opposite.

When you'd use one in real life

  • 🎵 Music playlist — you skip forward one, go back one, and occasionally splice a new track in.
  • 🌐 Browser history — Back and Forward are just "follow the previous arrow" and "follow the next arrow."
  • ↩️ Undo / Redo — each action is a node linked to the one before it.
  • 🚦 Round-robin turn-taking — the last person's arrow points back to the first, forming a circle so it never runs out.

The engineer's view

A linked list is a linear collection of nodes where each node holds a payload and one or more pointers/references to other nodes. Storage is non-contiguous; iteration is pointer-chasing. Three canonical flavours:

FlavourNode layoutKey property
Singly Linked (SLL){ value, next }Forward-only traversal. Cheapest per-node.
Doubly Linked (DLL){ value, next, prev }O(1) delete given a node reference; iterate both ways. Used by LRU cache, browser history, std::list, .NET LinkedList<T>, Linux kernel list_head.
CircularLast node's next points back to headRound-robin schedulers, Josephus, cyclic buffers, ring queues.

Invariants & edge cases to reason about

  • Empty list ⇔ head == null. Always test this before dereferencing.
  • Single-element list — head and tail are the same node; deleting means both become null.
  • Tail pointer must be maintained on every insert/delete at the tail; forgetting this is the classic bug.
  • Cycles — a corrupted next creates infinite loops. Use Floyd's tortoise & hare (two-pointer, one step vs. two) to detect O(n) time / O(1) space.
  • Reversal is the canonical interview problem. Iterative: three pointers (prev, curr, next) rewrites arrows in place, O(n)/O(1).
  • Cache locality — nodes are usually heap-allocated, so pointer chasing incurs cache misses. On modern CPUs this is often the deciding factor against linked lists for hot paths; an array or ArrayList/List<T> frequently beats a linked list even for "insert in the middle" scenarios up to surprisingly large N.

When NOT to use a linked list

  • You need indexed random access (arrays / List<T>).
  • Payload is tiny and cache-friendliness matters (contiguous storage wins).
  • You need binary search, sorting is frequent, or you plan to hand the data to SIMD/vectorised code.
  • Memory-constrained: two pointers per element is 16 bytes of overhead on 64-bit — significant for millions of small values.

Reference implementation (C#)

// A singly linked list with O(1) head/tail insert, reversal, and cycle detection.
public class LinkedList<T>
{
    private class Node
    {
        public T Value;
        public Node? Next;
        public Node(T v) { Value = v; }
    }

    private Node? _head, _tail;
    public int Count { get; private set; }

    // O(1) — insert at head
    public void AddFirst(T value)
    {
        var node = new Node(value) { Next = _head };
        _head = node;
        _tail ??= node;         // list was empty — new node is also tail
        Count++;
    }

    // O(1) — insert at tail (tail pointer maintained)
    public void AddLast(T value)
    {
        var node = new Node(value);
        if (_tail == null) { _head = _tail = node; }
        else              { _tail.Next = node; _tail = node; }
        Count++;
    }

    // O(n) — remove first node matching value; returns true if removed
    public bool Remove(T value)
    {
        Node? prev = null, cur = _head;
        while (cur != null)
        {
            if (EqualityComparer<T>.Default.Equals(cur.Value, value))
            {
                if (prev == null) _head = cur.Next; // removed head
                else              prev.Next = cur.Next;
                if (cur == _tail) _tail = prev;         // removed tail
                Count--;
                return true;
            }
            prev = cur; cur = cur.Next;
        }
        return false;
    }

    // O(n)/O(1) — iterative reverse (rewire arrows in place)
    public void Reverse()
    {
        Node? prev = null, cur = _head;
        _tail = _head;
        while (cur != null)
        {
            var next = cur.Next;   // remember the rest of the list
            cur.Next = prev;         // flip this arrow
            prev = cur;              // advance the two pointers
            cur = next;
        }
        _head = prev;
    }

    // Floyd's tortoise & hare — O(n) time, O(1) space
    public bool HasCycle()
    {
        Node? slow = _head, fast = _head;
        while (fast?.Next != null)
        {
            slow = slow!.Next;
            fast = fast.Next.Next;
            if (slow == fast) return true;
        }
        return false;
    }

    public IEnumerable<T> Values()
    {
        for (var n = _head; n != null; n = n.Next) yield return n.Value;
    }
}

Note: in production .NET, prefer System.Collections.Generic.LinkedList<T> — it's a doubly-linked list with an exposed LinkedListNode<T> giving true O(1) removal given a node reference. That handle-based API is the whole point.

🌍 Real-world scenarios where linked lists shine

Where they earn their keep in real systems

Linked lists rarely stand alone in modern app code — but they are everywhere inside the systems those apps sit on. Below are the classic ones, with the specific reason each system chose a linked list over an array.

Doubly

🧠 LRU Cache (Redis, Memcached, browsers, OS page cache)

A doubly linked list stores entries in "most-recently-used → least-recently-used" order; a hash map gives O(1) lookup to the node. On a hit, unlink the node and move it to the head — O(1). On overflow, evict the tail — O(1). An array can't do either without shifting.

Doubly

🌐 Browser history & Back/Forward buttons

Each page is a node; prev is Back, next is Forward. Navigating to a new URL from the middle truncates the forward chain by simply nulling one pointer — no array copy.

Singly

↩️ Undo / Redo stacks (Photoshop, VS Code, Word)

Each edit is pushed on a linked stack; branching (edit → undo → new edit) discards the tail chain by dropping one pointer. Cheap even when the history is huge.

Circular

🔁 Round-robin CPU / thread scheduler

Runnable threads form a circular list; after each time slice the OS advances current = current.next. Never runs out; adding/removing a thread is one pointer swap. Used by classic Unix schedulers and Windows internal ready queues.

Doubly

🐧 Linux kernel list_head

The kernel's most-used data structure. Processes, open files, network sockets, timers, memory regions — all threaded together with the list_head intrusive doubly-linked list. Insert/remove in O(1) without allocations because the pointer field lives inside the object.

Singly

💾 Free-list memory allocators (malloc, JVM, .NET)

Free memory chunks are chained into a linked list. Allocation pops the head; free() pushes the block back. Cheap, no compaction needed, and the "next" pointer lives inside the free chunk itself (zero overhead when in use).

Singly

🧱 Hash map collision chaining

Java's HashMap, Go's older map, glibc's dictionaries — each bucket holds a linked list (or tree, if long) of colliding entries. Adding a new colliding key is O(1) at the bucket head.

Doubly

🎵 Music player playlists

Spotify's queue, VLC's playlist, Apple Music's Up Next — inserts at cursor, drag-to-reorder, and prev/next are all one pointer flip. Random shuffle is a separate index.

Singly

📈 Adjacency list (graph representation)

Most graph implementations (social networks, road networks, Neo4j-style stores) represent each vertex's neighbours as a linked list. Sparse graphs use way less memory than an adjacency matrix.

Singly

⛓️ Blockchain

Each block stores the hash of the previous block — a linked list where the "arrow" is a cryptographic hash rather than a raw pointer. Tampering with any past block breaks every arrow after it.

Doubly

🗃️ Redis LIST data type

Historically implemented as a doubly linked list (now a quicklist of ziplists for memory efficiency). Powers LPUSH/RPUSH/BLPOP — job queues, chat backlogs, rate-limit windows all at O(1) at either end.

Circular

🎮 Game turn order

Poker, Uno, Mario Party — players are a circular list; whose-turn-next is current = current.next. Eliminating a player is one unlink.

Singly

✉️ Message queues & event loops

Windows message pump, Node.js task queues, actor mailboxes — an enqueue-at-tail / dequeue-at-head singly-linked FIFO with a tail pointer gives O(1) at both ends without ever resizing.

Doubly

🧵 Concurrency primitives

OS wait queues (mutex/semaphore/condvar waiters), Go's scheduler run-queue, Java's ConcurrentLinkedQueue. Lock-free versions (Michael-Scott queue) rely on linked structures for CAS-friendly single-pointer mutations.

The pattern behind the pattern

Look at every real-world use above and you'll see the same three fingerprints:

  1. Mutations dominate over indexed reads — you're always adding, removing, or moving nodes, not asking for "item #47."
  2. You already hold a reference to the node you want to change — via a hash map, a cursor, a stack pointer, a wait handle — so you never pay the O(n) find cost.
  3. The order matters and it changes — reorder, splice, evict-oldest, take-next. Order is the payload.

When those three line up, a linked list is the right tool. When they don't (fixed-size table, random-access lookups, tight numeric crunching) — reach for an array.

🔁 How it works, step by step

Let's insert 50 between 20 and 30 in the list [10 → 20 → 30 → 40]. Two pointer changes, nothing shifts.

Starting state

head │ ▼ ┌────┬───┐ ┌────┬───┐ ┌────┬───┐ ┌────┬────┐ │ 10 │ ●─┼──▶│ 20 │ ●─┼──▶│ 30 │ ●─┼──▶│ 40 │ ⛔ │ └────┴───┘ └────┴───┘ └────┴───┘ └────┴────┘
  1. Walk to the insertion point. Start at head; step until prev.value == 20. We now hold prev.
  2. Create the new node. Allocate node = {value: 50, next: null}. Nothing is wired up yet.
  3. Point the new node forward. node.next = prev.next — so 50's arrow now points to 30. Note we didn't touch 20's arrow yet; both 20 and 50 point to 30 for a moment. That's fine — no reader will observe the half-state in single-threaded code.
  4. Redirect the previous node. prev.next = node. Now 20 points to 50, and 50 points to 30. The list is repaired.
  5. Increment count. count++. Done. Two writes total, zero shifts.

After the insert

head │ ▼ ┌────┬───┐ ┌────┬───┐ ┌────┬───┐ ┌────┬───┐ ┌────┬────┐ │ 10 │ ●─┼──▶│ 20 │ ●─┼──▶│ 50 │ ●─┼──▶│ 30 │ ●─┼──▶│ 40 │ ⛔ │ └────┴───┘ └────┴───┘ └────┴───┘ └────┴───┘ └────┴────┘

Contrast with an array: to insert 50 at index 2 in [10, 20, 30, 40], positions 30 and 40 must physically move to indices 3 and 4 — that's O(n) memory writes. The linked list did it in two.

The reverse operation, visualised

Reversing [A → B → C → null] in place with three pointers (prev, curr, next):

initial: prev=null curr=A A → B → C → null step 1: A.next=null, prev=A, curr=B (A alone; B → C → null) step 2: B.next=A, prev=B, curr=C (B → A → null; C → null) step 3: C.next=B, prev=C, curr=null (C → B → A → null) ✓ head = prev = C

O(n) time, O(1) extra space, works on any singly-linked list.

📌 Cheat sheet

  • Shape: nodes = {value, next} (+ prev if doubly). Non-contiguous memory, connected by pointers.
  • Speed: insert/delete at a known node = O(1). Access index i = O(n). No random access — that's the whole trade.
  • Space: +1 pointer per node (singly) or +2 (doubly). 8–16 bytes overhead per element on 64-bit.
  • Bugs to watch for: forgetting to update the tail pointer, dereferencing a null next, cycles (use tortoise & hare), off-by-one in "walk to prev."
  • Pick it when: you insert/delete a lot at known positions, order matters and changes, you already have a handle to the node (LRU, wait queues, undo stacks).
  • Skip it when: you need index access, you're hot-loop scanning small numeric data (cache locality wins), or memory overhead per item is tight.
  • Canonical interview problems: reverse, detect cycle, merge two sorted lists, find k-th from end (two-pointer offset), remove n-th from end, LRU cache.
  • .NET: use LinkedList<T> for real O(1) node ops via LinkedListNode<T>. Use List<T> for indexed access — it usually beats a linked list even on "middle inserts" up to a few thousand items due to cache behaviour.
