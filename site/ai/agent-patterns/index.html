AI · Agent Design Patterns

Patterns for Building LLM Agents

A tour of the eleven patterns that show up in every production agent stack — ReAct, Chain-of-Thought, Human-in-the-Loop, Reflexion, Plan-and-Execute, Router/Handoff, Multi-Agent, RAG, Tool Use, Self-Consistency, Tree-of-Thoughts — each with a plain-English "what is this really doing?" analogy so you can pick the right one in an interview or design review.

🎯 The setup

What actually makes a program "an agent"?

An agent is an LLM wrapped in a loop that (1) can decide what to do next, (2) can call tools to affect the outside world, and (3) can observe the result and adjust. Take away the loop and you just have "call the model once." Take away tools and you have a chatbot. Take away the ability to observe results and you have a script that hallucinates its outputs.

Every pattern below is a recipe for that loop: what the LLM should be thinking about at each step (reasoning), who is allowed to act (the model, a human, another agent), how many paths are explored (one, N, a tree), and where the knowledge comes from (weights, retrieval, or a delegated specialist).

Mental model. Pick a pattern the same way you pick a data structure: first understand the shape of the problem (deterministic vs open-ended, one-shot vs multi-step, cheap vs high-stakes), then pick the pattern whose trade-offs match. Composing patterns is normal — a production agent is usually ReAct + RAG + HITL + a Router, not one pattern in isolation.

🧑‍🎓 The whole page in one paragraph

An agent is a very literal assistant with a small toolbelt

Picture a new intern who is brilliant at reading and writing but has never worked in your office. To make them useful, you have to teach them a few habits:

  • Think out loud before answering hard questions — that's Chain of Thought.
  • Try, look at what happened, try again instead of guessing in one shot — that's ReAct.
  • Ask a grown-up before doing anything scary (sending money, deleting files) — that's Human-in-the-Loop.
  • Grade your own work and redo the bad parts — that's Reflexion.
  • Write a plan first, then follow it — that's Plan-and-Execute.
  • Explore a few possible paths and pick the best — that's Tree of Thoughts.
  • Ask three interns the same question and go with the majority — that's Self-Consistency.
  • Give them a phone and a calculator — that's Tool Use / Function Calling.
  • Let them look things up in the company wiki — that's RAG.
  • Have a receptionist decide which specialist to call — that's a Router / Handoff.
  • A whole team of interns coordinating — that's Multi-Agent.

The rest of this page is those bullets, one section each, with a diagram of the loop, the trade-offs, and when to reach for it.

🧩 Foundational reasoning technique

Chain of Thought (CoT) — how it works

Origin: Wei et al. (Google, 2022), Chain-of-Thought Prompting Elicits Reasoning in Large Language Models. On GSM8K math, adding six words — "Let's think step by step" — lifted PaLM-540B from ~18% to ~57% accuracy. That single result kicked off the entire modern reasoning-agent field.

The core idea in one line

Instead of asking the model to jump to the answer, ask it to write down the intermediate steps, one by one, and only then commit to the final answer. Because LLMs generate token-by-token, every step it writes becomes context for the next step — so the reasoning literally happens on the page.

Layman: If I asked you "what's 23 × 47?" out loud, you'd probably fumble. If I said "show your work," you'd write 23 × 47 = 23 × 40 + 23 × 7 = 920 + 161 = 1081. CoT is the exact same trick — the model gets more right when it's allowed to write intermediate work, because each written step becomes an anchor for the next one.

Two flavors

FlavorWhat you writeWhen to use
Zero-shot CoT Just append "Let's think step by step." to the question. Quick, no examples handy, model is big enough (>60B).
Few-shot CoT Give 2–8 example (question, reasoning, answer) triples before the real question. Higher accuracy, more control over the reasoning format, works on smaller models too.

Under the hood — why writing helps

An LLM predicts the next token by attending to every previous token. When the model writes "step 1: I need to find the total revenue first," those tokens are now available as context for step 2. Without CoT, all the intermediate computation has to happen inside the fixed number of transformer layers between "read prompt" and "emit answer" — and there just aren't enough layers to do multi-step arithmetic in one forward pass. CoT turns depth (number of transformer layers) into width (number of output tokens), and the model has plenty of the latter.

Question→ "Step 1: …"→ "Step 2: …"→ "Step 3: …"→ "Therefore, the answer is X"

Example — CoT prompt vs direct prompt

// ❌ DIRECT (often wrong on multi-step problems)
user: A train leaves at 3:15 pm going 60 mph. Another leaves at 4:00 pm from the
      same station going 75 mph in the same direction. When does the second catch up?
assistant: 6:00 pm.   ← usually wrong

// ✅ CHAIN OF THOUGHT (right most of the time)
user: Same question. Think step by step.
assistant: Step 1: By 4:00 pm the first train has travelled 45 min × 60 mph = 45 miles.
           Step 2: The second train closes the gap at 75 - 60 = 15 mph.
           Step 3: Time to close 45 miles at 15 mph = 45 / 15 = 3 hours.
           Step 4: 4:00 pm + 3 h = 7:00 pm.
           Answer: 7:00 pm.
✅ When to use CoT
  • Math, logic puzzles, multi-hop reasoning.
  • Any task where the answer isn't a direct lookup.
  • When you want the model's reasoning to audit — you can inspect the steps.
⚠️ When CoT hurts
  • Small models (<10B params) — CoT can make them worse, they hallucinate steps.
  • Trivia and fact recall — writing steps doesn't help, just adds tokens.
  • Latency-critical paths — you pay for every reasoning token.

Modern note (2024–2026): "reasoning models" like OpenAI o1/o3 and Claude with extended thinking build CoT into the model — they run internal chain-of-thought before emitting the visible answer, so you don't have to ask for it. For classic chat models, you still ask.

🔁 Loop pattern

ReAct — Reason + Act

Origin: Yao et al. (Princeton + Google, 2022), ReAct: Synergizing Reasoning and Acting in Language Models. The paper that turned CoT from "think in a straight line" into "think, do, observe, think again."

The core idea

Loop through three token types: Thought (reasoning), Action (call a tool), Observation (what the tool returned). Repeat until the model emits a "Final Answer." The Thought steps are CoT. The Action steps make it an agent.

Layman: Imagine solving a mystery. You think about a suspect, ask them a question, hear their answer, then think again about the next suspect based on what you just learned. ReAct is Sherlock Holmes for LLMs — reason, act, observe, repeat.
User question→ Thought→ Action(tool)→ Observation→ Thought→ …→ Final Answer

Example trace — "Who is older, the CEO of OpenAI or the CEO of Anthropic?"

Thought: I need the birth years of Sam Altman and Dario Amodei.
Action:  web_search("Sam Altman date of birth")
Obs:     "April 22, 1985"
Thought: Altman = 1985. Now the other one.
Action:  web_search("Dario Amodei date of birth")
Obs:     "1983"
Thought: Amodei is 1983, Altman 1985. 1983 < 1985 → Amodei is older.
Final:   Dario Amodei is older than Sam Altman.
✅ Why ReAct wins
  • Reasoning grounds the action ("why am I calling this tool?").
  • Observations correct hallucinated intermediate facts — the model can't lie about tool output it can see.
  • The trace is fully auditable — you know exactly which tools ran and why.
⚠️ Watch out for
  • Loop-forever risk — always cap max iterations (typically 5–15).
  • Token cost grows linearly with steps.
  • A single bad Thought can send the whole trace off-course — pair with Reflexion for critical tasks.

Every mainstream agent framework — LangChain agents, AutoGen, CrewAI, LangGraph — implements ReAct under the hood. When someone says "an LLM agent," they usually mean ReAct.

🧑‍⚖️ Safety pattern

Human-in-the-Loop (HITL)

The core idea

The agent runs autonomously up to a boundary. Before crossing it — sending an email, executing a trade, deleting a resource, merging a PR — the agent pauses and asks a human to approve, reject, or edit the proposed action. The human's response becomes another observation that resumes the loop.

Layman: A rookie surgeon can prep and diagnose all day, but they don't get to cut without the attending physician nodding first. HITL is "you drive, but I hold the veto." Anywhere the cost of a wrong action is much higher than the cost of a 30-second pause, you want HITL.
Agent proposes action→ 🛑 Pause→ Human: approve / edit / reject→ Agent resumes with decision

Three levels of human oversight

LevelWhat the human doesTypical use
Human-in-the-loop Approves every risky action before it happens. Payments, sending emails on behalf of a user, prod DB writes, publishing content.
Human-on-the-loop Watches a live dashboard, can pause / roll back but doesn't gate each step. Trading bots, moderation queues, automated support agents.
Human-out-of-the-loop Only reviews after-the-fact via logs and metrics. Recommendation systems, ad auctions, spam filters.

Implementation shape

// Pseudo-code: agent asks for approval before a "write" tool
async runAgent(question) {
  while (!done) {
    const action = await plan(state);
    if (action.risk === "high") {
      const decision = await askHuman(action);   // blocks until human clicks
      if (decision.rejected) { state.log("user rejected"); continue; }
      action = decision.edited || action;
    }
    const obs = await execute(action);
    state.append(action, obs);
  }
}
Common failure: "approval fatigue." If every trivial action asks for approval, the human learns to click "yes" without reading. Reserve HITL for actions whose blast radius justifies the pause — money, data loss, external comms, privacy.
🪞 Self-critique pattern

Reflexion — grade your own work, then redo it

Origin: Shinn et al. (Northeastern, 2023), Reflexion: Language Agents with Verbal Reinforcement Learning. Beat GPT-4 by 11 points on HumanEval by adding one habit: after a failed attempt, write a paragraph of self-criticism, then try again with that criticism as context.

The core idea

Two-role loop: an actor attempts the task, an evaluator (either a test suite, another LLM, or the same LLM in a different role) grades the result. If it fails, a self-reflection step writes down what went wrong and what to try differently, and the actor runs again with that reflection appended to its prompt.

Layman: You submit an essay. The teacher says "your third paragraph doesn't support your thesis." You now write in the margin — "remember: every paragraph must tie back to the thesis" — and rewrite. That margin note is the reflection. Next time, you don't repeat the same mistake because the note is right there in your notebook.
Attempt→ Evaluate→ Pass?→ Reflect (write critique)→ Retry with critique
✅ When Reflexion shines
  • Code generation with a runnable test suite — the evaluator is objective.
  • Math and logic — wrong answers are provably wrong.
  • Any task where you can score attempts numerically.
⚠️ Doesn't help when
  • The evaluator is the same weak LLM that made the mistake — no new signal.
  • Task is subjective (creative writing) — reflection can drift.
  • Budget is tight — every retry is another full inference.

Reflexion pairs beautifully with ReAct — ReAct handles the outer act/observe loop, Reflexion handles the meta-loop of "did the whole trace succeed, and if not, what should I remember for next time?"

🗺️ Planning pattern

Plan-and-Execute (a.k.a. Planner/Executor)

Origin: BabyAGI (2023), LangChain "plan-and-execute" agent, Wang et al. (2023) Plan-and-Solve Prompting. Emerged from frustration with ReAct's step-by-step drift on long tasks — the agent kept forgetting the big picture.

The core idea

Split the agent into two roles. A planner (usually a bigger, slower model) reads the goal and produces a full task list up front. An executor (often a cheaper, faster model) picks each task off the list and runs it — usually with a mini ReAct loop of its own. The planner can be called again mid-run to re-plan if the world changed.

Layman: Imagine planning a wedding versus reacting to whatever the caterer just texted. Plan-and-Execute is the wedding planner writing the whole timeline on Monday, then the assistants ticking boxes Tuesday through Saturday. ReAct alone is more like "figure out lunch when it's noon" — fine for short trips, bad for weddings.
Goal→ Planner (LLM-Big)→ [Task 1, Task 2, Task 3, …]→ Executor (LLM-Small) on each task→ Re-plan if stuck

Why it works

  • Latency: big planner runs once, cheap executor runs many times.
  • Focus: executor sees only "task 4 of 12" instead of the whole conversation, so it doesn't lose the plot.
  • Auditability: the plan is a document — you can inspect and edit it before running.

Modern flavors: LLMCompiler (Kim et al. 2023) has the planner emit a DAG so independent tasks run in parallel. ReWOO (Xu et al. 2023) has the planner emit tasks with placeholders that get filled in as tools return — cutting tool-call round-trips.

🌳 Search-based reasoning

Tree of Thoughts (ToT)

Origin: Yao et al. (Princeton + DeepMind, 2023), Tree of Thoughts: Deliberate Problem Solving with LLMs. On Game of 24, GPT-4 with CoT scored 4%. With ToT it scored 74%.

The core idea

Chain-of-Thought is a path — one linear sequence of reasoning steps. Tree-of-Thoughts is search — at each step, the agent generates multiple candidate next steps, scores them (with the same or a different LLM as evaluator), keeps the promising ones, prunes the rest, and expands the best. It's classic BFS/DFS with the LLM as both the successor function and the heuristic.

Layman: Chess. You don't just play the first move that pops into your head — you consider three candidate moves, imagine what happens next for each, and pick the branch that looks best. ToT is teaching the LLM to think a few moves ahead instead of blurting out its gut answer.
Problem→ Generate k next-steps→ Score each→ Keep top-m→ Expand each→ Repeat
✅ When ToT is worth the cost
  • Puzzles with a clear "is this branch dead" signal (Sudoku, 24, crosswords).
  • Planning under constraints with pruning heuristics available.
  • When ~10× more compute is acceptable for >3× accuracy.
⚠️ Skip ToT when
  • No good scoring function — you can't tell branches apart.
  • Search space is small enough that a single CoT already works.
  • Real-time task — the branching factor blows the latency budget.

Graph-of-Thoughts (Besta et al. 2023) generalises ToT to a DAG — branches can merge when they arrive at the same intermediate state, useful for problems with overlapping subproblems (very DP-flavored).

🧮 Voting pattern

Self-Consistency

Origin: Wang et al. (Google, 2022), Self-Consistency Improves Chain of Thought Reasoning. Added +17 points on GSM8K on top of CoT alone — for the cost of running the model 5–40 times.

The core idea

Run the same CoT prompt N times at a non-zero temperature so the reasoning paths diverge. Different paths often reach the same answer, so majority-vote the final answers (not the reasoning). If 7 out of 10 paths say "$1,081," you trust "$1,081" more than any single path.

Layman: Ask ten friends the same tricky math question independently. If seven of them say 1,081 — even though each of them took a slightly different route to get there — you're much more sure the answer is 1,081. The variety in the routes is a feature: if all ten paths agree on the answer despite going different ways, it's probably really the answer.
CoT prompt × N→ N different reasoning paths→ N final answers→ Majority vote→ Winner

Cost model: N× inference. Typical N is 5–10 in production, 20–40 in benchmark papers. For very high-stakes single decisions (drug dose calc, medical triage summary), even N=40 can be cheaper than a wrong answer.

🛠️ Foundational agent capability

Tool Use / Function Calling

Origin: Toolformer (Schick et al., Meta, 2023), then productised as OpenAI function calling (June 2023) and Anthropic tool use (May 2024). It's the mechanism that turns "text generator" into "does things in the world."

The core idea

You describe the available tools as JSON schemas (name, description, input parameters). The LLM, when it decides a tool is needed, emits a structured tool call (JSON with tool name + arguments) instead of natural-language prose. Your runtime executes the tool, feeds the result back as an observation, and the LLM continues.

Layman: The LLM by itself is like a very smart person locked in a windowless room — it can only talk. Tools are the door: give it a calculator, a search bar, a database read, an email sender. Now it can affect the world instead of just describing it. The list of tools is what defines what your agent can and can't do — treat it like a security perimeter. 
// A tool the LLM can call
{
  "name": "get_weather",
  "description": "Return current weather for a city",
  "input_schema": {
    "type": "object",
    "properties": { "city": { "type": "string" } },
    "required": ["city"]
  }
}

// What the LLM emits when it decides to use it
{ "tool": "get_weather", "input": { "city": "Bengaluru" } }
Least privilege matters. A tool schema is a promise: whatever the LLM can request, your runtime will execute. Never expose a "run shell command" tool without HITL. Never give a customer-facing agent write access to a table it doesn't need. The blast radius of prompt injection is exactly the set of tools you exposed.
📚 Knowledge pattern

RAG — Retrieval Augmented Generation

Origin: Lewis et al. (Facebook AI, 2020), Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks. The default answer to "how do I make the LLM know about my company's private data without fine-tuning?"

The core idea

Before answering, retrieve the k most relevant passages from a knowledge base (a vector store, keyword index, or hybrid), stuff them into the prompt as context, and ask the model to answer using those passages. The model's weights don't know your data — the prompt does, for this one turn.

Layman: Take a very smart friend who's never seen your company. To answer "what's our refund policy?" they'd guess. RAG is you shoving a photocopy of the relevant policy page under their nose right before they answer. They don't need to memorize the manual — they just need it in front of them at the moment they speak.
Question→ Embed→ Vector search top-k→ Stuff into prompt→ LLM answers using context

RAG is often the "R" step of a larger ReAct loop — the agent calls a knowledge_base_search tool the way it might call any other tool. This lets the agent decide when to retrieve and what to retrieve, rather than always retrieving upfront.

🚦 Orchestration pattern

Router / Handoff

The core idea

A small, cheap "router" LLM (or classifier) looks at each incoming request and decides which specialist agent should handle it. The specialists are usually different in one or more of: prompt, tools, model size, fine-tune, or safety profile.

Layman: Reception at a big clinic. You walk in with a broken wrist — the receptionist doesn't try to set the bone, they send you to orthopedics. Walk in with the flu, you go to general medicine. The router doesn't do the work; it decides who should do the work.
Request→ Router LLM→ "This is a billing question"→ Handoff to BillingAgent

OpenAI's Swarm and Agents SDK, LangGraph's supervisor pattern, and CrewAI's manager-agent all implement this. It's usually the first step of scaling a single agent that got too many tools crammed into one system prompt.

👥 Team pattern

Multi-Agent Collaboration

Origin: AutoGen (Microsoft, 2023), CrewAI, MetaGPT, ChatDev. The generalisation of Router + Planner: multiple agents with distinct roles pass messages to each other until the task is done.

The core idea

Assign each agent a role (product manager, engineer, tester, security reviewer), give each its own system prompt and tool set, and let them talk to each other under an orchestrator or in a group-chat pattern. The orchestrator either explicitly picks the next speaker (supervisor) or lets agents route based on their own outputs (event-driven).

Layman: A software team. The PM writes the spec, the engineer implements, the tester finds bugs, the reviewer catches security issues, the PM signs off. Each is bad at the others' jobs and great at their own. Multi-agent LLM systems just do this at machine speed, in a slack channel of prompts.
✅ Why it can help
  • Role-specialised prompts outperform "one giant prompt does everything."
  • Adversarial pairs (writer + critic) catch mistakes a single agent misses.
  • Parallelism — independent sub-tasks can run in parallel workers.
⚠️ Watch out for
  • Chatter explosion — agents can loop forever congratulating each other. Cap message counts hard.
  • Compounding hallucination — one agent's confident wrong answer becomes another's premise.
  • Cost — N agents means N× tokens per turn.

Rule of thumb: start with one agent + tools. Only split into a multi-agent system when a single-prompt version is measurably failing, and each new agent has a role that genuinely couldn't fit in the original prompt without confusing it.

⚖️ Side-by-side

Picking the right pattern

PatternReach for it whenWatch out forCompose well with
CoT Multi-step reasoning, math, logic. Trivia (adds noise), small models (hallucinates steps). Everything — CoT is the base substrate.
ReAct Any agent that needs tools + reasoning. Runaway loops — always cap iterations. RAG, Tool Use, HITL, Reflexion.
HITL High-blast-radius actions (money, prod writes, external comms). Approval fatigue — reserve for actions that truly need it. ReAct, Multi-Agent, Router.
Reflexion Objective evaluator exists (tests, math, checkers). Subjective tasks — reflection can drift. ReAct (as an outer loop).
Plan-and-Execute Long, multi-phase tasks where drift is a risk. Rigid plans in changing environments — allow re-planning. ReAct (as the executor inner loop).
Tree of Thoughts Puzzle-like problems with a scoring signal. Cost — often 10× a CoT run. Self-Consistency (per branch).
Self-Consistency High-stakes single decisions. N× cost; degenerates if all paths are wrong the same way. CoT, ToT.
Tool Use Any agent that must interact with the world. Least-privilege discipline; injection blast radius. ReAct, RAG, HITL.
RAG Private / fresh / large knowledge bases. Retrieval quality is a whole subsystem — poor retrieval → confidently wrong answers. ReAct, Tool Use.
Router / Handoff Distinct request types with distinct needs. Mis-classification silently sends users to the wrong specialist. Multi-Agent.
Multi-Agent A single prompt is measurably failing at role coverage. Loop chatter; compounding errors; N× cost. Router, HITL, Plan-and-Execute.
🗣️ Interview cheat sheet

One-liners you can quote out loud

  • Chain of Thought — "ask the model to write its steps, so each step becomes context for the next; depth becomes width."
  • ReAct — "Thought → Action → Observation, in a loop, until Final Answer. It's CoT plus tool calls."
  • HITL — "the agent pauses before high-blast-radius actions and waits for a human's approve/edit/reject."
  • Reflexion — "attempt → evaluate → write a critique → retry with the critique in context."
  • Plan-and-Execute — "a big-model planner writes the task list once, a small-model executor runs each task."
  • Tree of Thoughts — "CoT is a path, ToT is a search — branch, score, prune, expand."
  • Self-Consistency — "run CoT N times at temp>0 and majority-vote the answers."
  • Tool Use — "LLM emits a structured JSON call instead of prose; runtime executes and feeds the result back."
  • RAG — "retrieve top-k passages, stuff them into the prompt, answer grounded in them."
  • Router — "small classifier LLM decides which specialist agent handles the request."
  • Multi-Agent — "role-specialised agents (PM, engineer, tester) message each other under an orchestrator."
Design-review tip. In an interview, describe the agent as "ReAct at its core, RAG for company data, HITL on money-moving tools, Reflexion on the code-writing sub-task, and a router in front so we don't cram every intent into one prompt." That sentence names five patterns and shows you compose them — which is what real production agents look like.
