DNS: UDP vs TCP

Why DNS runs on UDP by default, when it falls back to TCP, the 512-byte myth, EDNS0, TC-bit truncation, zone transfers, and modern DoT/DoH.

🎯 Real-world scenario

What we're really being asked

Almost every network transaction on the planet begins with a DNS lookup: your phone opens Instagram, the browser resolves www.instagram.com to an IP address, and only then does the TCP handshake for HTTPS begin. That "one tiny lookup" happens trillions of times a day — Cloudflare's 1.1.1.1 alone answers on the order of two trillion queries daily. The protocol has to be blindingly fast, work through firewalls, survive packet loss, and now — under DNSSEC and IPv6 — carry payloads that no longer fit in a single UDP datagram.

The classic interview question is: "Why does DNS use UDP? When does it switch to TCP?" The honest answer is DNS is hybrid: UDP on port 53 for the fast path, TCP on port 53 for the reliable path, and modern encrypted transports (DoT on 853, DoH on 443) layering TLS on top of TCP. The nuance is where a strong candidate wins: the 512-byte limit isn't really 512 anymore (EDNS0 pushed it to 1232/4096), the TC ("truncated") bit is the fallback signal, and RFC 7766 made TCP support mandatory for every DNS implementation in 2016.

Real products this shapes: Cloudflare 1.1.1.1, Google 8.8.8.8, AWS Route 53, Quad9 9.9.9.9, every recursive resolver at every ISP, and the DNS-over-HTTPS clients built into Chrome, Firefox, iOS 14+, and Android 9+. Every one of them speaks both UDP and TCP — and they had to, the moment DNSSEC signatures made 512 bytes obsolete.

🧑‍🎓 In laymen terms

The everyday problem, without any jargon

Imagine you want to visit a friend named Priya, but you only know her name — not her address. You need a phone book that maps names to addresses. That's exactly what DNS is: the phone book of the internet. Every website has a friendly name (instagram.com) and a number-y address (157.240.19.174) that computers actually use. Before your phone can open Instagram, it has to look up that address.

Now imagine you had two ways to ask the phone book. Way #1 is a quick shout across a room: "Hey, what's Priya's address?" — someone shouts back instantly. It's fast, but if the answer is longer than one breath ("Priya lives at 42 Baker Street, Apartment 3B, London, and here's the doorbell code, the parking pass, and…") the shouter might not finish before running out of air. Way #2 is a proper phone call: you dial, say hello, ask the question, listen carefully to a long answer, and hang up. It's slower to set up — but it can carry a long, complicated reply reliably.

DNS uses Way #1 (called UDP) by default because most answers are tiny — just an address. But when the answer is too big to shout in one breath (say, when the phone book is signed and stamped for security, or when a company is telling you which mail servers to use, and there are twelve of them), the phone book replies "my answer got cut off — call me back on the phone". Your computer then dials up (that's TCP) and asks the question again, patiently, over a real connection.

Why bother with the shouting at all? Because speed matters enormously. Every time you tap a link, tap a photo, or open an app, one of these lookups happens. A single ISP handles millions of these per second — imagine placing a phone call for every single one. The building would collapse. Shouting works because the questions and answers are almost always tiny.

Real products that live and die by this: WhatsApp (looking up chat servers), Instagram (looking up image servers), your bank's app (looking up the login server), and every website you visit. All of them get their first answer via the shout — and only escalate to the phone call when the shout wasn't enough.

Tiny example to walk through: you tap google.com. Your phone shouts to your Wi-Fi router — "who is google.com?" Router shouts to your ISP's resolver, which either already knows (cached) or shouts up to the root, then to .com, then to Google's own name server. A tiny answer — one IP address — comes shouting back down. Total time: 10 to 40 milliseconds. If any answer along that chain had been too big, that hop alone would have upgraded to a phone call.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional

  • Answer A / AAAA / MX / TXT / CNAME / NS / SOA queries in milliseconds.
  • Support both UDP (fast, stateless) and TCP (reliable, ordered) on port 53.
  • Signal truncation via the TC flag when a UDP response would exceed the client's advertised buffer.
  • Support zone transfers: AXFR (full) and IXFR (incremental) between authoritative servers, always over TCP.
  • Optionally serve DNSSEC-signed responses (RRSIG, DNSKEY, NSEC/NSEC3) — which are large.
  • Optionally support DoT (RFC 7858, TLS on port 853) and DoH (RFC 8484, HTTP/2 on port 443).

Non-functional

  • Latency: p50 < 20 ms for a cache hit, p99 < 100 ms for a cache miss.
  • Throughput: a single recursive resolver box must handle 100k+ QPS on UDP.
  • Availability: 100% — DNS outages kill everything on top of it (Slack, Facebook, GitHub have all melted the internet with DNS incidents).
  • Security: resistance to reflection/amplification attacks, cache poisoning, and spoofing.

🏗️ High-level architecture

The full DNS resolution flow — and where TCP shows up

A DNS query is not a single-hop conversation; it's a recursive walk through a tree of authorities. Your stub resolver (the OS library on your device) sends a query to a recursive resolver, usually run by your ISP, your VPN, or a public resolver (1.1.1.1, 8.8.8.8, Route 53 Resolver). The recursive resolver either returns a cached answer, or does the actual walk on your behalf: root name servers → TLD (.com, .in, .io) name servers → authoritative name server → answer. Every one of those hops is a UDP-first, TCP-fallback exchange.

The moment an answer exceeds the requester's advertised UDP buffer, the responder sets the TC (truncated) bit in the header and sends a stub of the answer. The client sees TC=1, discards the UDP response, opens a TCP connection to the same server on port 53, and resends the query. That's the fallback, in one paragraph.

Every straight grey arrow is a UDP round-trip. The pink dashed arrow is the fallback path: the same client, the same server, port 53 — but TCP this time. The green arrow between the authoritative servers is a zone transfer (AXFR/IXFR), which is always TCP because a whole zone can be hundreds of KB to tens of MB — UDP can't carry that reliably. The purple dashed link is modern encrypted DNS, which layers TLS on TCP either as DoT (port 853) or DoH (port 443, wrapped in HTTPS to look like normal web traffic).

🔍 Component deep-dive

Why UDP is the default

DNS was designed in 1983 (RFC 883, then 1035) at a time when memory was measured in kilobytes and every server round-trip was expensive. The designers picked UDP for three reasons that still hold up: fewer packets, no per-connection state, and lower latency. A UDP query is exactly two datagrams — one out, one back. A TCP query requires a three-way handshake (SYN, SYN/ACK, ACK), then the query and response, then a four-way close (FIN, ACK, FIN, ACK) — roughly seven to nine packets on the wire. When you're a public resolver answering 100k+ QPS, that difference multiplies into gigabits of overhead.

The stateless nature is arguably even more important. On UDP the server holds nothing between queries — no socket, no kernel buffer, no ESTABLISHED row in the connection table. That means a single Route 53 or BIND box can absorb bursts and DoS scans without collapsing under connection-tracker pressure. Cache hits (which dominate real traffic) are essentially "receive 40 bytes, memcpy an answer, send 60 bytes" — the kernel path is almost free.

The 512-byte myth (and how EDNS0 fixed it)

RFC 1035 §4.2.1 famously capped a DNS UDP payload at 512 bytes. Interviewers love this number. But the honest answer is that 512 has been effectively dead since RFC 6891 (EDNS0) in 2013. EDNS0 adds a pseudo-record called OPT to the additional section of every query, and inside OPT the client advertises how large a UDP response it can accept. Common values:

  • 4096 — the RFC 6891 recommendation. Works on clean networks; risks IP fragmentation on hostile paths (firewalls dropping fragments).
  • 1232 — the DNS Flag Day 2020 operator consensus. Chosen so a packet + IPv6 headers fits inside the 1280-byte IPv6 minimum MTU, guaranteeing zero fragmentation.
  • 1400 / 1410 — Ethernet-frame-safe midpoint some operators used before Flag Day 2020.

So when a modern interviewer asks "what's the UDP DNS limit", the correct answer is: 512 without EDNS0, typically 1232 in practice today, up to 4096 if you're aggressive — and if the answer still doesn't fit, we retry over TCP.

The TC (truncated) bit and fallback

Every DNS message has a 16-bit flags field in its header. Bit 6 is TC — "message was truncated". Any server sending a UDP response that would exceed the client's advertised buffer must set TC=1 and send whatever fits (or nothing meaningful). The client's rule is simple: if TC=1, discard, open a TCP connection, resend the same query. That's the entirety of the fallback protocol. Well-behaved recursive resolvers even remember which authoritative servers required TCP for a given zone and skip UDP next time, saving an RTT.

Zone transfers — always TCP

When a secondary/replica name server needs to pull the current state of a zone from a primary, it does an AXFR (full transfer) or IXFR (incremental transfer, RFC 1995) — always over TCP. A zone can be megabytes of records; UDP simply can't carry it reliably. The primary streams records in order over a single TCP connection, and the secondary applies them atomically. This is the one case in DNS where UDP was never even attempted.

DNSSEC — why every large response is signed

DNSSEC (RFC 4033/4034/4035) adds cryptographic signatures to DNS records so a resolver can verify that an answer wasn't spoofed. The signatures (RRSIG), public keys (DNSKEY), and denial-of-existence records (NSEC/NSEC3) all live inline in DNS responses. The result: a DNSSEC-signed response is routinely 1–4+ KB, which blows straight past the 512-byte limit and even past the 1232-byte Flag-Day limit for larger zones. DNSSEC is why TCP fallback matters more today than it did in 1990.

RFC 7766 — TCP is mandatory now

Before 2016, some minimalist DNS implementations only supported UDP. RFC 7766 ended that: TCP support is now mandatory for every general-purpose DNS implementation — authoritative, recursive, and stub alike. RFC 7766 also blesses long-lived TCP connections (with edns-tcp-keepalive, RFC 7828), pipelining multiple queries on one TCP connection, and out-of-order responses matched by DNS Message ID.

Modern encrypted transport — DoT and DoH

DoT (DNS over TLS, RFC 7858) runs DNS inside TLS on port 853. It hides the query content from on-path observers and adds server authentication via TLS certificates. DoH (DNS over HTTPS, RFC 8484) goes further and disguises DNS as ordinary HTTPS traffic on port 443, indistinguishable from a web request. Cloudflare, Google, Quad9, and Apple's iCloud Private Relay all offer DoH endpoints. Both are TCP-based (DoH is technically HTTP over TCP or QUIC). The latency cost is real — TLS handshake ≈ +2 RTTs on cold connect — but the privacy win is why they exist, and connection reuse amortises the handshake across thousands of subsequent queries.

Why not just always use TCP?

Because at scale, the numbers are brutal. A UDP query costs ~1 KB of in-flight memory. A TCP connection needs a socket, a send/receive buffer (typically 8 KB minimum each in Linux defaults), sequence number state, a slot in the connection tracker, and a file descriptor. At 100k QPS, moving to TCP inflates memory pressure roughly 8×, adds one RTT of latency to every miss (fatal for page-load time), and multiplies the packet count on the wire by ~4×. UDP-first is not a hack — it's a load-shedding strategy that has held up for 40 years.

🧮 The DSA behind it

Data structures & algorithms

DNS is a systems problem, but there's real DSA under the hood — some in the wire format, some in the resolver itself.

Wire format

  • Fixed-size header (12 bytes) — ID (16b), Flags including QR, OPCODE, AA, TC, RD, RA, RCODE, then QDCOUNT/ANCOUNT/NSCOUNT/ARCOUNT.
  • Name compression (RFC 1035 §4.1.4) — a repeated domain name is replaced by a 2-byte pointer to its earlier occurrence, saving bytes in packed responses. That's a tiny purpose-built compression algorithm baked into the wire format.
  • Length-prefixed TCP framing (RFC 7766) — TCP is a stream; DNS is message-oriented. Each DNS message on TCP is prefixed with a 2-byte big-endian length. Same trick as HTTP/2 frames, Kafka records, Redis RESP arrays.

Resolver cache

  • Hash table with TTL eviction keyed by (QNAME, QTYPE, QCLASS). Every entry has an absolute expiry (arrival time + TTL from the answer).
  • LRU eviction under memory pressure, layered on top of TTL expiry.
  • Negative cache (RFC 2308) — NXDOMAIN responses are cached too, so bogus lookups don't hammer authoritative servers.

Mapping the design to AWS

AWS runs one of the largest DNS deployments on earth. On the authoritative side, Route 53 serves hosted zones from an anycast fleet globally. On the resolver side, the Route 53 Resolver (formerly VPC DNS at 169.254.169.253, the ".2" VPC address) does recursive resolution for every EC2 instance, Lambda, and Fargate task inside a VPC. Both sides speak UDP and TCP on port 53, and Resolver additionally supports DoT/DoH endpoints for private DNS.

💻 C# implementation

A minimal DNS client that speaks both UDP and TCP: it sends the query on UDP first, checks the TC flag, and transparently retries over TCP if truncated. This is essentially what every resolver does on the wire.

using System;
using System.Buffers.Binary;
using System.Net;
using System.Net.Sockets;
using System.Threading.Tasks;

// Minimal DNS query client demonstrating the UDP→TCP fallback pattern.
// Real resolvers add: caching, TTL, EDNS0 OPT, DNSSEC, retry/backoff, etc.
public sealed class DnsClient
{
    private const int DnsPort = 53;
    private const int UdpBufferSize = 1232;    // DNS Flag Day 2020 default
    private const byte TcMask = 0x02;         // TC bit is bit 1 of flags byte 2

    public async Task<byte[]> QueryAsync(IPAddress server, string qname, ushort qtype = 1 /* A */)
    {
        byte[] query = BuildQuery(qname, qtype);

        // 1. Try UDP first — the fast path.
        using var udp = new UdpClient(new IPEndPoint(IPAddress.Any, 0));
        await udp.SendAsync(query, query.Length, new IPEndPoint(server, DnsPort));

        var udpTask   = udp.ReceiveAsync();
        var timeout   = Task.Delay(TimeSpan.FromSeconds(2));
        if (await Task.WhenAny(udpTask, timeout) == udpTask)
        {
            byte[] response = udpTask.Result.Buffer;
            bool truncated = (response[2] & TcMask) != 0;   // header byte 2 → TC bit
            if (!truncated) return response;                // happy path: 40-byte question, ~90-byte answer
        }

        // 2. TC=1 or no response → retry over TCP. RFC 7766: length-prefixed.
        using var tcp = new TcpClient();
        await tcp.ConnectAsync(server, DnsPort);
        using var stream = tcp.GetStream();

        byte[] lenPrefix = new byte[2];
        BinaryPrimitives.WriteUInt16BigEndian(lenPrefix, (ushort)query.Length);
        await stream.WriteAsync(lenPrefix);
        await stream.WriteAsync(query);

        byte[] respLenBuf = new byte[2];
        await ReadExactlyAsync(stream, respLenBuf, 2);
        int respLen = BinaryPrimitives.ReadUInt16BigEndian(respLenBuf);

        byte[] full = new byte[respLen];
        await ReadExactlyAsync(stream, full, respLen);
        return full;
    }

    private static async Task ReadExactlyAsync(NetworkStream s, byte[] buf, int n)
    {
        int read = 0;
        while (read < n)
        {
            int got = await s.ReadAsync(buf, read, n - read);
            if (got == 0) throw new EndOfStreamException("DNS/TCP peer closed early");
            read += got;
        }
    }

    // Very small hand-rolled DNS query builder — 12-byte header + QNAME + QTYPE + QCLASS.
    private static byte[] BuildQuery(string qname, ushort qtype)
    {
        using var ms = new MemoryStream();
        // Header: ID=0x1234, RD=1 (recursion desired), one question.
        byte[] hdr = { 0x12, 0x34, 0x01, 0x00, 0x00, 0x01, 0, 0, 0, 0, 0, 0 };
        ms.Write(hdr, 0, hdr.Length);
        foreach (var label in qname.Split('.'))
        {
            byte[] bytes = System.Text.Encoding.ASCII.GetBytes(label);
            ms.WriteByte((byte)bytes.Length);
            ms.Write(bytes, 0, bytes.Length);
        }
        ms.WriteByte(0); // root label terminator
        Span<byte> tail = stackalloc byte[4];
        BinaryPrimitives.WriteUInt16BigEndian(tail.Slice(0, 2), qtype);
        BinaryPrimitives.WriteUInt16BigEndian(tail.Slice(2, 2), 1); // QCLASS=IN
        ms.Write(tail);
        return ms.ToArray();
    }
}

The key line is (response[2] & TcMask) != 0. That single-bit check is the entire fallback protocol. Everything else — TLS for DoT, HTTP framing for DoH, name compression, EDNS0 OPT records — is elaboration on top.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Where the design bites

Reflection/amplification. The UDP + spoofable source IP combination is a gift to attackers. A 40-byte query with a spoofed source can trigger a 3+ KB DNSSEC response aimed at the victim — a 60× amplification. Mitigations: rate-limiting (BCP 38 source-address filtering at ISPs), Response Rate Limiting (RRL) on authoritative servers, and the mandatory TCP fallback that RFC 7766 gives you (TCP requires a completed handshake, so you can't spoof the source).

Fragmentation. A UDP response over 1500 bytes gets fragmented at the IP layer, and many firewalls silently drop fragments. That's why DNS Flag Day 2020 pushed everyone down to a 1232-byte EDNS0 buffer — enough for most answers, still small enough to never fragment on modern paths.

Path MTU variance. IPv6 minimum MTU is 1280, IPv4 is 68 (theoretical) / 576 (practical). The 512-byte legacy limit was chosen precisely so a full DNS message would always survive a 576-byte MTU minus IP+UDP headers. Modern EDNS0 sizing is an ongoing operational compromise.

Cache poisoning. Because UDP has no handshake, an attacker who can guess the DNS transaction ID and source port can inject a forged response. Kaminsky's 2008 attack made this practical. Mitigations: source port randomization, DNS cookies (RFC 7873), and — the real fix — DNSSEC-signed responses that clients can verify.

Likely follow-up questions

Q: Isn't DNS switching to TCP-only these days?

No. UDP is still the default for every recursive+authoritative exchange. TCP-only would multiply memory and CPU cost per query 5–10×. What is shifting is client-to-resolver: DoT and DoH (both TCP-based) are increasingly the default at the browser and OS layer for privacy. Behind the resolver, UDP-first is still the norm.

Q: How does the resolver decide the EDNS0 buffer size?

Operator config, usually 1232 today (Flag Day 2020) or 4096 on clean private networks. It's advertised in every query's OPT record; if truncation still happens, the resolver may drop the advertised size on retry and eventually fall back to TCP.

Q: Why is AXFR always TCP, but IXFR often UDP-tried first?

IXFR (RFC 1995) sends only the diff since the secondary's last serial. If the diff is small enough to fit in a UDP packet, the primary may reply on UDP as an optimization. If the diff is bigger — or the primary chooses — the secondary falls back to TCP. AXFR is always TCP because a full zone is virtually always too big for UDP.

Q: How does DoH differ operationally from DoT?

DoT is easy to identify (port 853) and easy to firewall. DoH looks like ordinary HTTPS (port 443) — same TLS handshake, same ALPN as web traffic — so a network operator can't distinguish DNS traffic from a browser fetch without deep inspection. That's a privacy win for users and a governance headache for enterprise networks.

Q: What happens if TCP fallback itself fails?

Resolver retries a different NS from the delegation, or retries the same NS from a different source port. If all fail, the client sees SERVFAIL. Negative-cache TTLs kick in so the resolver doesn't hammer a broken authoritative.

Q: What did DNS Flag Day 2020 actually change?

It got the major open-source servers and public resolvers (BIND, Unbound, PowerDNS, Cloudflare, Google, Quad9) to advertise 1232 bytes as their default EDNS0 buffer — eliminating IP fragmentation in the common path and pushing large-answer traffic to TCP where fragmentation is not an issue.

🗣️ Interview cheat sheet

The 30-second pitch: "DNS is hybrid. UDP on port 53 is the default because a query + reply is two packets, stateless, and cache-friendly — perfect for the trillion+ small lookups a day. When the answer exceeds the client's advertised UDP buffer — 512 bytes historically, 1232 today per DNS Flag Day 2020, up to 4096 with EDNS0 — the server sets the TC bit and the client retries over TCP on the same port. TCP is also mandatory for zone transfers (AXFR/IXFR) and is now required for every DNS implementation per RFC 7766. Modern encrypted DNS — DoT on 853, DoH on 443 — runs on TCP by design."

Numbers to quote

  • Port 53 for UDP + TCP; 853 for DoT; 443 for DoH.
  • 512 B (RFC 1035) → 1232 B (Flag Day 2020) → 4096 B (RFC 6891 max).
  • UDP round-trip = 2 packets. TCP round-trip = ~7 packets.
  • Cache-hit latency < 20 ms; TCP fallback adds ~1 RTT.
  • Cloudflare 1.1.1.1 answers ~2 trillion queries/day — that's why UDP-first.

Five talking points that win the round

  • Why UDP: stateless, 2 packets, cheap under 100k QPS bursts.
  • When TCP: TC=1 truncated response, DNSSEC signatures, zone transfers, DoT/DoH.
  • The magic bit: TC flag in the header — one bit is the whole fallback protocol.
  • The modern number: 1232, not 512 — reference DNS Flag Day 2020.
  • The mandate: RFC 7766 (2016) made TCP support mandatory for every DNS implementation.
