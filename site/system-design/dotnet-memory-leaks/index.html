🎯 Real-world scenario

Why "we have a GC" is not the full story

Every .NET engineer eventually gets paged for the same story: pods are healthy, latency looks fine — and then Kubernetes starts killing them every eight hours with an OOMKilled (137). CPU is idle, GC counters look calm, but the working set climbs 30 MB every hour until it hits the container limit. The garbage collector is doing its job perfectly; the problem is that something we wrote is still pointing at objects we no longer want.

This is the .NET memory leak: not unreachable-and-unfreed (the C/C++ definition), but reachable-but-unwanted. The GC only reclaims objects nothing can point at. If a static field, an event delegate, a running timer, a captured closure, or a native handle keeps a reference alive, the object stays — and the graph it pins with it.

These leaks have real names and real bug trackers behind them. Simon Timms's 2016 "You're using HttpClient wrong" post is the reason IHttpClientFactory exists. Microsoft's ASP.NET Core memory doc walks through a PhysicalFileProvider native-handle leak filed as dotnet/aspnetcore#844. StackExchange's Nick Craver blogs have chronicled cache-without-eviction bugs that grew Stack Overflow's servers by gigabytes overnight. The interview question isn't "what is a leak" — it's "tell me about one you found, and how".

🧑‍🎓 In laymen terms

The bathtub with a hidden drip

Imagine your app is a bathtub. Water flowing in is memory your program uses; the drain at the bottom is the janitor — in .NET we call it the garbage collector — who pulls the plug and lets the water out whenever the tub gets full. Most of the time this works beautifully. You fill the tub, the janitor drains it, you fill it again. Nobody thinks about plumbing.

A memory leak is what happens when someone quietly leaves a rubber ducky floating in the tub. The janitor comes to drain, sees the ducky, and thinks, "someone still wants this" — so the water around the ducky stays. Every hour a new ducky gets left behind. The tub slowly fills, and eventually the whole thing overflows onto the floor. In production, "overflows onto the floor" is a server crash at 3 AM.

The tricky part is that the duckies aren't obviously garbage. They're things like a phone number you handed to a friend — you're done with the friendship, but the friend still has your number written on a slip of paper. As long as that paper exists, the janitor won't touch it. In code, that "slip of paper" is often an event subscription, a static cache, or a timer that nobody turned off.

Real products fight this every day. Instagram, Netflix, Stack Overflow, Azure services — every large .NET service has a story of a small piece of forgotten code that ate a few kilobytes per request until, three days later, machines started falling over. The fix is almost never "add more RAM"; it's find the slip of paper and tear it up.

Here's the everyday example: imagine you sign up for a magazine and forget to cancel. Every month a new issue arrives. Your mailbox slowly fills. The postman keeps delivering — from his side, everything is working. That's exactly what a subscription-that-was-never-cancelled looks like inside a .NET app.

Functional vs non-functional

Functional: detect that memory is climbing; localise the retention path (which object roots the leak); apply the smallest fix that removes the root. Non-functional: do all that on a live pod without a restart (a restart hides the evidence), with tooling that ships with the .NET SDK, and with a repeatable playbook a junior can run at 3 AM.

🏗️ High-level architecture

The .NET heap — the mental model interviewers listen for

The whole conversation makes sense once you can draw the heap. Objects are born on the Small Object Heap (SOH) in Gen 0. Survive a collection → get promoted to Gen 1. Survive again → Gen 2, where objects live "forever" and only full collections reclaim them. Allocations ≥ 85,000 bytes skip SOH entirely and go on the Large Object Heap (LOH). Pinned buffers (byte arrays used by native I/O) live on the Pinned Object Heap (POH) since .NET 5. Everything above is one .NET process; on top of that, roots — statics, running-thread locals, GC handles — anchor the graph the collector traces.

Gen 0 — most objects die here Gen 1 — buffer generation Gen 2 — leaks accumulate here LOH — 85 KB threshold POH — pinned

The interview line: "A leak means an object graph is still reachable from a live root — a static, an event delegate, a running timer, or a native handle — even though logically we're done with it. Because it's reachable, the GC won't collect it. My job is to find that root and cut the reference."

🔍 The eight real-world scenarios you should be able to name

An interviewer asking "tell me about a leak you've seen" wants concrete stories. These eight are the canon — each pulled from a real Microsoft doc, GitHub issue, or well-known engineering blog. Learn the symptom and the fix line for each.

1. HttpClient socket exhaustion (the classic)

Wrapping every outgoing call in using (var c = new HttpClient()) { … } looks textbook-correct — HttpClient is IDisposable, so of course you dispose it. But HttpClient owns a HttpMessageHandler, which owns a socket that stays in TIME_WAIT for ~240 s (Windows) after Dispose. Under load you exhaust ephemeral ports and start throwing SocketException. Simon Timms's 2016 post surfaced this; IHttpClientFactory in .NET Core 2.1 was the answer, pooling handlers and rotating them every 2 min so DNS changes are picked up.

2. Singleton HttpClient that never sees DNS changes

The naïve "fix" is static readonly HttpClient _c = new(). This solves sockets but creates a new bug (dotnet/runtime #18348): the underlying handler caches a resolved IP forever. A blue/green deploy or DNS failover looks broken on your side of the wire. Fix: IHttpClientFactory, or set SocketsHttpHandler.PooledConnectionLifetime.

3. Event handler leak (WiFiManager pattern)

A long-lived publisher's event holds a delegate; the delegate's Target is your subscriber; the subscriber can never be collected. In WPF/Blazor/WinForms this manifests as pages/views that "still work" invisibly and mutate stale UI state. Fix: IDisposable + -=, or weak-event pattern.

4. Static cache without eviction

Microsoft's official "Debug a memory leak" tutorial ships this exact bug: a static CustomerCache : List<Customer> that grows on every request. In the tutorial, !dumpheap -stat reveals 206,770 String instances (~19 MB) and !gcroot walks straight back to the static list. Fix: IMemoryCache with SetSize + SizeLimit, or Redis with TTL.

5. LOH fragmentation from oversized buffers

Any allocation ≥ 85,000 bytes lands on the LOH. Do that per-request and you trigger a Gen 2 collection every second and cut throughput in half — Microsoft's ASP.NET Core memory doc reproduces the chart. ASP.NET Core's own ResponseCaching middleware chunks entries below 85 KB precisely to dodge the LOH. Fix: ArrayPool<byte>.Shared or MemoryPool<byte>; return the buffer.

6. Native handle leak (PhysicalFileProvider #844)

Some managed APIs open OS resources. new PhysicalFileProvider(TempPath).Watch("*.*") registers an inotify / ReadDirectoryChangesW handle. Miss the Dispose and the managed heap looks perfectly flat while private bytes and file-descriptor counts climb — a native leak masquerading as a happy .NET process. Fix: using the file provider, or hold one instance for the process.

7. EF Core change-tracker retention

A singleton or forgotten-scoped DbContext, or reading millions of rows without .AsNoTracking(), keeps every entity in the change tracker → the context turns into a giant hash-map that grows until pod eviction. Fix: scoped lifetime + AsNoTracking() for read paths.

8. Captive dependency (singleton captures scoped)

You inject a scoped repository into a singleton service. The singleton is resolved once at startup and holds a reference to that first scope's DbContext, request-tenant, principal — everything — forever. Both the DI container and your monitoring will look normal. Fix: IServiceScopeFactory inside the singleton, or a scoped delegate factory.

🧮 The DSA / GC behind it

How the collector actually works — and why that matters for finding leaks

You cannot debug a leak without a working model of the tracing collector. .NET's GC is a generational mark-and-sweep with compaction. On collection it starts at the roots, does a graph walk marking every reachable object, then sweeps the unreachable ones and compacts the survivors so allocation stays a pointer bump. The five interview words: root, reachability, generation, promotion, and retention path.

Structure / algorithmComplexityWhy it matters for leaks
Tracing GC (mark-sweep-compact)O(live objects) per collectionCost scales with the surviving set, not the total heap — a leak that grows Gen 2 makes every full GC slower.
Generational hypothesisAmortised O(1) per allocMost objects die young → collecting Gen 0/1 is cheap and frequent; Gen 2 is rare and expensive.
Card table (write barriers)O(1) per pointer writeLets a Gen 0 collection skip Gen 2 objects unless they point down to a young object.
Reference graph traversal (!gcroot)O(V + E)SOS traces backwards from an object to a root — the single most valuable command for leak hunting.
Hash-set of live handlesO(1) lookupHow GCHandle pinned/weak references are tracked.
ArrayPool<T> (bucketed free lists)O(1) rent/returnFixes LOH pressure by reusing buffers instead of allocating.

The five words you must define

  • Root — anything the runtime can point at without going through another managed object: static fields, JIT-tracked locals on live stacks, CPU registers, GC handles (incl. pinned), and the finalize queue.
  • Reachability — the transitive closure of "pointed at by a root or by another reachable object". Only unreachable objects are collected.
  • Generation — an age bucket. Gen 0 = new. Gen 1 = survived one GC. Gen 2 = survived two — treated as long-lived.
  • Promotion — surviving a collection moves you up one generation, up to Gen 2.
  • Retention path — the chain of references from a root to a leaked object. This is what !gcroot prints.

💻 C# — before / after for the two most-quoted leaks

Event handler leak — before

// ❌ Every StatusView subscribes to a long-lived singleton and never unsubscribes.
// The delegate's Target field points back at the StatusView, so it stays rooted
// as long as WiFiManager lives — which is forever.
public class StatusView {
    public StatusView(WiFiManager mgr) {
        mgr.SignalChanged += OnSignalChanged;
    }
    void OnSignalChanged(object? s, EventArgs e) {
        // update UI…
    }
}

Event handler leak — after (IDisposable + explicit unsubscribe)

public sealed class StatusView : IDisposable {
    private readonly WiFiManager _mgr;

    public StatusView(WiFiManager mgr) {
        _mgr = mgr;
        _mgr.SignalChanged += OnSignalChanged;
    }

    void OnSignalChanged(object? s, EventArgs e) { /* update UI */ }

    public void Dispose() {
        _mgr.SignalChanged -= OnSignalChanged;  // ✅ delegate leaves the invocation list
    }
}

HttpClient socket exhaustion — before

// ❌ New handler + socket per call. TIME_WAIT (240 s on Windows) means ~125 conn/s
// exhausts 30k ephemeral ports in ~4 minutes → SocketException.
[HttpGet("/catalog/{id}")]
public async Task<IActionResult> Get(int id) {
    using var c = new HttpClient();
    var resp = await c.GetAsync($"http://catalog/api/{id}");
    return Content(await resp.Content.ReadAsStringAsync());
}

HttpClient — after (IHttpClientFactory, typed client)

// Program.cs — register a typed client. Handlers are pooled and rotated every 2 min
// so DNS changes are picked up; no per-call socket churn.
builder.Services.AddHttpClient<CatalogClient>(c => {
    c.BaseAddress = new("http://catalog/");
    c.Timeout     = TimeSpan.FromSeconds(2);
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));

// CatalogClient.cs — inject and use like any DI service.
public sealed class CatalogClient {
    private readonly HttpClient _http;
    public CatalogClient(HttpClient http) => _http = http;

    public async Task<string> Get(int id) =>
        await _http.GetStringAsync($"api/{id}");
}

LOH pressure — use ArrayPool instead of new byte[]

// ❌ byte[100_000] per request → LOH allocation, triggers Gen 2 GCs, halves throughput.
var buf = new byte[100_000];

// ✅ Rent from a shared pool; return in a finally.
var buf = ArrayPool<byte>.Shared.Rent(100_000);
try { /* use buf[0..100_000] */ }
finally { ArrayPool<byte>.Shared.Return(buf); }

⚖️ Trade-offs, bottlenecks & likely follow-ups

Server GC vs Workstation GC. Server GC (default for ASP.NET Core) uses one heap and one GC thread per logical CPU — high throughput, larger ephemeral segments (~1–4 GB), but a bigger footprint. Workstation is lower-footprint and better for small containers or client apps. On a 512 MB Fargate task, forcing Workstation with <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection> + <ServerGarbageCollection>false</ServerGarbageCollection> can be the right call.

Compact-on-full-GC vs sweep-only. Since .NET Core 3.0 the LOH can be compacted on demand (GCSettings.LargeObjectHeapCompactionMode). It's expensive — pauses can hit hundreds of ms — but it's the escape hatch when LOH fragmentation is real.

The classic bottleneck sequence. Allocation rate too high → Gen 0/1 GCs frequent → objects survive into Gen 2 they didn't deserve → Gen 2 grows → full-GC pause grows → ALB health checks fail → tasks recycle → the surviving tasks take the traffic and start doing the same thing → thundering herd.

How would you find a memory leak in production?

Baseline with dotnet-counters on a live pod. If Gen 2 or working-set climbs while allocation rate stays flat, that's a leak. Take two dotnet-gcdump snapshots ~5–10 min apart, diff them in Visual Studio or PerfView, follow the biggest positive-delta type, and run !gcroot on one instance to get the retention path back to a root. Fix the root, redeploy, watch the graph go flat.

Why does .NET have leaks if it has a garbage collector?

Because the GC only frees unreachable objects. A leak in .NET is reachable-but-unwanted: something we wrote is still pointing at an object we've logically finished with — a static field, an event delegate, a running timer, a captive closure, or a native handle. The GC is doing its job perfectly.

Difference from a C++ leak?

C++ leaks are unreachable-and-unfreed — you forgot to delete. .NET leaks are reachable-and-unwanted — you forgot to -= or Dispose. Fix in C++ = smart pointers. Fix in .NET = cut the reference or add IDisposable + using.

Why was IHttpClientFactory added?

To fix two bugs at once. new HttpClient() per call exhausts sockets (TIME_WAIT). A static singleton fixes sockets but caches DNS forever. IHttpClientFactory pools handlers and rotates them every 2 min so DNS changes propagate — best of both.

🗣️ Interview cheat sheet

"A .NET leak is reachable-but-unwanted — the GC can't collect an object something still points to. My job is to find the retention path back to the root and cut it. The five roots that produce 90 % of leaks are statics, event delegates, timers, undisposed IDisposables, and native handles. I detect with dotnet-counters + two dotnet-gcdumps diffed; I confirm with !gcroot in SOS."

  • The one-line definition — reachable-but-unwanted (vs C++ unreachable-and-unfreed).
  • Five leak sources to name — static cache, event handler, timer, undisposed handle, captive dependency.
  • Three numbers to quote — LOH threshold 85,000 bytes; handler lifetime 2 min; TIME_WAIT ~240 s Windows / 60 s Linux.
  • The tool chain — dotnet-counters → two dotnet-gcdumps → diff → !gcroot.
  • The classic fix stories — IHttpClientFactory, weak-event pattern, ArrayPool, AsNoTracking, IMemoryCache with size limit.
  • Container gotcha — OOMKilled 137 with flat managed heap = native leak; pre-3.0 runtimes ignored cgroup limits.
