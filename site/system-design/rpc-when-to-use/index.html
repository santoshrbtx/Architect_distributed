🎯 Real-world scenario

The "we made an order — should the cart service call the pricing service via gRPC?" question

An architect on your team is designing a new microservice. They ask: "should this service call the next one via REST, gRPC, or a message queue?" Every serious system-design interview asks this. The wrong answer never gets you rejected outright, but a weak answer marks you as junior. The strong answer names the actual axes — coupling, latency, evolution, browser reach, human debuggability, streaming needs, network topology — and picks the tool that fits this call, not "the one we always use".

Remote Procedure Call (RPC) is not one thing. It's a family — from the original 1980s Sun RPC and DCE/Java RMI, through SOAP, Thrift, JSON-RPC, all the way to today's dominant flavour, gRPC (Google's open-source, HTTP/2 + Protobuf framework). RPC's promise is that calling a function on another machine looks like calling one locally. Its trap is that the network is not local — latency, partial failure, and versioning are all real, and pretending they aren't is how distributed monoliths are born.

This page shows two concrete sample cases — one where RPC is the right call, one where it is exactly wrong — and gives you an interview-defensible architecture, decision rubric, and code for both.

🧑‍🎓 In plain English

The story, told without jargon

Imagine you work in a busy office. You need three things done to finish a task: check the budget, get a signature, and notify the mailroom to send a letter. Three colleagues can each do one of these.

RPC is a phone call. You dial extension 42, ask "what's the budget for project X?", wait for the answer, hang up. It's quick, direct, and you get the answer now. That's great when you need the answer before you can move on. But phone calls have downsides: if the colleague isn't at their desk, you're blocked. If ten people call the same colleague, they can't answer anyone. If the phone line is bad, you get a wrong number and hear "I'm sorry, wrong department". You have to trust the phone system to work every time.

A message queue is the office mail tray. You drop a note in the tray, walk away, get on with other work. Someone will pick it up when they're free. You never wait; the mail room never gets overwhelmed. But you don't get an immediate answer — and sometimes the note gets read twice by mistake, so your colleague has to know how to say "already done" when a duplicate arrives.

REST is like a phone call to a receptionist who reads out a page from a well-published catalogue ("what are the details of order 42?"). It's a phone call too, but with a shared, self-describing format that anyone in any language can understand — even a stranger who has never been in this office.

So when do you pick which? Use the phone (RPC/gRPC) when you need an immediate answer, you're calling the same office (your own microservices in the same data centre), and both sides speak the same private shorthand for speed. Use the mail tray (queue) when the answer can wait, when the other side might be busy, or when you want to hand off work and forget about it. Use the receptionist (REST) when you're talking to strangers — customers, partners, other companies — who need a well-documented, human-readable interface. That's the whole idea.

📋 What RPC actually is

Definitions and the modern lineup

Remote Procedure Call makes a call to a service on another machine look like a local function call. The client holds a "stub" that mirrors the server's methods; behind the stub, plumbing serialises the arguments, sends them over the network, deserialises the reply, and returns it as if it were local. The details differ, but the family is consistent.

Whenever a modern architect says "RPC", they usually mean gRPC — HTTP/2 for multiplexing, Protobuf for compact schema-first payloads, generated client + server code, native support for four streaming modes (unary, server-stream, client-stream, bidi). It is up to 8× faster than JSON REST and payloads are 60–80% smaller (Microsoft's numbers). We'll use gRPC as the concrete stand-in for "RPC" throughout the rest of the page.

🏗️ Architecture — two sample designs

Sample A (RPC is right) vs Sample B (RPC is wrong)

Sample A — RPC is right: Checkout aggregator calls Pricing, Inventory, and Tax services in real time

The user has clicked "Place Order". The Checkout Aggregator (a Backend-For-Frontend service) needs three answers to compute the cart total: the current price, stock availability, and tax rate for this jurisdiction. All three answers are needed before the client can be told the final total. The three services live in the same VPC, are all owned by the same team, and can all speak Protobuf. This is the textbook case for gRPC.

Aggregator Backend gRPC service Request Reply

Why gRPC wins here: internal, same-VPC hops; needs immediate answer to complete the parent request; polyglot backend teams; strict schema is a plus (breaking the shape breaks the compile). This is exactly the Microsoft eShopOnContainers pattern — a REST edge, gRPC inside. Under 4 KB per Protobuf frame, HTTP/2 multiplexes 100 concurrent calls on one TCP connection. Total P95 for the three parallel calls sits in the 3–8 ms range.

Sample B — RPC is wrong: Order placed → warehouse pick, invoice email, loyalty points, analytics

The user has already been told "order placed successfully". Now four downstream things must happen: (1) the warehouse must pick and pack, (2) an invoice email must be sent, (3) loyalty points must be credited, (4) the analytics data warehouse must ingest the order. None of these need to happen before the response returns; some may take minutes. Some downstream systems (warehouse) may be temporarily offline. Two more downstream consumers will be added next quarter. Every one of those signals points at asynchronous messaging, not RPC.

Publisher Event flow (async) Subscribers

Why gRPC would be wrong here: the Order Service does not need any of the four responses to continue. If it made four synchronous gRPC calls, one slow subscriber (say, the email SMTP gateway is degraded) would slow every checkout. Adding a fifth consumer next quarter would mean editing the Order Service. Retries and dead-letter queues would have to be reinvented in code. Publishing an event once and letting subscribers pull is dramatically simpler and more resilient.

✅ When to reach for RPC — and when not to

✅ Great fit for RPC (gRPC)

  • Internal microservice-to-microservice calls where an immediate answer is required — pricing, tax, geocoding, auth, feature-flag checks.
  • Polyglot backend teams — schemas defined in .proto, code generated for every language.
  • Low-latency, high-throughput hot paths — binary Protobuf + HTTP/2 multiplexing beats JSON/REST by up to 8×.
  • Streaming — real-time telemetry, chat, log tail, ML inference, live game state (gRPC bidirectional streaming).
  • Bandwidth-constrained environments — mobile, IoT, embedded devices where every byte matters.
  • Backend-for-Frontend aggregators — client-facing REST/JSON at the edge, gRPC to internal services (the eShop pattern).
  • Service mesh (Istio, Linkerd, App Mesh) — mesh sidecars natively speak gRPC; retries, mTLS, canary, load-balancing all first-class.

❌ Wrong tool — avoid RPC here

  • Fire-and-forget or fan-out — OrderPlaced, UserSignedUp, PaymentReceived — anywhere N unknown consumers care about the event. Use pub/sub.
  • Long-running work — video encoding, report generation, batch import. Use a queue + workers.
  • Cross-organisation / public APIs — third-party developers expect JSON REST or GraphQL, not a Protobuf toolchain. RPC couples too tightly.
  • Browser-facing traffic — modern browsers cannot open native gRPC; you need gRPC-Web or a JSON gateway.
  • Human-debuggable traffic — you want to be able to curl the endpoint or read logs raw. Binary Protobuf is invisible to tcpdump.
  • Highly evolving contracts where you cannot force clients to re-generate stubs — REST + JSON schema is more forgiving.
  • When one side may be offline — sync RPC fails immediately; queues buffer for hours or days.
  • Cross-region & unreliable networks — high tail-latency makes sync calls costly; async with retries is safer.

🔍 Deep-dive — how gRPC actually works

1. The wire — HTTP/2 with Protobuf frames

gRPC runs on HTTP/2 (2015). HTTP/2 changes everything vs HTTP/1.1: binary framing, header compression (HPACK), stream multiplexing on one TCP connection, bidirectional flow. gRPC uses these to send 30 or 300 parallel requests over one TCP socket with no head-of-line blocking above the transport. The payload is a Protobuf-encoded binary message — 60-80% smaller than the equivalent JSON, no field names on the wire (just tag numbers).

2. The IDL — .proto files

Every gRPC service is defined in a .proto file:

// pricing.proto
syntax = "proto3";
package pricing.v1;

service PricingService {
  rpc GetPrice(GetPriceRequest) returns (GetPriceReply);
  rpc GetPrices(GetPricesRequest) returns (stream PriceReply);
}
message GetPriceRequest { string sku = 1; string currency = 2; }
message GetPriceReply   { int64  cents = 1; string currency = 2; }

Run protoc and the compiler generates a strongly-typed client stub (PricingClient) and a server base class (PricingBase) in whichever language you like. C#, Go, Java, Python, JS, Kotlin, Swift — all interop over the same wire format.

3. Four call modes

  • Unary — one request, one reply (like a regular function call). 95% of gRPC traffic.
  • Server-streaming — one request, N replies. e.g. price stream, log tail.
  • Client-streaming — N requests, one reply. e.g. upload chunks, then done.
  • Bidirectional streaming — N up, N down, independent. e.g. chat, collaborative editing, live ML inference.

4. Deadlines, cancellation, retries

Every gRPC call carries a deadline — an absolute timestamp propagated through the call chain. When the deadline expires, all in-flight work in every downstream service is cancelled. Modern service meshes (Istio, Linkerd) enforce this automatically. This is a huge operational win over ad-hoc HTTP timeouts.

5. Load balancing & the connection-per-endpoint problem

HTTP/2 multiplexes over one long-lived TCP connection. Naïve load balancers (L4/TCP) will pin all traffic to one backend. Solutions: (a) client-side load balancing (the gRPC client itself does round-robin across N sub-channels), (b) proxyless service mesh that steers each RPC, (c) Envoy / Linkerd sidecar that terminates and re-balances. This is a real production gotcha — a naïve ALB gRPC deployment can hot-spot on one pod.

6. gRPC-Web — because browsers can't

Native gRPC uses HTTP/2 features (trailers, binary frames) browsers cannot expose. gRPC-Web is a small protocol variant plus a proxy (usually Envoy) that translates browser-friendly requests to real gRPC upstream. You get typed clients and Protobuf payloads in Angular/React/Blazor; the proxy handles the plumbing.

7. Failure model — "the network is not local"

The RPC illusion is the network looks like a local function. The trap is partial failure. Local functions don't return "connection reset" or "deadline exceeded". Every RPC call must be treated as fallible: retry with backoff on transient errors, circuit-break on repeated failure, propagate the deadline, prefer idempotent methods, and use correlation-ids for tracing. The Fallacies of Distributed Computing (network is reliable, latency is zero, bandwidth is infinite, topology doesn't change) all bite you eventually. RPC does not fix them; it just makes the boilerplate easier.

8. Contract evolution

Protobuf has strong rules for forward/backward compatibility: never reuse a tag number, only add new fields at higher tags, mark deprecated fields (never delete), avoid changing types. If you follow the rules, old clients keep working against new servers and vice versa. This is one reason large orgs (Google, Meta) prefer Protobuf over JSON — the compiler enforces the rules.

💻 Code — same call, two ways

gRPC in .NET (Kestrel + Grpc.AspNetCore)

// pricing.proto  ─ shared schema
syntax = "proto3";
service PricingService {
  rpc GetPrice(GetPriceRequest) returns (GetPriceReply);
}
message GetPriceRequest { string sku = 1; }
message GetPriceReply   { int64 cents = 1; }

// Server — Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddGrpc();
var app = builder.Build();
app.MapGrpcService<PricingImpl>();
app.Run();

// Server — generated base class
public class PricingImpl : PricingService.PricingServiceBase {
  public override Task<GetPriceReply> GetPrice(GetPriceRequest req, ServerCallContext ctx) {
    var price = Lookup(req.Sku);           // local business logic
    return Task.FromResult(new GetPriceReply { Cents = price });
  }
}

// Client — Checkout aggregator
using var channel = GrpcChannel.ForAddress("https://pricing.internal:443");
var client = new PricingService.PricingServiceClient(channel);
var reply = await client.GetPriceAsync(new GetPriceRequest { Sku = "SKU-42" },
              deadline: DateTime.UtcNow.AddMilliseconds(50));   // deadline!
Console.WriteLine(reply.Cents);

Async event publisher (SNS) — the pattern that RPC would ruin

// Order Service — commit + publish, no synchronous waiting
public async Task PlaceOrder(CreateOrderCommand cmd) {
    using var tx = db.BeginTransaction();
    var order = db.Orders.Add(new Order(cmd));
    db.Outbox.Add(new OutboxEvent("OrderPlaced", order));   // same transaction
    await tx.CommitAsync();
    // A background worker ships outbox rows to SNS.
    // Warehouse, Email, Loyalty, Analytics — all subscribed. Zero coupling to Order.
}

Note the shape: the synchronous call gets the answer in real time. The asynchronous event fans out to four subscribers who never block the caller. Same domain, opposite tools, both correct.

🧭 Decision rubric — the two-question test

When someone hands you a call to design, ask two questions before picking a transport:

  1. "Does the caller need the answer before it can continue?"
    • Yes → synchronous. Then ask: "Public boundary or internal?" Public → REST. Internal → gRPC.
    • No → asynchronous. Use SNS/SQS/EventBridge/Kafka.
  2. "How many consumers care about this signal, and can they change independently?"
    • One or few, tightly co-owned → sync (RPC or REST) is fine.
    • Many, or "we might add more later" → async pub/sub, always.

Those two questions correctly classify 95% of the design choices you'll face. The remaining 5% are streaming, real-time, or hybrid — where gRPC's bidi streaming or a WebSocket becomes the answer.

🗣️ Interview cheat sheet

30-second pitch: "RPC — usually gRPC in modern systems — is the right choice for internal microservice-to-microservice calls that need an immediate answer: HTTP/2 multiplexes N parallel calls on one TCP connection, Protobuf keeps payloads 60-80% smaller than JSON, generated stubs give you type-safe polyglot clients, and streaming is first-class. It is the wrong choice for fire-and-forget, fan-out, long-running, browser-facing, cross-organisation, or heavily-evolving traffic — those want REST or async messaging instead. The rule of thumb: REST at the perimeter, gRPC on the inside, events for anything downstream. Every RPC call must still handle partial failure — deadlines, retries with backoff, circuit breakers, correlation IDs — because the network is never local, no matter how transparent the stub is."

Five talking points that win the round

  • "Sync when you need an answer, async when you need durability and decoupling."
  • "gRPC = HTTP/2 + Protobuf + generated stubs + streaming" — one-line definition.
  • "Deadlines propagate down the call chain" — the operational win people forget to mention.
  • "Browsers can't speak native gRPC" — you need gRPC-Web via Envoy for front-end.
  • "Naïve L4 load-balancing pins traffic to one pod" — the production gotcha that shows you've operated it.

Numbers to quote

  • gRPC up to 8× faster than JSON REST; payloads 60-80% smaller.
  • Internal gRPC P95 sits at 1-5 ms in the same VPC.
  • HTTP/2 multiplexes 100+ concurrent streams on one TCP socket.
