🎯 Real-world scenario

What we're building & where it's used

We're designing a real-time messaging system — the class of product that powers WhatsApp, Facebook Messenger, iMessage, Telegram, Signal, Slack, Discord, WeChat and Microsoft Teams. A user opens the app, types a message, and it appears on the other person's phone in well under a second — even though the two devices might be on different continents, on different networks, and one of them might have been offline for the last three hours. Under the hood the system must maintain hundreds of millions of persistent connections, route messages to whichever server owns the receiver's socket, buffer anything the receiver hasn't picked up yet, and deliver every message exactly once, in order, with strong delivery and read receipts.

This scenario is the archetypal stateful system-design interview: unlike a URL shortener where every request is a one-shot HTTP call, a chat backend has to hold long-lived connections and coordinate fan-out across devices. Interviewers use it to probe how you reason about WebSockets, service discovery, message queues, event-driven fan-out, distributed key-value storage, presence detection, and multi-device synchronization — and how you defend the trade-offs when they push back.

🧑‍🎓 In laymen terms

The whole thing, without any jargon

You type "hey, are you free tonight?" and tap send. A second later your friend's phone buzzes. That short second is what we're designing. It sounds trivial — but two billion people are doing this at the same time, from every country, on flaky trains and packed metros, and the app promises the message will always arrive, in the right order, even if their phone was off when you sent it.

Picture a giant international post office. When you sign in to WhatsApp, the app quietly walks over to one specific clerk's window and says "I'm here — anything for me?" and then stays at the window with the phone line open. That's the trick: instead of you calling every few minutes to ask "got any mail?", you leave a permanent line running so the clerk can just shout your name the instant a letter drops on the counter. This permanent line is called a WebSocket, and it's what makes chat feel instant instead of laggy.

When your friend Priya sends you a message, her app hands it to her clerk. Her clerk stamps it with a number so ordering never gets scrambled, writes a copy into a giant filing cabinet (in case something breaks), and then figures out which clerk you're currently talking to — using a big directory that says "Sonu is at window 47B." Your clerk shouts down your open line, your app buzzes, and up pops the message.

What if your phone was off when Priya sent it? Easy — the message just waits in the filing cabinet, and the moment you sign back in, the system replays everything you missed, in order. This is why WhatsApp never says "you missed 3 messages, sorry" — it will always catch you up.

The little grey ticks you see are the story of that journey: one tick means the server got it, two ticks mean your friend's phone got it, two blue ticks mean their eyes actually looked at it. Each tick is a tiny confirmation message travelling the other way. And when you use WhatsApp Web at the same time as your phone, the same trick keeps both screens in sync — every device gets a copy through its own line.

The hard part isn't one message — it's a hundred billion messages a day. No single post office could hold that. So there are thousands of clerks in dozens of buildings around the world, all talking to each other over super-fast internal pipes, and a smart directory that tells your app which building to walk into. That's the design.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • 1-on-1 messaging with delivery + read receipts (single grey tick → double grey tick → double blue tick).
  • Group messaging (WhatsApp caps at 1024 members per group; WeChat caps at 500).
  • Presence (online/last-seen).
  • Offline delivery — messages sent while you were offline arrive as soon as you reconnect, in order.
  • Media messages (images/video) stored separately in blob storage.
  • Multi-device — same account on phone + web + desktop, kept in sync.
  • End-to-end encryption — the server can never read message content.

Non-functional requirements

  • Low latency: p99 send-to-deliver < 500 ms for online users.
  • Extreme availability: multi-region active-active, 99.99% uptime.
  • Durability: never lose a message that the server has acknowledged.
  • Ordering: monotonic ordering within a conversation (not globally).
  • Consistency: read-your-writes and monotonic reads within a device.

🏗️ High-level architecture

How the pieces fit together

The system splits into three planes. Stateless services (auth, signup, profile, friend list, media upload) sit behind a normal load balancer — any node can serve any request. Stateful chat services hold long-lived WebSocket connections; each client is pinned to exactly one chat server, so we need a service-discovery layer (typically Apache ZooKeeper) to tell a signing-in client which chat server to connect to. Finally, storage is split: user profiles and group metadata live in a relational DB (MySQL), messages live in a horizontally sharded key-value store (Cassandra / HBase / DynamoDB), and media blobs live in an object store (S3) fronted by a CDN.

When Priya sends a message to Sonu, the request travels: Priya's phone → her chat server → ID generator (Snowflake) → message KV store → message sync queue (Kafka) → Sonu's chat server → Sonu's phone. If Sonu is offline, the last hop is replaced with a push notification via APNs/FCM; the message stays in the KV store until Sonu reconnects and pulls anything above his last-synced message ID. Read receipts flow the same way in reverse, encoded as tiny control messages on the same WebSocket.

🔍 Component deep-dive

1. WebSocket connection — how messages reach online users

Every online user opens a WebSocket (WSS on port 443) to a specific chat server. Unlike HTTP request/response, a WebSocket is bidirectional and persistent — the server can push a new message the millisecond it arrives without the client polling. Behind the scenes the server pins userId → (server, socket_fd) in an in-memory table (backed by Redis across the fleet) so that any other server can look up "where is Sonu right now?" in O(1). This is the piece a lot of candidates get wrong: chat is stateful — a load balancer alone doesn't help, because you need to route the packet to the exact server that owns the recipient's socket.

Why WebSocket and not HTTP long-polling? Three reasons interviewers want to hear: (1) real bidirectional push, no polling waste; (2) one connection per device instead of one HTTP request per message — massively lower CPU and memory; (3) the server can immediately detect a graceful close, so presence flips cleanly. The trade-off: WebSockets are stateful, so autoscaling is harder — you can't just add a box and route half the traffic to it.

2. Offline handling — Kafka + durable KV

Before a message is acked to the sender, the chat server writes it to Kafka (a FIFO log) and to a replicated key-value store (Cassandra / HBase / DynamoDB). Only then does it send the single grey tick back. This is the write-then-ack pattern — the message is durable before we promise anything. If the recipient is offline, we simply skip the WebSocket push; the message sits in the KV store keyed by (recipient_id, message_id) where message_id is a time-sortable Snowflake ID. When the recipient reconnects, its device sends "give me everything > cur_max_message_id" — a bounded, ordered replay.

WhatsApp historically used Mnesia (an Erlang-native distributed DB) for pending-message storage, which is why they can run so few servers per user — but modern designs use Cassandra or DynamoDB with a similar shape.

3. Guaranteed delivery — at-least-once + idempotent client-ack

Real messengers are at-least-once with client-side dedup, not exactly-once. The flow: the sender generates a client-side UUID (client_msg_id) and retries the send until it gets a server-ack. The server generates a durable Snowflake ID and stores the mapping client_msg_id → server_msg_id. If the sender ever retries the same client_msg_id, the server returns the existing server_msg_id instead of creating a duplicate. On the receiver side, the client also tracks the highest server ID it has stored and drops duplicates by ID. This gives you effectively exactly-once without needing distributed 2PC.

4. Read receipts — three-state ACK chain

Every message has three delivery states, each triggering a tiny control packet the other way:

  • Server-ack (✓ single grey tick) — chat server has durably stored the message.
  • Delivery-ack (✓✓ double grey tick) — receiver's device has received it over its WebSocket.
  • Read-ack (✓✓ blue) — the receiver actually opened the chat and rendered the message.

These acks are just small JSON envelopes on the same WebSocket: {type: "ack", state: "read", server_msg_id: 87342...}. The sender's client renders them into the little ticks you see under each bubble.

5. Multi-device sync — per-device identity + client fan-out

The 2021 WhatsApp multi-device rewrite (see the Meta engineering post in Sources) is worth memorising because it flips a common assumption. Instead of the phone being the single source of truth that mirrors to companions, each device (phone, web, desktop, Portal) has its own identity key. When Priya sends a message to Sonu, her client encrypts and transmits N times — once per device in Sonu's device list, using pairwise Signal Protocol sessions. This is called client-fanout. The server never sees plaintext; it just routes N ciphertexts. For app state (contact names, archived chats, starred), the server holds an end-to-end encrypted snapshot each device can pull.

For sync ordering, every device tracks cur_max_message_id. On reconnect it asks "give me everything > my max" and gets back an ordered stream. Because Snowflake IDs are monotonic within a partition, this is trivially O(log N) with a range query.

6. Presence — heartbeats, not disconnect events

Naïvely you'd say "flip user to offline when the WebSocket closes." That fails in practice — mobile users drop and reconnect constantly (tunnels, metros, switching Wi-Fi ↔ 4G). A single close-event would make Priya's app flicker "online / last seen 3s ago" every 30 seconds. Instead, clients send a heartbeat every 5 seconds, and presence flips offline only after ~30 seconds of no heartbeat. Presence changes fan out via pub/sub (Redis channels or Kafka) to only the friends who currently have that user's chat open — not to everyone.

7. Group messaging — server fan-out vs client fan-out

Two approaches: (a) server fan-out — the sender ships one ciphertext to the server, the server duplicates it into N recipient inboxes; (b) client fan-out — the sender's client ships N ciphertexts, one per recipient. WhatsApp uses (b) for E2E encryption reasons (server can't hold decryption keys). For large groups (1024 members) this uses the Signal Sender Key optimisation: the sender encrypts the message once with a symmetric group key and only sends that group key pairwise to each member — a huge reduction. Facebook Messenger and Discord historically used server fan-out because they don't do E2E by default.

8. Storage schema

Two tables in a Cassandra-style KV store:

-- 1-on-1 messages (partitioned by chat_id, ordered by message_id) CREATE TABLE messages ( chat_id uuid, -- deterministic hash(min(a,b), max(a,b)) message_id bigint, -- Snowflake, time-sortable sender_id uuid, content blob, -- ciphertext sent_at timestamp, PRIMARY KEY ((chat_id), message_id) ) WITH CLUSTERING ORDER BY (message_id DESC); -- Per-user inbox (used for offline replay) CREATE TABLE inbox ( user_id uuid, message_id bigint, chat_id uuid, PRIMARY KEY ((user_id), message_id) ) WITH CLUSTERING ORDER BY (message_id DESC);

The messages table is the source of truth. The inbox table is a per-user projection that makes "pending offline messages for user X" a single partition read. Both are shardable by their partition key.

Deployment shape: multi-region active-active. Each region owns a slice of users (assigned by phone-number country code hashed into a region). Cross-region messages travel over a Kafka MirrorMaker link to the destination region, then out to the recipient's chat server. DynamoDB Global Tables replicate the message store between regions asynchronously for disaster recovery, but the write path is region-local for latency.

💻 C# implementation

A minimal-but-correct chat server: it accepts WebSocket connections, tracks online users in a Redis-backed routing table, generates Snowflake message IDs, persists to a message store, and routes the message to the recipient's chat server. Ack/read receipts are just typed frames on the same socket.

// ChatServer.cs — hosting a WebSocket endpoint at /ws
using System.Net.WebSockets;
using System.Text;
using System.Text.Json;
using StackExchange.Redis;

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
var redis = await ConnectionMultiplexer.ConnectAsync("redis:6379");
var db    = redis.GetDatabase();
var pubsub= redis.GetSubscriber();
var serverId = Environment.MachineName;                // e.g. "chat-us-east-2-42"
var sockets = new ConcurrentDictionary<string, WebSocket>();

app.UseWebSockets();

app.Map("/ws", async (HttpContext ctx) =>
{
    if (!ctx.WebSockets.IsWebSocketRequest) { ctx.Response.StatusCode = 400; return; }
    var userId = AuthenticateJwt(ctx.Request.Headers["Authorization"]);
    var ws = await ctx.WebSockets.AcceptWebSocketAsync();

    sockets[userId] = ws;
    await db.StringSetAsync($"route:{userId}", serverId, TimeSpan.FromMinutes(2));
    var inboxChannel = new RedisChannel($"deliver:{serverId}", RedisChannel.PatternMode.Literal);
    await pubsub.SubscribeAsync(inboxChannel, (_, msg) => DeliverToSocket(msg!));

    // Heartbeat + drain incoming
    var buf = new byte[8192];
    while (ws.State == WebSocketState.Open)
    {
        var res = await ws.ReceiveAsync(buf, CancellationToken.None);
        if (res.MessageType == WebSocketMessageType.Close) break;
        var frame = JsonSerializer.Deserialize<Frame>(buf.AsSpan(0, res.Count));
        await HandleFrame(userId, frame!);
        await db.KeyExpireAsync($"route:{userId}", TimeSpan.FromMinutes(2)); // refresh
    }

    sockets.TryRemove(userId, out _);
    await db.KeyDeleteAsync($"route:{userId}");
});

async Task HandleFrame(string senderId, Frame f)
{
    switch (f.Type)
    {
        case "send":
            var serverMsgId = Snowflake.NextId();                     // 64-bit time-sortable
            await PersistMessage(senderId, f.RecipientId!, serverMsgId, f.Content!);
            await AckToSender(senderId, f.ClientMsgId!, serverMsgId); // ✓ single tick
            await Route(f.RecipientId!, new Frame("deliver", senderId, serverMsgId, f.Content));
            break;

        case "delivered_ack":                                     // ✓✓ double tick
        case "read_ack":                                          // ✓✓ blue tick
            await Route(f.OriginalSenderId!, f);
            break;

        case "heartbeat":
            await db.KeyExpireAsync($"presence:{senderId}", TimeSpan.FromSeconds(30));
            break;
    }
}

async Task Route(string targetUserId, Frame frame)
{
    var targetServer = await db.StringGetAsync($"route:{targetUserId}");
    if (targetServer.HasValue)                                    // online
    {
        await pubsub.PublishAsync($"deliver:{targetServer}",
                                 JsonSerializer.Serialize(frame));
    }
    else                                                          // offline
    {
        await EnqueueInbox(targetUserId, frame);                   // KV write
        await SendPushNotificationAsync(targetUserId);
    }
}

async Task DeliverToSocket(string serialised)
{
    var f = JsonSerializer.Deserialize<Frame>(serialised)!;
    if (sockets.TryGetValue(f.RecipientId!, out var ws) && ws.State == WebSocketState.Open)
    {
        var bytes = Encoding.UTF8.GetBytes(serialised);
        await ws.SendAsync(bytes, WebSocketMessageType.Text, endOfMessage: true, CancellationToken.None);
    }
}

record Frame(string Type, string? SenderId = null, long? ServerMsgId = null,
              string? Content = null, string? RecipientId = null,
              string? ClientMsgId = null, string? OriginalSenderId = null);

app.Run();

What to point out in an interview when walking through this: (1) the routing table (route:{userId}) is the entire trick — any server can push to any user in one Redis lookup; (2) the send handler acks after durable persist, not on socket accept — that's what makes the single grey tick meaningful; (3) the Redis pub/sub channel-per-server means a message crosses at most one hop between chat servers; (4) heartbeat + TTL on the Redis key handles graceful and non-graceful disconnects uniformly.

⚖️ Trade-offs, bottlenecks & likely follow-ups

The scaling bottlenecks

The WebSocket layer is always the first bottleneck. Each connection burns ~30–50 KB of kernel + user memory, plus a file descriptor. On a well-tuned Linux box you can push ~1–2M concurrent sockets, WhatsApp reportedly ran up to ~10M with heavy kernel tuning on Erlang. Above that you're just adding boxes. The routing table (Redis) is the second bottleneck — it takes a hit on every message; you shard it by hash(userId) % N. The message store is the third: at 1M writes/sec you must partition by chat_id, not by user or by time.

Consistency trade-off

We chose availability over strong consistency (AP in CAP terms). If a partition happens between regions, sending still works — messages queue locally and reconcile when the link heals. The cost is that a message can very briefly land out of order if it crossed a region right at partition — the Snowflake ID lets clients reorder on receive, so users never see it.

Delivery-guarantee trade-off

We do at-least-once + client-side idempotency, not exactly-once. Building true exactly-once would require distributed 2PC on every message — too slow. The dedup key (client_msg_id) makes retries invisible in practice.

Follow-ups you should expect

What happens if a chat server crashes with 1M connected users?

All those TCP connections drop. Clients detect the RST and immediately reconnect through the load balancer, which routes them (via ZooKeeper/Cloud Map) to a healthy server. On reconnect, each client asks the KV store for messages above its cur_max_message_id. Nothing is lost because the message was durable before we acked it.

How do you scale groups to 1000+ members without server fan-out costing 1000× storage?

Two techniques. (1) Client fan-out with Signal Sender Keys: sender encrypts once with a group key, sends N tiny key envelopes but only one ciphertext. (2) Server stores one copy of the ciphertext in a "channel" partition and uses per-user pointers rather than duplicating.

How is ordering preserved when two people type at the same time?

Ordering is only guaranteed within a conversation. Both messages get Snowflake IDs; the client sorts by ID before rendering. Because Snowflake embeds a millisecond timestamp, ties are extremely rare and broken deterministically by machine ID.

How does WhatsApp Web stay in sync with your phone?

Post-2021 architecture: each device has its own identity key and its own WebSocket to the server. Every message is client-fanout'd to every device in the recipient's device list. On new-device link, the primary device transfers an E2E-encrypted history bundle. App state (mutes, archives) sits on the server as an E2E-encrypted blob each device can pull.

How do you handle a user with 100,000 friends going online?

You don't broadcast presence to all of them. Presence pub/sub only fires for the subset of friends who currently have that user's chat open — a much smaller set. For the rest, presence is fetched on demand when they next open the chat.

How does end-to-end encryption survive multi-device without exposing keys server-side?

The server holds identity public keys, one per device, and never sees a private key. The Signal Protocol's Double Ratchet establishes a pairwise session between every (sender-device, receiver-device) pair. The server just routes ciphertexts.

🗣️ Interview cheat sheet

30-second pitch: "I'd build it as three planes — stateless APIs behind ALB, stateful chat servers holding WebSockets, and durable storage in DynamoDB + S3. A Redis routing table maps userId → chat_server so any node can push to any user in one hop. Sends are written to Kafka + DynamoDB before we ack, giving durable at-least-once delivery with client-side dedup on client_msg_id. Offline users get catch-up via a range scan on their inbox partition. Read receipts are just typed control frames on the same socket. Multi-device works via per-device identity keys and client-fanout, so E2E encryption stays intact."

5 talking points that win the round

  • WebSocket routing — a stateful chat needs a fleet-wide userId → server map, not just a load balancer.
  • Write-then-ack — durable persist before returning ✓; that's how the single grey tick becomes a promise.
  • Snowflake IDs — monotonic, time-sortable, decentralised — enable "everything above my last ID" replay.
  • Client fan-out for multi-device — per-device identity keys keep E2E encryption intact across web/phone/desktop.
  • Heartbeats, not disconnect events — the only sane way to handle presence on flaky mobile networks.
