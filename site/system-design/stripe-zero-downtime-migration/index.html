Stripe's Zero-Downtime Data Migration

How Stripe moves hundreds of millions of live records — and reshapes the schema underneath them — without a single minute of downtime and zero data inconsistency.

🎯 Real-world scenario

What we're building & where it's used

Stripe processes payments for millions of businesses — DigitalOcean, Squarespace, Shopify merchants, Amazon, Uber Eats — and its Subscriptions table alone holds hundreds of millions of live records. In its early days, Stripe stored subscription data as an array field inside the Customer record. That worked at a few hundred customers. It stopped working at scale: every subscription change had to rewrite the whole Customer document, and the design collapsed once customers wanted multiple subscriptions.

The obvious fix — pull subscriptions into their own dedicated table — is trivial on paper and terrifying in practice. The old field is referenced from thousands of lines of code across many services. The system serves live traffic 24/7 for businesses that make real revenue every second the API is up. And running a bulk migration sequentially would take, in Stripe's own math, over three years for 100M records at one second each.

This is the "engine change while the plane is flying" problem, and every large system hits it — Facebook, Shopify, GitHub, LinkedIn, Uber. The playbook Stripe wrote for it is now the industry-standard four-phase online migration: dual-write, backfill, migrate reads with a shadow-compare, then remove the old field. It's a classic staff/senior interview question because every candidate has to migrate a schema someday, and doing it without downtime — or a Sunday-morning outage post-mortem — is what separates senior engineers from principal ones.

🧑‍🎓 In laymen terms

Explain it like I've never written code

Imagine you run a massive filing cabinet business. Every customer has a folder, and inside that folder — jammed into the same page — you scribble down their monthly subscriptions. It worked when you had 200 customers. Now you have hundreds of millions, some with dozens of subscriptions each, and every time someone changes one, your clerk has to grab the whole folder, rewrite the whole page, and file it back. Everything is slow. Everything is fragile.

You decide subscriptions deserve their own filing cabinet. Great idea — but here's the catch: your business never closes. Customers are signing up, cancelling, and paying right now, this second. You cannot say "we'll be back Monday." You cannot lose a single record. And you have thousands of clerks in different departments who all know the old system by heart.

So you move in four calm phases, and this is the whole trick:

1) Write to both places. From today, whenever a clerk updates a subscription, they write it in both the old folder and the new cabinet. New data is safe from day one.

2) Copy the old stuff over. At night, a huge team of movers scans a snapshot of every folder (not the live ones — a photocopy, so you don't slow the business down) and copies each subscription into the new cabinet. When they're done, they run the scan again to confirm nothing was missed.

3) Switch reading, but check yourself. Now, whenever someone looks up a subscription, you read from the new cabinet — but you also secretly peek at the old folder and compare. If the two ever disagree, an alarm rings. Only when the alarms stay silent for weeks do you trust the new cabinet fully.

4) Throw out the old page. Finally, stop writing to the old folder, delete the scribbled subscription page, and the migration is done.

Every big company you use — WhatsApp, Instagram, Uber, Netflix, your bank — has done this dance many times. Nobody noticed. That's the whole point.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Move a live entity (Subscriptions) from being nested inside a parent record to its own dedicated table with its own schema.
  • All existing code paths — thousands of call sites across many services — must keep working through the transition.
  • New writes go to the new store from day one; old data must be reconciled without blocking traffic.
  • Every read must return the correct value at every moment of the migration; there is no "wrong for 10 minutes" tolerance.

Non-functional requirements

  • Zero downtime. No maintenance windows. Stripe's API SLA is 99.999%+ — every second of outage is real merchant money lost.
  • Zero data inconsistency. Any divergence between old and new must be detected in seconds, not days.
  • Bounded blast radius per change. Rollback must be possible at every phase.
  • Incremental rollout. Ramp writes and reads by percentage, monitor, escalate.

🏗️ High-level architecture

How the four phases fit together

The end-to-end pattern is a four-phase incremental rollout. The system is never in a "transitional half-state" — at every moment one store is authoritative for reads, both stores are being written, and a shadow-compare is running to detect drift. The migration only progresses when the previous phase has been silent for long enough to trust.

🔍 Component deep-dive

Phase 1 — Dual writing

The first move is additive, not disruptive. Create the new Subscriptions table. Add a dual-write code path in the data-access layer so every mutation on a subscription writes to both stores. Guard it behind a feature flag with a percentage rollout — Stripe ramps to 100% while watching p99 latency, error rate, and cache-hit rates on the primary DB. Existing objects that get touched during this phase are lazily copied on write, so hot data heals itself. The old field remains the source of truth for reads.

Key invariants: writes are ordered (old first, then new — or use an outbox pattern to avoid partial failures); dual-write failures are logged and retried; the code path is small enough (a few hundred lines) to review in one PR.

Phase 2 — Backfill via offline MapReduce

Running the backfill against production would double the write load and page oncall. Stripe instead used Hadoop snapshots — a nightly copy of the production DB into their data warehouse — and wrote MapReduce jobs using Scalding, Twitter's Scala DSL over Cascading. A "simple job in 10 lines of code" enumerates every subscription ID that exists in the old field, then a parallel multi-threaded migrator copies each into the new table via the same API path as a dual write. After the sweep, they re-run the Scalding job to confirm the delta is empty. This "scan → migrate → re-scan to zero" pattern is the safety net.

Phase 3 — Shadow reads and Scientist

Cutting reads over is the scariest phase — a bug here shows up as wrong data returned to real customers. Stripe uses GitHub Scientist, a library that runs two code paths in production for the same request, returning the control's result to the caller while asynchronously executing the candidate and publishing a mismatch record when the two disagree. In practice this means every read from the old store is shadowed by a read from the new; the returned value is still from the old (so no user-facing risk), but the difference feeds a dashboard.

Only when the mismatch rate stays effectively zero for days — after ignoring known-benign differences like ordering — does Stripe flip the primary read to the new store. Even then, dual-writes and shadow reads on the old store are kept live for a while so rollback is a one-flag flip.

Phase 4 — Cleanup and hard errors

The last phase drops the deprecated field. Stripe's technique is aggressive: replace the old accessor with a hard error so any straggler code path that still touches it explodes in staging or canary before it can silently regress. The subscriptions array on Customer becomes Opus::Error.hard("Accessing subscriptions array on customer"). A final Scalding job lazily deletes any remaining data, and the column can eventually be dropped.

Why it works

The whole design is a staircase of small, reversible steps. At every phase, one side is authoritative, the other is being validated. There is never a moment where the system depends on both being correct simultaneously. Every phase has a clear go/no-go metric — dual-write error rate, backfill completeness, Scientist mismatch rate — and rollback is always a feature-flag flip away.

🧮 The DSA behind it

Data structures & algorithms

Zero-downtime migration looks like ops, but under the hood it's a stack of classical CS primitives — parallel scans, set differences, distributed consensus (implicitly, through feature flags and consistent hashing), and probabilistic sketches for verification.

The core algorithms

  • MapReduce over a snapshot — the backfill is a distributed map (parse each old record → emit the flattened row) with no reduce; Scalding compiles it down to Hadoop tasks. Complexity: O(N/P) wall time on P mappers.
  • Set difference for completeness — after the sweep, compute {old_ids} − {new_ids}. If empty, we're done; otherwise re-migrate the delta. Two big-set diff via sort-merge is O(N log N) per store on the snapshot.
  • Shadow compare (Scientist) — deep-equality of two candidate values, with configurable normalization for known-benign ordering / whitespace / rounding differences. Runs on every read; overhead is bounded by enabled? sampling.
  • Reservoir sampling / percentage rollout — feature flags use a hash of the object ID modulo 100 to decide "does this request take the new path?" — a deterministic sampler that ramps cleanly from 0% → 100% and gives idempotent per-object routing.
  • Idempotent writes — dual writes must be safe to retry. Stripe uses idempotency keys (originally exposed in their public API) so the same write hitting both stores twice does not double-insert.
  • Bloom / count-min sketches (optional) — for very large datasets, a Bloom filter of "already migrated IDs" fits in RAM and avoids re-processing during checkpointed sweeps.
  • Transactional outbox pattern — an alternative to raw dual-write; the app writes to one DB with an outbox row in the same transaction, and a relay tails that outbox and writes to the new store. Guarantees at-least-once delivery even on partial failures.

Concretely: use DMS with ongoing replication to seed the target and keep it warm; run Glue Spark against a nightly S3 export for the heavy sweep; use DynamoDB Streams into Lambda to catch anything mutated after the export; drive dual-writes from application code guarded by AppConfig; emit a mismatch CloudWatch metric from every shadow read and alarm on any non-zero value; and gate the read cutover on that alarm being silent for a full week.

💻 C# implementation

Below is the shape of the pattern in C# — a repository wrapper that owns dual-write, shadow-read, and the Scientist-style compare. The exact percentages and stores are pluggable; the invariants are what matter.

// SubscriptionRepository — a dual-write, shadow-read facade over old + new stores.
// Feature flags drive the phase: dual-write %, read source, shadow-compare on/off.
public sealed class SubscriptionRepository
{
    private readonly ISubscriptionStore _old;      // Customers.subscriptions[]
    private readonly ISubscriptionStore _new;      // dedicated Subscriptions table
    private readonly IFeatureFlags       _flags;
    private readonly IMetrics            _metrics;
    private readonly ILogger<SubscriptionRepository> _log;

    public SubscriptionRepository(
        ISubscriptionStore oldStore, ISubscriptionStore newStore,
        IFeatureFlags flags, IMetrics metrics,
        ILogger<SubscriptionRepository> log)
    { _old = oldStore; _new = newStore; _flags = flags; _metrics = metrics; _log = log; }

    // ---------- WRITE PATH ----------
    public async Task<Subscription> SaveAsync(Subscription s, CancellationToken ct)
    {
        // Phase 1: always write to old; dual-write to new for X% of rollout.
        var saved = await _old.UpsertAsync(s, ct);

        if (_flags.IsEnabled("dual_write.subscriptions", s.Id))
        {
            try { await _new.UpsertAsync(saved, ct); }
            catch (Exception ex)
            {
                _metrics.Increment("migration.dual_write.new.error");
                _log.LogError(ex, "dual-write to new store failed for {Id}", s.Id);
                // swallow: old store is still authoritative in phase 1
            }
        }
        return saved;
    }

    // ---------- READ PATH — Scientist-style shadow compare ----------
    public async Task<Subscription?> GetAsync(string id, CancellationToken ct)
    {
        bool readFromNew  = _flags.IsEnabled("read.subscriptions.from_new", id);
        bool shadowCompare = _flags.IsEnabled("shadow.subscriptions", id);

        // Choose "control" (returned to caller) and "candidate" (validated silently).
        var primary   = readFromNew ? _new : _old;
        var secondary = readFromNew ? _old : _new;

        var primaryTask = primary.GetAsync(id, ct);
        if (!shadowCompare) return await primaryTask;

        // Run both, catch candidate exceptions, publish mismatches — never affect the caller.
        var secondaryTask = SafeGet(secondary, id, ct);
        await Task.WhenAll(primaryTask, secondaryTask);

        var p = primaryTask.Result;
        var s = secondaryTask.Result;
        if (!Equivalent(p, s))
        {
            _metrics.Increment("migration.shadow.mismatch");
            _log.LogWarning("mismatch id={Id} primary={P} secondary={S}", id, p, s);
        }
        return p;
    }

    private async Task<Subscription?> SafeGet(ISubscriptionStore store, string id, CancellationToken ct)
    {
        try { return await store.GetAsync(id, ct); }
        catch (Exception ex)
        { _metrics.Increment("migration.shadow.error"); _log.LogWarning(ex, "shadow read failed"); return null; }
    }

    // Normalize before compare — ordering, timestamps, whitespace, etc.
    private static bool Equivalent(Subscription? a, Subscription? b)
    {
        if (a is null && b is null) return true;
        if (a is null || b is null) return false;
        return a.Id == b.Id
            && a.CustomerId == b.CustomerId
            && a.Status == b.Status
            && a.PlanId == b.PlanId
            && a.PeriodEnd == b.PeriodEnd;
    }
}

// The backfill worker — idempotent, parallel, resumable.
public sealed class BackfillWorker
{
    public async Task RunAsync(IAsyncEnumerable<string> snapshotIds, int parallelism, CancellationToken ct)
    {
        await Parallel.ForEachAsync(snapshotIds,
            new ParallelOptions { MaxDegreeOfParallelism = parallelism, CancellationToken = ct },
            async (id, token) =>
            {
                var record = await _oldStore.GetAsync(id, token);
                if (record is null) return;
                // Idempotency: upsert by primary key so re-runs are safe.
                await _newStore.UpsertAsync(record, token);
                _metrics.Increment("migration.backfill.copied");
            });
    }
}

The pattern generalizes: swap Ruby for C#, MongoDB for RDS, Hadoop for Glue — the shape is identical. Idempotent upserts, feature-flag ramps, shadow reads with a metric, and a bounded rollback path.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Where this pattern hurts

Dual-write doubles the write path. If the primary store was already at 80% CPU, dual-writing sends it over. Mitigation: ramp slowly, throttle backfill during business hours, run the sweep off a snapshot not the live DB. Alternative: the transactional outbox pattern — write only once (to the outbox) inside the primary transaction and let a relay do the second write async. See Transactional Outbox.

Ordering across two stores is hard. If the new-store write succeeds but the old fails, you have a phantom row. Guardrails: idempotency keys, outbox to guarantee at-least-once, and a periodic reconciler that finds phantoms.

Deep-equality is fragile. Two stores rarely produce byte-identical results — timestamps have different precision, JSON key ordering differs, floats round differently. You'll spend real time writing the Equivalent() function and ignoring known-benign differences. Scientist supports this via ignore / compare blocks.

Feature-flag explosion. A big migration accumulates dozens of flags: dual-write, shadow-read, cutover, backfill-scope. Own the lifecycle — every flag has an owner and a deletion date, or your codebase will drown in ifs.

The final 0.001% is the hardest. Getting Scientist mismatches to zero takes weeks. The last mismatches are almost always real bugs in the new code path or race conditions between the two writes — that's exactly why the shadow phase exists.

Likely interview follow-ups

Why not just take a maintenance window?

For a payment API the outage cost is real merchant revenue and SLA credits. Even a 30-min window at Stripe's scale would strand thousands of live checkouts. And you can't "just do it faster" — sequential migration of 100M rows is measured in years.

What if the backfill runs during dual-writes and overwrites a fresh value with an old one?

Use compare-and-swap or last-write-wins with a version/timestamp column. Backfill writes only if new.updated_at < source.updated_at, so a live dual-write that hit the new store first is never clobbered.

How do you handle deletes during the migration?

Tombstones. Deletes are dual-written just like inserts. Backfill of a snapshot must reconcile against a tombstone log so it doesn't "resurrect" already-deleted rows.

How do you roll back if you're already in phase 3 and something goes wrong?

Flip the read.from_new flag back to false. Because you kept dual-writing to the old store, its state is still fresh; the shadow-read alarm goes silent immediately. That's why you never remove the safety net early.

Would you use CDC (Change Data Capture) instead?

CDC (DynamoDB Streams, Debezium, DMS CDC) is a fine implementation of the "outbox tail" — it eliminates dual-write in application code by streaming DB changes into the new store. The four-phase strategy stays; the mechanism changes.

How is this different from a schema migration inside one DB?

Same pattern, smaller blast radius. Add the new column, backfill it, cut reads over, drop the old. Tools like gh-ost / pt-online-schema-change for MySQL implement this at the storage layer. The Stripe pattern generalizes to cross-store and cross-schema.

What's the analog to Scientist in a .NET / Java shop?

There's no library as popular; teams roll their own. Practically it's ~50 lines: run both code paths inside a Task.WhenAll, catch candidate exceptions, deep-compare, publish a metric. That's the C# snippet above.
