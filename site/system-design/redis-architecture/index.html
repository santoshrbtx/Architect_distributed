🎯 Real-world scenario

What Redis is, and where it's used

Redis (Remote Dictionary Server) is an open-source, in-memory data-structure store. It's the Swiss Army knife of the data layer — used as a cache, a session store, a pub/sub bus, a rate-limiter backend, a leaderboard engine, a distributed lock, a message queue, and even a primary datastore for latency-critical workloads. It answers most operations in < 1 ms at 100k+ ops/sec per node, which is why almost every large-scale system has a Redis tier somewhere in the stack.

Real products that rely on it: Twitter caches timelines in Redis, Stack Overflow serves nearly every page from it, GitHub uses it for job queues, Snapchat uses it for real-time messaging, Instagram uses it for feed and counters, Uber uses it for driver-location and geo queries, and Discord uses it for presence. Managed offerings — AWS ElastiCache, Amazon MemoryDB, GCP Memorystore, Azure Cache for Redis, Redis Cloud — are among the largest revenue lines for cloud providers.

In an interview, "add Redis" is the single most defensible way to justify sub-second reads, offload the database, and unlock features (leaderboards, sessions, pub/sub, rate limits) that would take weeks to build on top of a relational DB.

🧑‍🎓 In laymen terms

Explain it like I have never coded

Imagine a busy coffee shop. Every time someone orders "the usual", the barista could go to the storeroom, unlock it, find the recipe folder, flip to the customer's page, and read it. That would work — but with a queue of 200 people, it's painfully slow.

So the barista keeps a whiteboard right beside the counter. On it are the last 500 customers' usual orders, written in big letters, ready to read at a glance. When Alice walks in, the barista just looks at the board and shouts "cappuccino, oat milk" — no trip to the storeroom, no unlocking, no flipping through folders. Redis is that whiteboard. The storeroom is your database (Postgres, MySQL, DynamoDB), and Redis is the fast-glance surface sitting next to the counter.

Because it's a whiteboard and not a filing cabinet, three things follow: (1) it's much faster — a glance versus a walk; (2) it can lose data if the shop catches fire — a whiteboard isn't fireproof, so most people also keep the folders in the storeroom; and (3) it's small — you can't fit a million customers' orders on it. So Redis is used for the hot data — the stuff you look up again and again in the next few minutes.

Redis also does more than just remember answers. It can count things instantly ("how many people liked this photo?"), keep a ranked scoreboard ("who's #1 on the leaderboard right now?"), broadcast messages to many listeners at once ("new order came in — anyone free?"), and act as a traffic cop that says "sorry, you've asked 100 times this minute, come back later" (rate limiting). Every one of these is a tiny problem a database can technically do, but a whiteboard does it a thousand times faster.

Almost every app you use has one of these whiteboards behind the scenes: Instagram remembers your feed there, Uber remembers where the nearby drivers are, Twitter remembers your timeline, WhatsApp remembers who's currently online. When you tap something and the answer comes back instantly, there's a good chance a Redis whiteboard just answered you.

📋 Requirements & scale

What Redis is optimized for (and what it isn't)

Redis is not a general-purpose database — it's a data-structure server that keeps everything in RAM and speaks a very simple TCP protocol (RESP). That single decision is where most of its performance comes from, and it also defines the boundaries of what you should ever use it for.

Functional

  • Sub-millisecond GET / SET on primitive types and rich data structures (strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog, geo).
  • Atomic multi-command scripting via Lua or Functions.
  • Pub/sub messaging and Streams (Kafka-lite).
  • Server-side TTL / expiration on every key.
  • Optional persistence (RDB, AOF, or both) and replication for durability.

Non-functional (typical single-node targets)

DimensionTypical target
Latency (p99)< 1 ms local, < 5 ms same-AZ
Throughput100k – 1M ops/sec per node (pipelined)
Memory per node16 GB – 256 GB (bounded by RAM)
Max key/value size512 MB per value (practical limit ~ MB)
Cluster max size1 000 nodes (recommended); 16 384 hash slots
Durability0 s – 1 s data loss (AOF everysec) up to fully durable (fsync always)

Back-of-the-envelope for interview: "a single Redis node comfortably handles 100k ops/sec at < 1 ms p99. With Redis Cluster (16 384 hash slots) we shard horizontally across N masters — a 6-node cluster gives us ~600k ops/sec and roughly 6× the memory."

🏗️ High-level architecture

How Redis is put together

Redis is famously simple: one process, one main thread, one event loop. Every command lands on that thread, runs to completion, and the reply is queued back out. There's no lock contention because there are no other threads competing for the data structures. The main thread is helped by a small pool of I/O threads (Redis 6+) that read/write sockets, and by background threads that do fsync, close-on-write, and lazy freeing of large objects — but the command execution itself is single-threaded. That's why every command in Redis is atomic by construction.

request path single-threaded core persistence replication HA / sharding

Around the core sit three orthogonal concerns: persistence (should this data survive a restart?), replication (do we need a hot standby?), and topology (single node, Sentinel-managed HA pair, or a sharded Cluster?). You pick each independently based on the workload.

🔍 Component deep-dive

1. Core data structures — the real reason Redis is different

Redis isn't a KV store where the value is opaque bytes. Every key points to a typed data structure whose native operations run server-side. That single fact removes one round-trip per operation and is why Redis crushes Memcached on non-trivial workloads.

2. The single-threaded event loop

The main thread runs an epoll-based reactor. Sockets are non-blocking; when one is ready, its command is parsed, executed against the key-space, and the reply is written back. Because everything happens on one thread, transactions (MULTI/EXEC) and Lua scripts are trivially atomic — there is no other thread to interleave with. The tradeoff: a single slow command blocks every other client. KEYS *, giant LRANGE, or DEBUG SLEEP can freeze the entire node. In production you use SCAN instead of KEYS, cap value sizes, and offload lazy-free work to background threads.

3. Persistence — RDB vs AOF

RDB (snapshots)
  • Point-in-time binary dump of the whole key-space (dump.rdb).
  • Triggered by save 60 1000-style rules or BGSAVE.
  • Redis fork()s a child; the child writes while the parent keeps serving — uses copy-on-write.
  • Pros: compact, fast restart, great for backups/DR.
  • Cons: can lose the last few minutes of data; fork() can stall multi-GB instances for hundreds of ms.
AOF (append-only file)
  • Every write command appended to a log in RESP format.
  • fsync policies: always (safest, slowest), everysec (default — at most 1 s loss), no (OS decides).
  • Auto-rewrites (multi-part in Redis 7+) compact the log into a fresh base + increments.
  • Pros: up to 1-second durability, replayable, easy to inspect and repair with redis-check-aof.
  • Cons: larger files, slower restarts, extra CPU for rewriting.

Best of both: enable both. On restart Redis prefers the AOF (more complete); RDB snapshots go to S3 for disaster recovery. For a pure cache where you don't care about loss, disable both.

4. Replication

Redis replication is asynchronous by default. A replica connects and issues PSYNC with its offset and replication ID; if the master still has the missed bytes in its replication backlog, it streams just those (partial resync). Otherwise it triggers a full sync — RDB snapshot streamed to the replica, followed by the backlog. Replicas can chain (replica-of-a-replica). Because replication is async, the client sees a write ack before the replica has seen it — a master crash can lose the last few ms of writes. WAIT numreplicas timeout exists to make a write wait for replicas, but it's still best-effort, not synchronous consensus.

6. Memory management & eviction

Redis enforces maxmemory. When it's hit, it applies the maxmemory-policy:

  • noeviction — writes fail; reads still work. Safe for a primary datastore.
  • allkeys-lru / allkeys-lfu — evict the least-recently- or least-frequently-used key across all keys. Standard cache policy.
  • volatile-lru / volatile-lfu / volatile-ttl — same, but only among keys with a TTL.
  • allkeys-random / volatile-random — cheap and dumb.

Redis uses an approximated LRU/LFU — it samples a few candidates and evicts the worst — because a strict LRU list would cost too much memory. In production, always set maxmemory + a policy. An unbounded Redis is a Redis that OOM-kills itself.

Why Redis is fast — the data structures at play

The performance and the feature list both come from the fact that Redis picks a textbook data structure for each type and exposes its native operations verbatim.

The clever bits: incremental rehashing (never stall on a resize), listpacks (tightly packed byte blobs for small objects — 30% memory savings), skip lists (simpler than balanced trees, same asymptotics, easier concurrency), and 16 384 hash slots (small enough to bitmap efficiently, big enough to shard fine-grained).

💻 C# implementation

The de-facto Redis client in .NET is StackExchange.Redis — it multiplexes many logical operations over a single TCP connection per endpoint, so you keep exactly one ConnectionMultiplexer for the app's lifetime and share it. The snippet below shows the three most common Redis patterns you'll be asked to write on a whiteboard: cache-aside, atomic counter (INCR), and token-bucket rate limiter using a Lua script for atomicity.

using StackExchange.Redis;
using System.Text.Json;

public sealed class RedisPatterns
{
    // One multiplexer per app. Thread-safe. Reuse everywhere.
    private static readonly ConnectionMultiplexer Mux =
        ConnectionMultiplexer.Connect("redis-cluster:6379,abortConnect=false,ssl=true");

    private static IDatabase Db => Mux.GetDatabase();

    // ─── 1. Cache-aside GET ─────────────────────────────────────────
    public async Task<User?> GetUserAsync(long id, Func<long, Task<User?>> loadFromDb)
    {
        var key = $"user:{id}";
        var cached = await Db.StringGetAsync(key);
        if (cached.HasValue) return JsonSerializer.Deserialize<User>(cached!);

        var fresh = await loadFromDb(id);
        if (fresh is not null)
            await Db.StringSetAsync(key, JsonSerializer.Serialize(fresh), TimeSpan.FromMinutes(10));
        return fresh;
    }

    // ─── 2. Atomic like-counter ─────────────────────────────────────
    public Task<long> IncrementLikesAsync(long postId) =>
        Db.StringIncrementAsync($"post:{postId}:likes");   // INCR — atomic, O(1)

    // ─── 3. Token-bucket rate limiter (atomic via Lua) ──────────────
    private const string RateScript = @"
        local now      = tonumber(ARGV[1])
        local rate     = tonumber(ARGV[2])   -- tokens per second
        local capacity = tonumber(ARGV[3])
        local last     = tonumber(redis.call('HGET', KEYS[1], 'ts') or now)
        local tokens   = tonumber(redis.call('HGET', KEYS[1], 'tk') or capacity)
        local delta    = math.max(0, now - last) * rate
        tokens         = math.min(capacity, tokens + delta)
        if tokens < 1 then
            redis.call('HMSET', KEYS[1], 'ts', now, 'tk', tokens)
            return 0
        end
        tokens = tokens - 1
        redis.call('HMSET', KEYS[1], 'ts', now, 'tk', tokens)
        redis.call('EXPIRE', KEYS[1], 3600)
        return 1
    ";

    public async Task<bool> AllowAsync(string userId, double ratePerSec = 5, int capacity = 10)
    {
        var now = DateTimeOffset.UtcNow.ToUnixTimeSeconds();
        var allowed = (int)(long)await Db.ScriptEvaluateAsync(
            RateScript,
            new RedisKey[] { $"rl:{{userId}}" },  // hashtag pins to a single slot
            new RedisValue[] { now, ratePerSec, capacity });
        return allowed == 1;
    }
}

public record User(long Id, string Name, string Email);

Three notes an interviewer will probe: (a) reuse one ConnectionMultiplexer — creating one per request is the #1 misuse; (b) Lua scripts execute atomically because the event loop is single-threaded — that's the whole point of using EVAL for the rate-limiter; (c) the {userId} hash tag forces all keys sharing that tag onto the same slot so multi-key ops work in Cluster mode.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Use Redis when…
  • You need sub-millisecond reads and can afford RAM.
  • You want counters, leaderboards, geo, sets, TTLs — server-side.
  • You need a pub/sub or stream bus without spinning up Kafka.
  • You need a distributed lock or rate limiter that's actually atomic.
Avoid Redis when…
  • Working set doesn't fit in RAM — RAM is 10–100× the cost of disk.
  • You need multi-key transactions across shards — Cluster doesn't support them.
  • You need strong durability + strong consistency — plain Redis loses writes on failover (use MemoryDB if you must keep the API).
  • You need rich queries (joins, aggregations) — use a real DB or a search engine.

Common bottlenecks

  • Big keys. A 500 MB hash blocks the event loop when it's touched. Split large objects; use UNLINK instead of DEL.
  • Hot keys. One key (e.g. a global counter) can saturate a single shard. Use per-partition sub-keys and aggregate.
  • Fork stalls. RDB snapshots and AOF rewrites fork() — on large instances this can stall for hundreds of ms. Use replicas for snapshotting or disable persistence on the primary.
  • Async replication loss. A master crashing after ack loses the un-replicated tail. Use WAIT for critical writes or move to MemoryDB.
  • Eviction storms. Reaching maxmemory without a policy stalls writes. Always set allkeys-lfu for caches.

Likely follow-up questions (and short answers)

Why is Redis single-threaded, yet fast?

In-memory data + non-blocking I/O + no lock overhead makes the CPU the bottleneck, and a single core happily pushes 100k+ ops/sec. You scale out with sharding (Cluster) or up with more nodes, not more threads on one node.

Redis vs Memcached?

Memcached is a pure LRU cache of opaque strings, multi-threaded. Redis has rich data types, persistence, replication, pub/sub, streams, Lua, and clustering. Today, prefer Redis unless you have a pure hot-string cache and want the simpler ops.

Can Redis be a primary datastore?

Yes, but understand the durability model. With AOF everysec you can lose 1 s of writes; on failover, unreplicated writes are gone. If the app can't tolerate that, use Amazon MemoryDB (multi-AZ synchronous journal) or accept Redis is a cache tier only.

How does Redis Cluster shard?

Every key is hashed with CRC16 modulo 16 384 — the resulting slot lives on exactly one master. Clients cache the slot→node map; a MOVED reply means "resharded, refresh the map". Multi-key commands need all keys to share a {tag} so they hash to the same slot.

How do you build a distributed lock?

Simple: SET lock:X uniqueId NX PX 30000 — atomic acquire with TTL. Release with a Lua script that only deletes if the value still matches your uniqueId. For higher safety across nodes, the Redlock algorithm acquires the lock on a majority of independent masters, but its safety is famously debated (Kleppmann vs antirez) — for a single Redis, the simple pattern is enough.

Redis Pub/Sub vs Streams?

Pub/Sub is fire-and-forget — subscribers connected at publish time get the message, no history. Streams are an append-only log with consumer groups, offsets, and replay — think Kafka-lite. Use Pub/Sub for notifications; use Streams for anything a subscriber might miss.

🗣️ Interview cheat sheet

"Redis is a single-threaded, in-memory data-structure server. One event loop, no locks — that's why every command is atomic and every op is sub-millisecond. It ships strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog and geo natively, so features like leaderboards, rate limiters, and pub/sub are one command away. Persistence is optional (RDB snapshots + AOF log), replication is async, and we shard with Redis Cluster's 16 384 hash slots. In production it's the cache tier, the session store, the rate limiter, the distributed lock, and often the pub/sub bus — but never the durable source of truth unless we swap it for MemoryDB."

  • Numbers: 1 ms p99, 100k ops/sec/node, 16 384 slots, 512 MB max value.
  • Persistence: RDB (compact, some loss) + AOF (durable, larger) — enable both.
  • Topologies: Standalone → Sentinel → Cluster — pick by need for HA and sharding.
  • Eviction: always set maxmemory + allkeys-lfu for caches.
  • Cluster ops: multi-key needs {hashtag}; no cross-slot txns; MOVED/ASK redirects.
  • Not a database of record unless you use MemoryDB.
