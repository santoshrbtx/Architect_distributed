How Amazon S3 Works Internally

Designing planet-scale object storage: 500 trillion objects, 11 nines of durability, and 200M requests/sec — on millions of ordinary hard drives.

🎯 Real-world scenario

What we're building & where it's used

We are designing an object storage service: a system where clients PUT and GET arbitrary blobs of bytes (0 bytes to 5 TB) addressed by a simple key, over a plain HTTP REST API, with effectively unlimited capacity, extreme durability, and a flat 99.9%+ availability SLA. This is exactly what Amazon S3 (Simple Storage Service, launched March 2006) provides, and it is the template every "design a blob store / Dropbox / photo backend" interview is really asking about.

Object storage is the quiet foundation of the modern internet. S3 and its peers — Google Cloud Storage, Azure Blob Storage, Backblaze B2, MinIO, Ceph — sit underneath data lakes (Athena/Spark/Snowflake scanning petabytes), media libraries (Netflix streams its catalog from S3), backups and disaster recovery, static website assets served through a CDN, machine-learning training corpora, and the storage tier of countless SaaS products. The reason companies reach for object storage instead of a filesystem or a database is that it decouples durability and scale from any single machine: you hand bytes to an API and the service guarantees they will survive disk failures, rack failures, and even the loss of an entire data hall, while scaling from one object to hundreds of trillions without you provisioning anything.

In an interview, the thing that makes S3 fascinating is the gap between the trivial-looking API (four verbs: PUT, GET, DELETE, LIST) and the staggering machinery behind it. Your job is to explain how you turn millions of failure-prone 120-IOPS hard drives into a service that never loses data and never has a hotspot.

🧑‍🎓 In laymen terms

The endless warehouse of numbered lockers

Picture the biggest warehouse you've ever seen, then imagine it a million times bigger — so big that trucks drive inside it. Now fill it with simple metal lockers, each one with a shiny label on the front. When you want to keep something safe — a wedding photo, a movie, a copy of your tax return — you drive up to the loading dock, hand over your box, and give it a name like "sarah/holiday-2024/beach.jpg". A worker takes your box, walks off into the warehouse, and slides it into a locker. Any time later, you come back and say that same name, and out comes your box.

The magic is what you don't see. There are no folders, no filing cabinets — just flat labels and lockers. And every box you hand in is quietly copied three times — one copy in this building, one in a building across town, one on the other side of the city. If the whole building floods tonight, your wedding photo is still fine. This is what people mean when they say Amazon S3 has "eleven nines of safety" — they've done the maths so that losing your box would take longer than the universe has been around.

You already use this all day without knowing. When you watch Netflix, the movie itself is sitting in one of these warehouses. When Instagram loads your holiday photos, they came from here. When your friend WhatsApps you a voice note, it lands in a locker for a bit before it reaches you. The reason companies love it: they don't have to think about disk drives, backups, or "what if the building burns down?" They just say "please keep this" and trust the warehouse.

The clever puzzle is how to run a warehouse this enormous without a single traffic jam. That's really what the whole design is about — spreading trucks, boxes, and workers so evenly that nobody ever has to wait in line.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • PUT an object (key → bytes) into a bucket; GET it back by key; DELETE; LIST keys by prefix.
  • Objects up to 5 TB; single upload capped at 5 GB (larger uses multipart upload).
  • Bucket namespace, per-object metadata, versioning, and range reads (fetch byte x…y of a large object).

Non-functional requirements (the hard part)

  • Durability: 99.999999999% (11 nines). For 10 million objects, that's a statistical expectation of losing one object every ~10,000 years.
  • Availability: 99.9%–99.99% for the request path; scale to any request rate with no pre-provisioning.
  • Strong read-after-write consistency (S3 has offered this since December 2020) — a GET after a successful PUT always returns the latest bytes.
  • Elastic scale and cost efficiency at exabyte volume.

The killer insight to volunteer: a single hard drive does only ~120 random IOPS, and that hasn't improved in ~20 years even as capacity exploded. So on a 200 TB drive you get roughly 1 IOP per 2 TB of data. You cannot make one drive fast — you win only by spreading every workload across thousands of drives so their IOPS sum up. That single sentence frames the entire architecture.

🏗️ High-level architecture

How the pieces fit together

S3 is not one program — it's hundreds of microservices grouped into a few large fleets, each with an API-level contract. The request path splits cleanly into a metadata plane (where is this object?) and a data plane (the actual bytes on disks). A PUT flows: client → Frontend fleet (auth, request routing) → Index / Namespace service (allocates the object's location, records metadata) → Storage fleet (erasure-codes the bytes into shards and writes them across many drives). A GET reverses it: look up the location in the index, fetch enough shards from the storage fleet to reconstruct, stream back. A separate background operations fleet handles replication, tiering, repair, and continuous durability audits — off the critical path.

synchronous request path async / background (repair, audit, tiering)
  1. Client → Frontend: a request hits the frontend fleet behind DNS load balancing; it authenticates (SigV4), authorizes (IAM/bucket policy), and routes.
  2. Frontend → Index: the namespace service resolves the bucket+key to physical shard locations (for GET) or allocates new ones (for PUT), and durably records metadata.
  3. Frontend → Storage: for a PUT, bytes are erasure-coded and the shards are written across many independent drives in multiple availability zones; the write acks only when enough shards are durable.
  4. GET reconstruction: fetch any k of the (k+m) shards, verify checksums, reassemble, and stream to the client.
  5. Background: continuously scrubs data, re-generates lost shards after drive failures, moves cold objects to cheaper tiers, and runs the durability model.

🔍 Component deep-dive

1. The index (namespace) — a giant distributed key-value store

The index maps (bucket, key) → {shard locations, size, etag, version, metadata}. With 500 trillion objects this map is itself one of the largest databases on earth, so it is horizontally partitioned. The partitioning key is derived from the object key's prefix — which is exactly why S3's documented throughput is expressed per prefix (3,500 writes / 5,500 reads per second). When a prefix gets hot, S3 automatically splits its partition so different key ranges land on different index servers. This is the single most practical S3 fact for engineers: you scale by spreading keys across many prefixes (e.g. lead with a hash or a high-cardinality field), not by hammering one sequential prefix.

2. Strong consistency

Since December 2020, S3 provides strong read-after-write consistency for all operations, at no cost and no performance penalty. The trick is that the index is the single source of truth for "which shards are the current version of this object." A PUT is not acknowledged until the new metadata is durably committed in the index; any subsequent GET reads that committed pointer, so it can never see stale bytes. Consistency is therefore a property of the metadata commit, not of the (immutable) data shards.

3. The storage fleet & ShardStore

The storage fleet is "full of hard disks." The lowest layer — the on-disk key-value store that manages shards on each node — was rewritten as ShardStore, built in Rust for memory safety and validated with lightweight formal verification: engineers wrote an executable specification (~1% the size of the real code) and used property-based/reference testing to prove the implementation matches it. This matters because at S3's scale, a rare correctness bug in the storage layer would corrupt data somewhere every single day.

4. Durability: erasure coding, not just copies

Naïve durability = keep N full copies (replication). That's simple and read-efficient but triples your cost at 3×. S3 instead leans on erasure coding (Reed–Solomon): split an object into k data shards, compute m parity shards, and store all k+m on different drives across multiple availability zones. Any k shards can reconstruct the object, so you survive m simultaneous failures with far less overhead than replication (e.g. a 5+4 scheme survives 4 losses at ~1.8× cost vs 3× for triple replication). Every shard is checksummed to catch the silent bit-rot that's statistically guaranteed at exabyte scale.

5. Heat management — the anti-hotspot superpower

"Heat" is the request rate landing on a given disk. Because a drive does only ~120 IOPS, a concentrated workload would create a hotspot — a straggler drive that drags down tail latency. S3's answer is spreading: a single customer's objects are scattered across a huge number of drives, and conversely each drive holds shards from countless unrelated workloads. Aggregating millions of bursty, mostly-idle workloads means their peaks don't line up, so aggregate demand is smooth and no single workload can create a hotspot on any one disk. A customer can momentarily burst onto over a million drives — capacity no one could build alone. This is the decorrelation-through-scale argument, closely related to shuffle sharding.

6. Multipart upload & range reads

Objects over 5 GB (and in practice anything large) use multipart upload: the client splits the object into parts, uploads them in parallel (each part independently retried), and sends a final "complete" call that stitches the part list together in the index. Reads can request a byte range, so a client fetches only the slice it needs and can parallelize a large download across many connections — turning one big serial transfer into many concurrent ones across many drives.

Data structures & algorithms

Object storage looks like plumbing, but it's built on a tight set of algorithms — each chosen to beat a specific physical constraint (drive IOPS, disk failure, silent corruption, hot keys).

Why erasure coding over replication: at exabyte scale the cost delta is billions of dollars. Reed–Solomon buys the same (or better) fault tolerance as 3× replication at roughly half the storage, and the CPU cost of encode/decode is negligible next to the disk savings. The trade-off is that reconstructing a lost shard requires reading k other shards (more I/O on repair) — acceptable because repair is a background, not a request-path, cost.

💻 C# implementation

Two things worth showing in code: (1) how an app actually talks to S3 — multipart upload with a pre-signed URL, the pattern interviewers love — and (2) the durability core, a minimal Reed–Solomon-style erasure split so you can explain shards concretely.

Talking to S3: presigned URL + multipart upload (AWS SDK for .NET)

// AWSSDK.S3. The app never proxies bytes — it hands the client a presigned URL,
// so uploads/downloads go straight to S3 and scale independently of your servers.
using Amazon.S3;
using Amazon.S3.Model;
using Amazon.S3.Transfer;

public class S3Store
{
    private readonly IAmazonS3 _s3;
    public S3Store(IAmazonS3 s3) => _s3 = s3;

    // (1) Hand the browser a short-lived URL to PUT directly to S3.
    public string GetUploadUrl(string bucket, string key) =>
        _s3.GetPreSignedURL(new GetPreSignedUrlRequest
        {
            BucketName = bucket,
            Key        = key,
            Verb       = HttpVerb.PUT,
            Expires    = DateTime.UtcNow.AddMinutes(15)
        });

    // (2) Large object? TransferUtility auto-splits into parts and uploads them
    //     in parallel — this is S3 multipart upload under the hood (>5GB requires it).
    public async Task UploadLargeAsync(string bucket, string key, string path)
    {
        var tu = new TransferUtility(_s3);
        await tu.UploadAsync(new TransferUtilityUploadRequest
        {
            BucketName  = bucket,
            Key         = key,
            FilePath    = path,
            PartSize    = 16 * 1024 * 1024,   // 16 MB parts, uploaded concurrently
            ChecksumAlgorithm = ChecksumAlgorithm.CRC32C // end-to-end integrity check
        });
    }

    // (3) Range read — fetch only bytes [start..end] of a big object.
    public async Task<Stream> GetRangeAsync(string bucket, string key, long start, long end)
    {
        var resp = await _s3.GetObjectAsync(new GetObjectRequest
        {
            BucketName = bucket, Key = key,
            ByteRange  = new ByteRange(start, end)
        });
        return resp.ResponseStream;
    }
}

The durability core: erasure-coding a blob into k+m shards

// Illustrative Reed–Solomon-style split: k data shards + m parity shards.
// Any k of the (k+m) shards can rebuild the object. Real impl uses GF(2^8)
// matrix math (e.g. the 'ReedSolomon' NuGet); this shows the shape.
public sealed class ErasureCoder
{
    private readonly int _k, _m;              // data shards, parity shards
    public ErasureCoder(int k, int m) { _k = k; _m = m; }

    public byte[][] Encode(byte[] obj)
    {
        int shardLen = (obj.Length + _k - 1) / _k;   // ceil split into k pieces
        var shards = new byte[_k + _m][];
        for (int i = 0; i < _k; i++)          // slice the k data shards
        {
            shards[i] = new byte[shardLen];
            Array.Copy(obj, i * shardLen, shards[i], 0,
                       Math.Min(shardLen, obj.Length - i * shardLen));
        }
        // Compute m parity shards over the data matrix (Reed–Solomon).
        for (int p = 0; p < _m; p++)
            shards[_k + p] = ComputeParity(shards, p);

        // Scatter these k+m shards onto k+m DIFFERENT drives / AZs.
        return shards;
    }

    public byte[] Decode(byte[][] surviving)   // need ANY k of them
    {
        if (surviving.Count(s => s != null) < _k)
            throw new DataLossException("fewer than k shards — unrecoverable");
        return ReconstructFromAnyK(surviving, _k);  // invert the RS matrix
    }
}

Beyond C#, S3's real storage layer (ShardStore) is written in Rust for memory safety, and clients exist in every language; the code above is about explaining the shape of the system, not reimplementing it.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Latency vs. durability & cost. S3 is disk-backed, so first-byte latency is ~100–200ms — great cost per byte, poor for hot small-object reads. The design choice is deliberate: you get 11 nines and pennies-per-GB, and you're expected to layer CloudFront/ElastiCache when you need milliseconds. Never pitch S3 as a low-latency cache.

The metadata plane is the real bottleneck. Bytes scale trivially by adding drives; the index is what's hard. A hot prefix concentrates load on one index partition. The mitigation — and the #1 practical S3 tip — is key-space design: spread writes across many high-cardinality prefixes so partitions split and throughput scales. Sequential keys (timestamps, monotonic IDs) are an anti-pattern.

Erasure coding vs replication. Erasure coding wins on cost and matches replication's fault tolerance, but repair reads k shards to rebuild one — heavier repair I/O and higher small-object overhead. That's why hot, tiny objects and single-AZ tiers sometimes use different schemes (e.g. S3 Express One Zone trades multi-AZ durability for latency and cost).

Failure modes. Drive failure → background fleet rebuilds shards from parity. AZ failure → surviving AZs still have ≥ k shards. Silent corruption → checksums + continuous scrub catch it. Correctness bugs in storage code → mitigated by ShardStore's formal verification. Region-wide durability still depends on Cross-Region Replication if you need it.

Q: How does S3 achieve 11 nines of durability?

Erasure coding (Reed–Solomon k+m shards) spread across multiple AZs, end-to-end checksums, continuous background scrubbing that repairs lost shards from parity, and a statistical durability model reviewed like a security threat model. It's redundancy + active repair + verification, not just "many copies."

Q: How did S3 add strong consistency without a performance hit?

The index is the single source of truth for the current version's shard pointers. A PUT isn't acked until that metadata is durably committed, so any later GET reads the committed pointer — no stale reads, no extra round-trips.

Q: Why does S3 talk about "per-prefix" throughput?

The index is partitioned by key prefix; each partition serves ~3,500 writes / 5,500 reads per second and auto-splits when hot. More distinct prefixes → more partitions → more aggregate throughput. Hence: never use sequential keys for high-write workloads.

Q: Why hard drives and not SSDs everywhere?

Cost per byte. At hundreds of exabytes, HDDs are dramatically cheaper. S3 overcomes their ~120 IOPS limit not by making one drive fast, but by spreading each workload across thousands of drives so their IOPS aggregate. SSD-backed tiers (Express One Zone) exist where latency justifies the price.

Q: How does S3 avoid hotspots?

Decorrelation through scale: each customer's data is scattered over huge numbers of drives, and each drive holds many unrelated workloads. Millions of bursty, idle-most-of-the-time workloads have peaks that don't align, so aggregate demand is smooth — related to shuffle sharding.

🗣️ Interview cheat sheet

30-second pitch: "S3 is object storage exposing a dead-simple HTTP API — PUT/GET/DELETE/LIST by key. Internally it splits into a metadata plane (a massively partitioned key-value index mapping keys to shard locations) and a data plane (millions of hard drives). Durability comes from erasure coding — Reed–Solomon k+m shards spread across AZs, so any k rebuild the object — plus checksums and continuous background repair, hitting 11 nines. It scales by spreading: every workload lands on thousands of drives, so no single disk gets hot. Throughput is per-prefix, so you design keys for high cardinality."

  • 3,500 writes / 5,500 reads per prefix/sec · object 0B–5TB · single PUT ≤ 5GB, else multipart.

5 talking points that win the round

  • Separate the metadata plane from the data plane — the index is the hard part, not the bytes.
  • Erasure coding beats replication on cost at scale for the same fault tolerance (~1.5–1.8× vs 3×).
  • Scale = spreading: aggregate thousands of slow drives; decorrelation kills hotspots (shuffle sharding).
  • Consistency lives in the metadata commit, not the immutable data shards.
  • Key/prefix design is the real lever engineers control for S3 throughput.
