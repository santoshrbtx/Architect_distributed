🎯 Real-world scenario

What we're building & where it's used

A rate limiter controls how many requests a client may make to a service in a given window of time, rejecting or delaying the excess. It's the bouncer at the door of an API: it protects the service from being overwhelmed — whether by a malicious flood (DoS/brute-force), a buggy client stuck in a retry loop, a scraper, or just an unexpected traffic spike — and it enforces fair usage so one noisy tenant can't starve everyone else.

It's one of the most common system-design interview questions precisely because it's everywhere and it forces you to reason about algorithms, state, concurrency, and distributed coordination in a small space. Real examples: Stripe rate-limits its payments API and says its request limiter alone "has rejected millions of requests this month" — largely runaway test-mode scripts. Twitter/X caps tweets (e.g. 300 per 3 hours); the Google Docs API allows ~300 read requests per user per 60 seconds; GitHub, Cloudflare, and every major cloud API do the same. The universal signal for "you've been limited" is HTTP 429 Too Many Requests (and 503 when the server itself is shedding load).

Why companies invest in it: without a limiter, a single client can degrade or take down a shared service, drive up infrastructure cost, and ruin the experience for everyone. A good limiter is also a graceful-degradation tool — under overload you shed the least-important traffic first and keep the critical paths (like "create a charge") alive.

🧑‍🎓 In laymen terms

The bouncer with a bucket of tokens

Imagine a very popular club with a strict bouncer. The rule of the night is simple: "You get 100 free drink tokens. Come back when you run out." Every time you order a drink, the bouncer takes one token out of your hand. When your fist is empty, he smiles politely and says "come back in 30 seconds." Slowly — say, one token per second — the bouncer quietly slips new tokens back into your hand, so you're never permanently cut off. That's it. That's a rate limiter.

Now, why does every big website need this bouncer? Picture what happens on IRCTC at 10 AM when Tatkal train tickets open. Twenty million people mash the "Book Now" button at the same instant. If the website tried to serve everyone at once, it would keel over and nobody gets a ticket. Worse: one person could write a small robot to click the button a thousand times a second and hog every seat. The bouncer's job is to say, "Sorry — you personally get 5 clicks per second, no matter how fancy your script is."

The bucket analogy also handles bursts nicely. Say you're a well-behaved app and you haven't made any requests for 30 seconds. Your bucket has quietly filled back up to 100 tokens. Now you suddenly need to send 20 requests at once — maybe a page just loaded. No problem! You have plenty of tokens saved up. This is why real websites use the "bucket of tokens" idea instead of a rigid "no more than 5 per second, ever" rule — it lets honest users burst when they need to, but stops abusers cold.

There's a tricky part though. A website like Stripe or GitHub doesn't run on one computer — it runs on thousands. If each computer keeps its own bucket, a clever attacker could hit computer A with 100 requests, then computer B with 100 more, then C, and effectively cheat. So all the bouncers have to share one central scoreboard (usually a super-fast in-memory store called Redis) so everyone agrees on how many tokens you have left. That shared scoreboard has to answer in less than a millisecond or the bouncer becomes the bottleneck. That's the whole engineering challenge in one sentence: a bouncer fast enough to never slow down the party.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Limit requests per client identity (API key, user id, or IP) to N per time window.
  • Return HTTP 429 when the limit is exceeded, ideally with a Retry-After and rate-limit headers (X-RateLimit-Remaining, -Reset).
  • Support different rules per endpoint / tier (a free user vs. an enterprise user; a cheap GET vs. an expensive POST).
  • Allow controlled bursts above the steady rate (flash-sale traffic) without permanently raising the limit.

Non-functional requirements (the ones that shape the design)

  • Low latency — the check sits in front of every request, so it must add well under ~1 ms.
  • Distributed correctness — the limit must hold across a fleet of servers, not per-instance.
  • High availability & fail-open — if the limiter's datastore is down, legitimate traffic should still flow (Stripe explicitly catches exceptions so a Redis outage doesn't block traffic).
  • Memory efficiency — millions of distinct clients ⇒ per-client state must be tiny.
  • Accuracy — avoid the boundary-burst problem where 2× the limit slips through at a window edge.

🏗️ High-level architecture

How the pieces fit together

The rate limiter is a middleware check that runs before your business logic — usually in the API gateway or a thin filter in front of the app servers. The critical design decision is where the counter lives. Per-instance in-memory counters are fast but wrong in a fleet (10 servers × limit N = 10N allowed). So the counter state moves to a shared, fast datastore — almost always Redis — and the check must be a single atomic operation (a Lua script or INCR+EXPIRE) so concurrent requests across many servers can't race past the limit.

The flow: a request arrives, the gateway extracts the client identity, and asks the limiter "is this client under its limit?" The limiter atomically updates the client's bucket/counter in Redis and returns allow/deny. On allow, the request proceeds; on deny, the gateway short-circuits with 429 and a Retry-After. If Redis is unreachable, the design fails open — allow the request rather than take down the whole API.

Allowed request flow Atomic limiter check Rejected → 429

The request path

  1. Request hits the gateway; middleware derives the client key (API key / user id / IP) and the applicable rule.
  2. Middleware runs one atomic op in Redis (Lua script): refill the bucket by elapsed time, try to take a token.
  3. Token available → decrement, return allow; request proceeds to app servers.
  4. Bucket empty → return deny; gateway responds 429 with Retry-After and rate-limit headers.
  5. If Redis errors/timeouts → fail open (allow) so the limiter never becomes the outage.

🔍 Component deep-dive: the five algorithms

The heart of this interview is knowing the algorithms cold — how each works, its memory cost, and its burst behavior. Here they are, weakest to strongest.

1. Fixed Window Counter

Split time into fixed windows (say, 1-second buckets). Keep one counter per client per window; increment on each request; reject once it exceeds the limit, then reset at the next window. Pros: trivially simple, one integer of memory, easy in Redis (INCR + EXPIRE). Con — the boundary burst: a client can send the full limit at the very end of one window and again at the start of the next, pushing 2× the limit through in a fraction of a second. Good enough for coarse quotas, dangerous for tight protection.

2. Sliding Window Log

Store a timestamp for every request in a sorted set; to decide, drop timestamps older than the window and count what remains. Pros: perfectly accurate, no boundary burst. Con: memory grows with request volume — you store every single request timestamp — so it's expensive for high-traffic clients. Great accuracy, poor scalability.

3. Sliding Window Counter (the sweet spot)

A hybrid: keep the current and previous fixed-window counts and weight the previous window by how much of it still overlaps the sliding window. Estimated count = curr + prev × (overlap fraction). Pros: smooths the boundary burst almost as well as the log, but with fixed, tiny memory (two counters). This is the algorithm most production systems reach for when they want accuracy without the log's cost.

4. Token Bucket (the industry favorite)

A bucket holds up to b tokens and refills at rate r (one token every 1/r seconds; overflow is discarded). Each request removes one token; if the bucket is empty, the request is non-conformant (rejected or queued). The genius is controlled bursts: a client that's been quiet accumulates up to b tokens and can spend them in a burst (a flash sale), but the long-run average is still capped at r. Memory is just {tokens, last_refill}. This is what Stripe uses — they note clients "can always spread out their requests a bit more," and they layer a burst allowance on top for real-time spikes. It's the default answer to "which algorithm?".

5. Leaky Bucket

Requests enter a queue and are processed ("leak out") at a constant rate. Overflowing the queue drops requests. Pros: perfectly smooth, jitter-free output — ideal for traffic shaping a downstream that needs steady load. Con: it doesn't allow bursts and adds queueing latency; it's a shaper, not really a burst-friendly limiter. Token bucket is its "mirror image" and is usually preferred for APIs.

Making it distributed & atomic

The single hardest part in a fleet is the race condition: two servers read "1 token left" simultaneously and both allow. The fix is to make the read-modify-write atomic. In Redis this means a Lua script (executed atomically on the server) that does refill-and-take in one shot, or INCR+EXPIRE for fixed windows. You also decide between centralized (one Redis, exact but a round-trip per request) and local-token / sticky approaches (each node gets a slice of the budget for lower latency, at the cost of some accuracy). Stripe runs it on Redis (self-hosted or ElastiCache) and explicitly designs to fail open, ships kill switches, and dark-launches new limiters to see what would be blocked before enforcing.

Stripe's four-layer production model (worth quoting)

  • Request rate limiter — caps requests/sec per user; the primary defense. Rejects millions/month, mostly runaway scripts.
  • Concurrent requests limiter — caps in-flight requests (e.g. 20 at once) to protect CPU-heavy endpoints from retry storms.
  • Fleet usage load shedder — reserves a % of the fleet for critical methods; sheds non-critical traffic with 503 when it exceeds its allocation.
  • Worker utilization load shedder — last line of defense in incidents: sheds by priority tier (test mode → GETs → POSTs → critical).
🧮 The DSA behind it

Data structures & algorithms

Under the hood these are small, elegant data-structure choices, and the interviewer wants to hear the memory/accuracy trade-off for each. The token bucket is just arithmetic on two numbers; the sliding window log is a sorted set; the sliding window counter is a clever weighted estimate.

Sliding window counter2 integer countersO(1) — tinySmooths boundary burst; best accuracy-per-byte.

The token-bucket math

With refill rate r tokens/sec and capacity b: the long-run average request rate is bounded by r, while the maximum burst is governed by bucket depth b. Formally, if M is the peak arrival rate, the max burst duration is T_max = b / (M − r) (for M > r) and max burst size B_max = T_max × M. The elegant trick: you don't run a timer to add tokens — you lazily compute refill on each request as tokens = min(b, tokens + (now − last_refill) × r). That's why the check is O(1) and needs no background job.

💻 C# implementation

Here's a correct, idiomatic token bucket in C# — first the single-node version showing the lazy-refill math, then the crucial note on making it atomic in a distributed fleet with Redis + Lua.

// Thread-safe, single-node token bucket. State is just two numbers per client.
public sealed class TokenBucket
{
    private readonly double _capacity;     // b: max tokens (burst size)
    private readonly double _refillPerSec;  // r: tokens added per second
    private double _tokens;                 // current tokens
    private long   _lastRefillTicks;        // last update (Stopwatch ticks)
    private readonly object _gate = new();

    public TokenBucket(double capacity, double refillPerSec)
    {
        _capacity = capacity;
        _refillPerSec = refillPerSec;
        _tokens = capacity;                  // start full ⇒ allow an initial burst
        _lastRefillTicks = Stopwatch.GetTimestamp();
    }

    // Returns true = allowed (a token was taken); false = rejected (429).
    public bool TryConsume(double cost = 1.0)
    {
        lock (_gate)
        {
            long now = Stopwatch.GetTimestamp();
            double elapsed = (now - _lastRefillTicks) / (double)Stopwatch.Frequency;
            _lastRefillTicks = now;

            // LAZY refill: add tokens for the elapsed time, capped at capacity.
            _tokens = Math.Min(_capacity, _tokens + elapsed * _refillPerSec);

            if (_tokens >= cost)
            {
                _tokens -= cost;             // conformant: take the token(s)
                return true;
            }
            return false;                     // non-conformant: no tokens left
        }
    }
}

// ---- Distributed: the check MUST be atomic across the fleet. ----
// A per-instance lock is NOT enough — 10 servers would allow 10x.
// Run this Lua on Redis; it does refill+take in ONE atomic step, keyed by client.
private const string TokenBucketLua = @"
local key      = KEYS[1]
local rate     = tonumber(ARGV[1])   -- tokens per second (r)
local capacity = tonumber(ARGV[2])   -- bucket size (b)
local now      = tonumber(ARGV[3])   -- current time (seconds, from caller)
local cost     = tonumber(ARGV[4])

local b = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now

tokens = math.min(capacity, tokens + (now - ts) * rate)  -- lazy refill
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end

redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, math.ceil(capacity / rate) + 1) -- reclaim idle keys
return allowed and 1 or 0
";

public async Task<bool> TryConsumeDistributedAsync(IDatabase redis, string clientKey)
{
    try
    {
        var res = (long)await redis.ScriptEvaluateAsync(TokenBucketLua,
            new RedisKey[] { $"rl:{clientKey}" },
            new RedisValue[] { 50, 100, DateTimeOffset.UtcNow.ToUnixTimeSeconds(), 1 });
        return res == 1;
    }
    catch (RedisException)
    {
        return true;   // FAIL OPEN: never let the limiter cause the outage (Stripe's rule)
    }
}

The two takeaways an interviewer wants: (1) the lazy refill (min(capacity, tokens + elapsed × rate)) means no background timer — the bucket is recomputed on demand in O(1); and (2) in a distributed setting the read-modify-write must be atomic, which the Redis Lua script guarantees because Redis runs it single-threaded to completion. Note the catch → return true: failing open is a deliberate availability choice. .NET's built-in System.Threading.RateLimiting (with TokenBucketRateLimiter) is the production library for the single-node case.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Accuracy vs. cost. Sliding window log is exact but memory-hungry; fixed window is cheap but allows boundary bursts; sliding window counter and token bucket are the pragmatic middle. State the trade-off explicitly and recommend token bucket (bursts) or sliding window counter (strict smoothing) as your default.

Centralized vs. distributed accuracy. One Redis is exact but adds a network round-trip and is a potential bottleneck/SPOF; per-node local budgets are fast but approximate (each node allows its slice). The usual answer: centralized Redis with atomic Lua, sharded by client key if you outgrow one node, with local caching only if latency demands it.

The race condition is the classic follow-up. Two servers checking "1 token left" concurrently must not both succeed — hence atomic Lua / INCR, not read-then-write in app code.

Fail-open vs. fail-closed. If the limiter store dies, do you block everything (safe for the backend, terrible for users) or allow everything (Stripe's choice — the limiter must never be the outage)? For most APIs, fail open. For protecting a fragile downstream, you might fail closed on specific critical paths.

Clock skew & what key to limit on. Distributed nodes have skewed clocks — pass a single authoritative time (or use Redis's clock in the script). And choose the identity carefully: IP is easy but punishes users behind NAT/proxies and is spoofable; API key/user id is fairer but requires auth to happen first.

Q: Which algorithm would you choose and why?

Token bucket by default — O(1) memory (two numbers), it allows controlled bursts (good for flash sales), and its average is cleanly capped at the refill rate. If I need to strictly smooth traffic with tiny memory and no bursts, sliding window counter. Stripe uses token bucket.

Q: How do you enforce one global limit across 50 servers?

Move the counter to a shared store (Redis) and make the check a single atomic operation — a Lua script that refills and takes a token in one step, keyed by client. Per-instance counters would multiply the effective limit by the server count.

Q: What happens when Redis goes down?

Fail open — catch the error and allow the request, so the limiter never becomes the point of failure (Stripe does exactly this). Optionally degrade to a coarse per-node local limit as a backstop.

Q: How do you avoid the fixed-window boundary burst?

Use sliding window counter (weight the previous window by its overlap) or token bucket — both spread the limit continuously instead of resetting hard at a window edge, so a client can't push 2× through the boundary.

🗣️ Interview cheat sheet

30-second pitch: "A rate limiter is middleware in the gateway that caps requests per client per window and returns 429 on excess. The five algorithms are fixed window (cheap, boundary-burst bug), sliding window log (exact, memory-heavy), sliding window counter (cheap + accurate), token bucket (allows controlled bursts — the industry default, what Stripe uses), and leaky bucket (smooth shaper). In a fleet the counter lives in Redis and the check is a single atomic Lua script so concurrent servers can't race past the limit. State is just two numbers per client, so millions of clients fit in one Redis node. And it fails open — the limiter must never be the outage."

Numbers to quote

  • Token-bucket state ≈ 2 numbers (~30 B) per client ⇒ 10M clients ≈ few hundred MB.
  • Reject signal: HTTP 429 (client limited) / 503 (server shedding).
  • Fixed window flaw: up to 2× the limit at the boundary.
  • Stripe: request limiter rejects millions/month; concurrent limiter set to e.g. 20 in-flight.
  • Real limits: Twitter 300 tweets/3h, Google Docs API ~300 reads/user/60s.

5 talking points that win the round

  • Token bucket — controlled bursts, O(1) state, lazy refill; the default pick.
  • Atomicity — Redis Lua kills the race condition across the fleet.
  • Boundary burst — name it as the fixed-window flaw; fix with sliding window counter.
  • Fail open — availability over strictness; the limiter can't be the SPOF.
  • Layered defense — Stripe's 4 tiers: request limiter → concurrency limiter → fleet shedder → worker shedder.
