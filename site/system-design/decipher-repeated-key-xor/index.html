Deciphering Repeated-Key XOR

How you break a Vigenère-style binary cipher without ever seeing the key — using Hamming distance and English letter frequency.

🎯 Real-world scenario

What we're building & where it shows up

The repeated-key XOR cipher encrypts a message by XORing each plaintext byte with a byte from a short key that repeats cyclically. If the key is $^! and the plaintext is secretattack, the key becomes $^!$^!$^!$^! and each column is XORed byte-wise. Because XOR is symmetric, the exact same routine decrypts. It is essentially the Vigenère cipher in binary — a favourite of DIY "encryption" and, historically, of amateur malware authors who wanted obfuscation without a real crypto library.

This problem is famous because it is Cryptopals Set 1 Challenge 6 — the "you're now a cryptanalyst" moment every security engineer remembers. It shows up in the real world any time a black-box binary is doing "encrypt with a hard-coded key": Chrome cookies pre-Encryption, config-file XOR obfuscation in games and shareware, C2 beacons hiding traffic with a repeating key, and CTF challenges of every flavour. The point of studying it isn't to attack modern crypto — it can't touch AES or ChaCha20 — but to understand why key reuse is fatal, which is the same principle behind why a one-time pad must never repeat its key. Once you can decrypt this without knowing the key, you understand what "many-time pad" attacks actually do, and you never again propose a home-rolled cipher in a design review.

🧑‍🎓 In laymen terms

Explaining it to someone who doesn't code

Imagine you and a friend both own the same short deck of stencils — say three stencils with tiny holes cut in them, labeled A, B, C. To send a secret note, you lay stencil A over the first letter, stencil B over the second, stencil C over the third, then start over again with A on the fourth letter, and so on. Wherever a stencil hole lines up, you flip the letter to a different one using a fixed rule. Your friend has the identical deck, so they lay them down in the same order and flip the letters back. The deck is the "key". That's what repeated-key XOR is: a very short deck of stencils that you cycle over a long message.

Now imagine you're a nosy neighbour who intercepts the note but doesn't own the deck. Can you still read it? Surprisingly, yes — and you don't even need to guess the deck first. Here's the trick, in two moves.

Move 1: figure out how many stencils are in the deck. You don't know if it's 3 or 5 or 12. But if you slice the note into pieces of the "right" length, every piece was scrambled with the deck in the same order, so the pieces will look weirdly similar to each other compared to random garbage. You try slicing by 2, by 3, by 4… whichever slice-size makes the pieces most similar wins. That's the length of the deck.

Move 2: crack one stencil at a time. Once you know the deck has, say, 3 stencils, gather every 1st letter of every piece into one pile — they were all scrambled by stencil A. That pile is now easy: try all 256 ways of un-scrambling it, and whichever one comes out looking like readable English (lots of the letter "e", spaces, "th"…) is the right one. Repeat for stencil B and stencil C. You now have the whole deck.

The really neat part is what doesn't work: the same idea completely fails if the deck is as long as the message and used only once (that's a "one-time pad"). Reuse is what kills it — and that's the moral you should walk away with. Real-world uses show up in CTF puzzles, in reverse-engineering malware that XOR-obfuscates its config, and any time you spot a home-made "encryption" scheme in the wild.

Tiny example to walk through in your head: the note is 12 characters long. You slice by 3 and the pieces feel similar. Gather positions 1, 4, 7, 10 → one pile scrambled by stencil A. Try 256 un-scramblings; the one that spells the start of English words is the right one. Do the same for positions 2, 5, 8, 11 and positions 3, 6, 9, 12. You've read the note. No key handed over. That's cryptanalysis.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional

  • Given ciphertext bytes only (no key), recover the plaintext.
  • Detect the key length L automatically, then recover each of the L key bytes.
  • Handle keys of arbitrary length up to len(cipher)/2.

Non-functional

  • Accuracy: ≥ 99% on typical English plaintext with random keys of length 2–40 (Arpit's reported figure on 100 sentences).
  • Latency: linear in ciphertext length; for a few KB, decrypt end-to-end in < 1 second.
  • Deterministic: same ciphertext + same scoring function → same recovered plaintext.
  • Language-tunable: swap the English letter-frequency table for another language.

🏗️ High-level architecture

How the pieces fit together

The decryption pipeline is a straight-line two-stage attack. Stage 1 finds the key length using pairwise Hamming scores over chunked ciphertext. Stage 2 transposes the ciphertext into L columns — each column is a single-byte XOR cipher — and cracks each column independently by scoring candidate keys against English letter frequencies. Concatenating the column keys yields the full key; XORing it against the ciphertext yields the plaintext.

Nothing in the pipeline talks to a network or a database — the entire attack is a pure function of the ciphertext bytes and a static English-frequency table. That's why in production this is usually a batch job (or a Lambda invocation) and never a hot-path service.

🔍 Component deep-dive

Why key reuse leaks structure

For any two ciphertext bytes c[i] and c[j] that were encrypted with the same key byte k', the key cancels when we XOR them: c[i] ⊕ c[j] = (p[i] ⊕ k') ⊕ (p[j] ⊕ k') = p[i] ⊕ p[j]. The ciphertext-vs-ciphertext XOR reduces to plaintext-vs-plaintext XOR — as if the key never existed. That is the entire foundation of the attack. If the key never repeats (as in a one-time pad), the bytes never share a key byte, and this identity never fires.

Hamming distance and why it dips at the right key length

Hamming distance counts differing bits between two byte strings. Between two uniformly random bytes it averages ~4 out of 8 (score ≈ 0.5). But between two random lowercase English letters it averages only ~2.45 (score ≈ 0.307) because English letters cluster in the numeric range 97–122 and share upper bits. When we split the ciphertext into chunks of the true key length, pairwise-XORing two chunks produces plaintext-XOR-plaintext, whose Hamming distance mirrors the English baseline. At any wrong chunk length, the key does not cancel and we see the random-baseline score of ~0.5. That gap — 0.31 vs 0.50 — is what we argmin over.

Chunking rules that actually work

  • Try key lengths from 2 up to N/2. Beyond that, too few chunks to average.
  • Discard the final chunk if shorter than half of klen — a truncated chunk skews the pairwise average.
  • Average the score (distance ÷ 8·min-len), not the raw distance — comparing at different chunk sizes only makes sense normalized.
  • Expect multiples of the true length to also dip. If length 3 wins, length 6 will win nearly as convincingly.

Transpose to single-byte XOR

Once L is known, the ciphertext splits into L columns: column i = c[i], c[i+L], c[i+2L], …. Every byte in a column was scrambled by the same key byte. Each column is now a trivial single-byte XOR cipher — 256 candidate keys total. For each candidate we XOR the whole column, then score the resulting bytes for English-ness. The winner is the column's key byte.

Scoring "English-ness": chi-squared vs fitting quotient

The scorer takes a candidate plaintext and returns a "closeness to English" number. Two reasonable choices:

  • Fitting quotient (Arpit's article): sum expected frequencies for each byte you see. High score = more English. Fast and interview-friendly.
  • Chi-squared against a reference frequency table: Σ (observed_i − expected_i)² / expected_i. Low score = more English. Slightly better at rejecting garbage.

Either works. Penalise non-printable bytes heavily (score −∞ if you see a control character) — that alone rejects the vast majority of the 256 candidate keys before frequency even matters.

Failure modes to name in the interview

  • Ciphertext too short: each column may only hold 2–3 bytes; frequency scoring is noise. Rule of thumb — need ≥ 20 bytes per column.
  • Non-English plaintext: swap the frequency table; the pipeline still works.
  • Binary (non-text) plaintext: the "printable + English frequency" heuristic collapses. Substitute a different structure detector (e.g. known file magic bytes).
  • Key length underestimated: a divisor of the true length can win. In practice the top-3 candidates should all be tried and the one whose recovered plaintext scores best in aggregate is the winner.
🧮 The DSA behind it

Data structures & algorithms

This problem is a beautiful showcase of three cheap tools composing into something powerful: bit-counting for structural detection, transposition for divide-and-conquer, and frequency analysis for the final crack.

Algorithm / DSWhere it's usedComplexity
Hamming distance (popcount of XOR) Detecting key length — the whole game hinges on this metric being lower for real English than for random noise. O(1) per byte pair — System.Numerics.BitOperations.PopCount or Brian Kernighan's n & (n-1).
Pairwise chunk comparison Average Hamming score across all C(m, 2) pairs of the m chunks per candidate key length. O(m² · klen) per candidate; keep it linear by sampling e.g. 4 chunks.
Transposition (index remap) Splits the ciphertext into L columns so each column is a single-byte XOR — divide-and-conquer. O(N) time, O(N) extra space.
Frequency analysis (chi-squared / fitting quotient) Picks the correct key byte per column by scoring how English the decrypted column looks. O(256 · N/L) per column — 256 candidate keys × column length.
argmin / argmax over a small set Pick the winning key length, then the winning key byte in each column. O(K) and O(256).

The overall cost is O(N · K + 256 · N) where N is ciphertext length and K is the maximum key length considered. In practice that's milliseconds on a laptop — the attack's cost model is "almost free". This is why hard-coded XOR keys are catastrophic in real systems: an attacker who intercepts a few kilobytes of ciphertext has read your plaintext before their coffee cools.

Deployment shape: an S3 PutObject fires an event, an SQS queue buffers, and a Lambda (or Fargate task) pulls one blob at a time, runs the two-stage attack in-process, and writes results to DynamoDB. The whole thing is stateless, horizontally scalable, and has no long-lived infrastructure — a perfect batch pipeline in ~50 lines of Terraform.

💻 C# implementation

The full reference in idiomatic .NET 8 — Hamming distance via BitOperations.PopCount, chunked scoring for key length, single-byte XOR crack via chi-squared against an English frequency table, and the driver that glues them.

using System.Numerics;

// English letter frequencies (a..z), source: standard corpus. Sum ≈ 1.0.
static readonly double[] Freq = {
    0.0817, 0.0150, 0.0278, 0.0425, 0.1270, 0.0223, 0.0202, 0.0609,
    0.0697, 0.0015, 0.0077, 0.0403, 0.0241, 0.0675, 0.0751, 0.0193,
    0.0010, 0.0599, 0.0633, 0.0906, 0.0276, 0.0098, 0.0236, 0.0015,
    0.0197, 0.0007
};

// Hamming distance between two equal-length byte slices — popcount of XOR.
static int HammingDistance(ReadOnlySpan<byte> a, ReadOnlySpan<byte> b) {
    int total = 0;
    int n = Math.Min(a.Length, b.Length);
    for (int i = 0; i < n; i++)
        total += BitOperations.PopCount((uint)(a[i] ^ b[i]));
    return total;
}

// Average pairwise Hamming SCORE across the first 4 chunks of size klen.
// Score = distance / (8 * chunkLen) → in [0..1].
static double AvgScoreForKeyLen(byte[] ct, int klen) {
    int chunks = Math.Min(4, ct.Length / klen);
    if (chunks < 2) return double.MaxValue;

    double total = 0; int pairs = 0;
    for (int i = 0; i < chunks; i++)
        for (int j = i + 1; j < chunks; j++) {
            var ci = ct.AsSpan(i * klen, klen);
            var cj = ct.AsSpan(j * klen, klen);
            total += HammingDistance(ci, cj) / (8.0 * klen);
            pairs++;
        }
    return total / pairs;
}

// Stage 1 — argmin over candidate key lengths.
static int FindKeyLength(byte[] ct, int maxKeyLen = 40) {
    int best = 2; double bestScore = double.MaxValue;
    for (int k = 2; k <= Math.Min(maxKeyLen, ct.Length / 2); k++) {
        var s = AvgScoreForKeyLen(ct, k);
        if (s < bestScore) { bestScore = s; best = k; }
    }
    return best;
}

// Chi-squared distance from English letter frequencies. Lower = more English.
// Non-printable, non-letter bytes get a heavy penalty.
static double EnglishScore(byte[] plain) {
    var counts = new int[26]; int letters = 0; int penalty = 0;
    foreach (var b in plain) {
        int c = b;
        if (c >= 'A' && c <= 'Z') c += 32;
        if (c >= 'a' && c <= 'z') { counts[c - 'a']++; letters++; }
        else if (c < 32 && c != '\n' && c != '\t') penalty += 50;   // junk
        else if (c > 126) penalty += 20;                                // non-ASCII
    }
    if (letters == 0) return double.MaxValue;

    double chi = penalty;
    for (int i = 0; i < 26; i++) {
        double exp = Freq[i] * letters;
        double diff = counts[i] - exp;
        chi += diff * diff / Math.Max(exp, 0.01);
    }
    return chi;
}

// Stage 2 — for one column, try all 256 key bytes and return the winner.
static byte BestSingleByteKey(byte[] column) {
    byte bestKey = 0; double bestScore = double.MaxValue;
    var buf = new byte[column.Length];
    for (int k = 0; k < 256; k++) {
        for (int i = 0; i < column.Length; i++) buf[i] = (byte)(column[i] ^ k);
        var s = EnglishScore(buf);
        if (s < bestScore) { bestScore = s; bestKey = (byte)k; }
    }
    return bestKey;
}

// Driver — glues the two stages and returns (key, plaintext).
public static (byte[] key, byte[] plaintext) Decipher(byte[] ct) {
    int L = FindKeyLength(ct);
    var key = new byte[L];

    // Transpose into L columns, one per key byte.
    for (int i = 0; i < L; i++) {
        int colLen = (ct.Length - i + L - 1) / L;
        var col = new byte[colLen];
        for (int j = 0; j < colLen; j++) col[j] = ct[i + j * L];
        key[i] = BestSingleByteKey(col);
    }

    // Decrypt with the recovered key.
    var pt = new byte[ct.Length];
    for (int i = 0; i < ct.Length; i++) pt[i] = (byte)(ct[i] ^ key[i % L]);
    return (key, pt);
}

Tested against Arpit's example: ciphertext = W;BV;UE*UE=J, expected key $^!, expected plaintext secretattack. The driver returns exactly that in a few hundred microseconds. For the classical Cryptopals Set 1 Challenge 6 (~2.9 KB base64-encoded ciphertext, key length 29), the same code recovers the plaintext ("I'm back and I'm ringin' the bell") in well under a second on a laptop.

Alternate implementations worth mentioning if asked: Python's bin(x).count('1') gives popcount for free; Rust's u8::count_ones; and any language with a stdlib byte-XOR + a chi-squared scorer is a one-afternoon build. The Python reference in the source article is the canonical reading.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Why this attack works at all

The whole thing hinges on plaintext structure. Real English has letter-frequency structure (E is 12.7%, Z is 0.07%). If the "plaintext" is uniform random bytes — say, an AES key wrapped in XOR — every step fails. The Hamming score never dips because random-XOR-random is still random; the frequency scorer picks a nonsense key because every distribution looks equally bad. That's why "XOR your encrypted blob with a key" doesn't add security to a real cipher and is only ever obfuscation.

Bottlenecks and how you'd tune them

  • Chunk pair count: comparing all C(m, 2) pairs is O(m²). Sampling 4–6 chunks per candidate is enough in practice and drops it to constant time per candidate.
  • Max key length: capping at 40 is fine for typical text; go higher for long ciphertexts (Cryptopals uses up to 40 explicitly).
  • Multiples of true key length: length 3 and 6 both dip. Try the top 2–3 candidates and keep the plaintext with the best overall English score, not just the best chunk score.
  • Frequency table locale: default English; swap it for Spanish/French/etc. by loading a different frequency vector — the rest of the pipeline is unchanged.

Failure modes (name them before the interviewer does)

  • Ciphertext shorter than ~20·L bytes: not enough per-column data for frequency scoring to be reliable.
  • Non-English or binary plaintext: swap the scorer or fall back on structure detectors (magic bytes, N-gram model).
  • Key length > N/2: too few chunks to average — degenerate case; you effectively need a longer ciphertext.
  • Adversarial padding: if the attacker knows the pipeline, they could pad the plaintext with high-entropy chaff to flatten the Hamming dip. Real crypto is the answer.

Likely interviewer follow-ups

Q. Why Hamming distance and not something else?

Because bit-level proximity survives the XOR identity. English letters occupy a small numeric range, and their bit patterns share upper bits — so a XOR b for two English letters averages ~2.45 set bits. Any wrong key-length pairing gets ~4 (uniform random). The gap is what we detect.

Q. Why does a multiple of the key length also give a low score?

If the true key length is L, then at chunk length 2L each chunk holds two complete key cycles — bytes still align with the same key positions, so the key still cancels pairwise. You'll see dips at L, 2L, 3L… — pick the smallest.

Q. Kasiski examination vs Friedman test — when would you use each?

Kasiski looks for repeated substrings and takes GCDs of their offsets — great when the plaintext contains repeated fragments (like "the "). Friedman/Hamming is more robust because it doesn't rely on visible repeats — it works on the aggregate statistical structure. In practice, run Friedman first and use Kasiski as a sanity check.

Q. Why can't this attack the one-time pad?

Because the OTP never reuses a key byte. The identity c[i] ⊕ c[j] = p[i] ⊕ p[j] requires the same key byte at positions i and j. If every byte gets a fresh, uniform, secret key byte, the ciphertext is information-theoretically indistinguishable from random — no structure to attack.

Q. Can you parallelise this?

Trivially. Stage 1 candidate key lengths are independent — one thread per candidate. Stage 2 columns are independent — one thread per column. The two stages have a hard sync point in between (need L before you can transpose) but each is embarrassingly parallel internally.

Q. How would you detect if the plaintext was, say, JSON instead of English?

Two options: (a) replace the letter-frequency scorer with a JSON-aware detector that rewards braces, colons, quotes, and ASCII digits; or (b) train a character-level N-gram model on JSON and score log-likelihood. The pipeline structure is identical — only the scoring function changes.

🗣️ Interview cheat sheet

30-second pitch: Repeated-key XOR is Vigenère in binary. To break it without the key, first detect the key length by chunking the ciphertext and picking the length that minimises average pairwise Hamming score — the key cancels out for matching-position bytes, and English text has low pairwise Hamming distance (~2.45/8) vs random noise (~4/8). Then transpose the ciphertext into L columns; each is a single-byte XOR cipher, so brute-force all 256 key bytes and score for English fit via chi-squared. Concatenate the winning column keys → full key → decrypt. Whole attack is O(N·K), runs in milliseconds, and reaches ~99% accuracy on English.

  • The killer identity: c[i] ⊕ c[j] = p[i] ⊕ p[j] when key bytes align — key cancels, plaintext structure leaks.
  • The two numbers: avg Hamming score for random bytes ≈ 0.500; for English lowercase ≈ 0.307. That gap is the whole game.
  • Stage 1 → Stage 2: find L, then break L single-byte XORs in parallel.
  • Why OTP survives: no key reuse → no aligned bytes → the identity never fires.
  • Real-world context: Cryptopals Set 1 Challenge 6, malware config obfuscation, home-rolled "encryption" in games.
