🎯 Real-world scenario

What we're building & where it's used

A URL shortener is a service that takes a long URL — say a 200-character product link with tracking parameters — and returns a compact alias such as https://bit.ly/3xY9aZ. When anyone visits the short link, the service looks up the original URL and issues an HTTP redirect so the browser lands on the real page. It sounds trivial, but it's a favourite interview question precisely because it hides almost every distributed-systems concept behind a one-sentence problem statement: unique ID generation, read-heavy caching, horizontal sharding, the consistency-vs-availability trade-off, and global low-latency delivery.

You use one every day. Bit.ly and TinyURL are the classic public shorteners; t.co is Twitter/X's internal shortener that wraps every link in a tweet; lnkd.in (LinkedIn), fb.me (Facebook), youtu.be (YouTube), and g.co (Google) are first-party shorteners. Companies build them for very practical reasons:

  • Shareability — short links fit in SMS, tweets, QR codes, and printed ads where character count or pixels matter.
  • Analytics & attribution — every click can be logged, so marketers see geography, device, referrer, and campaign performance in real time.
  • Link management — the destination behind a short code can be changed later, links can expire, and malicious destinations can be revoked centrally.
  • Safety & branding — wrapping outbound links (like t.co) lets a platform scan for spam/malware and present a branded domain.

Say this in the interview: "It's a read-heavy, write-light key-value lookup at global scale where the hard parts are generating collision-free short keys and serving redirects in single-digit milliseconds."

🧑‍🎓 In laymen terms

The tiny sticker with a code, and the giant address book

You've probably tried to text a friend a link to a product on Amazon and watched a horrifying 250-character monster tumble into the chat — full of question marks, equals signs, and random numbers. Nobody wants to type or share that. What you really want is something like bit.ly/xyz — six letters, easy to say out loud, fits on a business card. That's the whole job of a URL shortener.

Think of it like this. Imagine you're organising a wedding and you print out little sticker codes to hand to guests — "Table 7", "Table 14". Each sticker is short and cheap, but the code by itself doesn't tell you anything. It only makes sense because there's a huge printed address book at the entrance saying "Table 7 → Aunt Sarah's family in the red van, seated left of the DJ." The sticker is the short link; the address book is the shortener's database. When someone shows up with a sticker, the greeter flips to that entry and points them to the real destination.

You use these every day. When you click a link in a tweet, that t.co/abc you glimpsed is a sticker Twitter attached — it looks it up in its address book and quietly redirects you to the real article. Bit.ly, TinyURL, LinkedIn's lnkd.in, YouTube's youtu.be — all doing the same trick. The reason companies bother: short links fit in text messages, look tidy on posters, print nicely on receipts, and — bonus — the sticker can be counted every time someone touches it, so marketers can see which poster actually worked.

The hard part? Making sure no two stickers ever collide, and answering "which sticker is this?" in the blink of an eye when a billion people are asking at once. That's what all the clever machinery underneath is quietly solving.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Always split requirements into functional (what it does) and non-functional (how well it must do it). Interviewers grade you on volunteering the non-functional ones and the capacity math without being asked.

Functional requirements

  • Given a long URL, return a unique short URL.
  • Given a short URL, redirect (HTTP 301/302) to the original long URL.
  • Optional: custom aliases (vanity links), link expiration (TTL), and per-link click analytics.

Non-functional requirements

  • High availability — if the redirect path is down, every link everywhere breaks. Target 99.9%+.
  • Low latency — redirects must feel instant (< ~10 ms server-side, single-digit ms from cache/edge).
  • Scalable & read-heavy — reads dominate writes by ~100:1.
  • Short codes must be unpredictable-ish and unique — no collisions, hard to enumerate.

Capacity estimation (the numbers to quote)

🏗️ High-level architecture

How the pieces fit together

There are two distinct paths and you should draw them separately. The write path (create a short link) is rare and can afford a little work: a request hits the load balancer, lands on a stateless write service, which obtains a unique ID, Base62-encodes it into a 7-char code, and persists the code → long URL mapping in the database. The read path (resolve & redirect) is the hot path and must be brutally fast: the request hits a CDN/edge, then the load balancer, then a stateless read service that checks Redis cache first and only falls through to the database on a miss, returning a 301/302 redirect. Click events are emitted asynchronously to a queue so analytics never slow the redirect.

Walk the interviewer through the redirect: client requests /3xY9aZ → edge/LB routes to a read service → Redis lookup → on hit, return 301 immediately; on miss, read the DB, populate the cache, then redirect → fire a click event onto the queue and return. That's the whole hot path, and it's why latency stays in single-digit milliseconds.

🔍 Component deep-dive

1. Short-code generation (the heart of the design)

This is what the interviewer is really testing. There are three credible strategies, and you should name the trade-offs:

  • Hash + truncate (MD5/SHA → Base62, take 7 chars): hash the long URL (plus a salt like timestamp), Base62-encode, and keep the first 7 characters. Simple and stateless, but can collide, so you must check the DB and retry on collision, and identical URLs naturally map to the same code.
  • Counter + Base62 (recommended): keep a globally unique, monotonically increasing 64-bit counter; Base62-encode the number to get the code. Zero collisions by construction and O(1) generation. The challenge becomes distributing the counter — solved with a Key Generation Service (KGS) that hands out ranges/tickets to each app server, or a Snowflake-style ID (timestamp + machine-id + sequence).
  • Pre-generated keys (KGS): a separate service generates random unique 7-char keys in advance, stores them, and hands them to write servers in batches. Generation is moved off the critical path entirely.

Most strong answers settle on counter-based Base62 via a KGS or Snowflake because it eliminates the collision-check round-trip and keeps writes O(1).

2. Caching strategy

Because reads dominate, an in-memory cache (Redis/Memcached) sits in front of the DB using a cache-aside (lazy loading) pattern with an LRU eviction policy — the 20% of links that are "hot" (a viral campaign, a pinned tweet) serve the bulk of traffic from memory. Mappings are immutable once created, so cache invalidation is a non-issue except for deletions/expiry; you can cache aggressively with long TTLs.

3. Datastore & partitioning

The access pattern is a pure key lookup (code → long URL), so a NoSQL key-value store (DynamoDB, Cassandra) is the natural fit — it scales horizontally and gives single-digit-ms reads. Partition/shard by the short code (hash-based sharding) so reads and writes spread evenly across nodes; range-based sharding risks hot partitions. A relational DB works at smaller scale with the short code as the primary key.

4. Redirect type: 301 vs 302

A subtle point that impresses: 301 (permanent) lets browsers cache the redirect, cutting load — but then you lose per-click analytics because repeat visits never hit your server. 302 (temporary) forces every click through your service, preserving analytics at the cost of more traffic. Analytics-driven products (bit.ly) lean 302.

5. Analytics & rate limiting

Click events are pushed to a queue (Kafka/SQS) and aggregated offline so the redirect never waits on analytics writes. A rate limiter on the create endpoint (by API key/IP) prevents abuse and key-space exhaustion.

🧮 The DSA behind it

Data structures & algorithms

Behind the buzzwords, a URL shortener runs on a few classic data-structures-and-algorithms ideas:

  • Base62 encoding — convert a 64-bit integer ID into [0-9a-zA-Z] (62 symbols). It's just base conversion: repeatedly take n % 62 and n /= 62. 7 digits give 62⁷ ≈ 3.5 trillion codes. Base62 (not Base64) avoids the URL-unsafe + and / characters.
  • Distributed counter / Snowflake ID — a 64-bit unique ID assembled from a timestamp, a machine/worker id, and a per-ms sequence counter, guaranteeing global uniqueness without coordination on every request.
  • Hashing (MD5/SHA-256) — used by the hash-and-truncate strategy to map a long URL to a fixed-width, uniformly-distributed value before Base62.
  • Hash table — the cache and the KV store are conceptually one giant hash map: O(1) average lookup from code to URL.
  • Bloom filter — a probabilistic set used to answer "have we seen this short code / custom alias before?" in O(1) memory-cheap time, avoiding a DB round-trip on most negatives.

💻 C# implementation

The core logic is the Base62 codec plus the shorten/resolve handlers. Here's a clean, correct C# reference. The encoder converts a unique 64-bit ID to a short code; the service caches resolves and falls through to the store on a miss.

// ---- Base62 codec: converts a unique long ID to/from a short string ----
public static class Base62
{
    private const string Alphabet =
        "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"; // 62 chars

    public static string Encode(long id)
    {
        if (id == 0) return Alphabet[0].ToString();
        var sb = new StringBuilder();
        while (id > 0)
        {
            sb.Insert(0, Alphabet[(int)(id % 62)]); // take remainder = next digit
            id /= 62;                              // shrink toward 0
        }
        return sb.ToString();
    }

    public static long Decode(string code)
    {
        long id = 0;
        foreach (var c in code)
            id = id * 62 + Alphabet.IndexOf(c); // Horner's method
        return id;
    }
}

// ---- Service: shorten + resolve with cache-aside ----
public class UrlShortener
{
    private readonly IIdGenerator _ids;   // KGS / Snowflake: hands out unique 64-bit ids
    private readonly ICache _cache;       // Redis / ElastiCache
    private readonly IUrlStore _store;     // DynamoDB

    public UrlShortener(IIdGenerator ids, ICache cache, IUrlStore store)
        => (_ids, _cache, _store) = (ids, cache, store);

    public async Task<string> ShortenAsync(string longUrl)
    {
        long id = await _ids.NextIdAsync();   // unique → no collision check needed
        string code = Base62.Encode(id);
        await _store.SaveAsync(code, longUrl); // persist code -> longUrl
        await _cache.SetAsync(code, longUrl, TimeSpan.FromHours(24));
        return $"https://sho.rt/{code}";
    }

    public async Task<string?> ResolveAsync(string code)
    {
        var hit = await _cache.GetAsync(code);   // 1) cache first (hot path)
        if (hit is not null) return hit;

        var url = await _store.GetAsync(code);   // 2) miss → datastore
        if (url is not null)
            await _cache.SetAsync(code, url, TimeSpan.FromHours(24)); // 3) backfill
        return url;
    }
}

⚖️ Trade-offs, bottlenecks & likely follow-ups

Where it breaks under load: the redirect read path is the bottleneck, mitigated by caching and edge CDN. The unique-ID generator is the second risk — a single global counter is a single point of failure and a write hotspot, which is exactly why you distribute it (KGS ranges or Snowflake). Hot keys (one viral link) can overload a single cache node; mitigate with client-side caching, request coalescing, or replicating the hot entry.

Consistency vs availability: a URL mapping is immutable after creation, so eventual consistency is fine — favour availability (AP) on the read path. A brief replication lag just means a freshly created link might 404 for a few hundred ms; acceptable. Never sacrifice redirect availability for strong consistency.

Q: How do you avoid two servers generating the same short code?
A: Don't hash-and-hope. Use a globally unique 64-bit ID source — a KGS handing out non-overlapping ranges, or Snowflake (timestamp+machineId+sequence) — then Base62-encode it. Uniqueness is guaranteed by construction, so no collision check is needed.
Q: 301 or 302 redirect?
A: 302 if you want per-click analytics (every visit hits your server); 301 if you want to offload traffic by letting browsers cache the redirect, at the cost of losing repeat-click data.
Q: How do you handle custom/vanity aliases?
A: Treat the alias as a chosen key; check existence (Bloom filter → DB) and reject duplicates. Keep custom and generated keys in the same namespace so they can't collide.
Q: How do you expire or delete links?
A: Store a TTL/expiry timestamp; lazily treat expired rows as 404 on read and sweep them with a background job (or DynamoDB native TTL). Evict from cache on delete.
Q: How do you stop abuse and key-space exhaustion?
A: Rate-limit the create endpoint per API key/IP (token bucket), require auth for bulk creation, and scan destinations for malware/spam.

🗣️ Interview cheat sheet

30-second pitch: "A URL shortener is a read-heavy, write-light key-value service. I generate a unique 64-bit ID per URL — via a distributed Key-Generation Service or Snowflake — Base62-encode it into a 7-character code, and store the code→URL mapping in a horizontally-sharded NoSQL store like DynamoDB. Reads go through Redis with cache-aside, fronted by a CDN, so redirects return a 301/302 in single-digit milliseconds. Click events fire async to a queue for analytics. It's available (AP) over strongly consistent because mappings are immutable."

Numbers to quote

  • 100:1 read:write ratio → ~40 writes/sec, ~4,000 reads/sec (at 100M new URLs/month)
  • 7 Base62 chars → 62⁷ ≈ 3.5 trillion unique codes
  • ~500 bytes/record → ~600 GB/year storage
  • Cache the hot 20% of links (serves ~80% of reads)

5 talking points that win the round

  • Unique IDs by construction (KGS/Snowflake + Base62) — not hash-and-retry.
  • Read path = cache + CDN; the DB is almost a fallback.
  • Shard by short code (hash partitioning) to avoid hot partitions.
  • 301 vs 302 trade-off framed around analytics.
  • AP over CP because mappings are immutable; async analytics off the hot path.
❓ FAQ — your follow-up questions

Questions asked about this topic

Why is horizontal scaling necessary here, not vertical scaling?

Vertical = one bigger box; horizontal = more boxes sharing load. Horizontal wins because: (1) data outgrows one machine — ~600 GB/yr forever → multi-TB, past any single server's disk/RAM ceiling; sharding spreads it across N nodes. (2) availability — a single big box is a single point of failure, fatal when the whole job is "always up"; many nodes across AZs survive a node/AZ loss. (3) hard ceiling vs near-unlimited growth — the biggest instance is finite, but you meet 10× spikes by adding stateless read nodes. (4) cost/elasticity — commodity nodes are cheaper per unit throughput and auto-scale out/in, vs paying for one peak-sized monster 24/7. (5) the design is already built for it — stateless services + hash-partitioned KV + cache/CDN, all of which add identical copies behind a load balancer. Balanced note: scale vertically first for simplicity, then out once you outgrow one node — but a global always-on service inevitably ends up horizontal.

It's read-heavy, so why choose NoSQL — and how is sharding chosen for NoSQL?

NoSQL isn't picked because it's read-heavy (SQL reads fast too) — it's picked because the workload is a pure key lookup (GET by short_code, no joins/scans/transactions), needs billions of rows with automatic horizontal scaling, and tolerates eventual consistency / favours availability (AP) since mappings are immutable. At small scale, PostgreSQL with short_code as PK is perfectly fine; NoSQL wins on scale + access-pattern fit, not because SQL "can't". Sharding: partition by hash of the short_code (DynamoDB internal hash; Cassandra Murmur3 on a consistent-hashing ring). Hash — not range — because counter-based Base62 codes are sequential, so range sharding would dump all new/hot links on the last shard (hotspot); hashing scatters them uniformly. Reads stay single-shard (you know the exact code → route to one partition → O(1)). Consistent hashing means adding a node remaps only a few keys. Viral hot keys are absorbed by the cache/CDN, not by changing the shard key.
