Consistent Hashing

Why hash(key) mod N breaks the world when N changes — and how a ring of virtual nodes moves only K/N keys instead of nearly all of them.

🎯 Real-world scenario

The problem: what happens when your cache tier scales?

You run a Memcached or Redis tier with 10 nodes. To decide which node holds a key, you do server = hash(key) % 10. Life is good. Then Black Friday hits and you scale to 11 nodes. Now hash(key) % 11 sends nearly every key to a different server than before — ~10 out of every 11 keys become cache misses. The origin database is suddenly hit with a stampede that can knock it over. This isn't hypothetical: the whole reason consistent hashing was invented (Karger et al., MIT, 1997) was to keep web caches sane when servers come and go.

Consistent hashing solves it. Both keys and servers are mapped onto a circular hash space (the "ring"). A key is served by the first server encountered walking clockwise from the key's hash position. When you add or remove a server, only the keys that fall in that server's arc move — roughly K/N keys, not all K. That's the magic property: a change touches a fraction proportional to 1/N, so the origin database is barely disturbed.

This one idea powers a shocking amount of infrastructure: Amazon DynamoDB partitions data across nodes with consistent-hashing-inspired schemes; Apache Cassandra and Riak use a token ring; Memcached clients use the Ketama library; Netflix Open Connect and other CDNs use it to place video content; Envoy Proxy and HAProxy use it for sticky session load balancing; Discord uses it to locate chat-server shards. It's a bread-and-butter interview topic for FAANG staff and principal roles because it shows you understand distributed hashing, load balancing, and graceful scaling in one algorithm.

🧑‍🎓 In laymen terms

Think of a round dinner table with waiters and dishes

Imagine you're running a big restaurant with a round dinner table, and you have five waiters stationed at different spots around it. Every time an order comes in, you write it on a small ticket and drop the ticket on the table. The rule is simple: the ticket belongs to the next waiter you meet if you walk clockwise from where it landed. This is fair, easy to explain, and every waiter ends up with roughly the same number of tickets.

Now suppose a sixth waiter joins for the dinner rush. In a bad system, you'd have to collect every single ticket off the table and redistribute them all — a huge disruption. But in this system, all you do is seat the new waiter in one open spot. Only the tickets sitting in the arc between the new waiter and the previous waiter change hands. Everyone else keeps the tickets they already had. Adding one waiter only touches one-sixth of the tickets. That's the whole trick.

The same thing happens in reverse: if a waiter gets sick and leaves, the tickets that were theirs slide to the next waiter clockwise. Nobody else is disturbed. This is exactly how Netflix decides which storage box holds which piece of a movie, how Amazon DynamoDB decides which server owns your shopping cart, and how a load balancer keeps sending you back to the same web server you were talking to five minutes ago so your session doesn't get lost.

There's one more clever tweak. If you only have five waiters, one might end up guarding a huge stretch of the table and get slammed. So instead of placing each waiter in one spot, we place each waiter at many spots — imagine each of the five waiters wearing five hats scattered around the ring. Now the arcs are small and even, and if one waiter leaves, their many small arcs get absorbed by many different neighbors — no single neighbor gets overwhelmed. These "extra hats" are what engineers call virtual nodes. The idea is delightfully simple; the elegance is that it stays fair no matter how big the restaurant grows.

📋 Requirements & scale

What we're optimizing for

Functional requirements

  • Given a key, deterministically pick a server from the current cluster.
  • When a server joins, remap only the keys that now belong to it.
  • When a server leaves (planned or crash), remap only that server's keys to its clockwise neighbor(s).
  • Support heterogeneous nodes (bigger nodes get more keys via more virtual replicas).

Non-functional requirements

  • Minimal remapping: on a node change, at most ~K/N keys move.
  • Balanced load: with V virtual nodes per physical node, load spread stays within a few % of average when V is ~100–500.
  • Fast lookup: O(log N·V) per key.
  • Client-side or coordinator-side: the algorithm must work with no shared coordination (many implementations do it purely in the client library).

🏗️ High-level architecture

Where consistent hashing sits in a system

The client (or a load balancer/proxy) holds a small in-memory data structure called the ring — a sorted map from hash position to server id. To route a request it hashes the key, does a binary search for the smallest ring position ≥ that hash (wrapping to the start if past the end), and forwards to the matching server. Membership changes flow in through a gossip protocol (Cassandra), a coordinator/config service (DynamoDB, Zookeeper), or by service discovery like Consul/etcd. Each node registers itself with V virtual positions on the ring; every client rebuilds its ring on membership change.

🔍 Component deep-dive

1. The ring — a big integer space treated as a circle

The hash output space (e.g., 128-bit MD5, 32-bit Murmur, 64-bit xxHash) is treated as a circle: value MAX wraps around to 0. Every node is hashed to a position; every key is hashed to a position; the key is served by the first node encountered walking clockwise. In an implementation, the ring is a sorted map (TreeMap in Java, SortedDictionary in .NET, std::map in C++) keyed by hash value. A key lookup is a ceiling(hash) call — O(log N·V). If the ceiling is missing (past the largest position), you wrap to first().

2. Why virtual nodes are non-negotiable

With one position per physical node, the ring is easily lopsided: if 3 node hashes cluster together by bad luck, one node covers a huge arc and gets slammed. The fix is V virtual node positions per physical node (typically V = 100 to 500). Each vnode is hash(nodeId + "-" + i), spread pseudo-randomly around the ring. With enough vnodes the standard deviation of load per node drops to a few percent. Vnodes also let heterogeneous hardware carry proportional load: give a 2× bigger machine 2× the vnodes.

3. Adding a node: the arc-transfer step

When a new node D joins, its vnode positions divide up the arcs currently owned by neighbors. Each vnode's arc "steals" the keys sitting in it from whichever node used to own the arc. In a stateful system like Cassandra, that means D must stream in the data corresponding to those arcs from the previous owners before it can serve reads. During the stream, reads can go to either the old or new owner to preserve availability. Only K/N keys need moving.

4. Removing a node

When a node leaves, each of its vnodes vanishes and the clockwise-next vnode absorbs that arc. In a replicated system, the second replica for those keys usually already holds them, so no re-streaming is needed for durability — just re-election. Cassandra achieves this via replicas being placed at the N successors on the ring.

5. Replication on the ring (RF > 1)

To replicate each key R times, walk clockwise from the primary and pick the next R−1 distinct physical nodes (skipping vnodes of nodes already picked). This is how Cassandra achieves REPLICATION_FACTOR = 3 across an arbitrary ring — the property "consecutive on the ring" makes it trivial. Rack- and datacenter-aware placement modify the walk to skip over nodes in the same failure domain.

6. Bounded-load consistent hashing

Vanilla consistent hashing balances keyspace, not traffic. A few keys can go viral (a hot celebrity, a trending video ID) and overload one node. Bounded-load consistent hashing (Google, 2016) caps a node's load at c × average; if a lookup lands on an "over-quota" node it forwards to the next node clockwise, but still deterministically. HAProxy ships this algorithm; Vimeo uses it for streaming load balancing.

7. Alternatives you should know

Rendezvous (Highest-Random-Weight / HRW) hashing: for each key, compute a weight hash(key, node_i) for every node and pick the max. No ring, no vnodes; adding a node still moves only K/N keys. Simpler code, ~O(N) per lookup (fine for small N or with caching). Used in some CDNs and Kafka clients. Google Maglev uses a lookup table generated by a deterministic permutation; O(1) lookup, memory scales with entries but fantastic for high-QPS load balancers. Jump consistent hash (Google, 2014) is a two-line algorithm that assigns a bucket in O(log N) with zero memory — great when nodes are numbered sequentially but doesn't support arbitrary node identities.

8. Membership and gossip

The ring only works if every client agrees on who's on it. In small deployments this comes from a config service (Zookeeper, Consul, etcd). In large peer-to-peer systems (Cassandra, DynamoDB internal, Riak) it comes from a gossip protocol: each node periodically exchanges its view of the cluster with a random peer, converging to a consistent view in O(log N) rounds. During transitions, brief inconsistency is expected and requests may be handed off ("hinted handoff").

💻 C# implementation — a ring with virtual nodes

Below is a compact, production-shaped implementation. It supports adding/removing nodes with different weights, and the lookup is a binary search over a SortedDictionary (backed by a red-black tree). This is essentially the algorithm Cassandra clients ship with — swap in Murmur3 or xxHash for real workloads.

using System;
using System.Collections.Generic;
using System.Linq;
using System.Security.Cryptography;
using System.Text;

public class ConsistentHash<TNode> where TNode : IEquatable<TNode>
{
    // Sorted map: ring position -> owning node. Red-black tree under the hood
    // so ceiling() and add/remove are O(log N).
    private readonly SortedDictionary<uint, TNode> _ring = new();

    private readonly int _defaultReplicas;

    public ConsistentHash(int defaultReplicas = 150) => _defaultReplicas = defaultReplicas;

    // Non-crypto hash is faster and just as uniform for load balancing.
    // Using MD5 here for portability; swap to Murmur3/xxHash in production.
    private static uint Hash(string s)
    {
        using var md5 = MD5.Create();
        byte[] b = md5.ComputeHash(Encoding.UTF8.GetBytes(s));
        return BitConverter.ToUInt32(b, 0);
    }

    // Add a physical node with `replicas` virtual positions on the ring.
    // Higher-capacity nodes → pass a larger `replicas` value.
    public void AddNode(TNode node, int? replicas = null)
    {
        int r = replicas ?? _defaultReplicas;
        for (int i = 0; i < r; i++)
        {
            uint pos = Hash($"{node}-vnode-{i}");
            _ring[pos] = node;
        }
    }

    // Removing a node deletes every vnode owned by it; keys in those arcs
    // slide to the next clockwise vnode automatically.
    public void RemoveNode(TNode node, int? replicas = null)
    {
        int r = replicas ?? _defaultReplicas;
        for (int i = 0; i < r; i++)
        {
            uint pos = Hash($"{node}-vnode-{i}");
            _ring.Remove(pos);
        }
    }

    // Lookup: hash key, find smallest ring position >= hash, wrap to first if none.
    public TNode GetNode(string key)
    {
        if (_ring.Count == 0) throw new InvalidOperationException("empty ring");
        uint h = Hash(key);

        // Binary search for the ceiling. SortedDictionary doesn't expose one
        // directly, so we do a LINQ FirstOrDefault; a real impl uses SortedList
        // with a BinarySearch for true O(log N).
        foreach (var kv in _ring)
            if (kv.Key >= h) return kv.Value;

        return _ring.First().Value;   // wrap around
    }

    // Replication factor: return R distinct physical nodes starting at
    // GetNode(key), walking clockwise. Skip duplicates (multiple vnodes of same node).
    public List<TNode> GetNodes(string key, int replicationFactor)
    {
        var results = new List<TNode>();
        var seen    = new HashSet<TNode>();
        uint h = Hash(key);

        // One full sweep at most.
        var ordered = _ring.SkipWhile(kv => kv.Key < h)
                            .Concat(_ring.TakeWhile(kv => kv.Key < h));
        foreach (var kv in ordered)
        {
            if (seen.Add(kv.Value))
            {
                results.Add(kv.Value);
                if (results.Count == replicationFactor) return results;
            }
        }
        return results;
    }
}

In Go, this is the groupcache package; in Java, it's Guava HashFunction.consistentHash and Cassandra's Murmur3Partitioner; in Python, the uhashring library.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Uneven load without virtual nodes

With one position per node and only a handful of nodes, load can be catastrophically lopsided — the standard deviation of arc size is O(1/√N). Mitigate with V vnodes per physical node; V ≈ 100–500 keeps load within ~2–5% of the mean.

Hot keys still overload one node

Consistent hashing balances the keyspace, not the traffic. A single trending key (a celebrity, a hot Kafka partition) still hits one owner. Fix: bounded-load consistent hashing, request coalescing, or an L1 in-process cache in front of the shard.

Client memory and ring rebuild cost

Each client holds the whole ring: N × V entries × ~30 bytes each. At 100 nodes × 500 vnodes = 50k entries ≈ 1.5 MB — trivial. Rebuilding on membership change is O(N·V·log(N·V)) but happens rarely (seconds-scale events).

State movement dominates the win

For a stateless cache, adding a node is instantaneous — the new node just starts filling from misses. For a stateful store (Cassandra, DynamoDB storage nodes), the arc-transfer step involves streaming gigabytes across the network before the new node can serve reads. Bandwidth, not the algorithm, is the bottleneck.

Likely interview follow-ups

Q: Why is hash(key) % N bad?

A: Because it moves ~(N−1)/N of keys when N changes — for N=10 that's 90% cache invalidation. Consistent hashing moves only ~1/N.

Q: How do virtual nodes actually help?

A: They smooth arc-size variance. With V vnodes per node, standard deviation of load per physical node drops from O(1/√N) to roughly O(1/√(N·V)). V=100–500 gives 2–5% deviation.

Q: How would you replicate a key R times?

A: Starting from the key's primary owner, walk clockwise and collect the next R−1 distinct physical nodes (skipping additional vnodes of already-picked nodes). This is exactly Cassandra's SimpleStrategy. Rack-aware placement adds "skip if same rack" logic.

Q: What if a hot key overwhelms one node?

A: Vanilla consistent hashing won't help. Options: (1) bounded-load consistent hashing (Google, 2016) — if a node is over quota, forward to next clockwise; (2) client-side L1 cache; (3) key salting (split "trending-video-123" into ":shard-0", ":shard-1", ...); (4) request coalescing at the shard.

Q: Consistent hashing vs Rendezvous vs Jump hash — when to use each?

A: Ring is the industry standard, supports weights and replication trivially. Rendezvous (HRW) is simpler code, O(N) per lookup, great for small N. Jump hash is zero-memory and blazing fast but only works when nodes are numbered 0..N-1 and you don't need arbitrary node ids (bad for dynamic membership).

Q: What hash function should we use?

A: For load balancing, use a fast non-cryptographic hash: Murmur3 or xxHash. Avoid SHA-1/MD5 unless you already depend on them — they're 5–10× slower and cryptographic strength is unnecessary here.

🗣️ Interview cheat sheet

30-second pitch: "Consistent hashing maps both keys and servers onto a ring. A key is served by the next server clockwise. When a server is added or removed, only that server's arc — roughly K/N keys — is reassigned. Virtual nodes fix load imbalance. It's what makes cache tiers, DynamoDB partitions, Cassandra rings, and sticky load balancers scale gracefully."

Numbers to quote

  • Naïve modulo hashing moves ~(N−1)/N of keys on any change; consistent hashing moves ~1/N.
  • Virtual nodes per physical node: typical 100–500; load variance drops to 2–5 %.
  • Lookup complexity: O(log N·V) per key, ring memory ~30 bytes × N·V.
