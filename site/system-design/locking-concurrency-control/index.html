Locking & Concurrency Control in Distributed Systems

A field guide for choosing between optimistic, pessimistic, row-level, distributed, atomic-update, and versioning strategies — with the real-world scenarios that make each one the right answer, and the interview traps that make them the wrong one.

🎯 The problem

Two things want to change the same thing at the same time

Every real system eventually hits the same shape of bug: two requests arrive concurrently, both read the same value, both make an independent decision, and both write. The second write silently overwrites the first — money vanishes, inventory goes negative, five copies of a "daily report" email land in the customer's inbox, or a table row shows a state that neither user actually asked for. This is the concurrency problem, and it doesn't care whether you have one server, five servers, or five hundred.

The concurrency literature offers a small toolbox: optimistic locking (let everyone work, verify before saving), pessimistic locking (lock the resource before touching it), row-level database locks, distributed locks across servers via Redis or ZooKeeper, advisory locks for cross-transaction coordination, atomic database operations that dodge locking altogether, and versioning / compare-and-swap / ETag patterns for stateless APIs. Each is right somewhere. Each is disastrous somewhere else.

This page is the map. Every mechanism is explained the same way: what problem it solves, its mental model, an architecture diagram, one crisp production scenario, and where it fails. Then a decision matrix and a decision tree bring it all back together. The goal is not to be able to say what optimistic locking is — it is to look at a new problem and instantly answer "which mechanism, why, and what fails if we pick wrong?".

🧑‍🎓 In laymen terms

Five ways to share one whiteboard

Imagine a whiteboard in a shared office. Ten people occasionally walk up, read what's there, erase some part, and write something new. If two of them arrive at once, one person's changes disappear. How do we prevent that?

Pessimistic locking is the most obvious answer — put a padlock on the whiteboard. Whoever arrives first turns the key, does their edit, then unlocks. Everyone else stands in a queue. Nothing gets lost, but the queue can be slow and if the first person faints while holding the key, nobody moves.

Optimistic locking is more relaxed. Everyone photocopies the whiteboard, walks off to their desk, edits their copy in peace, then comes back. Before they write anything on the real board, they check: "is the board still exactly the way it was when I photocopied?" If yes, they write. If someone else has edited it in the meantime, they throw their copy away, take a fresh photocopy, and redo the edit. Fast when conflicts are rare, wasteful when they aren't.

Atomic operations are cleverer still — instead of locking the whole board, you tell it: "if the current number is 1, subtract 1". The board handles the check and the write in one indivisible motion. No lock. No photocopy. This is what a good database engine does on your behalf when you write UPDATE stock SET qty = qty - 1 WHERE qty > 0.

Distributed locks are for when the whiteboard is on a different floor and multiple offices want to edit it. Now you need one shared padlock that every office can see — usually a Redis key. Whoever writes their name on the padlock first owns it for a while.

Versioning / ETag is the postal-mail version of optimistic locking. Every version of the board is stamped with a number. When you mail in your edit, you also mail in the version you were editing. The board only applies your edit if that version is still the latest.

Every real product uses several of these together. Gmail's drafts are optimistic (last-save-wins, with conflict UI). Payment systems are pessimistic on money rows. Instagram inventory decrements are atomic. Kubernetes scheduling is distributed-lock territory. The trick is not knowing what each does — it's knowing which to reach for.

Two rules of thumb before we dive in. First, reach for an atomic DB operation first — the fewer explicit locks in your design, the fewer failure modes. Second, distributed locks are a coordination tool, not a correctness tool — always pair them with an idempotency ledger if the outcome must be exactly-once.

🏗️ Big picture

Where each mechanism sits in a real stack

The two "sides" of concurrency control are the data layer (where the resource actually lives) and the application layer (where the caller decides how to touch it). Locks can live on either side; usually the answer is the one closer to the resource.

The picture makes one thing obvious. Row-level, atomic, versioning, and advisory locks all live inside the database — they are natural, transactional, and safe. Distributed locks live outside the database in Redis / etcd / ZooKeeper — they exist precisely because the database cannot help coordinate work between servers that aren't touching the DB (like "only one pod runs the nightly job"). ETag is optimistic locking translated to HTTP. Pick the layer closest to where the actual conflict happens.

🔍 Every mechanism — concept, architecture, and one scenario

1. Optimistic locking — "let everyone work, verify before saving"

Concept. Nobody blocks. Two users can open the same row and edit it side-by-side. When one of them clicks Save, the server checks whether the row is still the way it was when they opened it. If yes, save. If not, the save is rejected and the user reloads. Called optimistic because it assumes conflicts are rare and does not pay any locking cost upfront.

Scenario — two edits to the same customer row. User A opens Customer 1001 and changes the phone. User B opens the same row and changes the address. Both saved rows started as Version = 10. The application issues:

-- Optimistic UPDATE embeds the previously-read version
UPDATE Customer
SET    Address = 'Mumbai',
       Version = 11
WHERE  CustomerId = 1001
  AND  Version    = 10;

The first request lands. RowsAffected = 1. The second lands moments later — the row is now Version 11, so the WHERE clause matches nothing. RowsAffected = 0. The app returns a 409 Conflict; the client reloads and re-applies. No locks were held during editing, so a user could take three hours in the form and not block anyone.

2. Pessimistic locking — "lock, then modify"

Concept. Before I read the row, I claim it. Anyone else who tries to read it with intent-to-write must wait. Guarantees no conflict but at the cost of throughput. Called pessimistic because it assumes conflicts are common and pays the coordination cost upfront.

Scenario — the last hospital appointment slot. One slot remains at 10 AM. Two receptionists on two servers both click "Book". Server A begins a transaction and issues SELECT … FOR UPDATE, which places a row lock. Server B issues the same statement moments later — its request queues inside the DB until Server A commits.

Server A DB row: appointment 123 │ │ │ BEGIN │ │ SELECT * FROM Appointment │ WHERE Id = 123 FOR UPDATE ────────▶ lock granted │ (verify slot available) │ │ UPDATE Appointment SET userId = A │ │ COMMIT │ │ ────────────────────────────────────▶ lock released │ │ Server B │ │ BEGIN │ │ SELECT * FROM Appointment │ WHERE Id = 123 FOR UPDATE ────────▶ WAIT for A │ │ │ ← Server A commits ← │ │ ────────────────────────────────────▶ lock granted, sees userId=A │ (slot no longer available) │ │ ROLLBACK │

Syntax differs by engine:

-- Postgres / MySQL
SELECT * FROM Appointment WHERE Id = 123 FOR UPDATE;

-- SQL Server
SELECT * FROM Appointment WITH (UPDLOCK, ROWLOCK) WHERE Id = 123;

-- Oracle
SELECT * FROM Appointment WHERE Id = 123 FOR UPDATE;

Rules. Hold the lock as briefly as possible — a transaction that lingers on a hot row destroys throughput. Never call external services (SMTP, payment gateway, HTTP APIs) while holding a row lock. Match lock ordering across code paths to avoid deadlocks.

3. Database row-level locking — pessimistic, done right

Row-level locking is the granular form of pessimistic locking. Modern engines (Postgres, MySQL InnoDB, SQL Server) default to per-row locks rather than table locks, so contention only happens on the exact rows being modified. Lock escalation (row → page → table) is the pathological failure mode when too many rows are locked in one transaction — beware bulk updates without a batching strategy.

4. Atomic database operations — the "no lock at all" option

Concept. Express both the check and the write in one SQL statement, and let the engine handle the concurrency. This is the cheapest correct answer for inventory decrement, account debit, quota consumption — any pattern shaped as "if the value satisfies X, change it".

-- Inventory decrement — DB engine serialises writes to the same row
UPDATE Inventory
SET    Quantity = Quantity - 1
WHERE  ProductId = 101
  AND  Quantity  > 0;

-- rowsAffected = 1  →  purchase allowed
-- rowsAffected = 0  →  out of stock — reject purchase

Why prefer this over pessimistic locks? No lock is explicitly held by application code; the DB acquires and releases a very short internal lock on the affected row for the duration of one UPDATE. Application timeouts, client crashes, and GC pauses cannot leave a lock behind. Common atomic idioms:

  • Conditional increment/decrement — inventory, credits, seats.
  • Insert-if-not-exists — INSERT … ON CONFLICT DO NOTHING (Postgres) or a UNIQUE constraint. Great for idempotency ledgers.
  • Conditional update on state — UPDATE order SET status='PAID' WHERE id=@id AND status='PENDING'. State-machine transitions.
  • DynamoDB conditional writes — ConditionExpression: attribute_not_exists(pk) or ConditionExpression: version = :v.

5. Distributed locking — coordinate work across servers

Concept. Sometimes the resource you want to protect is not a database row — it's an action. "Only one of our five pods runs the nightly report." "Only one process rebuilds the cache." Row locks and atomic updates cannot help because the resource is a job, not a row. A distributed lock is a shared coordination primitive — a Redis key, an etcd lease, a ZooKeeper ephemeral znode — that only one caller across the whole cluster can own at a time.

Scenario — five app servers, one nightly report. All five have the same code and the same cron. At 00:00 each server races to Redis with:

# One atomic write. NX = only if not exists. PX = expire in 30 s.
SET daily-report-lock <unique-token> NX PX 30000

Redis awards the lock to exactly one caller and returns OK; the others receive nil and skip. The winner runs the job, then releases the lock atomically:

-- Safe release: DEL only if the stored token still equals mine.
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

Every option matters:

  • SET — the write. Redis is single-threaded, so evaluation of NX + write is one indivisible step.
  • NX — "only if the key does not exist" — this is the mutual-exclusion primitive.
  • PX 30000 — lease expiration in milliseconds. A crashed owner cannot hold the lock forever.
  • <unique-token> — a 128-bit random value identifying this specific execution. Not the hostname.

6. Why the unique token is not optional

Consider the timeline where Server A's job overruns:

t=0 A acquires lock (token=A-uuid, TTL=30s) t=30 Redis TTL expires → lock auto-deleted t=30 B acquires the same key (token=B-uuid) t=40 A finishes its work t=40 A calls DEL daily-report-lock ⚠ would erase B's lock!

Solution: A releases only if the stored value equals its own token. But even a client-side GET-then-DEL is unsafe — another owner can intervene between the two commands. Redis's Lua execution is atomic on the single-threaded event loop, so the GET+DEL+comparison happen indivisibly. That is why the release is a Lua script, not two client calls.

7. Lock renewal — the watchdog

If the job may take longer than the TTL, run a background thread that renews the lease every TTL/3 seconds, but only if the token still matches:

-- Compare-and-renew
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
    return 0
end

With TTL = 30 s and renewal every 10 s, you tolerate two consecutive missed ticks (network blip, brief Redis slowness) before losing the lock. If renewal fails, the owner must treat the lock as lost and abort the job — do not "keep going and hope". This is precisely what Redisson's watchdog does. See our companion page for the full nightly-job walkthrough.

Failure modes to alert on: network partition (renewal fails), application pause (GC / stop-the-world) longer than the TTL, Redis primary failure with async replication lag, and process crash between "did the work" and "wrote the completion row". Distributed locking is genuinely harder than DB locking — combine with an idempotency ledger if you need exactly-once outcomes.

8. Database advisory locks — named locks inside your DB

Concept. Postgres and SQL Server expose application-defined named locks: your app calls pg_advisory_lock('nightly-report'::hashtext) and the DB serialises all callers who ask for the same name. Great for coordinating actions inside a single DB deployment when the "resource" isn't a specific row.

-- Postgres — session-scoped advisory lock
SELECT pg_advisory_lock(hashtext('nightly-report'));
-- do the work
SELECT pg_advisory_unlock(hashtext('nightly-report'));

-- Postgres — transaction-scoped variant (auto-releases at commit)
SELECT pg_advisory_xact_lock(hashtext('nightly-report'));

-- SQL Server
EXEC sp_getapplock @Resource = 'nightly-report', @LockMode = 'Exclusive';
-- work
EXEC sp_releaseapplock @Resource = 'nightly-report';

Best for: lightweight cross-transaction coordination in a single-DB deployment. Less operational overhead than adding Redis just for this. Not great for: multi-service coordination where the DB isn't the common denominator (use Redis / etcd) or when the DB itself is the bottleneck.

9. Compare-and-Swap · RowVersion · ETag — optimistic in three costumes

The same idea shows up under different names depending on the layer:

LayerNameWire form

Application ↔ SQL ServerRowVersion / rowversionAuto-incremented per row; used same way
Application ↔ DynamoDBConditional writesConditionExpression: version = :old

ETag in REST — the wire trace. A first-class citizen of HTTP:

GET /customers/1001                        HTTP/1.1
<-- 200 OK
    ETag: "v15"
    { "id": 1001, "address": "Bangalore", "phone": "…" }

PUT /customers/1001                        HTTP/1.1
    If-Match: "v15"
    { "address": "Mumbai" }
<-- 200 OK              if the resource is still v15
    ETag: "v16"

<-- 412 Precondition Failed
    if some other client updated it to v16 in the meantime

Conceptually identical to WHERE Version = 15 — expressed at the HTTP layer so a stateless client can participate in the concurrency control.

🎬 Full production scenarios — what to actually build

Payment flow — never hold a lock across a slow external call

An order service reserves inventory, then calls a payment gateway. The gateway takes 5–20 seconds on the slow path. The wrong design holds a database row lock the whole time:

BAD: BEGIN TX SELECT … FROM Inventory WHERE product = 42 FOR UPDATE ← lock held qty -= 1 call Stripe /charges (takes 10 s) ← still holding lock if success then commit else rollback COMMIT

Ten seconds of held lock across the entire product's peak traffic will melt the DB. The fix is a reservation state machine — commit the "reserved" state to the DB (releasing the lock), call the gateway, then transition state:

GOOD: BEGIN TX UPDATE Inventory SET qty = qty - 1 WHERE product = 42 AND qty > 0 ← atomic INSERT INTO Reservation (order_id, product, expires_at) … COMMIT ← lock released call Stripe /charges (async, off-lock) if paid: BEGIN TX UPDATE Order SET status='PAID' WHERE id=? AND status='RESERVED' UPDATE Reservation SET status='CONFIRMED' … COMMIT else: ← payment failed / timed out BEGIN TX UPDATE Inventory SET qty = qty + 1 WHERE product = 42 UPDATE Reservation SET status='RELEASED' … COMMIT

State transitions: Available → Reserved → Payment Pending → Paid → Confirmed, with the escape hatch Reserved → Payment Failed → Reservation Released. Every transition is an atomic conditional UPDATE. This pattern is what powers real-world checkout at Amazon, Shopify, Bookmyshow, etc. Combine with a Saga if the workflow crosses microservices.

REST document editing — ETag is the whole answer

Two editors open PUT /docs/42. Server returns ETag: "v9". Both edit locally. Editor A saves first; server responds 200, ETag now "v10". Editor B saves; server compares If-Match: "v9" against current "v10", returns 412. Client reloads, offers a diff/merge to the user. No server-side lock, no timeouts, works across mobile clients on slow networks.

Kubernetes: exactly-one leader across pods

Not a DB row problem, so Redis / etcd is the right layer. Kubernetes itself uses etcd leader election for the controller manager, scheduler, and every operator that must be a singleton. Applications typically use a Redis lock or a lease object. Same "unique-token + TTL + safe release" pattern applies.

Deadlock — the classical picture

Transaction A Transaction B │ │ Lock Row 1 Lock Row 2 │ │ Wait for Row 2 ←──── Wait for Row 1 A owns Row1 ─────► wants Row2 ▲ │ ← DB deadlock detector aborts one │ transaction; the other proceeds B owns Row2 ─────► wants Row1

Prevention. Always acquire multi-row locks in a consistent order (e.g. by primary key ascending). Prefer atomic single-row updates when possible. Keep transactions short so the window for cycles is small. Alert on deadlock rate; a spike almost always indicates a bug in lock ordering or a missing index that turned a "row lock" into a "scan + range lock".

The correct question is not "which lock?" but "does this need a lock at all?". Atomic updates, unique constraints, idempotency keys, message queues, state machines, and Sagas replace locks in more scenarios than most engineers realise.

🪤 Common system-design interview traps

"I'll use a Redis distributed lock for every concurrency problem."

This is the biggest tell of an inexperienced answer. Redis locks are a coordination primitive for actions that span servers — nightly jobs, cache warmup, singleton runners. For single-row concurrency, an atomic UPDATE or a short pessimistic row lock is safer, simpler, and doesn't add a coordination service to the failure surface.

"I'll hold a database lock while calling the payment gateway."

This will melt production. External calls take seconds; row locks take microseconds. Never combine them. Use a reservation state machine — commit the "reserved" state, release the lock, then call the gateway, then transition state.

"I'll set the Redis TTL to 10 minutes to be safe."

A long TTL means a crashed owner wedges the system for 10 minutes before recovery. Set the TTL just longer than expected work + one renewal cycle. Use a watchdog to renew rather than a giant fixed TTL.

"I'll just call DEL when done."

Not without ownership validation. If your work overran the TTL, the lock now belongs to someone else, and your DEL just released their lock. Always use the Lua compare-and-DEL script.

"A distributed lock gives me exactly-once processing."

It does not. If you acquire the lock, send an email, then crash before writing "done", the next run acquires and re-sends. Locks prevent concurrent execution; idempotency ledgers prevent duplicate outcome. Use both.

"I read the row, then update it — that's enough."

Classical lost update. In-between your read and your write, someone else has done the same. Move to an atomic UPDATE with a predicate, or add a Version column for optimistic locking.

"I'll just use SERIALIZABLE isolation everywhere."

You just made the DB single-threaded on any dataset the two transactions touch. Retry storms and abort rates will spike. Match isolation level to the specific data conflict, not the app globally.

"HttpOnly cookies prevent all attacks, so we don't need CSRF tokens."

(For completeness — not a locking trap, but often asked together.) HttpOnly prevents JS from reading the cookie. CSRF uses the browser's auto-attach behaviour, which HttpOnly doesn't affect. Different problem, different control.

"Distributed lock in Redis is safe even during failover."

Redis replication is asynchronous. A lock written on the primary that isn't yet on the replica can be lost after failover — briefly, two owners can hold the same lock. For correctness-critical workloads use etcd / ZooKeeper (Raft / ZAB consensus) or add a fencing token that the resource itself enforces.

💻 C# reference — every mechanism in one file

// -----------------------------------------------------------------------
// 1. Optimistic locking — Dapper / EF Core with a Version column
// -----------------------------------------------------------------------
public async Task<bool> UpdateCustomerAsync(Customer c)
{
    const string sql = @"
        UPDATE Customer
        SET    Address = @Address, Phone = @Phone, Version = Version + 1
        WHERE  CustomerId = @Id AND Version = @Version";
    var affected = await _db.ExecuteAsync(sql, c);
    return affected == 1;   // false → tell the caller to reload and retry
}

// -----------------------------------------------------------------------
// 2. Pessimistic locking — SELECT … FOR UPDATE inside a transaction
// -----------------------------------------------------------------------
public async Task ReserveAppointmentAsync(Guid apptId, Guid userId)
{
    using var tx = _db.BeginTransaction(IsolationLevel.ReadCommitted);
    var row = await _db.QuerySingleAsync<Appointment>(
        "SELECT * FROM Appointment WHERE Id=@id FOR UPDATE",
        new { id = apptId }, tx);
    if (row.UserId is not null) { tx.Rollback(); throw new ConflictException(); }
    await _db.ExecuteAsync(
        "UPDATE Appointment SET UserId=@u WHERE Id=@id",
        new { u = userId, id = apptId }, tx);
    tx.Commit();
}

// -----------------------------------------------------------------------
// 3. Atomic UPDATE — the recommended default for inventory / counters
// -----------------------------------------------------------------------
public async Task<bool> TryDecrementStockAsync(int productId)
{
    const string sql = @"
        UPDATE Inventory SET Quantity = Quantity - 1
        WHERE ProductId = @pid AND Quantity > 0";
    return (await _db.ExecuteAsync(sql, new { pid = productId })) == 1;
}

// -----------------------------------------------------------------------
// 4. Redis distributed lock — SET NX PX + Lua safe release
// -----------------------------------------------------------------------
public async Task<string?> TryAcquireAsync(string key, TimeSpan ttl)
{
    var token = Guid.NewGuid().ToString("N");
    bool ok = await _redis.StringSetAsync(
        key, token, expiry: ttl, when: When.NotExists);
    return ok ? token : null;
}
public Task ReleaseAsync(string key, string token) =>
    _redis.ScriptEvaluateAsync(
        @"if redis.call('GET', KEYS[1]) == ARGV[1] then
             return redis.call('DEL', KEYS[1])
          else return 0 end",
        new[] { (RedisKey)key },
        new RedisValue[] { token });

// -----------------------------------------------------------------------
// 5. HTTP ETag — ASP.NET Core minimal-API endpoint
// -----------------------------------------------------------------------
app.MapPut("/customers/{id}", async (int id, HttpRequest req, CustomerRepo repo) =>
{
    var current = await repo.GetAsync(id);
    var incoming = req.Headers.IfMatch.ToString().Trim('"');
    if (incoming != $"v{current.Version}")
        return Results.StatusCode(412);   // Precondition Failed

    var updated = await req.ReadFromJsonAsync<Customer>();
    var saved   = await repo.SaveWithOptimisticLockAsync(updated!, current.Version);
    return saved
        ? Results.Ok().WithHeader("ETag", $"\"v{current.Version + 1}\"")
        : Results.StatusCode(412);
});

// -----------------------------------------------------------------------
// 6. Postgres advisory lock — one-liner via Dapper
// -----------------------------------------------------------------------
await _db.ExecuteAsync("SELECT pg_advisory_xact_lock(hashtext(@name))", new { name = "nightly-report" });
// … work inside the same transaction; lock releases at commit

Six mechanisms, one file. The point is not the specific library — it's that each mechanism collapses to a few lines when you pick the right one, and to hundreds of lines of retry logic and bug reports when you pick the wrong one.

🗣️ Final mental model — the decision tree you memorize

Multiple requests modifying the same thing? │ ▼ Can the operation be expressed as a single atomic DB query? │ │ Yes No │ │ Atomic UPDATE ▼ Conflicts rare? │ │ Yes No │ │ Optimistic Need short exclusive access? (Version / │ ETag) ▼ Pessimistic (FOR UPDATE) Different servers must coordinate a job / action? │ ▼ Distributed lock (Redis / etcd) + idempotency ledger Long-running business workflow with external calls? │ ▼ State machine / Saga — do NOT hold locks Duplicate request retries from clients? │ ▼ Idempotency key — no lock needed

Say this in the interview. "I default to an atomic UPDATE when the operation can be expressed as a single predicate — inventory, counters, state transitions. When the conflict window is longer than a query, I use optimistic locking with a Version column, or ETag/If-Match if the concurrency crosses HTTP. Pessimistic FOR UPDATE is reserved for genuinely scarce rows where the critical section is short and inside one transaction. Distributed locks come out only when the resource isn't a DB row — nightly jobs, singletons, cache warmup — and I always pair them with an idempotency ledger because a lock alone does not give exactly-once. And I never hold a lock across an external call — that's what reservation state machines and Sagas are for."

The 5 lines that win the round

  • "Atomic UPDATE first, lock only if you can't."
  • "Optimistic when conflicts are rare, pessimistic when they aren't."
  • "Distributed lock is for actions across servers, not rows in a DB."
  • "Lock ≠ exactly-once. Combine with idempotency."
  • "Never hold any lock across a network call to a third party."
