🎯 Why it matters

Why an interviewer asks about networking

Every distributed system runs on top of these seven ideas. When a senior interviewer asks you to design a chat app or a payments API, they're really asking two things: "do you know how packets actually travel between hosts?" and "can you turn a vague failure like 'the site is slow' into a precise fix?". Someone who knows the OSI model, IP, TCP vs UDP, HTTP/HTTPS, DNS, checksums, and proxies can point at exactly the layer that broke and justify why they chose a Layer-4 network load balancer over a Layer-7 application load balancer.

You see all seven in every real product you use. WhatsApp picks UDP-based QUIC for calls and TCP for message delivery. Cloudflare is a reverse proxy at the edge that also does DNS resolution and TLS termination. Netflix uses DNS latency-based routing to steer you to the closest CDN edge. Amazon.com is fronted by an Application Load Balancer (a Layer-7 reverse proxy) that inspects HTTP hostnames and cookies. Zoom gracefully degrades from UDP to TCP if a firewall blocks UDP. Even GitHub's git clone is HTTPS over TCP with SHA-1 checksums (moving to SHA-256) verifying every object it downloads.

In an interview these show up as follow-up ambush questions: "why does DNS use UDP?", "what does a 502 versus 504 mean?", "how would you migrate from HTTP/2 to HTTP/3?", "would you put your API behind an NLB or an ALB?", "how would you protect a webhook against tampering?". Answering any one crisply demonstrates that you actually understand the wire — not just the diagram on the whiteboard.

🧑‍🎓 In laymen terms — for a beginner

The internet as a postal system

Imagine the internet as a giant postal system that delivers letters between phones and computers. To send anything — a photo, a message, a video call — the postal service has to solve seven separate problems, and every one of the topics on this page is one of those problems.

First, the mail has to physically travel — a truck on a road, a plane in the air, or a signal on a wire (this is the physical and data-link layer). Then each house needs a unique address so the mail can find it — that's your IP address, like a house number. But you don't remember house numbers for your friends; you remember their names. So there's a giant phonebook that translates "whatsapp.com" into an actual address — that phonebook is DNS.

Once you know the address, you have to decide how careful the delivery should be. If you're sending a legal contract, you want a courier who guarantees delivery, has a signature on arrival, and re-sends anything lost — that's TCP. If you're sending a live news reporter's video feed, and losing one frame is fine because a new one will arrive in a fraction of a second, you send it by UDP — no signatures, no retries, just fast.

The letter itself — the shape of the request and answer — is written in a shared language called HTTP. When you want the letter to be secret, you put it inside a sealed, tamper-proof envelope — that's HTTPS. Every envelope has a small tamper-check sticker on it — if the sticker looks scratched, the receiver throws the letter out. That sticker is a checksum.

Finally, big companies don't want everyone knocking on their front door. They put a receptionist at the entrance who talks to visitors, checks their ID, hands out cached answers, and forwards real work to the right desk inside. That receptionist is a reverse proxy. On the other side, a company might also put a security guard between its own employees and the outside world — the guard is a forward proxy. Same job, different sides of the door.

Tiny example: You open Instagram. Your phone asks the phonebook "what's instagram.com's address?" (DNS). It gets back an address, calls that address, uses HTTPS to secure the call, uses TCP so nothing is lost, and hits a Cloudflare receptionist (reverse proxy) that says "I already have your feed cached — here you go" without ever bothering Instagram's actual servers. All that happened in about 200 milliseconds.

🔍 Component deep-dive — all 7 topics

1. OSI Model — the seven-layer diagnostic tool

The OSI model isn't a protocol; it's a diagnostic vocabulary. When production says "the network is broken", OSI turns it into a specific accusation: "the client got a TCP RST from the LB, so it's a Layer-4 problem", or "the TLS handshake fails with unknown_ca, so it's a Layer-6 issue". Real systems implement the tighter 4-layer TCP/IP model, but interviewers ask about the 7-layer OSI because its finer granularity makes it easier to point at exactly what broke.

Memorize the mnemonic "Please Do Not Throw Sausage Pizza Away" — Physical, Data-Link, Network, Transport, Session, Presentation, Application. When you're picking infrastructure, the key question is which layer does this thing operate at? An AWS Network Load Balancer is L4 (TCP-only, fast, protocol-agnostic). An AWS Application Load Balancer is L7 (understands HTTP, can route on Host / Path / cookies, can terminate TLS). A service mesh like Istio uses L4 for connection handling but adds L7 for mTLS and traffic policy.

Modern reality: layer boundaries have blurred. TLS lives ambiguously between L5 and L6. QUIC is technically L4 (transport) but bundles TLS 1.3 and reliability. gRPC is L7 but rides HTTP/2 which is also L7. Don't get stuck on where exactly a protocol lives; know why you're naming it.

2. IP Address — routing coordinates, not identity

An IP address is a location for a network interface, not an identity for a machine or a user. IPv4 uses 32 bits (~4.3 billion addresses, exhausted); IPv6 uses 128 bits with a common /64 subnet size. Real systems typically deploy dual-stack: both an A record (IPv4) and an AAAA record (IPv6) point at the same service. In cloud VPCs, the private ranges from RFC 1918 (10/8, 172.16/12, 192.168/16) are used internally, and a NAT gateway or LB is what makes the service reachable from the public internet.

CIDR (Classless Inter-Domain Routing) is how modern networks slice address space. Notation is network/prefix-length: 10.0.0.0/16 means "the first 16 bits identify the network, the last 16 bits identify hosts" — 65 536 addresses. Routers use longest prefix match: if two routes cover the same destination, the more specific one (larger prefix) wins.

NAT keeps IPv4 alive by rewriting private source IPs to a shared public IP as traffic leaves the network. It works beautifully for outbound, painfully for inbound (you need port forwarding or a load balancer). NAT is why the true client IP arrives in the X-Forwarded-For / Forwarded header rather than the TCP source field — and why rate-limiting purely by IP is dangerous: an entire CGNAT block might share one public address.

3. TCP vs UDP — the "what if data is late or missing?" question

The single best framing for TCP vs UDP is "what should the application do when data is late, lost, duplicated, or reordered?". TCP answers: "I'll hide all of that from you — you get an in-order byte stream and I retransmit whatever gets lost." UDP answers: "here's your datagram, good luck, deal with loss yourself."

TCP opens with a three-way handshake (SYN → SYN-ACK → ACK), then guarantees ordered delivery, retransmits on loss, and applies flow control (receiver window) and congestion control (sender adjusts rate). Header is 20 bytes base. Suffers from head-of-line blocking: a lost segment freezes later bytes in the buffer even if they arrived. That's why HTTP/2 didn't solve everything and HTTP/3 moved to UDP.

UDP has no handshake, no reordering, no retransmission, 8-byte header. Perfect for real-time media (a lost 20 ms of audio doesn't matter — a fresh frame is already on the way), DNS (a single query fits in one packet; if it's lost, ask again), and modern QUIC / HTTP/3.

QUIC is the plot twist: built on UDP but adds TLS 1.3, retransmission, congestion control, and multiplexed streams — all in userspace. Its killer features are 1-RTT (or 0-RTT resumption) connection setup and connection migration, so your call survives a WiFi-to-cellular switch. When an interviewer asks "TCP or UDP?", the real 2026 answer is often "QUIC — because I want TCP-like reliability without TCP head-of-line blocking".

4. HTTP / HTTPS — the application-layer contract

HTTP is a request-response protocol: method + target line, headers, optional body. It's stateless at the protocol level — every request should carry enough context to be understood on its own. Methods have two important properties: safe (no side-effect, e.g. GET, HEAD) and idempotent (calling twice = calling once, e.g. GET, PUT, DELETE). POST is neither safe nor idempotent by default, which is why retrying a POST needs an idempotency key.

Status codes matter because they define the client's next move. 2xx = success. 3xx = follow the redirect / use cache. 4xx = don't retry blindly — you did something wrong. 5xx = server is broken; safe to retry with backoff, but only if the request is idempotent. The pair 502 vs 504 is a classic interview question: 502 Bad Gateway means the reverse proxy got a broken response from upstream; 504 Gateway Timeout means the reverse proxy didn't hear back in time.

HTTPS wraps HTTP inside TLS. The TLS 1.3 handshake takes 1-RTT: ClientHello (SNI + ALPN + supported ciphers) → ServerHello + Certificate + ephemeral ECDHE key share → client verifies chain + derives keys → encrypted HTTP begins. Forward secrecy is guaranteed by ephemeral DH. TLS 1.3 also supports 0-RTT for repeat connections, but replay-vulnerable, so use only for idempotent reads.

HTTP versions: HTTP/1.1 is text-based, one request per TCP connection (or serialized with keep-alive) — a slow response blocks the connection. HTTP/2 is binary and multiplexes many streams over one TCP connection but still suffers TCP-layer head-of-line blocking. HTTP/3 runs over QUIC (UDP) with per-stream loss recovery and connection migration. HTTP/2 server push turned out to be a bad idea and is effectively deprecated.

5. DNS — the internet's phonebook

DNS translates human names into IP addresses. When you visit google.com, your OS asks a recursive resolver (your ISP's, or a public one like 8.8.8.8 or 1.1.1.1). If the resolver doesn't have a cached answer, it walks the hierarchy: root nameserver → TLD nameserver (for .com) → authoritative nameserver for google.com. The authoritative server hands back an A record (IPv4) or AAAA record (IPv6). The whole thing usually completes in tens of milliseconds because of caching.

Every DNS record has a TTL (time-to-live) telling downstream caches how long they may reuse the answer. Long TTLs are cheaper but make cutovers slow; short TTLs make cutovers fast but multiply query volume. Most production systems use 60-300 s TTLs for A records and much longer for stable records like MX or NS.

DNS's underrated superpower is traffic steering: geo-routing, latency-based routing, weighted round-robin, health-check-driven failover. AWS Route 53, Cloudflare, Akamai FastDNS all do this. Your netflix.com resolves to a completely different IP address depending on where you are — that's DNS deciding for you which CDN edge is closest.

DNS is stateless UDP by default (single-packet request/response on port 53). Large responses fall back to TCP:53. Modern deployments use DoT (DNS over TLS) or DoH (DNS over HTTPS) to hide queries from network operators. DNSSEC adds authenticity: authoritative servers sign records so resolvers can verify they weren't tampered with — but adoption is patchy.

6. Checksums — integrity, not authenticity

A checksum is a compact value computed from a block of data; you recompute it on the receiver and compare. It's how Ethernet frames, IPv4 headers, TCP segments, and UDP datagrams detect accidental corruption on the wire. IPv6 dropped the IP-layer checksum because L2 and L4 already provide integrity, and doing it once at each layer is enough.

The key distinction to volunteer: checksums catch accidents; they do not stop adversaries. A CRC-32 is fast and hardware-accelerated (CRC-32C in particular) and reliably catches burst bit-flips — perfect for a lossy WiFi link. But if an attacker modifies the payload, they can also recompute a valid CRC. So a checksum gives you integrity ("did the bytes change accidentally?"), not authenticity ("did the right person send them?").

When authenticity matters, use a cryptographic hash (SHA-256, BLAKE3) as a fingerprint (Git object IDs, container image digests), or better, an HMAC (shared-secret keyed hash — great for webhook signatures) or a digital signature (asymmetric — anyone with the public key can verify, only the private-key holder can sign — great for signed package releases). MD5 and SHA-1 should not be used where security matters.

7. Proxy vs Reverse Proxy — same box, different side of the door

The single-sentence definition: a forward proxy is on the client's side, a reverse proxy is on the server's side. Both sit between clients and servers, but they exist for opposite reasons. A forward proxy is your outbound gatekeeper — corporate egress filtering, content blocking, audit logging, or plain caching for many clients. A reverse proxy is the server's front door — one stable public endpoint that hides a farm of backends behind it.

Everything modern lives behind a reverse proxy. NGINX, HAProxy, Envoy, Caddy, Traefik for self-hosted; Cloudflare, Fastly, AWS ALB, GCP HTTPS LB, Azure App Gateway for managed. In a K8s cluster, an ingress controller is a reverse proxy. In a service mesh, every sidecar (Envoy under Istio, linkerd-proxy) is a reverse proxy for that pod. What do reverse proxies actually do? TLS termination, load balancing, routing (host/path/header), caching, compression, WAF, rate limiting, auth-token check, logging & tracing.

The other big distinction: L4 vs L7 proxies. An L4 proxy (an NLB, or NGINX in stream mode) forwards TCP/UDP bytes without opening them — fast, protocol-agnostic, works for anything. An L7 proxy (an ALB, NGINX HTTP mode) reads HTTP requests, so it can route on host name, URL path, method, header, or JWT claim. You pay for that intelligence with latency and CPU.

TLS handling has three modes: (a) TLS termination — proxy decrypts, gets full L7 visibility, re-encrypts (or not) to backend; (b) TLS pass-through — proxy forwards encrypted bytes, keeps end-to-end encryption but loses L7 features; (c) TLS re-encryption — decrypt, inspect, re-encrypt to backend — the safest common pattern. Also: when a proxy is in front, the backend sees the proxy's IP as the source. Preserve the true client identity in X-Forwarded-For and only trust that header from proxies you control.

💻 C# implementation

Three of the most testable pieces: parsing a CIDR and checking whether an IP is inside it, computing the classic TCP/IP one's-complement 16-bit checksum, and signing/verifying an outgoing webhook with an HMAC-SHA256 — exactly what production reverse proxies do to prove authenticity end-to-end.

// ---- 1) CIDR containment check ---------------------------------------
// "Is 10.0.5.42 inside 10.0.0.0/16?"  Used by IP allow-lists / NACL rules.
public static class Cidr
{
    public static bool Contains(string cidr, string ip)
    {
        var parts = cidr.Split('/');
        uint network = Ip4ToUint(parts[0]);
        int prefix   = int.Parse(parts[1]);
        uint mask    = prefix == 0 ? 0u : 0xFFFFFFFFu << (32 - prefix);
        return (Ip4ToUint(ip) & mask) == (network & mask);
    }

    private static uint Ip4ToUint(string s)
    {
        var o = s.Split('.');
        return ((uint)byte.Parse(o[0]) << 24)
             | ((uint)byte.Parse(o[1]) << 16)
             | ((uint)byte.Parse(o[2]) <<  8)
             |  (uint)byte.Parse(o[3]);
    }
}

// ---- 2) Classic TCP/IP 16-bit one's-complement checksum -------------
// Same algorithm used in IPv4 / TCP / UDP headers. Detects accidental
// bit flips, NOT tampering (no key involved).
public static class InetChecksum
{
    public static ushort Compute(ReadOnlySpan<byte> data)
    {
        uint sum = 0;
        int i = 0;
        for (; i + 1 < data.Length; i += 2)
            sum += (uint)((data[i] << 8) | data[i + 1]);
        if (i < data.Length) sum += (uint)(data[i] << 8);   // odd length pad
        while ((sum >> 16) != 0) sum = (sum & 0xFFFF) + (sum >> 16);
        return (ushort)~sum;
    }
}

// ---- 3) HMAC-SHA256 webhook signing ---------------------------------
// Reverse-proxy / API gateway signs every outgoing webhook so the
// receiver can prove it wasn't tampered with AND came from us.
using System.Security.Cryptography;
using System.Text;

public sealed class WebhookSigner
{
    private readonly byte[] _key;
    public WebhookSigner(string secret) => _key = Encoding.UTF8.GetBytes(secret);

    public string Sign(string body, long unixTs)
    {
        var payload = Encoding.UTF8.GetBytes($"{unixTs}.{body}");
        using var h = new HMACSHA256(_key);
        var mac = h.ComputeHash(payload);
        return $"t={unixTs},v1={Convert.ToHexString(mac).ToLowerInvariant()}";
    }

    public bool Verify(string body, string header, TimeSpan tolerance)
    {
        var parts = header.Split(',');
        long ts = long.Parse(parts[0][2..]);
        string given = parts[1][3..];
        if (Math.Abs(DateTimeOffset.UtcNow.ToUnixTimeSeconds() - ts)
            > tolerance.TotalSeconds) return false;                          // replay window

        using var h = new HMACSHA256(_key);
        var expected = h.ComputeHash(Encoding.UTF8.GetBytes($"{ts}.{body}"));
        return CryptographicOperations.FixedTimeEquals(          // constant-time compare
            expected, Convert.FromHexString(given));
    }
}

In production ASP.NET Core, CIDR checks are usually delegated to System.Net.IPNetwork (available in .NET 8+), the TCP checksum lives inside the kernel and you rarely compute it in userspace, and the HMAC pattern above is exactly what Stripe, GitHub, Slack, and AWS SNS use for their signed webhooks. Always constant-time-compare MACs (CryptographicOperations.FixedTimeEquals) — a naive == is a timing-side-channel bug.

⚖️ Trade-offs & likely follow-ups

Which trade-off dominates each topic

  • TCP vs UDP: reliability vs latency. TCP hides loss at the cost of head-of-line blocking; UDP exposes loss but never freezes a stream.
  • HTTP/2 vs HTTP/3: HTTP/3 wins under packet loss and network changes; HTTP/2 wins where UDP is blocked (some corporate firewalls).
  • L4 vs L7 load balancer: speed & protocol-agnosticism vs routing intelligence. NLB for gRPC/TCP passthrough, ALB for host/path routing.
  • DNS TTL length: short = agile failover, more query load; long = cheap, slow to change. 60-300 s is the modern default for A records.
  • TLS termination at edge vs backend: edge = simpler certs and better L7 features; backend = end-to-end encryption but harder cert management.
  • CRC vs cryptographic hash: speed vs tamper resistance. CRC for accidental bit-flips; SHA-256/HMAC for anything an attacker might touch.

Common interviewer follow-ups

"Why does DNS use UDP instead of TCP?"
A typical DNS query and response each fit in one packet (~50–100 bytes), so the ~1 RTT TCP handshake would be pure overhead. UDP is 8-byte header and connectionless — if a query is lost, the resolver just asks again. DNS falls back to TCP when the response is larger than 512 bytes (zone transfers, DNSSEC-signed records).
"What's the difference between 502 and 504?"
Both come from a reverse proxy. 502 Bad Gateway = the proxy contacted the upstream and got a broken/invalid response back (e.g., connection reset, malformed HTTP). 504 Gateway Timeout = the proxy contacted the upstream and never heard back within the timeout. The debugging move is opposite: 502 → check upstream logs / crash; 504 → check upstream load / slow downstream / bad timeout config.
"Would you use an NLB or an ALB for your service?"
NLB (L4) when I want minimum latency, protocol-agnostic passthrough, preserved source IP, or when running non-HTTP protocols like raw TCP, gRPC-over-h2c, or MQTT. ALB (L7) when I need host- or path-based routing, cookie stickiness, WAF, or TLS termination with modern cipher suites. In a modern web service the answer is usually "CloudFront in front of ALB in front of ECS" — you get edge caching plus L7 routing plus health checks.
"How would you prevent tampering on a webhook?"
HMAC-SHA256 the payload with a shared secret, put the tag plus a timestamp in a header, and validate on the receiver with a constant-time compare and a small replay window (say 5 minutes). Never rely on the checksum alone — a plain checksum has no key, so an attacker can recompute it after modifying the payload.
"You have a service that sees traffic drop after a deployment even though the app is fine. First guess?"
Something in the path is misclassifying traffic. Walk the stack: L3 — did the security group / NACL change? L4 — is the LB target-group health check failing on the new pods (wrong port / path / expected status)? L6 — did TLS cert renew but a client bundle now rejects it? L7 — did the ingress route on Host header stop matching? The OSI model is the checklist.
"Client IP shows up as the load balancer's IP in the backend logs — why?"
The reverse proxy terminated the client TCP connection and opened a new one to the backend, so the backend sees the proxy's IP. The true client IP is forwarded in the X-Forwarded-For header (or Forwarded, or via Proxy Protocol at L4). Only trust that header from proxies you control — anyone can send it.

Ninety percent of prod incidents live at L3, L4, or L7 — naming the layer is half the fix."

  • TCP vs UDP: "what should the app do when data is late or lost?" — TCP hides it, UDP exposes it. QUIC (UDP + TLS + reliability) is the modern default.
  • HTTP methods: GET/HEAD safe & idempotent; PUT/DELETE idempotent; POST is neither → needs idempotency keys.
  • Status codes: 2xx OK, 3xx redirect, 4xx you broke it, 5xx we broke it. 502 = broken upstream response, 504 = upstream timeout.
  • DNS: UDP:53, TTL controls agility vs load. Route 53 does latency-based / geo / weighted / failover routing.
  • CIDR: 10.0.0.0/16 = 65k addresses, prefix bits identify the network. Routers use longest prefix match.
  • Checksums: integrity ≠ authenticity. CRC / TCP checksum catches accidents. HMAC / signatures catch attackers.
  • Reverse proxy: one endpoint hiding a fleet — TLS termination, L7 routing, WAF, caching, rate limiting.
