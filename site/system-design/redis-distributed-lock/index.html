Redis Distributed Lock — the Nightly Report Job

Five servers, one Redis, one email. How SET NX PX, a unique token, a Lua release script, lease renewal, fencing tokens, and idempotency come together so the user opens their inbox to exactly one daily report.

🎯 The problem

Five servers, one job — and one user who does not want five emails

The setup is a very common backend interview trap. A SaaS application is deployed on five identical backend servers behind a load balancer for high availability. On every server the same code runs, and each server has its own scheduler that fires a job every night at 12:00 AM. The job pulls the previous day's data, generates a PDF daily report and emails it to the user.

The moment the clock hits midnight, all five schedulers wake up together, all five servers query the database, all five generate the same PDF, and all five hit the SMTP gateway. The user opens their inbox in the morning and sees five identical emails. Support tickets follow within the hour.

The obvious fix — "just run the scheduler on one server" — sounds fine until that one server crashes, or the deployment is picked up randomly by whichever pod comes up first in Kubernetes, or a rolling deploy runs the job twice on adjacent hosts. What we actually want is a rule the whole fleet agrees on: whoever runs this job at midnight is the only one running it. That is a distributed mutual exclusion problem, and the classical starter solution is a Redis distributed lock.

Real products solving similar problems every day: Shopify, Stripe, GitHub, DoorDash, Airbnb — every SaaS with a nightly billing rollup, invoice generation, dunning email, cache warmup, index rebuild, or partner reconciliation hits this problem. It is arguably one of the top three "have you ever built a distributed system?" questions asked in interviews, along with rate limiter and URL shortener.

🧑‍🎓 In laymen terms

Imagine five twins sharing one printer

Picture a family of five identical twins who all have the same to-do list. At exactly midnight each of them is supposed to print out a copy of a report and drop it in Grandma's mailbox. If nobody coordinates, Grandma finds five identical copies of the same letter. Sweet, but annoying.

The twins agree on a trick. Before anyone starts printing, they run to the front hallway where there is a single whiteboard. The rule is simple: whoever gets there first writes their name on the whiteboard. Everyone else who arrives, reads the whiteboard, sees someone else's name is already there, and quietly walks away. Only the twin whose name is on the board actually prints and mails the letter.

That whiteboard is Redis — a super fast shared notepad that every server on the internet can look at. The "write your name if the board is empty" trick has an official name in Redis: SET key value NX. NX just means "only if nobody else has written here yet".

Two very natural worries come up:

1. What if the twin who wrote their name faints? They will never rub their name off and everyone else is blocked forever. Solution: they don't just write their name, they write "this claim expires in 30 seconds". If they faint, the note peels itself off the wall. In Redis this is PX 30000 — the note lives 30 seconds and then vanishes on its own.

2. What if the twin is slow and the note expires while they are still printing? Then another twin might see the empty board, write their name, and start printing too. Now we have two workers again. There are two fixes here that experienced engineers combine: renew the note every 10 seconds while you are still working (the "watchdog"), and also keep a receipt book that says "the letter for Grandma on Tuesday has already been mailed" — so even if a second twin sneaks past the whiteboard, the receipt book stops them from mailing a duplicate.

The whiteboard rule is called a distributed lock. The receipt book is called idempotency. Real companies like Stripe, Shopify and Amazon use exactly this pair for anything a customer would notice twice — payments, refunds, emails, invoices. In this page we build both, on top of Redis, in a way that survives crashes, network hiccups and slow jobs.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • At 12:00 AM local time, generate one daily report per user and email it.
  • All 5 backend servers run the same code and the same scheduler.
  • Exactly one server must execute the job for a given (user, date).
  • If the winning server crashes mid-way, another server must be able to take over.
  • If a job succeeds but the "done" flag never gets written, a retry must not send a second email.

Non-functional requirements

  • Correctness: at most one email per user per report date. Zero duplicates is a hard business requirement.
  • Availability: if 1 of 5 app servers dies, the report still goes out. If Redis primary dies, the system either fails over or fails safely (does not double-send).
  • Latency: lock acquisition should complete in under ~5 ms. Redis SET is O(1) and typically < 1 ms on the same VPC.
  • Simplicity: the design must be explainable on a whiteboard in 10 minutes.
  • Cost: a single ElastiCache cache.t4g.small node handles the entire fleet — this is not a scale problem.

🏗️ High-level architecture

How the pieces fit together

At midnight the schedulers on all five servers race. They all call the same helper — tryAcquireLock("daily-report", token, 30_000ms) — which sends a single atomic Redis SET ... NX PX. Redis awards the lock to the first request that lands; the other four receive nil and skip the job immediately. The winner then checks a small "already done?" table (idempotency), runs the report, sends the email, marks the job complete, and finally releases the lock using a Lua script that verifies its unique token still owns the key.

Trigger & contention Redis lock keyspace Winner (owner path) Losers (skip path)

Two things matter about this picture. First, the whole race resolves in one Redis command — no coordinator service, no leader election. Second, the answer Redis returns is binary and immediate: OK means "you own it for 30 seconds, get to work"; nil means "someone got here first, sleep till tomorrow". This is why SET NX PX is the interview answer, not SETNX followed by EXPIRE.

🔍 Lock deep-dive — every piece, and why

1. Lock acquisition — one atomic command

The correct primitive is a single atomic write:

# Redis
SET daily-report-lock <unique-token> NX PX 30000

Every option matters:

  • daily-report-lock — the resource being protected. One key per (job, scope). For per-tenant isolation the key becomes daily-report-lock:{tenantId}:{yyyy-MM-dd}.
  • <unique-token> — a random 128-bit value (UUID v4, or 16 bytes from a CSPRNG) that identifies this specific execution. Not the hostname — because the same host may retry after a crash and must not match a lease it no longer owns.
  • NX — "only set if the key does not exist". This is the mutual-exclusion primitive. Redis evaluates NX and the write in a single, indivisible operation because the server is single-threaded.
  • PX 30000 — expiration in milliseconds (30 seconds). This is the lease. If the owner crashes or gets network-partitioned, Redis will auto-delete the key and the next scheduler run can proceed.

Redis returns OK to exactly one client and nil to everyone else. Losers must not retry immediately — they simply skip the job.

2. Why the naive two-step approach is a lock leak

An interviewer's favourite trap is:

# DO NOT DO THIS — two commands are not atomic together
SET daily-report-lock <token>
EXPIRE daily-report-lock 30

Between the two commands the application can crash, the network can drop, or the client can be paused by GC. If the crash happens after SET but before EXPIRE, the key exists with no TTL — a permanent lock. The next night, the job is blocked forever until an operator manually runs DEL. This is one of the most common outages in real systems, which is why Redis added the combined SET ... NX PX form back in Redis 2.6.12.

3. Safe release — Lua, because GET + DEL is another race

Symmetrically, releasing the lock naively is unsafe. Suppose Server A acquires with token A-uuid, its job runs long, the 30 s TTL elapses, Redis deletes the key, Server B (next scheduler tick or another server) acquires with token B-uuid, and then Server A finishes and calls DEL daily-report-lock. Server A just deleted Server B's lock, and now a third server can grab it. Two concurrent owners for the same resource — precisely what we were trying to prevent.

The fix is to release only if the stored value still equals your own token. But even that has to be atomic — a client-side "GET, compare, DEL" is still a TOCTOU race because Server B could acquire the lock between your GET and your DEL. Redis exposes atomic multi-command sequences via Lua:

-- Redis EVAL: atomic compare-and-delete
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

Because the Redis server is single-threaded, this whole script runs without any other command interleaving. The lock is released exactly when the caller still owns it, and no-ops otherwise. This is the "safe release" pattern from the Redis documentation.

4. The classic race — long job vs. short TTL

Here is the failure mode the interviewer is trying to lure you into:

Server A ran for 40 seconds. Its 30-second lease expired at t=30, so Redis auto-deleted the key. Server B acquired the same key at t=30 with its own token. At t=40, Server A calls DEL — and if it does so blindly it just erased Server B's lock. A third server can now walk in. The Lua script is the fence.

5. Long-running jobs — the watchdog / lease-renewal pattern

The other half of the fix is never letting the lease expire while you are still working. Set a short TTL for safety in case of a crash, but have a background thread renew it periodically as long as the job is alive. Renewal must be conditional: extend the TTL only if the stored token still equals mine. If Redis returns "value no longer matches", it means the lock has been lost — the job must abort or fence.

Server A owns lock (token = A-uuid, ttl = 30s) │ ▼ Every 10 seconds a watchdog thread runs: │ ▼ Lua: if GET key == A-uuid then PEXPIRE key 30000 else 0 │ ┌──┴──┐ │ │ match no match / GONE │ │ ▼ ▼ renew STOP · abort work · alert TTL

The renewal cadence is a rule of thumb: renew at 1/3 of the TTL. With TTL = 30 s and renewal every 10 s, we tolerate two consecutive lost renewal attempts (network blips, brief Redis latency spike) before losing the lock. In production libraries like Redisson this is called the "watchdog".

7. Fencing tokens — the fix for the fix

Layman version. The lock says "you're allowed to work now". A fencing token says "you're allowed to work now — and here is a number that proves you're the latest allowed worker". Every downstream system checks the number and refuses to accept work from an older number, even if you show up with the right token, because a newer worker has already been through.

Technical version. Each successful lock acquisition returns a monotonically increasing integer along with the lock. The lock owner attaches this number to every write it performs (email send, DB update, S3 put). The downstream service — the SMTP relay, the DB, the S3 API — remembers the highest token it has seen for this resource, and rejects any request whose token is smaller. This turns a "trust the client" system into one where correctness is enforced at the resource, not just at the lock.

Server A acquires lock → fencing token 100 ⚠ A pauses for 45s (GC / EBS stall / scheduler pause) ⚠ Its lease expires at t=30 Server B acquires lock → fencing token 101 ✓ B sends email — SMTP sees token 101, accepts, records highwater=101 Server A wakes up at t=45, still holding token 100 ✗ A tries to send email — SMTP sees token 100 < 101 → rejects ✗ A tries to write "job done" — DB rejects on stale token

Redis by itself does not give you a fencing token — its lock value is a random string, not a monotonic counter. You can bolt one on with INCR daily-report-lock:counter alongside the SET, but Kleppmann's critique is real: a single-node counter is not fault-tolerant, and multi-node monotonic counters basically require consensus. For the correctness edge, systems like ZooKeeper (znode version / czxid) or etcd (mod_revision) give you a monotonic revision for free.

8. Distributed lock ≠ idempotency

A common mistake is to think "if I have a Redis lock I can't send two emails". Not true. Consider this timeline:

Server A acquires lock (token A) │ ▼ Email successfully sent via SES │ ▼ Server A crashes before writing "done" row │ ▼ Lock TTL expires │ ▼ Next scheduler tick — Server B acquires lock │ ▼ Server B does not know Server A already sent the email │ ▼ Server B sends the SAME email again ← duplicate

The lock only guarantees at most one server is executing at a time. It does not guarantee at most one business outcome. Guaranteeing exactly one email requires an idempotency record that is written atomically with (or before) the side effect.

The idempotency ledger

A tiny relational table (or DynamoDB item) that acts as the source of truth for "has this job's business outcome already happened?":

CREATE TABLE DailyReportExecution (
    TenantId     UUID          NOT NULL,
    UserId       UUID          NOT NULL,
    ReportDate   DATE          NOT NULL,
    ExecutionId  UUID          NOT NULL,   -- same as fencing/lock token
    Status       VARCHAR(16)   NOT NULL,   -- STARTED · EMAIL_SENT · COMPLETED
    CreatedAt    TIMESTAMPTZ   NOT NULL,
    CompletedAt  TIMESTAMPTZ,
    PRIMARY KEY (TenantId, UserId, ReportDate)
);

The unique business key is (TenantId, UserId, ReportDate). Before doing anything, the job attempts an INSERT ... ON CONFLICT DO NOTHING. If it inserts, it owns the work; if it doesn't, the row already exists — check its status and skip (or resume, depending on your design). The row transitions STARTED → EMAIL_SENT → COMPLETED. Recovery logic reads the last state and does the right thing without duplicating side effects.

The mental model to memorize for the interview:

Distributed Lock → prevents concurrent execution Idempotency → prevents duplicate business outcome

Neither replaces the other. Serious systems use both.

9. Redis failover — the honest limitations

Redis replication is asynchronous by default. When your SET NX PX lands on the primary, Redis returns OK before the write has been propagated to replicas. If the primary then crashes and a replica is promoted, your lock can vanish from the fleet's point of view — even though your client thinks it holds the lock. Another server can now acquire the "same" lock on the new primary. Two lock owners at once.

The Redlock algorithm is Redis's answer for this: acquire on a majority (≥ N/2 + 1) of independent Redis instances with a shared timing window. It is more robust than single-node, but Kleppmann's 2016 critique shows Redlock still assumes bounded clocks and bounded pauses, and does not give fencing tokens — so it is not a substitute for a real coordination service when correctness is critical.

Practical guidance for interviews:

  • Efficiency locks (avoid duplicate email, deduplicate cache warm, cron guard) — single Redis instance with SET NX PX + unique token + Lua release. Combine with idempotency for the business layer. This is what the interviewer wants to hear for our nightly report.
  • Correctness locks (transferring money, releasing inventory, writing to a shared file) — use ZooKeeper (Curator's InterProcessMutex), etcd, Consul, or a database advisory lock. Every one of these gives you a monotonic version as a natural byproduct — a real fencing token.

10. Alternative production architecture — one scheduler, many workers

The interview problem assumes the same job fires on all 5 servers, so the Redis lock has to save us. In real production the cleanest design is to remove the race entirely by not letting every server be a scheduler. A central scheduler (or a managed one, like AWS EventBridge) enqueues one job into a durable queue, and any worker in the pool picks it up. The queue's visibility timeout gives you the "one worker at a time" property for free.

Why this can be cleaner in production: the queue is durable, so a worker crash mid-job just returns the message to the queue for another worker; the scheduler is a single managed service, not five copies of your code; and worker scaling is independent of the scheduler. The Redis-lock design is still the interview answer — but if the interviewer says "how would you actually run this", this is the diagram to draw next.

🧮 The DSA behind it

Data structures & algorithms

This design looks operational, but it stands on several concrete algorithmic ideas. Being able to name them separates a strong candidate from an average one.

Concurrent primitive — Compare-And-Set (CAS)

SET NX PX is a CAS on a single Redis key: "if the current value is nil, set this new value with this TTL, atomically". Redis's single-threaded command loop is what makes it atomic in O(1) time without any explicit locking on the server side. This is the same primitive that underlies lock-free algorithms and DynamoDB conditional writes (ConditionExpression: attribute_not_exists(pk)).

Lease-based mutual exclusion

Rather than the classical "lock until released" primitive from OS textbooks, distributed systems use leases — the lock has a time bound. A lease is a lock with a TTL, plus a renewal protocol. Textbooks: Gray & Cheriton, "Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency" (1989).

Fencing tokens — monotonic sequence

A monotonically increasing integer per resource, checked at the resource. Data-structure-wise it is trivial — a counter, plus a "highest seen so far" watermark at each writer. The interesting property is total order: every acquisition gets a token strictly greater than any previously issued one. In ZooKeeper this is the czxid (create zxid); in etcd it is mod_revision; in a SQL DB it is a sequence.

Idempotency via unique-key insert

The idempotency check is a hash-set-of-seen-outcomes pattern implemented as a UNIQUE constraint on (TenantId, UserId, ReportDate). Insert wins → do the work. Insert conflicts → work is already done (or in progress; check status). This is O(1) with a proper index.

Retries with jitter

Losers that want to try again (not this problem, but relevant) should back off with exponential jitter to avoid thundering herds. Full jitter: sleep = random(0, min(cap, base * 2^attempt)).

💻 C# implementation — StackExchange.Redis

Complete reference implementation with lock acquisition, safe release, watchdog renewal, and the idempotency guard. This code is production-shaped; drop it in an ASP.NET Core worker with StackExchange.Redis.

// -----------------------------------------------------------------------
// Package: StackExchange.Redis, Microsoft.Extensions.Hosting
// -----------------------------------------------------------------------

using StackExchange.Redis;

public sealed class RedisDistributedLock : IAsyncDisposable
{
    private readonly IDatabase _db;
    private readonly RedisKey _key;
    private readonly RedisValue _token;      // unique per acquisition
    private readonly TimeSpan _ttl;
    private readonly CancellationTokenSource _cts = new();
    private Task? _watchdog;

    // Atomic compare-and-delete — the safe release script
    private const string ReleaseLua = @"
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('DEL', KEYS[1])
        else
            return 0
        end";

    // Atomic compare-and-renew — only extend TTL if we still own the lock
    private const string RenewLua = @"
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('PEXPIRE', KEYS[1], ARGV[2])
        else
            return 0
        end";

    private RedisDistributedLock(IDatabase db, RedisKey key, RedisValue token, TimeSpan ttl)
    {
        _db = db; _key = key; _token = token; _ttl = ttl;
    }

    // Try to acquire the lock once. Returns null on failure — caller decides to skip.
    public static async Task<RedisDistributedLock?> TryAcquireAsync(
        IDatabase db,
        string resource,
        TimeSpan ttl)
    {
        var token = Guid.NewGuid().ToString("N");   // 128-bit unique token
        var key   = new RedisKey($"lock:{resource}");

        // SET key token NX PX ttl  — atomic on the Redis server
        bool won = await db.StringSetAsync(
            key,
            token,
            expiry: ttl,
            when: When.NotExists);

        if (!won) return null;

        var handle = new RedisDistributedLock(db, key, token, ttl);
        handle.StartWatchdog();
        return handle;
    }

    // Background renewal: every ttl/3, extend the lease if we still own it.
    private void StartWatchdog()
    {
        var interval = TimeSpan.FromMilliseconds(_ttl.TotalMilliseconds / 3);
        _watchdog = Task.Run(async () =>
        {
            while (!_cts.IsCancellationRequested)
            {
                try
                {
                    await Task.Delay(interval, _cts.Token);
                    var extended = (long)await _db.ScriptEvaluateAsync(
                        RenewLua,
                        new[] { _key },
                        new RedisValue[] { _token, (long)_ttl.TotalMilliseconds });
                    if (extended != 1)
                    {
                        // Lock lost — signal caller to abort.
                        _cts.Cancel();
                        break;
                    }
                }
                catch (OperationCanceledException) { break; }
            }
        });
    }

    public CancellationToken LockLost => _cts.Token;

    // Idempotent safe release via Lua — no-op if we no longer own the key.
    public async ValueTask DisposeAsync()
    {
        try { _cts.Cancel(); } catch { }
        if (_watchdog != null) await Task.WhenAny(_watchdog, Task.Delay(1000));

        await _db.ScriptEvaluateAsync(
            ReleaseLua,
            new[] { _key },
            new RedisValue[] { _token });
    }
}

// -----------------------------------------------------------------------
// The nightly job — combines the lock with an idempotency ledger
// -----------------------------------------------------------------------

public class DailyReportJob
{
    private readonly IDatabase _redis;
    private readonly IReportRepository _repo;      // DynamoDB / SQL
    private readonly IEmailSender _email;           // SES

    public async Task RunAsync(Guid tenantId, Guid userId, DateOnly reportDate)
    {
        var resource = $"daily-report:{tenantId}:{userId}:{reportDate:yyyy-MM-dd}";

        await using var handle = await RedisDistributedLock.TryAcquireAsync(
            _redis, resource, TimeSpan.FromSeconds(30));

        if (handle is null)
        {
            // Another server owns the lock. Skip cleanly.
            Metrics.LockAcquisitionFailure.Increment();
            return;
        }
        Metrics.LockAcquisitionSuccess.Increment();

        // Idempotency guard — atomic insert of (tenant, user, date).
        // Returns false if a row already exists → job already done or in-flight.
        bool claimed = await _repo.TryClaimExecutionAsync(tenantId, userId, reportDate);
        if (!claimed)
        {
            Metrics.DuplicateExecutionPrevented.Increment();
            return;
        }

        var jobCt = handle.LockLost;   // aborts if watchdog can't renew
        var report = await _repo.BuildReportAsync(tenantId, userId, reportDate, jobCt);

        await _email.SendAsync(userId, report, jobCt);
        await _repo.MarkCompletedAsync(tenantId, userId, reportDate);

        Metrics.JobExecutionSuccess.Increment();
        // Dispose releases the lock via the safe Lua script.
    }
}

Key things this snippet illustrates for the interview:

  • One SET NX PX call — no separate EXPIRE. StackExchange.Redis's StringSetAsync(..., when: When.NotExists) is exactly that.
  • Unique token per acquisition — Guid.NewGuid().ToString("N") gives 128 bits of entropy.
  • Watchdog — renewal at TTL/3, cancels the job's cancellation token if the lock is lost.
  • Safe release — the Lua compare-and-DEL, so a stale owner can't erase a fresh lock.
  • Idempotency ledger — orthogonal to the lock; the second line of defense against duplicate emails.

If you were on the JVM you'd reach for Redisson, which packages exactly this pattern (with a watchdog) as RedissonClient.getLock(). In Go, bsm/redislock. In Python, redis-py's Lock class. Same pattern everywhere.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Trade-offs

Simplicity vs. correctness. Redis SET NX PX is arguably the simplest distributed lock money can buy — one line of code, sub-ms latency, works for 99% of "avoid duplicate cron" problems. What you buy for that simplicity is a lock that can silently disappear during a failover, and a lock that gives you no fencing token. For efficiency use cases this is fine; for correctness use cases it is not.

TTL length. Short TTL protects against crashed owners (lock recovers fast) but risks premature expiration. Long TTL is safer for long jobs but wedges the system longer after a crash. The compromise is short TTL with watchdog renewal: 30 s TTL, renew at 10 s, tolerate one lost tick.

Do we still need idempotency if we have a lock? Yes — always. The lock protects "concurrent execution"; idempotency protects "duplicate business outcome". They cover different failure modes. Combining both is what makes the design actually correct.

Lock granularity. One global lock (daily-report-lock) is simple but serializes 100 K users into one server per minute — the job cannot be sped up by adding servers. A per-tenant lock (daily-report-lock:{tenantId}:{date}) partitions the work naturally and lets many servers work in parallel. Prefer per-tenant unless there's a reason not to.

Bottlenecks

  • Redis is a single point. Multi-AZ replication reduces blast radius but doesn't eliminate it. Redlock or ZooKeeper if the SLA requires it.
  • Global lock serializes work. Fix with per-tenant keys.
  • The scheduler racing itself. The interview asks us to keep the scheduler on every server; the "real production" fix is to move to a central EventBridge scheduler + SQS FIFO and stop racing altogether.
  • Downstream throttling. SES has send-rate quotas — even without duplicates, hammering it at midnight from 100 K parallel workers will get you throttled. Rate-limit at the worker side.

Interview follow-ups & short answers

Why not SETNX + EXPIRE?

Two commands are not atomic together. If the client crashes between them, the key has no TTL and the lock becomes permanent. SET NX PX is one atomic write.

Why the Lua release script instead of GET-then-DEL?

GET-then-DEL is a TOCTOU race. Between the GET and the DEL another client can acquire the lock and you'll delete their key. Lua runs atomically on Redis's single-threaded loop, so the compare-and-delete is indivisible.

What if the job takes longer than TTL?

Use a watchdog: renew the TTL every TTL/3 seconds with a Lua "renew only if my token still matches" script. If a renewal fails, the owner treats the lock as lost and aborts. This is exactly what Redisson's watchdog does.

Can this send zero emails? Can it send two?

It can send zero if the owner crashes after acquiring but before sending — the next scheduler tick retries. It can send two if the owner sends the email, then crashes before marking the ledger, and the lease expires and a new owner runs before the ledger row lands. The idempotency ledger is what makes "at most one" hold in practice.

What if Redis fails over?

Async replication means a lock written on the old primary may not be on the new one. Two servers could hold the "same" lock briefly. The idempotency ledger (strongly consistent — DynamoDB conditional write or a UNIQUE index in Postgres) absorbs that duplicate. If we cannot tolerate any duplicate, we move off Redis to ZooKeeper/etcd.

What is a fencing token and why isn't Redis enough?

A monotonically increasing number issued at lock-acquire time, checked at the resource — the resource rejects writes with a token older than the highest one it has seen. Redis doesn't natively provide monotonic tokens because a single-node counter isn't fault-tolerant. Consensus systems (ZooKeeper's zxid, etcd's mod_revision) give you one for free.

What alternative production design would you propose?

Remove the race entirely: a central EventBridge Scheduler enqueues one job per user into SQS FIFO (MessageGroupId = tenantId), and a pool of ECS/Lambda workers consumes with visibility timeout as the lease. Same idempotency ledger. Cleaner, no cross-server lock, but the Redis-lock design is the right answer for the interview because the interviewer explicitly asked about coordination between the 5 servers.

Observability — what to alert on

Every serious lock/job pair emits at least these metrics. Wire them to CloudWatch with the Embedded Metric Format (EMF) or Prometheus with equivalent gauges/counters:

lock_acquisition_success counter lock_acquisition_failure counter (most losers — expected) lock_acquisition_latency histogram (p50, p99 in ms) lock_renewal_success counter lock_renewal_failure counter (alert on rate) job_execution_duration histogram (vs. lock TTL — should be < TTL after renewals) job_execution_success counter job_execution_failure counter duplicate_execution_prevented counter (idempotency ledger caught a would-be dupe) email_delivery_success counter email_delivery_failure counter lock_owner_stale_seconds gauge (alert if any lock older than 2× expected job time)

The two golden alerts: duplicate_execution_prevented > 0 per hour (means the lock is failing and idempotency is saving you — investigate) and lock_renewal_failure / lock_renewal_success > 1% (means Redis or your network is misbehaving).

🗣️ Interview cheat sheet — the 2–3 minute answer

The verbal walk: "The problem is five servers running the same midnight cron, all racing to send one email. Textbook distributed mutual exclusion. My starter answer is a Redis distributed lock. On each server the scheduler runs SET daily-report-lock <random-uuid> NX PX 30000 — one atomic write. The NX ensures only the first client wins, the PX auto-expires the lock so a crashed owner can't hold it forever, and the random UUID is the token that identifies my execution. I would not use SET followed by EXPIRE — those two commands aren't atomic and a crash between them leaves a permanent lock.

"Losers get nil and skip. The winner runs the job and releases the lock via a Lua compare-and-DEL — if GET == mytoken then DEL end — because a naive DEL would delete someone else's lock if my job overran the TTL and a second server acquired it. For long jobs I add a watchdog thread that renews the TTL every 10 seconds using a similar Lua compare-and-PEXPIRE.

"Two things make this really correct rather than just clever. First, the lock alone doesn't prevent duplicate emails — if I send the email and then crash before releasing, the next run will retry. So I add an idempotency ledger keyed on (tenantId, userId, reportDate), and I do a conditional insert before sending. Distributed lock prevents concurrent execution; idempotency prevents duplicate outcome — different guarantees, both needed. Second, for stronger correctness — think payments, not emails — a Redis lock has a real weakness: replication is async, so a failover can lose the lock, and Redis doesn't give a monotonic fencing token. For those cases I'd reach for ZooKeeper or etcd — both give you a natural version number the downstream resource can enforce. But for a nightly report Redis plus idempotency is the right tool: sub-ms latency, one line of code, and correctness closed by the ledger."

5 talking points that win the round

  • Atomicity. Say "SET NX PX" and immediately explain why SET + EXPIRE is unsafe. This shows you've been bitten before.
  • Unique token + Lua release. Naming the TOCTOU race between GET and DEL is a strong signal.
  • Watchdog for long jobs. Anyone who says "just use a big TTL" fails the follow-up.
  • Lock vs. idempotency. This is the differentiator. Most candidates conflate the two.
  • When Redis isn't enough. Fencing tokens, ZooKeeper/etcd for correctness-critical workloads. Cite Kleppmann's argument without reciting it.

Numbers to quote

  • Redis lock latency: ~1 ms p50, ~5 ms p99 on same-VPC ElastiCache.
  • Default TTL: 30 s. Renewal cadence: TTL / 3 (10 s).
  • Lua script atomicity: O(1) and blocks the server for microseconds.
  • DynamoDB conditional put: single-digit ms, strongly consistent.
