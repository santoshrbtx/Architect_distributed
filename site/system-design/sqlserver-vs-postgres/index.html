SQL Server vs PostgreSQL

The architectural differences that actually matter — MVCC vs locking, WAL vs T-log, Always On vs streaming replication, licensing, extensibility, ecosystem, and how a senior architect picks between them.

🎯 Scenario

The question every architect gets asked

"We are starting a new service. Which relational database should we pick — Microsoft SQL Server or PostgreSQL?" It's the most common architecture-review question of the last twenty years. Both are mature, ACID-compliant, SQL:2023-aligned RDBMSs used at Fortune-500 scale. Both have huge ecosystems and cloud-managed offerings (Azure SQL, AWS RDS/Aurora). The wrong answer never gets you fired, but a weak answer marks you as a mid-level engineer. A strong answer names the underlying architectural choices, the licensing model, the failure modes, and — most important — the specific workload characteristics that tilt the decision one way or the other.

This page gives you the whiteboard-grade answer. It covers process architecture, concurrency model (MVCC vs lock-based with optional row versioning), storage engine (heap + PK-clustered vs heap + optional CLUSTER), write-ahead logging (WAL vs T-log), replication and HA (streaming/logical vs Always On availability groups), partitioning, extensibility, licensing/cost, and ecosystem fit. Then it gives you a decision rubric with worked examples so you can pick fast in an interview.

🧑‍🎓 In plain English

The story, told without any jargon

Both SQL Server and PostgreSQL are filing cabinets for your business data. Both keep every drawer neat, both can hand out receipts saying "your change is saved for good" (that's ACID), and both let you ask questions like "who spent the most money last month?" in the same language (SQL). If you only cared about the front door, they'd feel identical.

The real difference is how they handle two people reaching for the same folder at the same time. SQL Server, by default, does what feels intuitive: it locks the folder — you wait until the other person finishes. Simple, predictable, but if the other person is slow, you sit around doing nothing. PostgreSQL does something clever: it photocopies the folder for you. You each work on your own copy at the same time, and the system figures out how to merge (or reject) the changes at the end. That trick is called MVCC, and it is the single biggest architectural difference between the two products.

The second difference is who owns them. SQL Server is a Microsoft product — you buy it, you're tied to Microsoft's licensing, and everything works beautifully if you already live in Windows/.NET/Azure. PostgreSQL is a free, open-source community project — no vendor, no licence fee, and it runs equally well on Linux, Docker, AWS, Google Cloud, your laptop, or a Raspberry Pi. If you want to extend the database (add a new data type, plug in a new language, index geographic coordinates), PostgreSQL is designed to let you; SQL Server only lets you within the walls Microsoft built.

The third difference is the pack of tools each ships with. SQL Server comes with a full "business intelligence" toolkit — reporting servers, ETL packages, analysis cubes — all one purchase. PostgreSQL is just the database; anything else you build with best-of-breed pieces you glue together yourself. If you're a small IT team who wants "one thing that does everything", SQL Server wins. If you're a modern platform team who wants "the fastest, cheapest, most flexible SQL engine plus my own tooling", PostgreSQL wins.

That's the whole comparison in five paragraphs. The rest of this page is just how each of these plays out in practice.

🏗️ Architecture — how each is built

The two engines, side by side

Both are relational engines but they were designed from opposite starting points. SQL Server evolved from a Sybase codebase inside Microsoft — a single-process, multi-threaded engine with a bespoke user-mode scheduler (SQLOS) that thinks in terms of workers, tasks, and schedulers. PostgreSQL is a multi-process Unix-tradition engine — one postgres backend process per connection, coordinated through shared memory. That single choice ripples through everything else: pooling, concurrency, memory management, and failure isolation.

SQL Server subsystems Postgres processes Write-ahead log Data files

Two consequences of that process/thread split you should be able to name in an interview: (1) SQL Server connections are cheap — a thread inside the shared process. Postgres connections are expensive — each is a separate process holding ~10 MB, so a pooler (PgBouncer) is standard. (2) SQL Server is easier to run on Windows; PostgreSQL is a first-class citizen of Linux/Docker/Kubernetes and often feels more natural in cloud-native stacks.

🔍 Deep-dive — the architecturally interesting differences

1. Concurrency: MVCC vs locking (with row-versioning opt-in)

The single largest architectural difference. PostgreSQL uses MVCC everywhere: every UPDATE creates a new tuple version rather than mutating in place; readers see the version visible to their transaction's snapshot; writers never block readers, readers never block writers. This gives Postgres exceptional read throughput under concurrent writes — at the cost of bloat (dead tuples pile up until autovacuum cleans them). SQL Server started life pessimistic and lock-based: readers hold shared locks that block writers and vice versa. Since SQL Server 2005 you can opt-in to Read Committed Snapshot Isolation (RCSI) or Snapshot Isolation, which use row versioning stored in tempdb; SQL Server 2022 added Optimized Locking (TID + LAQ) to reduce lock memory. Even so, most SQL Server deployments still run with the pessimistic default and lean on indexes to avoid escalation. This is why "converting a legacy SQL Server app to Postgres" is not a purely mechanical port — the isolation semantics can differ subtly.

2. Storage: heap + clustered index vs heap + optional cluster

SQL Server stores data in 8 KB pages inside .mdf / .ndf files. Every table has either a heap or a clustered index — and by default, the primary key IS the clustered index, so the table is physically sorted by PK. This makes range queries on PK fast but makes inserts anywhere except the tail slow, and it means every non-clustered index carries the PK as its row locator. PostgreSQL stores every table as a plain heap (unordered by default); the PK is just another B-tree index pointing into the heap. Ordering by insertion is preserved unless you explicitly CLUSTER. This gives Postgres more predictable insert performance and simpler mental model, at the cost of losing the "clustered scan" trick.

3. Write-ahead log: T-log vs WAL

Both engines use write-ahead logging (durability, crash recovery, replication all depend on it). SQL Server's transaction log (.ldf) and Postgres's WAL segments (pg_wal/) serve the same purpose — flush the log before the data page. The differences are operational: SQL Server has a single per-database log file, backup modes (SIMPLE, FULL, BULK_LOGGED), and log-shipping/replication features tied to log backups. Postgres has fixed-size 16 MB WAL segments that stream continuously to replicas; recovery is naturally continuous (PITR to any second). Both support synchronous replication — commit blocks until the replica has ACKed the log record.

4. Replication & HA architecture

SQL Server's flagship is Always On Availability Groups (AG): a group of databases replicated to up to 8 secondaries (2 sync, rest async in Enterprise). Automatic failover uses Windows Server Failover Cluster (WSFC) as the quorum layer. Read-only routing at the listener lets you offload reads. Also available: log shipping (simple, granular), transactional replication (per-table CDC), Failover Cluster Instance (shared-storage HA). PostgreSQL gives you two flavours: physical streaming replication (byte-for-byte WAL shipped to hot standbys) and logical replication (row-level events, cross-version, subset of tables). Tools like Patroni, repmgr, or pg_auto_failover orchestrate failover; on cloud, RDS Multi-AZ and Aurora handle it for you.

5. Partitioning & sharding

Both offer native partitioning: split a big table into partitions by range, list, or hash; the planner prunes irrelevant partitions. Neither offers native cross-node sharding: SQL Server's answer is Azure SQL Hyperscale (managed distributed storage under one logical DB) or app-level shard maps; Postgres uses Citus (columnar + sharding extension, now Microsoft-owned), PostgresXL, or app-level routing. If you need > single-node writes, Aurora Postgres + read replicas + Citus is the modern shape.

6. Extensibility — Postgres's superpower

PostgreSQL was designed from day one to be extended without recompiling the server. New data types, operators, index methods, procedural languages, foreign data wrappers — all first-class extensions. The ecosystem is huge: PostGIS (geo, industry-leading), TimescaleDB (timeseries), pgvector (vector search for LLMs — the reason Postgres is now a top RAG engine), pg_partman, pg_cron, Citus, hstore. SQL Server's extension story is CLR integration (embed .NET assemblies) and native features shipped by Microsoft; there is no "install this open-source extension" culture. If you need a specialized data model, Postgres almost certainly has an extension for it already.

7. JSON & document workloads

Both engines support JSON, but architecturally differently. SQL Server stores JSON as nvarchar and provides JSON_VALUE / JSON_QUERY / OPENJSON functions — the JSON is unparsed on disk. PostgreSQL has native JSONB: JSON is parsed to a binary tree on write, indexed with GIN, queried with the -> and @> operators. Postgres genuinely competes with MongoDB for document workloads; SQL Server's JSON is best used sparingly.

8. Analytics & columnstore

SQL Server has native columnstore indexes since 2012: 10× compression, 100× scan speed, and hybrid clustered/nonclustered variants. This makes SQL Server genuinely capable at hybrid OLTP+OLAP without a separate warehouse. Postgres has no native columnstore; you use extensions (Hydra, Citus columnar, or replicate to ClickHouse or a warehouse). If your workload mixes transactions with heavy analytical scans, SQL Server has the built-in edge — although a Postgres + ClickHouse combo is a very common and cheaper alternative.

9. Ecosystem & tooling — first-party vs best-of-breed

SQL Server ships a full BI stack from Microsoft: SSMS (management), SSIS (ETL), SSAS (OLAP), SSRS (reports), Power BI. Buying one product buys you everything a small IT team needs. Postgres has none of that in-box — you pick pgAdmin or DBeaver for management, dbt, Airbyte, or Fivetran for ETL, Grafana or Metabase for dashboards, Debezium for CDC. This is either "flexible best-of-breed" or "too many moving parts" depending on your team.

10. Licensing & cost

This is the deciding factor for many organisations. SQL Server is expensive: Enterprise Edition can run five to six figures per socket-year; Standard is cheaper but drops Always On, columnstore optimisations, and unlimited memory. There's a free Express edition capped at 10 GB DBs and 1 CPU socket / 1.4 GB RAM. PostgreSQL is free forever, no editions — every feature is available in the free download. On cloud, Azure SQL vs Aurora Postgres pricing is closer than the on-prem numbers, but the licensing complexity difference remains.

11. Operational culture

SQL Server DBAs live in Windows and PowerShell; the tooling is GUI-heavy (SSMS is genuinely excellent). Postgres administrators live in psql, bash, and Terraform; the tooling is CLI-heavy and code-friendly. Neither is inherently harder — but a team's existing skillset makes a huge difference to day-2 operations. A shop full of .NET engineers on Windows will feel at home with SQL Server; a shop of Go / Node / Python engineers on Linux will feel at home with Postgres.

✅ Pros & Cons

Microsoft SQL Server

Strengths

  • Best-in-class GUI tooling (SSMS) — DBAs love it.
  • First-party BI stack in the box (SSIS, SSAS, SSRS, Power BI).
  • Native columnstore & excellent hybrid OLTP+OLAP.
  • Always On AGs — mature, well-documented HA.
  • Deep .NET / C# integration; Entity Framework's home ground.
  • Azure SQL family (DB, MI, Hyperscale) — the smoothest managed cloud story if you're already on Azure.
  • T-SQL is expressive and stable; MERGE, window functions, temporal tables are mature.

Weaknesses

  • Licensing cost — Enterprise is very expensive; edition matrix is confusing.
  • Lock-based concurrency default causes blocking under contention (RCSI helps).
  • Extensibility is limited — no rich extension ecosystem outside Microsoft-shipped features.
  • Weaker JSON support than Postgres.
  • Less popular in modern cloud-native / container-first shops.
  • Historically Windows-first; Linux support has caught up but ecosystem lags.
  • No native sharding — Hyperscale addresses read scale, not write scale.

PostgreSQL

Strengths

  • Free and open source — no licensing cost or edition tiers.
  • MVCC by default — excellent concurrency without configuration.
  • Huge extension ecosystem: PostGIS, TimescaleDB, pgvector, Citus, pg_partman, pg_cron.
  • Native JSONB — genuinely competes with MongoDB.
  • Cross-platform, container-native, cloud-neutral.
  • Rich standards-compliant SQL; multiple procedural languages (PL/pgSQL, PL/Python, PL/V8).
  • Logical replication for zero-downtime major-version upgrades and cross-region replication.

Weaknesses

  • One process per connection → connection pooling essentially mandatory at scale (PgBouncer / RDS Proxy).
  • Vacuum & bloat management — a real operational burden if you have very high update rates.
  • No native cross-node sharding (need Citus / app-level).
  • No native columnstore.
  • Tooling is fragmented — you assemble your own BI stack.
  • GUI clients (pgAdmin, DBeaver) are functional but not as polished as SSMS.
  • Enterprise vendor support is via third parties (EnterpriseDB, Crunchy, Percona) rather than a single vendor.

Two cloud-era trends: (1) Postgres has more managed options because of open-source portability — you're not locked in. 💻 Small code — same task in both dialects

Table + JSON + indexed query

-- SQL Server --------------------------------
CREATE TABLE orders (
    id      INT IDENTITY PRIMARY KEY,
    payload NVARCHAR(MAX)   -- JSON stored as text
);
CREATE INDEX ix_customer ON orders (JSON_VALUE(payload,'$.customerId'));

SELECT id, JSON_VALUE(payload,'$.total')
FROM   orders
WHERE  JSON_VALUE(payload,'$.customerId') = '42';

-- PostgreSQL --------------------------------
CREATE TABLE orders (
    id      SERIAL PRIMARY KEY,
    payload JSONB           -- native binary JSON
);
CREATE INDEX ix_customer ON orders USING GIN ((payload -> 'customerId'));

SELECT id, payload ->> 'total'
FROM   orders
WHERE  payload @> '{"customerId":"42"}'::jsonb;   -- uses GIN index

Snapshot isolation

-- SQL Server — opt-in per DB, then set the level
ALTER DATABASE mydb SET READ_COMMITTED_SNAPSHOT ON;
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
-- Postgres — always MVCC; just set the level
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

Read replica routing (ADO.NET / Npgsql)

// SQL Server — Always On listener with ApplicationIntent
var read = new SqlConnection("Server=agListener;Database=app;ApplicationIntent=ReadOnly;...");
var write= new SqlConnection("Server=agListener;Database=app;ApplicationIntent=ReadWrite;...");

// Postgres — separate primary and replica DSNs, app-side routing
var read = new NpgsqlConnection("Host=replica-1.db,replica-2.db;LoadBalanceHosts=true;TargetSessionAttributes=any");
var write= new NpgsqlConnection("Host=primary.db;TargetSessionAttributes=read-write");

Two worked examples an interviewer likes:

You're building a healthcare EMR at a hospital that already runs Windows/AD, Power BI, and SSRS. Which DB?

SQL Server. AD integration, in-box BI, mature backup story, existing DBA skills. The extra licence is small compared to retraining the org.

You're building a modern SaaS multi-tenant app deployed on Kubernetes, using Go microservices, needing geo + vector search.

PostgreSQL. Free, PostGIS + pgvector cover the specialised needs, container-native, no licence. Add PgBouncer for connection pooling and Citus if you outgrow one node.

🗣️ Interview cheat sheet

30-second pitch: "SQL Server and PostgreSQL are both mature ACID-compliant RDBMSs, but they differ architecturally in four ways. One: concurrency — Postgres is MVCC everywhere, SQL Server is lock-based with opt-in row versioning (RCSI / Snapshot / Optimized Locking). Two: process model — SQL Server is one process with many threads under SQLOS, Postgres is one process per connection so pooling is essential. Three: ecosystem — SQL Server ships a full first-party BI stack (SSIS, SSAS, SSRS, Power BI) plus native columnstore, Postgres is best-of-breed extensions (PostGIS, pgvector, TimescaleDB, Citus). Four: licensing — SQL Server is commercial, Postgres is free forever. Choose SQL Server when you're .NET + Azure + Windows + already invested in the Microsoft BI stack. Choose Postgres for open-source-first, container-native, multi-cloud, or specialised extension needs like PostGIS or pgvector."

Five talking points that win the round

  • "Postgres = MVCC by default, SQL Server = locking by default." One sentence, senior-level signal.
  • "Postgres has one process per connection — pooling isn't optional at scale." Naming PgBouncer / RDS Proxy is the tell.
  • "SQL Server has native columnstore; Postgres doesn't." Big deal for hybrid OLTP+OLAP workloads.
  • "Postgres wins on extensibility — PostGIS, pgvector, TimescaleDB." The reason modern AI/RAG stacks pick Postgres.
  • "Licensing is often the deciding factor." Enterprise SQL Server can be 5–6 figures per socket-year.
