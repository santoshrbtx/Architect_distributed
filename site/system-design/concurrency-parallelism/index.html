Concurrency & Parallelism

🎯 The interview question

The prompt — and the real-time use case

The ask

"Design a multithreaded web crawler. Given a start URL, fetch the page, extract links on the same hostname, and keep crawling — but use many workers to go fast. Each URL must be visited exactly once. Then tell me: how do the threads share the 'visited' set safely, how do you avoid crawling the same page twice, how do you know when you're done, and would you use threads or async here?"

The follow-ups they'll drill into

  • Concurrency vs parallelism — are they the same thing? (No.)
  • Threads vs async/await — this is I/O-bound, so which wins and why?
  • How do you make the shared visited set thread-safe without killing throughput?
  • Where's the race condition, and how would a naive lock cause a deadlock or a bottleneck?
  • How do you detect termination when work generates more work?

This is the canonical concurrency question (it's LeetCode 1242, "Web Crawler Multithreaded," and shows up at Google, Meta, Amazon, and Microsoft) because it packs every core concept into one tractable problem: shared mutable state, synchronization, work queues, thread pools, and the hardest part — termination detection. The same skeleton is what powers real systems: Googlebot and Bingbot (search indexing), site-scrapers and SEO tools (Ahrefs, Screaming Frog), link-checkers, and data-pipeline ingesters that fan out across thousands of endpoints. The interviewer wants to see that you can reason about correctness under concurrency, not just make it "fast."

First thing to say out loud: "Concurrency is dealing with many things at once (structure); parallelism is doing many things at once (execution on multiple cores). A crawler is I/O-bound — threads spend their time waiting on the network — so the goal is high concurrency, not CPU parallelism. That points me at async/await over raw threads."

🧑‍🎓 In laymen terms

The busy kitchen with one fridge and one chopping board

Picture a busy restaurant kitchen on a Saturday night. Ten cooks are all trying to prepare different dishes at the same time, but they share one fridge, one chopping board, and one big pot of stock. If two cooks reach for the last onion at the exact same moment, one of them ends up empty-handed and the whole dish is ruined. If a cook grabs the chopping board and then walks off to answer the phone, everyone else is stuck waiting.

That is what happens inside a computer when many pieces of work run at the same time. Each cook is a little worker, and the shared fridge is memory that everyone needs to touch. The trick is letting cooks work in parallel without stepping on each other's toes.

Now imagine our kitchen is really a website like Google going out to fetch a million web pages. Each fetch is like sending a runner to a shop across town — the runner spends ages just waiting in traffic, not doing real work. It would be silly to hire a thousand runners when they are all just standing around waiting. Instead, one clever runner drops off many orders and comes back to whichever one is ready first. This is what "async" means in plain words — don't hire more people, just stop them from waiting idly.

The hard parts show up in tiny moments. Two cooks both scribble "onion" on the shopping list at once — now it's on there twice. That's called a race. A cook holds the fridge key while asking a colleague for the pantry key, and that colleague is holding the pantry key waiting for the fridge — nobody moves. That's a deadlock. And the head chef has to somehow know when everyone is finally done, so they can turn off the lights and go home. Products you use every day — Google Search crawling the web, WhatsApp handling millions of chats, your browser loading a page — all quietly solve this exact kitchen problem.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Crawl starting from a seed URL; extract links; visit each unique URL exactly once.
  • Stay within the same hostname (the LeetCode constraint) — generalizes to a configurable allow-list.
  • Return the full set of reachable URLs; run correctly with N concurrent workers.

Non-functional requirements (the hard part)

  • Correctness under concurrency — no duplicate fetches, no lost URLs, no crashes from data races.
  • High throughput — saturate available bandwidth by overlapping many in-flight requests.
  • Clean termination — stop when (and only when) all reachable URLs are done.
  • Politeness & safety — bounded concurrency so we don't DoS the target or exhaust the thread pool.

The decisive back-of-the-envelope: a fetch takes ~100 ms of waiting and ~1 ms of CPU. So a single thread doing sync fetches is idle 99% of the time. If you scale with OS threads, each costs ~1 MB of stack + scheduler overhead, so 10,000 in-flight requests = 10 GB of stacks — infeasible. With async/await, an awaiting request holds no thread (it's a state machine parked on a completion callback), so a handful of thread-pool threads can juggle thousands of concurrent fetches. That asymmetry is the whole reason async beats threads for I/O-bound work.

🏗️ High-level architecture

How the pieces fit together

The design is a producer–consumer pipeline. A concurrent work queue holds URLs to fetch; a pool of worker tasks dequeue a URL, fetch it (async I/O), parse links, and for each newly seen link enqueue it back — workers are both consumers and producers. A shared, thread-safe visited set guarantees each URL is enqueued once. The crux is the termination detector: because work creates more work, you can't stop when the queue is momentarily empty — a worker might be about to enqueue more. You track "outstanding work" with an atomic counter (or a CountdownEvent) and stop only when the queue is empty and no worker is mid-flight.

fetch path (dequeue → HTTP) feedback loop (claim URL, enqueue new work)
  1. Seed: add the start URL to the visited set and the work queue; set outstanding-work counter to 1.
  2. Dequeue: a free worker pulls a URL from the concurrent queue (or awaits a channel reader).
  3. Fetch (async): await httpClient.GetStringAsync(url) — the worker yields its thread while the network responds.
  4. Parse & claim: extract same-host links; for each, visited.TryAdd(link) — the atomic add is what makes "visit once" correct.
  5. Enqueue new work: only URLs that were newly added get enqueued; increment the outstanding counter per new item.
  6. Terminate: when a worker finishes a URL it decrements the counter; when it hits 0 (queue empty and nothing in flight), signal completion.

🔍 Component deep-dive

1. Concurrency vs parallelism (nail this distinction)

Concurrency is a structuring concern: composing a program as independently-progressing tasks that may interleave — it exists even on a single core (the OS time-slices). Parallelism is an execution concern: literally running instructions simultaneously on multiple cores. You can have concurrency without parallelism (thousands of awaiting async operations on one core) and parallelism without much concurrency (a Parallel.For splitting a big array across 8 cores). The crawler needs massive concurrency (many overlapping waits) but almost no parallelism, because the CPU work is trivial.

2. Threads vs async/await — the I/O-bound decision

Per Microsoft's own guidance: if the code waits for a result (network, DB, file), it's I/O-bound → use async/await without Task.Run; if it runs an expensive computation, it's CPU-bound → offload with Task.Run/TPL across threads. A crawler is overwhelmingly I/O-bound, so async is the right primitive. The key mental model: await compiles to a state machine that yields control back to the caller and frees the thread while the I/O is outstanding — so an awaiting request occupies no thread at all. Spawning one OS thread per URL would instead burn ~1 MB of stack each and drown in context-switch overhead.

3. The shared visited set & the race condition

The correctness hazard: two workers extract the same link at the same instant, both check "is it visited?", both see "no," and both enqueue it — a classic check-then-act race condition causing a duplicate crawl. The fix is to make "check and claim" a single atomic operation. ConcurrentDictionary.TryAdd(url, true) does exactly this: it returns true to exactly one caller and false to the rest, so only the first worker "wins" the URL and enqueues it. This is faster than a coarse lock because the dictionary shards its buckets internally, allowing many threads to update disjoint keys in parallel.

4. Locks, atomics, and lock-free

Three escalating tools. A lock (Monitor/mutex) gives mutual exclusion but serializes access — over-locking creates a bottleneck (and, if two locks are taken in different orders by different threads, a deadlock). Atomics (Interlocked.Increment, CAS) update a single value without a lock, ideal for counters and flags. Lock-free structures (like ConcurrentDictionary/ConcurrentQueue) use fine-grained atomics internally to let many threads progress without a global lock. Rule of thumb: prefer a concurrent collection or atomic over a hand-rolled lock; if you must lock, hold it briefly and always acquire multiple locks in a consistent global order to avoid deadlock.

5. Thread pools & bounded concurrency

You never new Thread() per task — you use the thread pool (which the TPL/async schedules onto), which reuses a small set of threads and grows/shrinks with load. But you still bound in-flight work: a SemaphoreSlim(maxConcurrency) caps how many fetches run at once so you don't hammer the target host or exhaust sockets. This is "politeness" and self-protection in one knob.

6. Termination detection — the sneaky-hard part

Because each fetched page produces more URLs, "queue is empty" does not mean "done" — a worker could be mid-fetch about to enqueue ten links. You need to know that the queue is empty and no worker is still processing. The clean solution is an outstanding-work counter: increment it when you enqueue, decrement when a URL is fully processed; when it reaches zero, everything reachable is done. In .NET, Task.WhenAll over a dynamically-growing task list, a CountdownEvent, or a Channel you Complete() when the counter hits zero all express this.

Why ConcurrentDictionary.TryAdd over lock + HashSet: a single global lock around a HashSet serializes every worker at the exact hottest path, collapsing your N workers to effectively one. The concurrent dictionary shards its internal buckets so unrelated URLs touch different locks, preserving parallel progress while still making each individual claim atomic. This is the "prefer fine-grained/lock-free over coarse locks" principle made concrete.

💻 C# implementation

The idiomatic .NET answer: an async crawler with a ConcurrentDictionary for atomic dedupe, a SemaphoreSlim to bound concurrency, and a growing Task.WhenAll for termination. No raw threads, no manual locks.

Async, bounded, race-free web crawler

using System.Collections.Concurrent;

public class WebCrawler
{
    private readonly HttpClient _http = new();
    // Atomic "claim" set: TryAdd returns true to exactly ONE thread per URL.
    private readonly ConcurrentDictionary<string, bool> _visited = new();
    // Bound in-flight fetches — politeness + socket safety (async-aware).
    private readonly SemaphoreSlim _gate;
    private readonly IHtmlParser _parser;

    public WebCrawler(IHtmlParser parser, int maxConcurrency = 50)
    {
        _parser = parser;
        _gate   = new SemaphoreSlim(maxConcurrency);
    }

    public async Task<IReadOnlyCollection<string>> CrawlAsync(string startUrl)
    {
        var host  = new Uri(startUrl).Host;
        var tasks = new ConcurrentBag<Task>();

        void Schedule(string url)
        {
            // The claim: only the FIRST caller for this url proceeds. Fixes the
            // check-then-act race that would otherwise double-crawl a page.
            if (Uri.TryCreate(url, UriKind.Absolute, out var u)
                && u.Host == host
                && _visited.TryAdd(url, true))
            {
                tasks.Add(FetchAsync(url, Schedule));  // pass the scheduler in
            }
        }

        async Task FetchAsync(string url, Action<string> schedule)
        {
            await _gate.WaitAsync();                 // throttle: at most N in flight
            try
            {
                // await FREES the thread while the network responds — the
                // reason async scales to thousands of fetches on few threads.
                var html  = await _http.GetStringAsync(url);
                foreach (var link in _parser.ExtractLinks(html))
                    schedule(link);                    // worker is also a producer
            }
            catch { /* log & skip dead links; don't kill the crawl */ }
            finally { _gate.Release(); }
        }

        Schedule(startUrl);
        // Termination: drain the dynamically-growing task set until no work remains.
        while (tasks.Any(t => !t.IsCompleted))
            await Task.WhenAll(tasks.ToArray());

        return _visited.Keys.ToList();
    }
}

The atomic counter alternative for termination (Interlocked)

// When you prefer a queue + fixed worker loop over a growing task list,
// an atomic outstanding-work counter tells you exactly when to stop.
private int _outstanding;

void Enqueue(string url)
{
    if (_visited.TryAdd(url, true))
    {
        Interlocked.Increment(ref _outstanding); // one CPU instruction, no lock
        _queue.Enqueue(url);
    }
}

void OnUrlProcessed()
{
    // Empty queue is NOT "done" — only zero outstanding work is.
    if (Interlocked.Decrement(ref _outstanding) == 0)
        _completion.TrySetResult(true);       // signal all-done
}

Other stacks solve the same problem with equivalent tools: Java's ConcurrentHashMap.putIfAbsent + ExecutorService + ConcurrentLinkedQueue + a Phaser/CountDownLatch; Go's sync.Map + goroutines + a sync.WaitGroup and channels; Python's asyncio + a set guarded by an asyncio.Lock. The primitives differ; the design is identical.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Async vs threads — don't mix them up. Using threads (or Parallel.ForEach) for the crawl wastes ~1 MB per blocked thread and caps you at hundreds of in-flight requests; async scales to thousands because awaiting requests hold no thread. Conversely, don't use async-without-Task.Run for a CPU-bound crunch — you'd just block the pool. Match the tool to bound-ness.

The lock bottleneck. A single global lock on the visited set serializes all workers at the hottest path, erasing your concurrency. Fine-grained/lock-free structures (ConcurrentDictionary) keep workers progressing in parallel — the difference between linear and near-zero speedup.

Deadlock & the sync-over-async trap. Deadlock arises when two threads grab locks in opposite orders — avoid by acquiring locks in a consistent global order and holding them briefly. A subtler .NET trap is sync-over-async: calling .Result/.Wait() on a task can deadlock against the captured synchronization context — the guidance is "async all the way down," use await, and if you truly must block, prefer GetAwaiter().GetResult().

Failure isolation & politeness. One dead link must not kill the crawl (catch per-fetch). Unbounded concurrency can DoS the target and exhaust sockets/file handles — always cap with a semaphore and honor robots.txt/rate limits in production.

Q: Concurrency and parallelism — same thing?

No. Concurrency is structuring work as interleavable tasks (exists on one core); parallelism is executing simultaneously on multiple cores. The crawler wants high concurrency (overlapping I/O waits), not parallelism, because its CPU work is negligible.

Q: Threads or async for the crawler?

Async. It's I/O-bound, so await frees the thread during network waits and a few pool threads juggle thousands of fetches. Threads would burn ~1 MB stack each and drown in context switches.

Q: How do you make the visited set thread-safe without a bottleneck?

ConcurrentDictionary.TryAdd — an atomic check-and-claim that returns true to exactly one worker. Its internal lock-striping lets many threads update different keys in parallel, unlike a single global lock around a HashSet.

Q: How do you know when the crawl is done?

Not when the queue is empty — a worker may be about to enqueue more. Track an atomic outstanding-work counter (increment on enqueue, decrement on completion) and stop only when it hits zero, or await a dynamically-growing Task.WhenAll.

Q: Where's the race condition in a naive version?

Check-then-act: two workers both see a URL as "not visited" and both enqueue it. Fix it by fusing the check and the insert into one atomic operation (TryAdd), so only the first worker claims it.

  • Open with concurrency ≠ parallelism and classify the work as I/O-bound.
  • Name the check-then-act race and kill it with one atomic TryAdd.
