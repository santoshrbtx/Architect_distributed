Estimating Daily Active Users with HyperLogLog

How Instagram counts billions of unique daily visitors using a probabilistic sketch that fits in ~12 KB — with mergeable per-shard HLLs, ~1% error, and constant memory regardless of scale.

🎯 The problem

Two billion Instagram users a day — count the unique ones

Instagram has ~2 B monthly active users and roughly 1–1.5 B daily active users. Product, growth, ranking, and infra teams all want the same number: how many distinct people opened the app today? The naive answer — put every userId in a HashSet and read set.size() — is correct but expensive at this scale. Even a compact 64-bit long per user is 1.5 B × 8 bytes ≈ 12 GB of RAM for a single day's DAU on one counter. Multiply by every dimension the business cares about (per country, per feature, per app version) and you're gigabytes-per-dimension-per-day.

The interview trick is not the memory number — it's the observation that we don't need exactness. Reporting "1.42 B DAU ± 12 M" is indistinguishable from "1.418 B DAU" for every downstream decision. This is the exact use case for HyperLogLog: a probabilistic cardinality sketch that gives ~1% error in constant 12 KB regardless of scale, is mergeable across shards and regions, and is a one-line command in Redis (PFADD / PFCOUNT / PFMERGE). Used in production at Meta, Google, Twitter/X, Reddit, Cloudflare — anywhere "how many unique?" is asked at web scale.

🧑‍🎓 In laymen terms

Guess the crowd size from the rarest coin-flip streak

Imagine you're standing at the door of a stadium and you want to know how many different people walked in today. The obvious way is to write everyone's name on a list. If two billion people walk in, your list is huge — and most of the space is wasted because you're really only interested in the size, not the names.

Here's a magic trick. When each person walks in, you flip a coin repeatedly until you get tails, and you write down only the longest run of heads you have ever seen so far. If the longest streak you see all day is "8 heads in a row", that's a very rare event — about 1-in-256 — which suggests you must have seen around 256 different people. If the streak is 20 heads long, you've probably seen about a million people. The rarity of the rarest streak tells you the crowd size, and you only need to remember one small number.

One streak is noisy — you might get lucky or unlucky. So instead you split the incoming crowd into, say, 16 384 lines (buckets), each line runs its own coin game, and you combine the answers with a bit of statistics. That's HyperLogLog. It uses about 12 KB of memory total, works for a hundred users or a hundred billion, and gives an answer within ~1% of the true count. Repeatedly seeing the same user just re-computes the same streak — the max doesn't change, so duplicates cost nothing.

The killer feature: two stadiums running the same game can merge their answer by taking the max streak per bucket. That's how Instagram counts DAU across dozens of regions and hundreds of shards without ever putting all user IDs in one place.

📋 Requirements & scale

What we're designing for

Functional

  • Report DAU for a given day: dau:2026-08-22.
  • Report DAU per dimension: country, feature, app version, story vs reel.
  • Merge across shards, regions, and time (weekly = 7-day merge).
  • Freshness: hourly rollup is fine; real-time within ~1 minute for ops dashboards.

Non-functional

  • Scale: 1–1.5 B distinct users/day, 100 K+ events/sec at peak.
  • Memory: constant per counter, not proportional to user count.
  • Accuracy: ≤ 1% standard error is acceptable for DAU.
  • Mergeable: sharded ingest must combine losslessly.

🏗️ High-level architecture

Ingest → partition → per-shard HLL → merge → single DAU number

Events fan out from every app server into a partitioned event stream (Kafka / Kinesis). Each partition owns a per-day HLL sketch. At query time (or continuously on a hourly rollup) we PFMERGE the per-partition sketches into one and read the count. The keys carry the date so yesterday's answer is a stable, immutable object.

App ingest Partitioned stream Per-shard HLL (Redis) Merge → single answer

Why partition first, HLL second: consumers can scale independently, hot Redis keys don't bottleneck, and a bad node loses at most one partition's sketch — replay from Kafka rebuilds it. The same pattern works for weekly / monthly by merging per-day HLLs on the read path, so nothing is recomputed.

Watch one HLL sketch two users, then merge across shards

Each user's ID is hashed to a 64-bit value. The first few bits pick a register (bucket); the remaining bits are scanned for the longest run of leading zeros — that run count is written into the register only if it exceeds the current maximum. Two shards each keep their own array of registers; a merge takes the per-register max, then a fancy harmonic-mean formula reads off the estimated cardinality.

🔍 Intuition & production details

Why the "run of zeros" trick works

A good uniform hash function turns a userId into a uniformly random 64-bit string. The probability of the first bit being zero is 1/2. Two zeros in a row is 1/4. Three is 1/8. In general, seeing a run of k leading zeros happens with probability 1/2^k. Turn that around: if the longest run you've ever seen is k, a plausible estimate for how many distinct hashes you've drawn is 2^k.

P(1 leading zero) ≈ 1/2 P(2 leading zeros) ≈ 1/4 P(3 leading zeros) ≈ 1/8 … Seen max-run k → crowd size ≈ 2^k

One counter is noisy — a lucky streak in a small crowd inflates the estimate massively. So HLL uses m = 2^p registers (Redis uses p = 14, giving m = 16 384), routes each hash to a register by its first p bits, and stores the max run seen in the remaining bits. The final estimate is a harmonic mean across the registers — much more robust than an arithmetic mean because outlier registers don't dominate.

Why duplicates are free

The same userId hashes to the same bucket and the same run length. Updating a register with max(r, r) = r is a no-op. Regardless of whether user 42 opens Instagram 1 time or 1 000 times today, they contribute at most one register write — and only if their run happens to exceed the register's current max.

Merging — the killer feature

Two HLLs with the same register layout merge trivially: for each register index take the max across the two sketches. That single operation preserves the guarantee that each register holds "the longest run seen across the union of both input streams". Formally:

merge(A, B).register[i] = max(A.register[i], B.register[i]) for i in 0..m-1

Consequences: shard the ingest any way you like (by userId, by region, by hour), then merge on demand. Weekly UV = PFMERGE dau:2026-08-16 .. dau:2026-08-22. Monthly = merge 30 keys. All constant memory, all fast.

Daily key strategy

One HLL per (dimension, day). Namespacing:

dau:2026-08-22 -- global dau:2026-08-22:country=IN -- country-level dau:2026-08-22:feature=reels -- feature-level dau:2026-08-22:cohort=android-14 -- cohort-level dau:2026-08-22:region=us-east-1:p7 -- per-partition, per-region

All 12 KB each. Even 10 000 such keys is 120 MB total — trivial for one Redis node. Set TTL of a few weeks and archive daily snapshots to S3/warehouse.

Fraud/security "did we see this exact ID before?"❌ Membership test — HLL cannot answer that; use a Bloom filter or a real set
Very small cardinalities (< 100)⚠️ HLL has larger relative error here; Redis uses a "sparse" encoding to help. Exact set is fine too.
Intersection sizes (users active on both days)⚠️ HLL intersection via inclusion–exclusion is noisy at large scale. Consider MinHash or exact for critical intersections.
Interview one-liner. "HLL answers how many distinct? — not was this one seen?. For membership tests reach for a Bloom filter; for exact revenue-critical counts stay with a real set or a DB DISTINCT."
🧮 The DSA behind it

Data structures & complexity

  • Hashing. Uniform 64-bit hash (MurmurHash3 in Redis's HLL). Same input → same output → duplicates absorbed for free.
  • Register array. Fixed m = 2^p small counters (6 bits each in Redis). Constant memory regardless of cardinality.
  • Max-over-registers. Each register stores max(rank(payload)) — a monotone accumulator. Merging is register-wise max, which is associative and commutative → arbitrary partitioning is safe.
  • Harmonic-mean estimator. Final estimate E = α_m · m² / Σ 2^(-r[i]) where α_m is a bias-correction constant. Small-range and large-range corrections handle the tails.

💻 C# — StackExchange.Redis

// Package: StackExchange.Redis
using StackExchange.Redis;

public class DauCounter(IDatabase db)
{
    // Called once per app-open event (idempotent on repeat).
    public Task RecordVisitAsync(Guid userId, DateOnly day, string? country = null)
    {
        var key       = $"dau:{day:yyyy-MM-dd}";
        var countryKey = country is null ? null : $"{key}:country={country}";

        // PFADD returns 1 if the sketch changed. We don't need the result.
        var uid = userId.ToString("N");
        var t1 = db.HyperLogLogAddAsync(key, uid);
        var t2 = countryKey is null ? Task.CompletedTask
                                : db.HyperLogLogAddAsync(countryKey, uid);
        return Task.WhenAll(t1, t2);
    }

    // Global DAU for a day.
    public Task<long> GetDauAsync(DateOnly day) =>
        db.HyperLogLogLengthAsync($"dau:{day:yyyy-MM-dd}");

    // Weekly unique visitors — merge 7 daily HLLs into a scratch key.
    public async Task<long> GetWeeklyUvAsync(DateOnly weekStart)
    {
        var keys = Enumerable.Range(0, 7)
            .Select(i => (RedisKey)$"dau:{weekStart.AddDays(i):yyyy-MM-dd}").ToArray();
        var scratch = (RedisKey)$"wau:{weekStart:yyyy-MM-dd}:scratch";
        await db.HyperLogLogMergeAsync(scratch, keys);
        try { return await db.HyperLogLogLengthAsync(scratch); }
        finally { await db.KeyDeleteAsync(scratch); }
    }
}

That's it — the entire per-event write path is one Redis command, and every rollup is PFMERGE + PFCOUNT. No custom state, no math on our side.

⚖️ Trade-offs & follow-ups

  • Memory vs accuracy. Redis's p=14 / 12 KB / 0.81% is the sweet spot; lower p saves memory at higher error. Choose per counter.
  • Not a membership test. HLL cannot answer "did user 42 log in today?" — use a Bloom/cuckoo filter or a real set for that.
  • Intersection noise. "Users active both Monday and Tuesday" via |A|+|B|−|A∪B| compounds error. If intersections are business-critical, use MinHash or Theta sketches.
  • Bot / duplicate hashing. Same botnet using different userIds inflates the count. Filter upstream (WAF / auth checks) rather than in the sketch.
  • Hash quality. Requires a well-mixing hash. MurmurHash3 (Redis's choice) is the standard; do not use a weak hash like Java's String.hashCode.

Why not just SELECT COUNT(DISTINCT user_id) FROM events WHERE date = today?

Works at low scale. At Instagram scale it is a multi-hundred-GB scan, blocks other work, and can't be merged across regions without pushing all the data to one place. HLL is 12 KB and merges by max.

Why is the error ~0.81%?

It's the standard error of the harmonic-mean estimator over m registers: ≈ 1.04/√m. For m = 16 384 that's ~0.81%.

What if I have two HLLs from different p?

You can't merge them directly. Pick one p for the whole system. Downgrading a larger HLL to a smaller one requires re-partitioning registers.

Same user opens the app 500 times today — is that a problem?

No. Same hash → same register → max(r, r) = r. Duplicates are free by construction.

How would you shard the writes?

Partition the event stream by hash(userId) % N. Each partition owns its own HLL (dau:2026-08-22:pN). At read time PFMERGE them.

What about privacy / GDPR?

Bonus win — HLL is one-way. You cannot recover a userId from the sketch. Meta uses this for anonymised counts (Cloudflare and others too).

🗣️ How I'd explain this in a Meta interview

Framing. "The naive answer is a HashSet of userIds. It's exact but memory-linear in the number of users — for Instagram's ~1.5 B DAU that's roughly 12 GB per counter, times every dimension the product team wants (country, feature, cohort). I'd propose HyperLogLog: constant 12 KB per counter, ~0.81% error, mergeable across shards. For a DAU number the error is invisible, and the memory savings are ~10⁶×."

Intuition. "The trick is that a uniform hash gives a uniform bit string. The probability of seeing a run of k leading zeros is 1/2^k, so if the longest run you've ever observed is k, you've plausibly drawn 2^k distinct values. A single counter is noisy, so HLL splits into 2^14 = 16 384 registers by the first 14 hash bits, keeps the max run per register, and combines with a harmonic mean. Same userId always hits the same register with the same run, so duplicates cost nothing — which is exactly what we want for DAU."

Architecture. "App events go into Kafka partitioned by hash(userId). Each consumer owns one HLL per (day, dimension, partition) in Redis via PFADD. Reads do PFMERGE across partitions and PFCOUNT. Weekly and monthly are just merges of the daily keys — nothing recomputed. Daily HLLs snapshot to S3 for retention; Redshift and Athena both have approx_count_distinct so the same sketch idea lives at the warehouse layer too."

Trade-offs I'd volunteer. "HLL is not a membership test — use Bloom filters for that. It's not for finance-grade exact counts — use a real set. Intersections are noisy — use MinHash for that. And bot traffic must be filtered upstream, not in the sketch."
