🎯 Real-world scenario

The problem an interviewer is really asking

An interviewer draws twenty rectangles labelled App 1 through App 20, a load balancer on top, and says: "Each user is allowed 100 requests per minute. Any server may see any request. Design the rate limiter." The trap is subtle. On a single server you would use a hash-map counter and be done in five lines. In a distributed system that same map is twenty independent counters — the load balancer sprays requests across boxes, so a user who has already spent all 100 requests on server A can happily continue on server B and still look "under the limit" on both. Local memory is the wrong place for shared state.

The classic fix is to move the counter into a shared, in-memory store that every application server can hit with sub-millisecond latency: Redis. Redis gives you exactly what a rate limiter needs — atomic operations (INCR, EXPIRE, ZADD, sorted sets), TTL for automatic cleanup, and Lua scripting so a "read, decide, write" sequence executes as one indivisible unit. Once the counter lives in Redis, all twenty servers are agreeing on the same source of truth: one rate-limit:user:101:2026-08-22T10:15 key, one atomic increment, one decision.

Every serious API service you use has this in front of it: Stripe runs four layers of token-bucket limiters on Redis and rejects millions of requests a month; GitHub, Twitter, Cloudflare, and AWS API Gateway all publish 429s under the same design. It is a top-3 interview question at Amazon, Google, Meta, and Stripe because it touches distributed state, atomicity, algorithm choice, HA trade-offs, and the CAP conversation — all in a single, contained problem.

Without a shared limiter ======================== Client (userId=101) | v Load Balancer +---------------+---------------+ | | | v v v App 1 App 2 App 3 ... App 20 local: 30 local: 27 local: 26 each thinks "still fine" | | | +-------- 100+27+26+... requests -------> upstream service | v ~2,000 req/min slipping through a "100/min" limit
🧑‍🎓 In laymen terms

Explained like you've never written code

Imagine a busy coffee shop that has one loyalty rule for every customer: "You can order at most 100 coffees between 10:00 and 11:00." Simple enough — one barista could just keep a tally sheet under the counter for each regular. If Priya walks up for her 101st coffee, the barista sees her tally is full and politely says "come back at 11:00."

Now the shop gets popular and opens twenty checkout counters. Priya can walk up to any counter, and no barista knows what the others have already served her. If each counter keeps its own private tally sheet, Priya could get 100 coffees at counter 1, then another 100 at counter 2, and so on. Twenty tally sheets can't enforce one rule. This is exactly the situation for a website with many servers.

The fix is beautifully simple: put one shared tally sheet on the wall in the middle of the shop. Every barista, at every counter, must run to the same wall, put a mark next to Priya's name, and check that she hasn't crossed 100 marks in the current hour. Because the sheet lives in one place, all twenty counters agree on the same count. The "wall" in a real system is a lightning-fast in-memory scratchpad called Redis, and the marks are just numbers that get automatically wiped after an hour so the sheet doesn't fill up forever.

There's a hard part everyone misses on the first try. Two baristas can walk to the wall at the same instant, both read "99", both think "one more is fine", both put a mark, and now Priya has 101 with the wall reading 100. The counters were not talking to each other. So we don't ask the wall "what's the count?" and then write — we ask it "add one and tell me the new number" as a single unbreakable action. That way even if a thousand baristas rush the wall at the same nanosecond, they each get a unique number: 99, 100, 101, 102… and everyone past 100 is turned away. This "add-then-return" step is the atomic core of the whole idea, and it is why Redis is the go-to answer.

You've used this every day. When you refresh WhatsApp too fast and it says "please try again", when Instagram briefly stops loading after you scroll like a maniac, when Gmail says "you're sending too many messages" — you're being politely turned away by a system just like the one above. The whole point is fairness: no one user gets to hog the shop, so everyone else can still get their coffee.

📋 Requirements & scale

What we're actually building — and how big

Functional requirements

  • Enforce N requests / window per user (default: 100 per minute).
  • Return HTTP 429 Too Many Requests when the limit is exceeded, with Retry-After and standard RateLimit-* headers.
  • Support multiple dimensions: per user, per IP, per API key, per tenant, per endpoint (and combinations like user+endpoint).
  • Support multiple algorithms: fixed window (simplest), sliding window (accurate), token bucket (bursty), leaky bucket (smoothing).
  • Configurable limits per route (login gets 5/min, search gets 100/min, profile GET gets 1000/min).

Non-functional requirements

  • Low latency: rate-limit check must add ≤ 1–2 ms p99 to every request.
  • Atomic: no race condition ever produces "counter says 100 but 101 got through".
  • Horizontally scalable: works with 20 app servers today, 2,000 tomorrow, unchanged.
  • Highly available: Redis outage should not black-hole the whole product — need an explicit fail policy.
  • Observable: metrics for allowed / rejected, hot keys, script errors, Redis latency, decision distribution.
  • Automatic cleanup: no key ever leaks past its window (TTL on every counter).

🏗️ High-level architecture

How the pieces fit together

The request flow is a single Redis round-trip inserted between the load balancer and the business logic. Every app server holds a Redis client with connection pooling, and every rate-limit decision is a single call to a pre-loaded Lua script (EVALSHA) so the network cost is one command per request. The Redis cluster shards keys by their hash slot — rl:user:101:* lives on one shard, rl:user:502:* on another — and each shard is fronted by a primary with one or two async replicas for HA.

Redis key patterns

Key naming carries the entire rate-limit contract. Include the algorithm prefix, the dimension, the identifier, and (for fixed/sliding windows) the window bucket. This is what an interviewer wants to see on the whiteboard:

⚙️ Algorithm progression — the interview march

Interviewers listen for how you evolve the design, not for the fanciest algorithm dropped on the table. Start simple, name each failure mode, then upgrade. This is the exact ladder:

1. Fixed Window Counter (the "obvious" first cut)

For each user, mint a key that includes the current minute. Every request runs an atomic INCR; if the resulting value is ≤ 100, allow it. Set a TTL of 60–61 seconds so old windows evaporate on their own.

Key:    rl:fw:user:101:2026-08-22T10:15
INCR    -> 1, 2, 3, ..., 100, 101
IF count <= 100  allow
IF count >  100  return 429

Why this works even across 20 app servers. Redis processes commands one at a time on a single thread per shard, and INCR is a single command — no two concurrent increments can ever produce the same return value. Every server sees a unique, monotonically increasing counter for that user's window. That is the whole distributed-consensus story reduced to one command.

The atomicity bug you must call out: INCR then EXPIRE as separate commands is a subtle bug. If the app crashes or the network drops between the two, the counter has been incremented but has no TTL, so the key lives forever. Do them together in a Lua script (see below) or inside MULTI/EXEC. Also, only set the TTL when the counter is first created (count == 1); do not reset it on every increment or the window will silently slide forward.

2. The Fixed-Window Boundary Burst Problem

Fixed window looks tight but has a well-known hole. Suppose the limit is 100/min. A user sends 100 requests in the last second of window 1 (say 10:00:59), then 100 more in the first second of window 2 (10:01:00). Each individual window is at exactly 100 — both under the limit — but the user has effectively done 200 requests in ~2 seconds. Interviewers love this trap because it feels correct until you look at a two-second slice.

Fixed-window boundary burst =========================== 10:00:00 10:00:59 | 10:01:00 10:01:59 ------------------------------------|------------------------------------- 100 req || 100 req \ | || / \ | || / \ | || / v v vv v ~200 requests in a 2-second slice while every window "says 100"

Fix it by either (a) upgrading to a rolling window (log or counter), or (b) adopting token bucket. The next two algorithms do both.

3. Sliding Window Log (accurate but expensive)

Store one Redis Sorted Set per user. Each incoming request adds a member scored by its timestamp (in ms). Before deciding, drop everything older than now − window, then check how many members remain. If < limit, add the current request and allow. All four operations must run inside a single Lua script so no other request can interleave.

-- Lua, evaluated atomically on Redis
local key    = KEYS[1]
local now    = tonumber(ARGV[1])   -- ms
local window = tonumber(ARGV[2])   -- ms
local limit  = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, now .. ':' .. ARGV[4])   -- unique member
    redis.call('PEXPIRE', key, window + 1000)
    return {1, limit - count - 1}
else
    return {0, 0}
end

Verdict: perfectly accurate — every "in the last 60 seconds" question is answered exactly. The cost is memory (one sorted-set entry per request) and CPU (log-time inserts + range deletes). Fine at moderate scale, painful at millions of RPS.

4. Sliding Window Counter (95% accurate, 5% of the memory)

Keep only two fixed-window counters: the current one and the previous one. Weight the previous by the fraction of the current window still ahead of us.

Approx count = previous_count × (1 − elapsed/window) + current_count

Example
-------
Limit = 100/min
previous_count = 80  (10:14:00-10:14:59)
current_count  = 30  (10:15:00-10:15:14 → 25% elapsed)

Approx = 80 × (1 - 0.25) + 30
       = 60 + 30 = 90   →  allow (90 < 100)

Verdict: essentially eliminates the boundary burst while using only two integer keys per user. Cloudflare famously runs this in production. Most interviews accept this as "the right general answer" for accuracy-sensitive workloads.

5. Token Bucket (bursts allowed, average rate enforced)

Model the user as a bucket that holds up to capacity tokens and refills at a constant rate. Every request costs one token (or more, for expensive endpoints). If the bucket has ≥ cost tokens, deduct them and allow; otherwise reject. State fits in a Redis hash with two fields: tokens and last_refill_ms.

-- Token bucket, evaluated atomically
local key       = KEYS[1]
local now       = tonumber(ARGV[1])    -- ms
local capacity  = tonumber(ARGV[2])
local refillPerMs = tonumber(ARGV[3])  -- e.g. 100/60000 = 0.00167
local cost      = tonumber(ARGV[4])

local data = redis.call('HMGET', key, 'tokens', 'last')
local tokens = tonumber(data[1]) or capacity
local last   = tonumber(data[2]) or now

local delta  = math.max(0, now - last) * refillPerMs
tokens = math.min(capacity, tokens + delta)

if tokens >= cost then
    tokens = tokens - cost
    redis.call('HMSET', key, 'tokens', tokens, 'last', now)
    redis.call('PEXPIRE', key, math.ceil(capacity / refillPerMs) * 2)
    return {1, tokens}
else
    redis.call('HMSET', key, 'tokens', tokens, 'last', now)
    redis.call('PEXPIRE', key, math.ceil(capacity / refillPerMs) * 2)
    return {0, tokens}
end

Verdict: the general-purpose winner. It permits organic bursts (a real user clicking fast), enforces the average, supports weighted costs (a search costs 5 tokens, a report costs 20), and matches how Stripe, AWS API Gateway, and most cloud APIs actually behave. This is the safe answer to "which one would you pick in production?"

6. Leaky Bucket (constant output rate)

Requests are placed into a bounded FIFO queue; a worker drains the queue at a fixed rate. Excess is dropped. Where token bucket allows bursts of size capacity, leaky bucket smooths traffic to an exactly-constant rate. Use it when downstream systems need predictable pacing (video ingest, IoT metric fan-in, downstream call quotas). Rarely the first-choice algorithm for HTTP APIs.

🔍 Component deep-dive

Why the app-side "GET then SET" pattern is a bug

The single most common mistake candidates make is to read the counter, decide, then write. On distributed servers this is a race waiting to happen. Two servers see 99, both allow, both write 100 — 101 requests slip through while Redis still says 100.

Server A Server B Redis | | | | GET rl:user:101 -----> | | | <-- 99 | | | | GET rl:user:101 ------> | | | <-- 99 | | decide: allow | decide: allow | | SET rl:user:101 100 -> | | | | SET rl:user:101 100 -> | | | | Both requests admitted, counter shows 100. Real total: 101.

The fix is to never let the application make the decision — let Redis make it atomically. INCR is atomic. Better yet, wrap the entire "increment + expire + limit-check + return remaining" flow in a Lua script and call it via EVALSHA. Redis executes the whole script under its single-threaded event loop; nothing can interleave.

Race conditions and atomic Lua

Redis Lua is the interview power move. Every serious rate-limit implementation you'll read (Stripe, Cloudflare, Envoy, AWS SDK) ships a Lua script and calls it with EVALSHA <sha1> so the script bytecode is cached in Redis and only the args cross the wire. Because Redis is single-threaded per shard, the whole script is one atomic step: no other client can see an intermediate state, and no other command can slip in.

Multiple, layered rate limits

Real APIs need more than one rule at a time. A single request may need to pass a per-IP limit, a per-user limit, a per-tenant limit, and a per-endpoint limit. Naïvely that is four round-trips. The production pattern is a single Lua script that accepts an array of (key, limit, algo) tuples, evaluates them in order, and short-circuits on the first violation — one Redis call, all-or-nothing.

Layered check order (short-circuit on reject): Global 500,000 rps -> protect the site Per-tenant 10,000 rpm -> fairness across customers Per-user 100 rpm -> the problem statement Per-endpt /login 5 rpm -> security-critical routes Per-IP 500 rpm -> bot protection Single EVALSHA batches all of them, returns first-fail.

Redis HA and what happens during failover

Redis replication is asynchronous. If a primary crashes with a few writes not yet on the replica, and the replica is promoted, those in-flight increments are lost — a promoted replica may report fewer requests than actually happened. For a bank this would be a disaster; for a rate limiter it means a user briefly gets a handful of extra requests during failover. That is a trade-off almost every production system accepts, because rate limits are advisory, not correctness-critical.

If you genuinely need strict correctness across a failover, options are: (a) Redis WAIT to block until a replica ACKs (adds latency), (b) run Redis with AOF fsync=always (heavy write cost), or (c) use a stronger primitive like Redlock or a CP KV store. In an interview, explicitly name the trade-off — do not pretend Redis gives you strong consistency.

Hot keys and sharding

Redis Cluster distributes 16,384 hash slots across shards, and a key's slot is CRC16(key) mod 16384. Most rate-limit keys are per-user or per-IP, so traffic spreads naturally. But a global limit (rl:fw:global) becomes a single hot key — all traffic funnels to one shard. Options: shard the global counter across N sub-keys (rl:fw:global:{shardId}) and sum on read, or move the global limit up to an edge tier that pre-aggregates.

HTTP semantics — the response contract

Return HTTP 429 Too Many Requests. Attach these headers on every response (allowed or not), so clients can back off gracefully:

HeaderMeaning
RateLimit-Limit: 100Total requests permitted in the window.
RateLimit-Remaining: 37How many still available.
RateLimit-Reset: 42Seconds until the window resets (or Unix timestamp).
Retry-After: 42Standard header on 429/503. Seconds or HTTP-date.

For load-shedding (as opposed to per-user rate limiting), Stripe returns HTTP 503 instead of 429, because 503 signals "server is overloaded" rather than "you personally are over your quota".

Fail-open vs fail-closed — the design conversation that wins the interview

What should the app do if Redis is unreachable? This is not a bug — it is a policy decision.

Fail open (allow the request)

When Redis breaks, the API still serves. Availability wins.

  • ✅ Product doesn't go down because Redis has a hiccup.
  • ❌ Attackers can DoS Redis to bypass rate limiting.
  • Use for: public read APIs, browsing, low-risk endpoints, and Stripe's own default (they explicitly say limiter failure must not block the API).

Fail closed (reject the request)

When Redis breaks, requests are refused. Safety wins.

  • ✅ Protection is never lifted — good for auth and abuse-prone endpoints.
  • ❌ Redis is now on the critical availability path for the product.
  • Use for: login (brute-force protection), password reset, expensive/paid operations, security-sensitive writes.

The correct interview answer is "it depends on the endpoint, and I would set the policy per route in configuration." A login endpoint fails closed; a public listing endpoint fails open. Volunteering this nuance is what an interviewer waits to hear.

Where should the limiter live? Gateway vs app vs dedicated service

API Gateway (e.g., AWS API Gateway, Envoy, Kong)

  • 👍 One layer above the app fleet — cheap, uniform, no code in each service.
  • 👍 Blocks abuse before it reaches your compute; protects downstream systems.
  • 👎 Coarse: usually per-key/IP; less business context (user tier, endpoint cost).

Application middleware

  • 👍 Rich context — knows user tier, tenant, request cost.
  • 👍 Simple to reason about: same code path as auth and logging.
  • 👎 Every service must implement it; drift risk.

Dedicated rate-limit service (Envoy RLS pattern)

  • 👍 One team owns policy; used by many apps + the gateway.
  • 👍 Central place for observability, dashboards, kill switches.
  • 👎 Extra hop (though usually < 1 ms in-region).

Hybrid (the real answer)

  • Gateway does coarse global/IP throttling.
  • Dedicated service (or shared library) enforces user/tenant/endpoint policies backed by Redis.
  • Individual apps can still short-circuit with a local cache for hot allow-lists.

💻 C# implementation — atomic Lua on Redis via StackExchange.Redis

This is the reference implementation an interviewer expects to see: a single Lua script loaded once, executed via EVALSHA on every request, with a fail-open policy toggle and structured metadata returned to the caller. The script bakes in the classic "INCR then EXPIRE only if fresh" atomic pattern.

// -------- FixedWindowRateLimiter.cs --------
using StackExchange.Redis;

public sealed record RateLimitDecision(
    bool Allowed,
    long Count,
    long Remaining,
    int RetryAfterSeconds,
    bool FailedOpen);

public sealed class FixedWindowRateLimiter
{
    // Atomic on Redis: INCR + set TTL on first hit. Returns {count, remaining}.
    private const string Script = @"
        local c = redis.call('INCR', KEYS[1])
        if c == 1 then
            redis.call('EXPIRE', KEYS[1], ARGV[2])
        end
        local limit = tonumber(ARGV[1])
        return { c, math.max(0, limit - c) }
    ";

    private readonly IDatabase _db;
    private readonly LoadedLuaScript _script;
    private readonly ILogger<FixedWindowRateLimiter> _log;
    private readonly bool _failOpen;

    public FixedWindowRateLimiter(
        IConnectionMultiplexer mux, ILogger<FixedWindowRateLimiter> log, bool failOpen)
    {
        _db  = mux.GetDatabase();
        _log = log;
        _failOpen = failOpen;
        var server = mux.GetServer(mux.GetEndPoints()[0]);
        _script = LuaScript.Prepare(Script).Load(server);   // upload once, cached by SHA1
    }

    public async Task<RateLimitDecision> CheckAsync(
        string dimension, string id, int limit, TimeSpan window)
    {
        var nowMinute = DateTimeOffset.UtcNow.ToUnixTimeSeconds() / (long)window.TotalSeconds;
        var key = new RedisKey($"rl:fw:{dimension}:{id}:{nowMinute}");
        var ttl = (int)Math.Ceiling(window.TotalSeconds) + 1;

        try
        {
            var res  = (RedisResult[])await _script.EvaluateAsync(_db,
                new { key, limit, ttl })!;
            long count = (long)res[0];
            long remaining = (long)res[1];

            if (count <= limit)
                return new RateLimitDecision(true, count, remaining, 0, false);

            // how many seconds until the current window ends
            var retry = (int)(window.TotalSeconds -
                (DateTimeOffset.UtcNow.ToUnixTimeSeconds() % (long)window.TotalSeconds));
            return new RateLimitDecision(false, count, 0, retry, false);
        }
        catch (RedisException ex)
        {
            _log.LogError(ex, "Rate-limit Redis call failed for {Dim}:{Id}", dimension, id);
            if (_failOpen) return new RateLimitDecision(true, 0, limit, 0, true);
            throw;   // let middleware translate to 503
        }
    }
}

And the ASP.NET middleware that wires it into the request pipeline. Note the emitted headers, the 429 body, and the metrics hook:

// -------- RateLimitMiddleware.cs --------
public sealed class RateLimitMiddleware(
    RequestDelegate next,
    FixedWindowRateLimiter limiter,
    IMetrics metrics)
{
    public async Task InvokeAsync(HttpContext ctx)
    {
        var userId = ctx.User.FindFirst("sub")?.Value ?? ctx.Connection.RemoteIpAddress?.ToString() ?? "anon";

        var d = await limiter.CheckAsync("user", userId, limit: 100, TimeSpan.FromMinutes(1));

        ctx.Response.Headers["RateLimit-Limit"] = "100";
        ctx.Response.Headers["RateLimit-Remaining"] = d.Remaining.ToString();
        ctx.Response.Headers["RateLimit-Reset"] = d.RetryAfterSeconds.ToString();

        if (!d.Allowed)
        {
            metrics.Increment("rate_limit_rejected_total", ("route", ctx.Request.Path));
            ctx.Response.StatusCode = 429;
            ctx.Response.Headers["Retry-After"] = d.RetryAfterSeconds.ToString();
            await ctx.Response.WriteAsJsonAsync(new { error = "rate_limited", retryAfter = d.RetryAfterSeconds });
            return;
        }
        if (d.FailedOpen) metrics.Increment("rate_limit_fail_open_total");
        metrics.Increment("rate_limit_allowed_total");
        await next(ctx);
    }
}

Alternative language notes. The Lua script is portable — it runs unchanged on any Redis client. In Java, this is redisTemplate.execute(RedisScript.of(SCRIPT), keys, args); in Go, rdb.EvalSha(ctx, sha, keys, args); in Python, redis.evalsha(sha, 1, key, limit, ttl). The middleware structure is identical everywhere.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Q. Why not just do it in-process on each application server?

A. Because a user's requests can be load-balanced to any of the N servers. Each local counter only sees a fraction of the traffic, so 100 rpm easily becomes 100 × N rpm in aggregate. Shared state is not a nice-to-have here; it's required.

Q. Why Redis specifically?

A. Four properties in one package: sub-millisecond latency, atomic single-command primitives (INCR, ZADD), first-class TTL for automatic cleanup, and Lua for multi-op atomicity. Add horizontal scaling via Cluster and multi-AZ HA via ElastiCache — you rarely find that combination elsewhere.

Q. Is Redis INCR really atomic across a cluster?

A. Atomic within a shard — which is where the key lives. Redis is single-threaded per shard; each command runs to completion before the next starts. Two clients incrementing the same key can never observe the same return value.

Q. What if the INCR succeeds and the EXPIRE fails?

A. The counter has no TTL and lives forever, leaking memory. The fix is to combine the two into a single Lua script (or MULTI/EXEC), and only set the TTL when the counter was freshly created (if count == 1). Don't refresh the TTL on every increment — that would slide the window forward indefinitely.

Q. When would you pick sliding window over token bucket?

A. When you need strict rolling-window enforcement — e.g., "at most 5 login attempts in any 60-second sliding window." Token bucket allows short bursts by design, which is undesirable for auth. For "at most 100 req/min on average with small bursts okay", token bucket wins.

Q. How do you handle a Redis failover during traffic?

A. Async replication means a few writes may be lost on promotion, so a user may briefly get a handful of extra requests. That's acceptable for rate limiting (advisory, not correctness-critical). If strict correctness is needed, use WAIT for replica ACK (adds latency) or move to MemoryDB / a CP store — but call the trade-off out explicitly.

Q. How do you keep global limits from becoming a hot key?

A. Shard the global counter across N sub-keys (rl:global:{0..N-1}), route randomly, and check the aggregate — or push global throttling up to the API Gateway / WAF layer where it doesn't touch Redis at all. Never let all traffic pin one shard.

Q. What's the worst-case blast radius if this component fails?

A. Depends on the failure policy. Fail-open: rate limits are temporarily lifted, product stays up, abuse is possible. Fail-closed: legitimate users are rejected, product may as well be down. Almost all high-availability APIs default to fail-open with per-endpoint overrides for auth/payment.

Q. How do you support "different limits for different endpoints"?

A. Externalise policies. Store (route → algo, limit, dimension, failurePolicy) in AppConfig or a config table. The middleware looks up the policy by route and calls the appropriate Lua script. Operators change limits without redeploying code.

Q. Bottlenecks?

A. (1) Redis network round-trip — mitigate with connection pooling and colocated Redis (same VPC/AZ). (2) Hot keys — shard global counters. (3) Lua script errors — pre-load via SCRIPT LOAD and alert on NOSCRIPT misses. (4) Serialisation cost of headers — cheap, but real at 1M rps.

🗣️ How I'd explain this in an Amazon interview

The 2–3 minute verbal walkthrough

Here's the mental script — the exact sentences to say out loud, in order, when the whiteboard is empty and the interviewer says "design a rate limiter across our 20 app servers."

  1. Frame the problem. "The application is horizontally scaled, so requests for the same user can hit any of the 20 servers. Local counters can't enforce a global limit, so the rate-limit state has to be shared."
  2. Pick the store. "I'd keep that shared state in Redis — in-memory, atomic operations, sub-millisecond latency, TTL for automatic cleanup, and Lua for multi-op atomicity."
  3. Simplest working design. "For fixed-window, mint a key per user per minute — rl:fw:user:101:2026-08-22T10:15 — and run INCR. If the return is ≤ 100 allow; otherwise return HTTP 429."
  4. TTL and atomicity. "Set a TTL of 60 seconds so windows self-clean. Wrap INCR + EXPIRE in a Lua script so if the app crashes between them we don't leak a TTL-less counter."
  5. Name the fixed-window bug. "Fixed window has a boundary-burst problem: 100 requests at 10:00:59 plus 100 at 10:01:00 is 200 in two seconds. So for accurate enforcement I'd upgrade to sliding window (Redis sorted set) or the two-window sliding counter approximation."
  6. Production pick. "In production I'd default to token bucket — same Redis + Lua pattern, but state is {tokens, last_refill} in a hash. It permits organic bursts and supports weighted costs, which is what Stripe and API Gateway use."
  7. Race-safety statement. "The whole decision runs inside one Lua script via EVALSHA, so Redis single-threading guarantees no interleaving even across all 20 servers hitting the same key."
  8. HA behaviour. "For availability I'd run Redis Cluster with multi-AZ replicas. Async replication means a handful of extra requests may slip through during failover — that's fine for a rate limiter because it's advisory, not a bank ledger."
  9. Failure policy. "I'd make fail-open vs fail-closed a per-endpoint config. Public reads fail open so a Redis blip doesn't take the API down; login and payment fail closed so brute-force protection stays on."
  10. Scale. "At 1M rps I'd shard Redis by user hash; hot global keys get split across N sub-keys. Total memory is trivial because TTL keeps only active windows alive."
  11. Observability. "Emit allowed_total, rejected_total, redis_p99_latency, fail_open_total. Alarm on unusual 429 spikes and Redis error rate. Every limiter is behind a kill-switch flag."
  12. Placement. "Coarse throttling at the API Gateway or WAF (per-IP), business-aware limits at the application middleware (per-user, per-tenant, per-endpoint), all backed by the same Redis cluster."
Close with the one-liner: "Redis gives us shared state and atomicity for distributed rate limiting, but the real design decisions are the algorithm choice, atomic expiry handling, the failure policy, and the accuracy-versus-cost trade-off — all of which I'd tune per endpoint."

✅ Interview cheat sheet

30-second pitch: "Shared counter in Redis, atomic via Lua. Fixed window is simple but bursts on boundaries; sliding-window or token-bucket for accuracy; token bucket for controlled bursts. Fail-open for reads, fail-closed for auth. Redis Cluster for scale. Every limit is per-route configuration."

Numbers to quote

  • Redis single-shard: ~100k ops/s of simple commands, ~1 ms p99 including RTT.
  • Memory: ~80–120 B per active user for fixed window / token bucket.
  • Cluster: 16,384 hash slots, sharded by CRC16(key) mod 16384.
  • HTTP: 429 for per-user rate limits, 503 for global load shedding.

Five talking points that win the round

  • Atomicity: Lua script + EVALSHA, never GET-then-SET.
  • Boundary burst: name the fixed-window bug before the interviewer asks.
  • Token bucket = production default: bursts + weighted costs + Stripe-style tiers.
  • Fail-open vs fail-closed is a policy, not a bug: set it per route.
  • Rate limiting is advisory: async replication trade-offs are acceptable.
