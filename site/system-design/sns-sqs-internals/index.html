How SNS & SQS Work Internally

The distributed pub/sub topic and the polled queue that power almost every event-driven AWS system — architecture, message lifecycle, visibility timeout, FIFO dedup, fanout, and the numbers to quote in an interview.

🎯 Real-world scenario

Two of the most-used services in AWS — and almost nobody knows how they work inside

Every serverless architecture, every event-driven microservice mesh on AWS, every "an order was placed" fan-out you've ever seen is built on Amazon SNS (Simple Notification Service — pub/sub topics), Amazon SQS (Simple Queue Service — polled queues), or both together. They are the ambient plumbing of the AWS platform: Lambda uses SQS for its event source polling; S3 events go out via SNS or EventBridge; DynamoDB Streams → Lambda → SNS; every "customer signed up → send email + credit points + refresh cache" flow uses one of them. Combined, they process trillions of messages a day globally.

Interview-wise, "how does SQS work internally?" is a favourite architect question — because a strong answer requires you to reason about durability across AZs, at-least-once delivery, visibility timeouts, long polling, FIFO deduplication, in-flight limits, and dead-letter queues. Then "how does SNS deliver to five subscribers?" tests fanout, retry policy, and filter subscriptions. And the two together form the canonical SNS-SQS fanout pattern — one topic, N queues, each with its own consumer scaling independently.

This page opens the box and shows exactly how each service is built, with a system-design diagram you can whiteboard, a step-by-step animation of the message lifecycle, real numbers (30 s default visibility timeout, 4-day retention, 120k in-flight, 5-min dedup window, 300 TPS FIFO, 3000 TPS FIFO-batch, 70 k TPS high-throughput FIFO), and the C# code for a producer and consumer.

🧑‍🎓 In plain English

The story, told without jargon

Imagine a busy office again. Two rooms sit in the middle of the building.

SQS is the mail tray. When someone writes a memo ("please pay invoice #42"), they drop it into the tray. The tray is durable — even if the office building loses power on one side, the memo survives because three identical trays in three separate rooms hold a copy. When a colleague walks by, they pick up ONE memo, take it to their desk, and start working on it. Crucially, the mail tray hides the memo from everyone else for the next 30 seconds — so nobody else picks up the same memo. Once the colleague is done, they walk back and tear the memo up. If they don't come back in 30 seconds (they got sick, walked out, computer crashed), the memo reappears in the tray for someone else to try. Simple, safe, no lost work.

SNS is the office PA system. When someone says "an order was placed", they announce it over the loudspeaker. Everyone who has subscribed to the "orders" channel hears it — the warehouse guy, the email department, the loyalty desk, the analytics team. SNS doesn't store the memo the way the tray does; it just broadcasts, once, to whoever is listening. If a listener is deaf that moment (their service is offline), that message is lost to them — unless we told SNS to leave a copy in their personal mail tray (SQS). That combination — announce over PA, drop a copy in each listener's tray — is called fanout, and it's the single most common pattern on AWS.

Two products, two ideas: SQS = one-to-one durable queue. SNS = one-to-many broadcast. Put them together and you get resilient, decoupled, event-driven systems where the producer doesn't know or care who's listening, and each listener processes at its own pace.

Rule of thumb: use SNS when N subscribers care about the same event. Use SQS when a producer needs to hand work to a worker fleet at its own pace. Combine them (SNS → N SQS queues) when you want both fanout and per-subscriber durability. This is the canonical AWS event-driven pattern.

🏗️ Reference architecture — the fanout pattern

The design that appears in almost every AWS system

An Order Service publishes OrderPlaced once to an SNS topic. Four subscribers care: Warehouse, Email, Loyalty, and Analytics. Each has its own SQS queue subscribed to the topic. Each queue's consumer polls independently, processes at its own rate, retries on failure, and after N failures the poison message lands in that queue's dead-letter queue. Add a fifth subscriber next quarter? Just create another queue and subscribe it — the producer never changes.

SNS topic SQS queue Fanout (push) Long-polling (pull) Dead-letter

Why this design is genius: the producer publishes once; the topic replicates to each subscribed queue (SNS delivers, then SQS durably stores); each queue is independent, so a slow email worker never blocks warehouse pick-and-pack; each consumer scales independently; failures are isolated per-queue and each queue has its own DLQ; adding a new subscriber next quarter is a one-liner. This decoupling is the reason event-driven architectures on AWS work at scale.

📦 SQS internals — how a queue is actually built

Storage: replicated across multiple AZs

When you call SendMessage, SQS redundantly stores the message on multiple servers across multiple Availability Zones before it returns a MessageId. There is no single point of failure — an entire AZ outage doesn't lose a single message. Each AWS Region is a self-contained shard fabric; SQS is not natively cross-region (though you can bridge with cross-region SNS or DR replication tools).

The message lifecycle — three stages

  1. Send. Producer calls SendMessage. SQS assigns a MessageId, replicates across AZs, and returns.
  2. Receive. Consumer calls ReceiveMessage. SQS returns one or more messages and a ReceiptHandle — but does not delete them. Instead the message enters an in-flight state hidden from other consumers.
  3. Delete. After processing succeeds, the consumer calls DeleteMessage with the ReceiptHandle. The message is permanently removed. If the consumer never calls delete (crash, timeout, bug), the visibility timeout expires and the message re-appears for another try — this is at-least-once delivery.

Visibility timeout — the safety net

Default 30 seconds, configurable 0 s to 12 h. Its purpose: prevent duplicate work while one consumer is processing. If your handler is slow, call ChangeMessageVisibility to extend it. Setting it too short = duplicate processing; too long = slow recovery from consumer crashes. Rule of thumb: visibility timeout = P99 handler duration × 2.

Long polling vs short polling

  • Short polling (WaitTimeSeconds=0, default) — samples a subset of storage servers and returns immediately, even if empty. Result: empty responses cost you money. Almost never the right choice.
  • Long polling (WaitTimeSeconds=1..20) — queries all servers and waits until a message appears or the timeout expires. Fewer API calls, lower cost, faster message pickup. Set to 20 s for almost every consumer.

FIFO specifics — MessageGroupId, DeduplicationId, ReceiveRequestAttemptId

  • MessageGroupId — every message in a FIFO queue belongs to a group. Ordering is preserved within a group but not across groups. Choose group IDs carefully to control parallelism (all-one-group = strict serial; many groups = parallel throughput).
  • MessageDeduplicationId — within a 5-min dedup interval, duplicates with the same ID are silently discarded. Enable content-based deduplication to auto-hash the body.
  • ReceiveRequestAttemptId — used to retry ReceiveMessage idempotently after a network glitch, returning the same batch.

In-flight limits

SQS bounds how many messages can be simultaneously in the invisible/processing state:

  • Standard: ~120,000 in-flight per queue.
  • FIFO: 20,000 in-flight per queue.

Exceed and you get OverLimit. If you hit it, consumers aren't deleting fast enough — either scale out, extend the timeout, or check for stuck messages.

Dead-Letter Queues (DLQ) — the poison-pill catcher

Attach a second queue as the DLQ and set maxReceiveCount (typically 3–5). If a message is received that many times without being deleted, SQS moves it to the DLQ. Now you can inspect it, fix the bug, and either replay or discard. FIFO source needs FIFO DLQ; Standard needs Standard. Always add a CloudWatch alarm on DLQ message count.

Message retention & delay

  • Retention — default 4 days, configurable 60 s to 14 days. Undelivered messages auto-delete after retention expires.
  • Delivery delay — up to 15 min; makes new messages invisible for the delay period.
  • Message timers — same as delay, but per-message rather than queue-wide.

📣 SNS internals — how a topic fans out

Topic = logical multiplexer

An SNS topic is a named endpoint that publishers write to and subscribers subscribe to. It has no visible storage — SNS's job is to deliver, not to durably retain. When you publish, SNS's routing layer copies the message into the delivery pipeline for every confirmed subscription, then invokes the appropriate delivery protocol for each (HTTP POST for HTTP subscribers, SQS SendMessage for SQS subscribers, Lambda Invoke for Lambda subscribers, SES send for email, SMS gateway for text, APNs/FCM for mobile push).

Subscription types

  • A2A (Application-to-Application): SQS, Lambda, HTTP(S), Kinesis Data Firehose, EventBridge, Datadog / Splunk / MongoDB partner endpoints.
  • A2P (Application-to-Person): Email, SMS, mobile push notifications (iOS, Android, Windows).

Filter policies — per-subscriber routing

Each subscription can carry a JSON filter policy that inspects the message's attributes and decides whether to deliver. This is how you fan out to subsets — e.g. "email service only wants orders where country = US". The topic itself is unchanged; filtering happens at the subscription. Filters use exact match, anything-but, numeric range, prefix, exists — expressive enough for most routing needs without a separate service.

Delivery retries

SNS has a delivery retry policy per protocol. HTTP endpoints get exponential backoff for hours before a message is discarded. SQS subscribers get infinite retries (the delivery is a normal SendMessage, so eventually it lands or SNS gives up after ~1 hour). Failed messages can be routed to an SNS DLQ (an SQS queue) so no delivery is silently lost.

Standard vs FIFO topics

  • Standard topic: best-effort ordering, at-least-once, unlimited throughput.
  • FIFO topic: strict ordering per MessageGroupId, exactly-once within a 5-min dedup window, 300 TPS (up to 3,000 with batching). Only subscribes to FIFO SQS queues and other FIFO endpoints.

Cross-region & cross-account subscriptions

An SNS topic in us-east-1 can have a subscriber (SQS queue, Lambda, HTTP endpoint) in eu-west-1. This is one of the cleanest ways to do cross-region event replication — publish once, land in queues in every region.

Message archiving & replay (2023+)

FIFO topics support message archive — SNS keeps a durable copy of every message for up to 365 days and lets you replay them into new subscribers. This is huge for onboarding new services or debugging: you can replay yesterday's events into a fresh consumer without touching the producer.

🔀 The canonical SNS-SQS fanout pattern

The most important AWS architecture insight is that SNS alone is not durable per subscriber. If a subscriber's endpoint is offline when SNS publishes, and there's no DLQ, that subscriber missed the event. The fix is to subscribe an SQS queue for each subscriber, then have each subscriber's compute (Lambda, ECS, EC2) poll its own queue. This gives you:

  • Broadcast semantics from SNS (one publish → N destinations).
  • Durable buffering from SQS (each destination has its own retention, retries, DLQ).
  • Independent scaling — the analytics consumer can be slow without affecting the warehouse consumer.
  • Independent failure handling — each queue has its own DLQ; each consumer has its own metrics and alarms.
  • Add subscribers freely — no producer change needed.

When to use just SNS (no SQS)

  • Subscriber is Lambda and you're OK with SNS's built-in retry + DLQ (SNS-managed).
  • Subscriber is a webhook to an idempotent HTTP endpoint you own.
  • Subscriber is SMS / email / push — the endpoint is a human, no queue makes sense.

When to use just SQS (no SNS)

  • Single producer, single consumer group — you're just buffering work, not fanning out.
  • You need FIFO with strict order and only one consumer will process each message.
  • The producer already knows exactly which queue to write to; broadcast is not needed.

Common pitfalls

  • Filter policy typos silently drop messages. Test filters with the SNS console's "Test message" feature.
  • SNS → SQS access policy must allow the topic to send to the queue (AWS scripts this if you subscribe via the console; if you use Terraform, don't forget the queue policy).
  • Not enabling raw message delivery means SNS wraps your message in a JSON envelope — every consumer must unwrap. Turn on Raw Message Delivery for cleaner code.
  • Sync SendMessage before response: if you send the event then commit the DB, one may succeed and the other fail. Use the Transactional Outbox pattern to atomically write and publish.
  • Confusing visibility timeout with retention: visibility hides an in-flight message; retention is when unprocessed messages die.

💻 Code — producer and consumer in C#

Producer — publish to SNS with FIFO deduplication

using Amazon.SimpleNotificationService;
using Amazon.SimpleNotificationService.Model;

var sns = new AmazonSimpleNotificationServiceClient();
await sns.PublishAsync(new PublishRequest {
    TopicArn = "arn:aws:sns:us-east-1:123:orders.fifo",
    Message  = JsonSerializer.Serialize(new { OrderId = 42, Total = 299 }),
    MessageGroupId = "tenant-alpha",           // order within tenant
    MessageDeduplicationId = order.Id.ToString() // idempotent publish
});

Consumer — long-polling loop with retries and DLQ handling

using Amazon.SQS;
using Amazon.SQS.Model;

var sqs = new AmazonSQSClient();
var queueUrl = "https://sqs.us-east-1.amazonaws.com/123/warehouse-q";

while (!ct.IsCancellationRequested)
{
    var resp = await sqs.ReceiveMessageAsync(new ReceiveMessageRequest {
        QueueUrl = queueUrl,
        MaxNumberOfMessages = 10,
        WaitTimeSeconds = 20,             // long poll
        VisibilityTimeout = 60,           // double your P99 handler
        AttributeNames = { "ApproximateReceiveCount" }
    }, ct);

    foreach (var msg in resp.Messages ?? new())
    {
        try
        {
            var receiveCount = int.Parse(msg.Attributes["ApproximateReceiveCount"]);
            Process(msg.Body, receiveCount);                       // idempotent handler

            await sqs.DeleteMessageAsync(queueUrl, msg.ReceiptHandle);
        }
        catch (TransientException)
        {
            // don't delete — SQS will redeliver after visibility timeout
            // extend timeout if we know we need more time
            await sqs.ChangeMessageVisibilityAsync(queueUrl, msg.ReceiptHandle, 300);
        }
        // permanent errors → let receive-count climb → DLQ takes it after maxReceiveCount
    }
}

Two things to notice: idempotency is the consumer's job, not SQS's. Even Standard queues can (rarely) deliver duplicates. Store a de-dup key (message-id or business key) in your DB and short-circuit on replay. Never assume "at-least-once" means "exactly-once" in your handler.

⚖️ Trade-offs, gotchas, and likely follow-up interview questions

The three biggest gotchas in production

  • Visibility timeout < handler time = duplicate processing storm. Set visibility to P99 handler × 2.
  • No DLQ + poison message = infinite retry, throughput collapse. Always attach a DLQ and alarm on it.
  • Publish-then-commit = phantom events on DB failure. Use the Transactional Outbox pattern.

Likely interview follow-ups

Q: How does SQS guarantee durability?

Every SendMessage is replicated across multiple servers in multiple AZs before returning. A single-AZ outage never loses a message. Within a region, SQS is effectively 3-AZ replicated.

Q: What's the difference between short and long polling?

Short polling samples a subset of storage servers and returns immediately, often empty. Long polling (WaitTimeSeconds=1..20) queries all servers and waits until a message lands. Long polling is nearly always the right choice — fewer empty responses, lower cost, faster pickup.

Q: Why can SQS deliver duplicates on a Standard queue?

The distributed store may replicate a message to two shards in a rare partition, and both may serve it. Consumers must be idempotent. FIFO removes this via DeduplicationId within a 5-minute window.

Q: How does FIFO achieve ordering with parallelism?

Ordering is only guaranteed within a MessageGroupId. Different group IDs process in parallel. Choose group ID = user-id or tenant-id to keep per-user order without serialising the whole queue.

Q: What happens if a consumer crashes mid-processing?

The message is invisible only until the visibility timeout expires (default 30 s). Once it expires, another consumer receives it. That's why every handler must be idempotent.

Q: How do you replay events into a new subscriber?

FIFO SNS topics have message archive/replay (up to 365 days). Or replay from a Kinesis-based log if you built one alongside. Standard SNS/SQS have no built-in replay.

Q: SNS or EventBridge?

EventBridge for content-based routing across services/accounts and integration with SaaS providers. SNS for simple, cheap, low-latency fanout to SQS/Lambda. Same idea, different sweet spots.

Q: SQS or Kafka (MSK)?

SQS = simple, fully managed, unordered, one-consumer-per-message. Kafka = ordered per-partition, multi-consumer replay, unlimited retention. SQS is better for classic task queues; Kafka for event sourcing and streaming analytics.

🗣️ Interview cheat sheet

30-second pitch: "SNS is a pub/sub topic: a publisher writes once, SNS fans out to N subscribers — SQS queues, Lambda, HTTP, email, SMS, mobile push, Firehose. It's delivery-focused, not durability-focused. SQS is a durable, distributed queue: messages are replicated across multiple AZs, consumers long-poll and receive a ReceiptHandle plus a visibility timeout (default 30 s) that hides the message from other consumers until they delete it. If a consumer never deletes, the message reappears — at-least-once delivery. FIFO queues add strict ordering per MessageGroupId, deduplication within a 5-minute window, and exactly-once semantics — at the cost of 300 TPS (or 70k+ with high-throughput mode). The canonical AWS event-driven pattern is SNS-SQS fanout: publish to a topic, subscribe an SQS queue per consumer, each queue's DLQ isolates failures, and consumers scale independently."

Numbers to quote

  • Visibility timeout: 30 s default, 0 – 12 h configurable.
  • Retention: 4 days default, 60 s – 14 days configurable.
  • In-flight: ~120k Standard, 20k FIFO.
  • Dedup window: 5 minutes.
  • FIFO throughput: 300 TPS, 3,000 with batching, 70,000+ with high-throughput mode.
  • Message size: 256 KB (2 GB via S3 extended library).
  • SNS filter policies evaluate in constant time per subscription.
  • FIFO SNS topics support up to 365 days of archive/replay.
