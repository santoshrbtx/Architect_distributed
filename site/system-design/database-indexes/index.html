How Database Indexes Make Reads Faster

Turning an O(n) full-table scan into an O(log n) tree walk — the B+Tree, hash, LSM, and inverted indexes that power every serious database.

🎯 Real-world scenario

Why every serious database is built around indexes

Imagine a users table with 500 million rows and a query SELECT * FROM users WHERE email = 'alice@x.com'. Without an index, the database must open the table file and read every single row until it finds a match — a full table scan. On disk that's tens of gigabytes at ~100 MB/s, so the query takes minutes. With a B+Tree index on email, the database walks a tree of depth 4 — four disk reads, a millisecond or two. The index has turned an O(n) scan into an O(log n) lookup, and that is the single most important trick in a database's toolbox.

You've hit indexes every day without knowing it. When Gmail loads your inbox, an index on (user_id, received_at DESC) gives you the latest 20 messages instantly. When Instagram opens a profile page, an index on author_id retrieves the person's posts without scanning the whole posts table. When Amazon looks up an order by ID, a primary-key index makes it a point lookup. When Google searches the web, a giant inverted index maps every word to the list of documents that contain it. The index is what makes a database "fast" — the storage engine is really just a set of indexes with rules for keeping them consistent.

This is a classic system-design and staff-engineer interview topic because it touches everything: data structures (B+Tree, LSM, hash tables, tries, bitmaps, bloom filters), disk I/O (page size, sequential vs random reads), consistency (writes must update every index atomically), and workload trade-offs (read-heavy vs write-heavy, OLTP vs analytics). If you can explain why a B+Tree beats a binary search tree on disk, you can hold your own in any database conversation.

🧑‍🎓 In laymen terms

Think of it as the index at the back of a giant book

Imagine you have a 10,000-page cookbook and someone shouts across the room: "find me every recipe that uses saffron." You have two choices. You could read the whole book cover to cover, page by page, checking each recipe for the word "saffron." That would take you a week. Or you could flip to the index at the back — the little alphabetical list where every ingredient is followed by the page numbers it appears on. "Saffron … pages 47, 312, 981." Three page turns and you're done.

A database index is exactly that: a separate, sorted list that says "for this value, here's where to find the actual row." The database keeps it up to date every time you add, change, or delete a recipe (row), so it's always ready to answer "where is X?" in a heartbeat.

But here's the clever twist. If the ingredient list at the back of the book had a million entries, even scanning the index would be slow. So databases don't use a flat list — they use a tree of pages, like a phone book that first tells you "A–F is here, G–L is there, M–R over there, S–Z last." You flip to the S–Z section, then within it flip to "Sa–", then to "Saf–", and in three or four flips you've narrowed a million entries down to one. Every extra level of the tree lets you handle roughly a hundred times more data with just one more page turn. That's why even Amazon or Facebook, with hundreds of billions of rows, can answer "give me this user's profile" in a millisecond.

The hard part isn't the reading — it's the writing. Every time you edit the cookbook, you also have to update the index. Add a new saffron recipe? You have to insert "saffron … page 10,001" into the sorted list. That's why databases don't index everything: indexes make reads fast but writes slower, and take extra room on the shelf. The art of tuning a database is choosing which columns deserve an index and which don't.

You already benefit from this every day. When you type a friend's name in WhatsApp, an index makes their chat pop up instantly. When you search Amazon for "wireless headphones," an inverted index (like the cookbook example) finds every matching product in a blink. When your bank looks up your account by account number, an index turns "search 200 million accounts" into "walk down 4 signposts."

📋 Requirements & scale

What we're optimizing for

Functional requirements

  • Fast point lookups by a specific column (find the user with email = X).
  • Fast range queries (orders WHERE created_at BETWEEN a AND b).
  • Fast sorting (ORDER BY created_at DESC LIMIT 20) without extra work.
  • Enforce uniqueness constraints (primary keys, unique emails) as a side effect of the index.
  • Support compound queries on multiple columns (composite indexes).

Non-functional requirements

  • Read latency: <5 ms p99 for a keyed lookup on billions of rows.
  • Write amplification: acceptable 1× to 3× — every write updates the row plus every affected index.
  • Space overhead: an index typically costs ~10–20 % of the table size for a single column.
  • Durability & crash safety — the index must always match the base table after recovery.

Back-of-the-envelope: why a B+Tree wins

A B+Tree page is typically 8 KB and holds ~100–200 keys+pointers (call it a fan-out of ~100). Depth d holds 100d rows. So:

Rows in tableFull scan (100 MB/s)B+Tree depthIndexed lookup
10,000~1 ms2~1 ms (both cheap)
1,000,000~100 ms3~2 ms
100,000,000~10 s4~3 ms
1,000,000,000~100 s5~4 ms
1,000,000,000,000~28 hours6~5 ms

Only the root page is small enough to stay hot in RAM, so the top 1–2 levels are essentially free. In practice a 4-level index on a billion rows costs 2–3 real disk reads per lookup.

🏗️ High-level architecture

Where indexes sit inside a database

An index lives inside the storage engine, alongside the table (called the heap in Postgres, or the clustered index itself in InnoDB/SQL Server). When a query arrives, the parser turns it into an AST, the query planner asks the statistics collector "how selective is WHERE email = ??" and picks between a full scan and an index scan based on estimated cost. On an index scan, the executor calls the storage engine, which walks the B+Tree pages held in the buffer pool (an in-memory cache of disk pages), fetches the pointer to the row, then goes to the heap to read the row itself. Writes go through the write-ahead log (WAL) first for durability, then update the heap page and every affected index page in memory; the WAL is what lets the DB rebuild indexes after a crash.

🔍 Component deep-dive

1. What an index actually is

An index is a separate, sorted, redundant copy of one or more columns of a table, plus a pointer to the full row. Use-The-Index-Luke puts it bluntly: "an index is pure redundancy." That redundancy is the whole point — you trade a bit of disk, a bit of write overhead, and complexity in return for turning a linear scan into a logarithmic lookup. The base table is the "heap" (Postgres) or is itself organized as a clustered index (MySQL InnoDB, SQL Server). Any additional index is called a secondary index and holds (indexed_key, row_pointer) pairs.

2. Why B+Tree, not binary search tree

A plain binary tree of a billion keys is ~30 levels deep. Since each level lives on a different disk page, that's 30 random disk reads per lookup — awful. A B+Tree fixes this by making each node page-sized (~8 KB) and holding hundreds of keys per node. Fan-out of 100 means a billion rows fit in 5 levels; fan-out of 500 fits them in 4. The top 1–2 levels stay pinned in RAM in the buffer pool, so a real lookup is 2–3 disk I/Os. B+Trees also self-balance on insert/delete via node splits and merges, so the depth stays predictable as the table grows. Leaf nodes are chained in a doubly linked list, which is what makes range scans (BETWEEN, ORDER BY, LIMIT) essentially free — walk the list from where the tree landed you.

3. Clustered vs secondary indexes

A clustered index stores the table rows in the leaf pages of the index itself, sorted by the key — the table is the index. MySQL InnoDB and SQL Server default to this, keyed on the primary key. Lookups are one traversal, no extra hop to the heap. A secondary (non-clustered) index stores (key → primary_key) pairs; the engine then does a second walk of the clustered index to fetch the row. Postgres does not use clustered indexes; every index is secondary and points at a ctid (heap tuple id). Trade-off: clustered indexes are faster for the primary access pattern but every secondary index is one hop slower.

4. Composite (multi-column) indexes and the leftmost-prefix rule

An index on (a, b, c) is a single tree sorted first by a, then b, then c. It can serve queries filtering on a, on (a, b), or on (a, b, c) — any leftmost prefix. It cannot serve a query that filters only on b, because the tree isn't sorted that way. MongoDB codifies this as the ESR rule: put Equality columns first, then Sort columns, then Range columns. This lets one composite index cover many query shapes and often eliminates the sort step entirely.

5. Covering indexes and index-only scans

If every column the query needs is already in the index, the engine can answer from the index alone and skip the heap lookup — an index-only scan. This is why you'll see indexes with INCLUDE(...) clauses (SQL Server, Postgres 11+) that attach extra columns to leaf nodes without adding them to the sort key. A covering index is often 2–5× faster than a normal one on read-heavy paths.

6. Selectivity and cost-based planner choices

An index is only useful if the predicate is selective — i.e. it narrows the result to a small fraction of the table. The planner uses histograms and statistics to estimate selectivity. For WHERE gender = 'F' (roughly 50 % of rows), the planner will pick a sequential scan because reading half the table in order is cheaper than doing millions of random index lookups. For WHERE email = 'alice@x.com' (1 in 500 million), the index wins hands down. A common bug: an index exists but stats are stale, and the planner "forgets" to use it. Fix: ANALYZE table.

7. Write cost — the other side of the ledger

Every INSERT or UPDATE must update the row plus every index that references any affected column. Ten indexes on a table = ten B+Tree modifications per write. Under heavy write load, engines like Cassandra, HBase, and RocksDB replace B+Trees with LSM trees (Log-Structured Merge trees): writes go to an in-memory sorted table (memtable), get flushed to immutable sorted files (SSTables), then merged in the background. LSMs make writes cheap and sequential at the cost of higher read amplification (a read may probe multiple SSTables, mitigated by bloom filters).

8. Beyond B+Tree: the index zoo

Different workloads need different structures. Hash indexes are O(1) but only serve equality — Postgres has them, and DynamoDB partitions by hash of the partition key. Inverted indexes map each term to a posting list of document ids — the heart of full-text search (Lucene, Elasticsearch, OpenSearch). Geospatial indexes like GiST, R-Tree, and geohash prefixes handle "within radius" queries. Bitmap indexes shine for low-cardinality columns in data warehouses and support fast AND/OR combinations. BRIN indexes summarize block ranges — a tiny structure for tables where physical order correlates with a column (timestamps in append-only logs). Choose the structure to match the workload; a wrong choice makes an index useless.

💻 C# implementation — a minimal B+Tree-style index

Real database B+Trees are page-oriented, on-disk, concurrent, and crash-safe. The idea, though, fits in ~120 lines of C#. Below is a simplified in-memory B+Tree that supports Insert, Get (point lookup) and Range (range scan via the leaf-linked-list). It compiles and shows the shape of the algorithm — the same shape used by SQL Server and Postgres just with pages instead of C# nodes.

using System;
using System.Collections.Generic;

// Simple B+Tree for demo. Keys are int, values are string.
// Order = max keys per leaf; internal nodes hold up to Order separator keys.
public class BPlusTree {
    private const int Order = 4;   // tiny fan-out to keep the picture clear

    abstract class Node { public List<int> Keys = new(); }

    class Leaf : Node {
        public List<string> Values = new();
        public Leaf Next;          // linked list of leaves → range scans
    }

    class Internal : Node {
        public List<Node> Children = new();
    }

    private Node _root = new Leaf();

    // ---- Point lookup: O(log_b n) ----
    public string Get(int key) {
        var leaf = FindLeaf(_root, key);
        int i = leaf.Keys.BinarySearch(key);
        return i >= 0 ? leaf.Values[i] : null;
    }

    // ---- Range scan: walk one branch down, then hop leaves ----
    public IEnumerable<(int k, string v)> Range(int lo, int hi) {
        var leaf = FindLeaf(_root, lo);
        while (leaf != null) {
            for (int i = 0; i < leaf.Keys.Count; i++) {
                if (leaf.Keys[i] > hi) yield break;
                if (leaf.Keys[i] >= lo) yield return (leaf.Keys[i], leaf.Values[i]);
            }
            leaf = leaf.Next;
        }
    }

    private Leaf FindLeaf(Node n, int key) {
        while (n is Internal ni) {
            int i = 0;
            while (i < ni.Keys.Count && key >= ni.Keys[i]) i++;
            n = ni.Children[i];                // descend along the separator
        }
        return (Leaf)n;
    }

    // ---- Insert: recursive; splits propagate upward, may grow tree height ----
    public void Insert(int key, string val) {
        var split = InsertRec(_root, key, val);
        if (split.HasValue) {                     // root split → new root, tree grows one level
            var nr = new Internal();
            nr.Keys.Add(split.Value.pivot);
            nr.Children.Add(_root);
            nr.Children.Add(split.Value.right);
            _root = nr;
        }
    }

    private (int pivot, Node right)? InsertRec(Node n, int key, string val) {
        if (n is Leaf lf) {
            int pos = lf.Keys.BinarySearch(key);
            if (pos >= 0) { lf.Values[pos] = val; return null; } // upsert
            pos = ~pos;
            lf.Keys.Insert(pos, key);
            lf.Values.Insert(pos, val);
            if (lf.Keys.Count <= Order) return null;
            return SplitLeaf(lf);
        }
        var nd = (Internal)n;
        int ci = 0;
        while (ci < nd.Keys.Count && key >= nd.Keys[ci]) ci++;
        var childSplit = InsertRec(nd.Children[ci], key, val);
        if (!childSplit.HasValue) return null;
        nd.Keys.Insert(ci, childSplit.Value.pivot);
        nd.Children.Insert(ci + 1, childSplit.Value.right);
        if (nd.Keys.Count <= Order) return null;
        return SplitInternal(nd);
    }

    private (int, Node) SplitLeaf(Leaf lf) {
        int mid = lf.Keys.Count / 2;
        var right = new Leaf {
            Keys   = lf.Keys.GetRange(mid, lf.Keys.Count - mid),
            Values = lf.Values.GetRange(mid, lf.Values.Count - mid),
            Next   = lf.Next
        };
        lf.Keys.RemoveRange(mid, lf.Keys.Count - mid);
        lf.Values.RemoveRange(mid, lf.Values.Count - mid);
        lf.Next = right;
        return (right.Keys[0], right);   // pivot copied up (B+Tree semantics)
    }

    private (int, Node) SplitInternal(Internal nd) {
        int mid = nd.Keys.Count / 2;
        int pivot = nd.Keys[mid];
        var right = new Internal {
            Keys     = nd.Keys.GetRange(mid + 1, nd.Keys.Count - mid - 1),
            Children = nd.Children.GetRange(mid + 1, nd.Children.Count - mid - 1)
        };
        nd.Keys.RemoveRange(mid, nd.Keys.Count - mid);
        nd.Children.RemoveRange(mid + 1, nd.Children.Count - mid - 1);
        return (pivot, right);           // pivot moves up (not kept in either child)
    }
}

// Usage:
//   var idx = new BPlusTree();
//   idx.Insert(42, "Alice");
//   idx.Insert(43, "Bob");
//   Console.WriteLine(idx.Get(42));            // Alice
//   foreach (var (k,v) in idx.Range(40, 45))
//       Console.WriteLine($"{k}: {v}");

Notes for the interviewer: real databases add concurrent latch-crabbing so multiple readers/writers can walk the tree at once; keys are stored as byte slices, not int; pages have prefix compression; and after a crash the tree is rebuilt by replaying the WAL. The core algorithm is exactly what's above. If the interviewer swaps the language, in Java you'd use Collections.binarySearch, in Python bisect, in Go sort.Search — the shape is identical.

⚖️ Trade-offs, bottlenecks & likely follow-ups

The fundamental trade-off: reads vs writes vs space

Every index makes reads faster but writes slower and consumes disk. A table with ten indexes needs ten B+Tree updates per row change. On a write-heavy workload (event ingestion, high-frequency trading, IoT) the write amplification eats you alive, which is why systems like Cassandra and DynamoDB adopt LSM trees — writes become cheap sequential appends, at the cost of read amplification that bloom filters partially hide.

Selectivity — the reason indexes get ignored

If a predicate matches more than roughly 10–20 % of the table, a sequential scan is usually cheaper than millions of random index+heap lookups. The planner uses statistics (histograms, pg_stats) to decide. If your statistics are stale, the planner picks the wrong plan — always run ANALYZE after big data changes.

Hot-spot writes and index contention

An auto-increment primary key concentrates all inserts at the rightmost leaf of the B+Tree, which creates lock contention under high concurrency. Solutions: hash-partitioned primary keys (UUIDv4, ULIDs), MySQL's INSTANT DDL, or splitting the write path across partitions.

Index bloat and vacuum

Postgres uses MVCC: updates create new tuple versions, and until VACUUM runs, old versions linger in the heap and in every index. On a heavily updated table indexes can double in size. Solutions: REINDEX CONCURRENTLY, HOT updates (Heap-Only Tuple — when no indexed column changed, updates skip the index), and monitoring pg_stat_user_indexes.

Likely follow-up questions

Q: Why B+Tree instead of B-tree?

A: In a B+Tree, only leaves store values and they are chained together. Internal nodes hold only routing keys, so fan-out is higher, the tree is shallower, and range scans (ORDER BY, BETWEEN) become a linear walk over the leaf linked list instead of a repeated tree descent.

Q: When is a hash index better than a B+Tree?

A: When you only need equality lookups and nothing else — no range, no sorting, no prefix matching. Hash gives O(1) average vs B+Tree's O(log n). Postgres supports it via USING hash; DynamoDB partitions data by the hash of the partition key.

Q: How does an inverted index differ from a B+Tree?

A: An inverted index maps each term to a posting list of document ids ("cat" → [3, 17, 42]). It flips the direction of the map so full-text queries become O(terms × posting-list-merge) instead of a full scan. That's what Lucene/Elasticsearch and Postgres GIN do.

Q: What is a covering index?

A: An index that contains every column the query needs, so the engine can answer from the index alone and skip the heap fetch — an "index-only scan." Attach non-key columns via INCLUDE(...). Great for hot read paths.

Q: I created an index but the query plan still shows a Seq Scan. Why?

A: Most common causes: (1) the predicate isn't selective enough — the planner thinks the scan is cheaper; (2) statistics are stale — run ANALYZE; (3) the predicate isn't sargable — e.g. WHERE LOWER(email) = ? defeats an index on email unless you have a functional index on LOWER(email); (4) an implicit cast (e.g. text vs varchar) prevents index use.

Q: What does the "leftmost prefix" rule mean for composite indexes?

A: An index on (a, b, c) can serve WHERE a=?, WHERE a=? AND b=?, and WHERE a=? AND b=? AND c=?. It cannot serve WHERE b=? alone. Design the column order to match the equality-then-sort-then-range shape of your top queries.

🗣️ Interview cheat sheet

30-second pitch: "An index is a redundant, sorted copy of a column plus a pointer to the row, so lookups become O(log n) tree walks instead of O(n) scans. Databases use B+Trees for the general case, LSM trees for write-heavy workloads, hash for equality-only, inverted indexes for full text, and specialised trees for spatial data. The trade-off is disk space and slower writes; the win is orders of magnitude faster reads."

Numbers to quote

  • Page size ~8 KB, fan-out ~100–500, depth 3–5 for tables up to a billion rows.
  • Full scan of a 100 GB table: ~15+ minutes at 100 MB/s. Indexed lookup on the same table: ~2–5 ms.
  • Index overhead: ~10–20 % of table size per single-column B-tree.
  • Rule of thumb: if a predicate matches > 10–20 % of rows, a sequential scan may beat the index.

5 talking points that win the round

  • "B+Tree, not binary tree — the whole point is page-sized fan-out, so we do 3 disk reads instead of 30."
  • "Leaf nodes are a linked list, which is why ORDER BY and BETWEEN are essentially free after the descent."
  • "Every index is a write tax — I would justify each one against actual query patterns, and drop unused ones (pg_stat_user_indexes)."
  • "For write-heavy workloads I'd reach for an LSM store (Cassandra, RocksDB, DynamoDB) — writes become sequential appends, bloom filters keep read amplification in check."
  • "Composite indexes follow the ESR rule: equality columns first, then sort, then range — one index can cover many query shapes."
