Vertical Partitioning & Zero-Downtime Sharding

Splitting one wide table into narrow ones by columns — using ZooKeeper as the routing map, MySQL binlog / Postgres WAL to keep them in sync, and live cutover so users never see a blip.

🎯 Real-world scenario

The problem: one table is doing too much

Every fast-growing product hits the same wall. Your users table started with a handful of columns — id, email, password hash — and, three years later, it has 47 columns, some of them 4-KB blobs, and it's the hottest table in the database. Every login reads it, every profile view reads it, every settings page reads it. The table is too wide: rarely-used columns bloat the buffer pool, cold JSON payloads share a page with the hot ones, and a lock on any user row for any reason blocks unrelated queries.

Vertical partitioning is the surgical answer. Instead of splitting rows (that's horizontal sharding), you split columns — the wide table becomes several narrow tables that share the same primary key. The hot columns land in user_core. Profile bio and avatar go to user_profile. Preferences, notification settings, feature flags — the cold, rarely-touched fields — move to user_preferences. The hot path only reads user_core; the entire hot working set now fits in RAM, and locks on cold data no longer block auth.

This is exactly the pattern YouTube's Vitess team formalised as a first-class workflow (MoveTables), which is how they carved up MySQL for YouTube, Slack, and Square. Pinterest, Facebook, and Uber all describe similar moves in their engineering blogs — usually to isolate a hot subsystem from a slower one. The interview question is: how do you actually pull it off without downtime, without data loss, and without a big-bang deploy where hundreds of engineers have to change code at the same time? The answer is a coordinated dance between ZooKeeper (for the routing map), MySQL binlog / Postgres WAL replication (to backfill and keep the shards in sync), and reactive re-routing driven by ZooKeeper watches so the application layer picks up the new topology automatically.

🧑‍🎓 In laymen terms

Splitting one enormous filing cabinet into three specialised ones

Imagine one giant filing cabinet in the office that holds a folder for every customer. Each folder has grown huge over the years — a name and phone number at the top, then a chunky biography, a photo, a wish-list, notification preferences, historical purchases, feature-flag experiments the marketing team keeps adding, and so on. Every time anyone pulls a folder out, they lug the whole thing over — even if they only wanted the phone number.

The office manager decides to split each folder into three thinner folders, all with the same customer number stapled on top. The first folder — Core — holds only the name, email, and password. The second — Profile — holds the bio and photo. The third — Preferences — holds the notification settings and marketing preferences. The Core folders are the ones staff grab a hundred times a day, so they stay in a small locked drawer near the front desk. Profile and Preferences live in less-hot cabinets in the back room. Suddenly, the front-desk drawer is small enough that any folder can be found in seconds.

Here's the tricky part: doing this without closing the office. There's already a live queue of customers at the desk. You can't just say "we'll be back tomorrow." So the team does it in stages. First, they set up the three new cabinets, empty. Then a helper copies existing folders into the new cabinets, one customer at a time, in the background — while the front desk keeps working with the old cabinet. Every time a customer updates their address at the front desk, a "little scribe" writes the same update to the new cabinets too, so they stay in sync. Once the copy is complete and the scribe confirms both sets match perfectly, the office manager updates the noticeboard — a wall-mounted map that tells every staff member which cabinet holds which type of folder — and everyone switches to reading from the new cabinets. Nobody was turned away. The switchover took a second.

The noticeboard is called ZooKeeper. The little scribe is called binary-log replication. And the reason it doesn't lose any change is that the scribe reads the office's own daily log of updates — every write is recorded before it happens, so the scribe just replays those log entries into the new cabinet.

Concrete example. LinkedIn ran their profile system this way for years — hot login data on one MySQL shard, resume & work history on another, feed activity on a third. When you log in, you hit the fast one. When you view your resume, a second call goes to the slow one. Because the noticeboard says exactly where each type of data lives, the application code doesn't need to know the actual server addresses — it asks the noticeboard, gets an answer, and reads.

📋 Requirements & scale

Functional & non-functional

Functional

  • Split a wide table into ≥2 narrower tables by column group, preserving the primary key.
  • Perform the migration online — reads and writes continue throughout.
  • Route each query to the correct shard based on which columns it needs.
  • Keep source and target in strict sync during backfill and steady-state.
  • Allow reversible cutover — if something goes wrong, flip back to the old table with zero data loss.
  • Support cross-shard reads (joins) and, where necessary, transactions across shards.

Back-of-the-envelope

A billion-row users table with 47 columns totalling 4 KB average per row = 4 TB. If the hot path only needs 5 columns totalling ~200 bytes, then after vertical partitioning the hot table is 200 GB — small enough to hold entirely in RAM on a decent MySQL box. That single number — 4 TB → 200 GB — is the reason vertical partitioning is one of the highest-leverage database optimisations in existence.

🏗️ High-level architecture

The migration architecture, top-down

Three moving parts do the heavy lifting: (1) a routing proxy (Vitess VTGate, Pinterest PinDB, or your own thin layer) that reads a routing map from ZooKeeper and translates each query into requests against the right physical shards; (2) a replication worker (Vitess VReplication, Debezium, or a hand-rolled reader) that tails the source database's binlog (MySQL) or WAL (Postgres) and applies each change to the new tables; and (3) ZooKeeper itself, which holds the routing map and pushes updates via watches the instant the operator flips the cutover.

Three colour flows: the blue query path is what the app sees — one SQL statement fans out to whichever shards hold the columns it selected. The amber replication path is asynchronous — the worker tails the source binlog and writes to the new tables continuously. The green watch push is instant — the moment the operator changes the routing map, every proxy re-reads and re-routes without a restart.

🔍 Component deep-dive — every stage of the migration

1. What vertical partitioning actually is (and isn't)

Vertical partitioning splits columns. Horizontal partitioning (sharding) splits rows. Given the classic problem — a wide users table with 47 columns — vertical splitting decomposes it into narrow tables that share the same primary key:

Before: users(id, email, pwd_hash, status, display_name, bio, avatar_url, phone, country, locale, timezone, notification_email, notification_sms, notification_push, marketing_optout, feature_flag_1..N, last_login_at, ...) — 4 KB average row width.
After: user_core(id, email, pwd_hash, status) — ~120 bytes/row. Every auth request reads this table.
user_profile(id, display_name, bio, avatar_url, phone, country, locale, timezone) — ~1 KB/row. Read on profile view.
user_preferences(id, notification_email, notification_sms, notification_push, marketing_optout, feature_flags jsonb) — ~2 KB/row. Read on settings page only.

The critical property: every row in every child table shares the same user_id, so the original table can always be reconstructed via a three-way join. This 1:1 relationship is what distinguishes vertical partitioning from normalisation — you're not eliminating redundancy, you're isolating by access pattern.

2. Vertical vs horizontal — when to reach for each

SymptomRight tool
Too many rows (billions) on one node; disk fullHorizontal (sharding by user_id / hash)
Table is too wide; cold columns bloat memoryVertical (split by column group)
Hot subsystem (auth) blocked by cold subsystem (analytics events)Vertical, then move cold table to its own server
Read QPS higher than one primary can serveRead replicas first, then horizontal
Locks on unrelated fields hurt throughputVertical
Uneven skew — one user has 90% of rows in a related tableHorizontal with hash-based routing

They compose. Vitess routinely does vertical first, then horizontal on the tables that stay hot. YouTube's original migration path: monolithic MySQL → vertically split into ~30 keyspaces (users, videos, comments, ads) → horizontally shard the hottest 5-6 of those keyspaces to hundreds of shards each.

3. ZooKeeper's job — the routing map

The routing map is the single source of truth for "given a query for column X of table T, which physical DB holds it?" It lives in ZooKeeper as a small JSON blob under a well-known path, e.g.:

/vitess/topology/keyspaces/users/routing { "users.user_core": { "physical": "shard-users-old", "state": "serving" }, "users.user_profile": { "physical": "shard-users-new1", "state": "serving" }, "users.user_preferences": { "physical": "shard-users-new2", "state": "serving" }, "users": { "view_of": ["user_core","user_profile","user_preferences"] } }

Every VTGate (or your query proxy) sets a persistent watch on this znode. When the operator flips the map, ZooKeeper pushes the update to every proxy in under a second — the proxies re-read and start routing to the new physical destination immediately, without a restart. See the full ZooKeeper mechanics on this page.

Why ZooKeeper and not just a config file? Because a config file doesn't push updates. You'd have to poll or restart. And a config server that isn't strongly consistent might tell one proxy the new map and another the old map, causing writes to hit different physical DBs — a split-brain scenario that corrupts data. ZooKeeper's ZAB guarantees every proxy sees the same map at any point in wall-clock time, or gets an error.

4. Binlog / WAL replication — the "little scribe"

MySQL's binlog (binary log) and Postgres's WAL (write-ahead log) both record every write in strict order, before it's committed to the data files. This log is the foundation of every replication tool. Vitess's VReplication — the workflow originally built at YouTube — attaches to the binlog stream identified by a global transaction ID (GTID) and processes each event in order.

The migration runs in three canonical phases:

  1. Copy phase. The worker takes a consistent snapshot of the source (using MySQL's --single-transaction or Postgres logical replication slot) and streams rows into the target tables via a SELECT column_subset FROM users. Because it's a projection, only the columns you're moving actually get copied. This phase handles a billion rows in hours, not weeks, and can be interrupted and resumed at the same GTID.
  2. Replicate phase. Once the copy is done, the worker seamlessly transitions to tailing the binlog from the GTID at which the copy started. Every INSERT/UPDATE/DELETE on the source is projected and applied to the targets. Steady-state lag is milliseconds on a healthy system.
  3. Verification (VDiff). The worker takes fresh consistent snapshots of both sides and compares them row-by-row for the moved columns. Any drift is replayed. Only after VDiff reports 100% match do you cut over.

5. The cutover — SwitchTraffic in stages

Cutover is not a big bang. Vitess splits it into reads first, then writes, with a reversible checkpoint in between:

  1. SwitchReads. Update the routing map in ZooKeeper so read queries for the moved columns now go to the new tables. Writes still go to the old wide table; the replication worker still keeps the new tables current. If anything looks wrong (latency spike, error rate), the operator flips the map back and it's as if nothing happened.
  2. Freeze & drain. Wait for the binlog tail to reach zero lag — the new tables are 100% caught up.
  3. SwitchWrites. Briefly pause writes on the moved columns (~100 ms), wait for any in-flight replication to complete, update the routing map to send writes to the new tables. Because the pause is bounded by the wait for the last GTID to apply, it's imperceptible at the client. Vitess journals the binlog position of the cutover event so the reverse-replication stream (new → old) knows exactly where to start, giving you a working reverse replication in case rollback is needed.
  4. Drop the old columns. After a confidence window (hours or days), the columns are dropped from the source. This step is not urgent — the migration is already logically complete.

6. Handling reads & joins after the split

Queries that used to be a single table scan now become fan-out queries. The proxy is responsible for splitting a query like SELECT id, email, bio FROM users WHERE id = ? into two lookups — one against user_core, one against user_profile — and merging the results by user_id. For hot-path queries that only need core columns, the proxy sends a single query to a single shard — the whole point of the exercise.

For legacy code that still writes SELECT * FROM users, most proxies (including Vitess VTGate) expose a logical view that transparently joins the underlying tables. This lets you migrate the schema without simultaneously migrating every client — the client cutover can be an independent, gradual effort.

7. Transactions across the split

If all vertical partitions live on the same MySQL/Postgres instance, a standard local transaction covers all of them — no distributed transaction needed. This is the easy and common case; vertical partitioning does not require separate physical machines. The benefit even on one machine is smaller pages, better cache locality, and reduced lock contention.

If you move a partition to a different server for capacity reasons, cross-partition writes need either two-phase commit (correct but slow — Vitess supports 2PC with reasonable latency) or the outbox pattern (eventual consistency, no distributed transaction). In practice, most vertical splits keep all partitions on one host or one MySQL group so 2PC never comes up.

Typical deployment. Provision the source and target RDS/Aurora clusters. Deploy a 3-node ZooKeeper (or etcd) ensemble on EC2 across AZs. Deploy VTGate and VTTablet sidecars on EKS. Register the source in the ZK topology. Kick off MoveTables with the column projection defining the vertical split. Monitor lag via VReplication metrics; when VDiff reports zero drift, run SwitchReads then SwitchWrites. Leave reverse replication armed for a week before dropping the old columns. Total wall-clock for a 1 TB migration: 4–8 hours copy phase, then arbitrary hold at zero lag, then seconds for cutover.

💻 C# implementation — the routing proxy

Here's the core of the query proxy — the piece that reads the routing map from ZooKeeper and dispatches each SQL statement to the right underlying connection. In production this is Vitess VTGate written in Go; below is an idiomatic C# port showing the two important patterns: routing-map-driven dispatch and reactive re-load on ZK watch.

// Reactive routing proxy — reads the routing map from ZooKeeper, watches for
// updates, and dispatches each SQL statement to the correct physical shard.
using System.Text.Json;
using org.apache.zookeeper;

public class RoutingMap
{
    // logical_table.column_group → physical_dsn
    public Dictionary<string, string> Routes { get; set; } = new();
}

public class VerticalRouter : Watcher
{
    private readonly ZooKeeper _zk;
    private const string ROUTING_PATH = "/vitess/topology/keyspaces/users/routing";
    private volatile RoutingMap _map = new();

    public VerticalRouter(ZooKeeper zk) { _zk = zk; }

    public async Task StartAsync()
    {
        // Read the map AND arm the watch atomically.
        var res = await _zk.getDataAsync(ROUTING_PATH, watcher: this);
        _map = JsonSerializer.Deserialize<RoutingMap>(res.Data)!;
    }

    // Fires on any change to the routing znode — including operator SwitchTraffic.
    public override async Task process(WatchedEvent ev)
    {
        if (ev.get_Type() == Event.EventType.NodeDataChanged && ev.getPath() == ROUTING_PATH)
        {
            var res = await _zk.getDataAsync(ROUTING_PATH, watcher: this);
            _map = JsonSerializer.Deserialize<RoutingMap>(res.Data)!;
            // Sub-second: every query from this point onward uses the new map.
        }
    }

    // Given a query plan (which columns from which logical table) return
    // the set of physical connections to fan out to.
    public List<string> Route(string logicalTable, HashSet<string> columns)
    {
        var shards = new HashSet<string>();
        foreach (var col in columns)
        {
            var key = $"{logicalTable}.{ColumnGroupFor(col)}";
            if (_map.Routes.TryGetValue(key, out var dsn)) shards.Add(dsn);
        }
        return shards.ToList();
    }

    // A simple column → group mapping. In production this is part of the schema config.
    private static string ColumnGroupFor(string column) => column switch
    {
        "id" or "email" or "pwd_hash" or "status"          => "user_core",
        "display_name" or "bio" or "avatar_url"              => "user_profile",
        "notification_email" or "feature_flags"                => "user_preferences",
        _ => "user_core"
    };
}

// Executing a query — fan out, gather, merge on primary key.
public async Task<List<UserRow>> SelectUsers(
    VerticalRouter router, HashSet<string> columns, long[] userIds)
{
    var shards = router.Route("users", columns);
    var perShard = await Task.WhenAll(shards.Select(dsn =>
        QueryShard(dsn, columns, userIds)));

    // Merge results keyed by user_id — each shard returned a subset of columns.
    var merged = new Dictionary<long, UserRow>();
    foreach (var partial in perShard)
        foreach (var row in partial)
        {
            if (!merged.TryGetValue(row.Id, out var agg))
                merged[row.Id] = agg = new UserRow { Id = row.Id };
            agg.Merge(row);   // copy over columns present in this partial
        }
    return merged.Values.ToList();
}

Two things this snippet gets right: (a) the routing map is reloaded inside the watch callback and the watch is re-armed — same pattern as the ZooKeeper watches page. Miss this and you get exactly one update and then silently stop reacting. (b) The query merge happens on the primary key in the proxy layer — no cross-shard SQL join, just parallel single-shard reads followed by in-memory zip-by-PK. This keeps every physical DB doing single-table lookups, which is the whole reason vertical partitioning is fast in the first place.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Where it actually breaks

Cross-shard joins. If a query needs 10 columns spread across all three tables, you're doing three shard reads + merge on every request. For hot paths, either duplicate a small hot column across shards or redesign the split so the hot path only ever hits one shard. Foreign key constraints. Traditional FK constraints don't cross physical shards. You lose that referential integrity at the DB layer and have to enforce it in application code (delete-cascades become application-level cleanup jobs). Backfill throttling. A naïve copy-phase can max out the source disk IO and hurt production. Every serious tool (Vitess, DMS, gh-ost) throttles based on replica lag. Replication lag during binary migrations. If you're doing dual-write from the app instead of binlog-based replication, a partial failure between the two writes leaves the shards drifted — you must catch and reconcile. Binlog replication doesn't have this failure mode because the binlog write itself is transactional with the data write.

Consistency during cutover

Between SwitchReads and SwitchWrites, reads come from the new table but writes still land in the old and get replicated over. If replication lags by even 100 ms, a read-your-writes flow (user updates bio, immediately reloads profile) can show stale data. The mitigation is either (a) wait for zero lag before cutover, (b) route "read-your-writes" traffic to the old side until SwitchWrites completes, or (c) enforce read-after-write via a session cookie routed to primary — the same techniques you'd use with normal read replicas. See Consistency Models.

Interviewer follow-ups (with crisp answers)

Q. When would you pick vertical over horizontal?

A. When the pain is row width, heterogeneous access patterns, or subsystem isolation — not row count. If your users table is huge because there are two billion users, that's horizontal. If it's huge because each user has 50 KB of columns most of which are rarely read, that's vertical. Very often the answer is "vertical first, then horizontal on the resulting hot table."

Q. Why use binlog replication instead of dual-write from the application?

A. Binlog replication is transactionally consistent — the log is written atomically with the row commit, so there's no window where the app crashes between writes and the shards diverge. Dual-write requires distributed-transaction discipline (2PC or a compensating-action outbox) that most application code doesn't get right. The binlog is already there; use it.

Q. Why ZooKeeper for the routing map — why not put it in Redis or a config service?

A. Because during cutover, every proxy must see the same map at the same wall-clock instant. ZooKeeper's ZAB guarantees a single system image with sub-second watch propagation. Redis with keyspace notifications is best-effort and won't survive Redis restarts; a plain config service isn't strongly consistent. For a cutover that mustn't cause split writes, you want a coordinator with real consensus.

Q. How does Vitess achieve zero-downtime cutover exactly?

A. Three moves: reads flip first (readable from new tables, writes still on old, reverse replication armed); wait for replication lag to hit zero; then a brief coordinated pause on writes for the split columns while the last binlog events apply, then the routing map is flipped for writes. The write pause is bounded by the wait for the final GTID to catch up, usually under 100 ms. VReplication also journals the cutover position so reverse replication can start exactly there.

Q. What's a good acceptance test for the migration before flipping?

A. VDiff: a full row-by-row comparison of source and target using consistent snapshots. Ideally run it end-to-end at least once with zero mismatches, then re-run it in "streaming" mode during the confidence window. Also verify: replication lag is stable near zero for a sustained period, and no application errors under load with the new routing.

Q. How do you roll back if something goes wrong after SwitchWrites?

A. Because reverse replication was armed at the SwitchWrites moment, the old wide table has been receiving every new-side write via replication. To roll back, you simply update the routing map back to the old table — the old table is already caught up. This is the entire reason Vitess journals the cutover binlog position.

🗣️ Interview cheat sheet

30-second pitch: "Vertical partitioning splits a wide table into narrow tables by column group, sharing the same primary key, so hot columns get their own small fast table and cold columns get their own. To do it online, you use a routing proxy like VTGate that reads its map from ZooKeeper, a replication worker like VReplication that tails the source database's binlog to backfill and keep the new tables in sync, and a two-stage cutover: SwitchReads flips reads to the new tables while writes still go to the old and continue to replicate, then SwitchWrites briefly pauses, waits for zero lag, and flips writes — with reverse replication armed for rollback. ZooKeeper watches propagate the routing-map change to every proxy in under a second, so nobody needs a restart. This is the same pattern YouTube built into Vitess and Pinterest, LinkedIn, and Uber use in various forms."

Numbers to quote

  • Hot table footprint after split: 5–20% of original.
  • Replication lag steady-state: < 1 s p99.
  • Cutover write pause: < 100 ms, bounded by "wait for last GTID."
  • Routing-map propagation: < 1 s via ZK watch.
  • Backfill throughput: 10k–100k rows/sec per stream.
  • Rollback time: < 1 minute — just flip the routing map back.

5 talking points that win the round

  • Say "column-group projection, same primary key" — that's the crisp definition.
  • Describe the three replication phases: copy, replicate, verify. Interviewers listen for VDiff.
  • Split the cutover into SwitchReads and SwitchWrites — the reversible checkpoint is the win.
  • Name ZooKeeper watches as the mechanism that avoids proxy restarts.
  • Reverse replication is armed at cutover — that's what makes rollback safe, not a database backup.
