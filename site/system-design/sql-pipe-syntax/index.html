SQL Pipe Syntax

How Google fixed SQL's biggest ergonomic problem — with a |> operator that flips the query on its head.

🎯 Real-world scenario

What we're building & where it's used

SQL is the most-used database language on the planet, but everyone who writes it hits the same wall: the clause order doesn't match how you think. You start with SELECT, but the engine actually runs FROM first. You can't filter on an aggregate with WHERE, so a second keyword — HAVING — exists. You can't filter on a window function with HAVING, so a third keyword — QUALIFY — exists. Anything non-linear (post-aggregation joins, chained filters, adding a column mid-query) forces a nested subquery, which pushes the reader upward through parentheses.

Google's answer, shipped in GoogleSQL and detailed in the VLDB 2024 paper "SQL Has Problems. We Can Fix Them: Pipe Syntax in SQL", is a syntactic extension: a new |> operator that lets you write queries as a top-to-bottom pipeline where each step is a unary relational operation (one table in, one table out). The written order matches the execution order. No new algebra, no migrations, no learning curve — same engine, same catalog, same optimizer.

Where it runs. Pipe syntax is live in production across Google's shared SQL front-end and is available in BigQuery, F1 (the query engine behind Ads/AdWords), Spanner, and Procella (YouTube analytics). Google exposed it as a GA feature of GoogleSQL in 2024. The design has been picked up as a proposal in the SQL standard committee and is being explored by other engines. Analysts inside Google were the first heavy users — pipe queries are dramatically easier to read at review time.

Why interviewers love this topic. It sits at the intersection of language design, parser architecture, shared front-end infrastructure, and backward-compatible evolution of a global standard — every one of which is a Staff/Principal-level conversation.

🧑‍🎓 In laymen terms

The problem, without any jargon

Imagine you're writing down a recipe. A sensible recipe reads top to bottom: get the tomatoes, wash them, chop them, add salt, mix, serve. Each line takes what came out of the last line and does one more thing to it.

Now imagine a recipe format where you must write the final serving instructions first, then the ingredients at the end, then the seasoning in the middle, then flip back to say what to wash — that's SQL. You write SELECT (finished dish) FROM (ingredients) WHERE (rules), but the kitchen (the database) has to peek at every line, work out what to grab first, and only later figure out what you actually wanted served. It reads out of order compared to how it runs, and every cook has to learn that trick.

It gets worse. If you want to say "only keep dishes whose total price is more than $10", SQL won't let you say that with the normal rule word WHERE — you have to switch to a different rule word called HAVING. And if you want to rank the dishes and only keep the top three, you need a third rule word called QUALIFY. Three words that all mean "keep some rows", just at different points in the process.

And the moment you want to do two things in a row — filter, then join with another table, then filter again — SQL forces you to wrap the whole query in parentheses and start over, like tearing up the recipe and rewriting it with the old recipe stuffed inside a footnote. Real analytics queries at big companies end up with five or six of these nested parentheses. Nobody enjoys reading them.

Google's fix is beautifully simple: a small arrow |> (pronounced "pipe") that means "and then do this next". You start with a table, then |> filter, then |> join, then |> group, then |> pick columns, all going straight down the page in the order things actually happen. Same database underneath, same power, just a way of writing that matches how you think — the way a recipe should. And crucially, the old SQL still works too: they didn't break anyone's existing queries. Every product you've used that runs on BigQuery — YouTube analytics, Google Ads reporting, Search dashboards — can be queried this way now.

📋 Requirements & scale

What a fix for SQL must not break

This isn't a scaling problem in the QPS sense — it's a language-design problem. The "capacity" here is the number of existing SQL queries, users, tools, and dialects the fix must remain compatible with. That is the real constraint that killed every prior "SQL replacement" attempt.

Functional requirements

  • Linear top-to-bottom composition. Each step is a unary operator: one table in, one table out.
  • Any SQL expression (column refs, functions, subqueries, window functions, CASE, arithmetic) works inside pipe operators unchanged.
  • All relational operations reachable via pipes: filter, project, join, group/aggregate, window, sort, limit, set operations (UNION/INTERSECT/EXCEPT), TVF calls, pivot/unpivot, sampling.
  • Mixable with standard SQL. A pipe chain can start from a standard FROM ..., and a standard SELECT can wrap a pipe chain. A pipe chain is also a valid table subquery.
  • Introspection. A partial pipe query (the "prefix property") is itself a valid query — you can run any prefix to inspect intermediate results.

Non-functional requirements

  • Backward compatibility. Existing queries and clients must be untouched.
  • Zero new relational algebra. Same optimizer, same execution plans, same performance.
  • Shared implementation. One front-end binary reused across F1, BigQuery, Spanner, Procella — a change adopted in one is visible everywhere.
  • Standardizable. Grammar designed so it can be proposed to the SQL standard committee.

🏗️ High-level architecture

Where pipe syntax lives inside a database

A modern SQL engine is a stack: parser → resolver/analyzer → algebrizer → optimizer → executor. Everything from resolver downward operates on a well-defined relational algebra ("resolved AST") — not on SQL text. Pipe syntax is a change to the parser only: it adds a new grammar production for chained unary operators, and each parsed step lowers to the same resolved algebra node an equivalent standard-SQL clause would produce. From the optimizer's point of view, a pipe query is indistinguishable from a nested standard-SQL query.

Google's implementation lives in a component called ZetaSQL — the shared analyzer/parser used by all four engines. Adding pipe syntax to ZetaSQL made it instantly available in F1, BigQuery, Spanner, and Procella. This is the real system-design insight of the paper: one shared front-end binary is what made an evolution of this scale tractable at Google's scale.

Front-end (parse + analyze) Shared relational algebra Engines using the shared front-end

The key trick: two grammars, one algebra

Standard SQL clauses and pipe operators lower into the same resolved AST node types (ScanNode, FilterNode, ProjectNode, AggregateNode, JoinNode, OrderByNode…). This is why the optimizer, executor, and storage layer need zero changes. It's also why performance is exactly identical: a pipe query and its standard equivalent produce byte-identical plans.

🔍 Component deep-dive

1. Why the old syntax hurts (the paper's four grievances)

The Google paper opens by cataloguing SQL's design smells, and they map cleanly to interview talking points:

  • Written order ≠ execution order. SQL is written SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT, but executed FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Every SQL learner memorises this asymmetry.
  • Duplicate row-filter keywords. WHERE, HAVING, QUALIFY — three keywords to filter rows at three different execution points. In pipe syntax you use |> WHERE everywhere.
  • Subquery nesting for composition. Chaining filter → join → filter → aggregate in standard SQL forces you to wrap the middle in a (SELECT ... FROM (SELECT ...)) stack that reads inside-out. Pipe queries flatten this to a linear top-to-bottom read.
  • Extensibility barriers. Every new relational operator in standard SQL (PIVOT, UNPIVOT, QUALIFY, MATCH_RECOGNIZE) needs a new reserved keyword and a special place in the clause order. With pipes, adding a new operator is just adding |> NEW_OP ... — no new keyword, no reordering.

2. The |> operator, precisely

A pipe query is a chain: <starter> |> <op> |> <op> .... Each |> takes the table produced by everything above it and applies one relational operator, producing a new table. The starter is any expression that yields a table — typically a FROM t, but also a SELECT expr row constructor, a CTE, a subquery, or a table-valued function call. Because every step is unary and table-in-table-out, pipe operators are freely composable and reorderable.

3. The operator inventory (GoogleSQL)

Every standard SQL clause has a pipe equivalent, plus a few new ones the paper introduces to reduce clutter:

4. The "prefix property" and why analysts love it

Because each pipe step yields a valid table, any prefix of a pipe query is itself a runnable query. You can highlight the first three pipes in an IDE, hit run, and see the intermediate result — the same way you inspect a value halfway through a Python function. In standard SQL you'd have to comment out the tail, un-alias the inner select, and hope the parser cooperated. This is the single feature analysts cite as the biggest quality-of-life win.

5. The CALL operator and TVFs

Google's ML integration is a good example. Standard SQL forces model inference to be written inside-out as FROM ML.PREDICT(MODEL m, (SELECT ... FROM t)). In pipe syntax it's a normal step: FROM t |> CALL ML.PREDICT(MODEL m) |> CALL ML.PREDICT(MODEL m2). Chaining two models is now linear — no nested subqueries — which is exactly the reason the paper highlights it.

6. What is not a pipe operator (and why)

Grammar-level constructs that don't fit the "table in, table out" model stay in standard SQL: CREATE TABLE, INSERT, UPDATE, DELETE, MERGE, DDL, session settings. Pipe syntax is purely a read-path feature — the analytical query language, not the DML.

🧮 The DSA behind it

Data structures & algorithms

Pipe syntax is a compiler problem more than a systems problem. The concepts an interviewer will want you to name:

Parser: recursive-descent / LALR grammar

ZetaSQL uses a hand-crafted parser (Bison/Yacc-family LALR grammar) that produces an abstract syntax tree (AST). Adding pipe syntax was mostly adding a new grammar rule:

// Simplified grammar rule for a pipe query
pipe_query   := table_expr ( '|>' pipe_op )*
pipe_op      := WHERE expr
              | SELECT select_list
              | JOIN table_expr ON expr
              | AGGREGATE agg_list GROUP BY expr_list
              | ORDER BY expr_list
              | LIMIT integer
              | ... (~20 productions)

The parser produces a chain of pipe AST nodes; the resolver walks the chain, calling the existing resolver methods for WHERE, JOIN, GROUP BY, etc. — one per step — and stitching each into a resolved AST subtree.

Resolved AST: relational algebra tree

Every SQL engine, after parsing, works on a tree of relational-algebra operators: Scan, Filter (σ), Project (π), Join (⋈), Aggregate (γ), Sort (τ), Limit. Pipe syntax and standard SQL both lower into the same tree — so the optimizer's cost model, rules, and physical operators need zero changes. This is the algorithm-of-note: equivalent syntaxes → identical algebra.

Complexity table

ConcernComplexityNote

Related algorithms worth naming

  • Predicate pushdown: the optimizer moves filters below joins/aggregations to reduce data volume. Because pipe syntax and standard SQL produce the same algebra, pushdown works identically for both.
  • Common subexpression elimination: for chained pipes that could be shared (e.g. two pipe branches sharing a filter), the optimizer detects and dedupes.
  • Tree isomorphism: unit tests in ZetaSQL verify that a pipe query and its standard-SQL equivalent produce isomorphic resolved trees — a compile-time correctness check.

How you'd ship pipe syntax on AWS today

The pragmatic architecture is a front-end transpiler service that sits in front of Athena or Redshift and rewrites pipe SQL into standard SQL before it hits the engine. This is the same architectural pattern Google used before ZetaSQL matured — a rewriter that is engine-agnostic.

Concretely on AWS:

  • Amazon API Gateway — accepts pipe SQL from clients (or BI tools via a JDBC shim).
  • AWS Lambda (C# / .NET 8) — hosts the transpiler; parses |> chains, emits standard SQL, forwards to the target engine.
  • Amazon Athena / Amazon Redshift Data API — executes the emitted standard SQL against S3 or the cluster.
  • Amazon S3 + Glue Catalog — the actual data lake / metastore.
  • Amazon ElastiCache (Redis) — cache parsed AST for repeated identical pipe queries so re-parse isn't on the hot path.
  • Amazon CloudWatch — log the pre-transpile and post-transpile SQL side-by-side so query authors can debug.

This "sidecar transpiler" pattern is exactly how you'd introduce pipe syntax to any engine that hasn't adopted it natively — the point of the design (unified relational algebra as the lowering target) is that the emitted standard SQL is exactly equivalent, so the target engine's optimizer stays fully in charge.

💻 C# implementation — a minimal pipe → standard SQL transpiler

Here's a working, idiomatic C# implementation of the transpiler idea above. It tokenises the pipe query, folds each step into a nested SELECT ... FROM (...) layer, and emits standard SQL. Real ZetaSQL is orders of magnitude more sophisticated (types, catalog, scope), but this captures the algorithmic core — an interviewer will love that you can write it on the whiteboard.

// PipeTranspiler.cs — rewrites |> pipe SQL into nested standard SQL.
// Handles: FROM, |> WHERE, |> SELECT, |> JOIN, |> AGGREGATE / GROUP BY,
//          |> ORDER BY, |> LIMIT, |> EXTEND, |> DROP

using System.Text.RegularExpressions;

public sealed record PipeStep(string Op, string Body);

public static class PipeTranspiler
{
    // Ordered list of operators we recognise after a |>
    // Longer keywords first so "GROUP BY" beats "GROUP".
    private static readonly string[] Ops = {
        "AGGREGATE", "ORDER BY", "GROUP BY", "SELECT",
        "WHERE", "JOIN", "LIMIT", "EXTEND", "DROP"
    };

    public static string ToStandardSql(string pipeSql)
    {
        var parts = SplitOnPipes(pipeSql);
        if (parts.Count == 0)
            throw new FormatException("Empty query");

        // parts[0] is the starter (e.g. "FROM orders JOIN customers ON ...").
        // Each subsequent part starts with a pipe operator keyword.
        string starter = parts[0].Trim();
        var steps = parts.Skip(1).Select(ParseStep).ToList();

        // Fold left: wrap prior result in a subquery for each step.
        string current = starter;                // begins with "FROM ..."
        // We carry the current "SELECT list" separately so |> SELECT / EXTEND can update it.
        string selectList = "*";

        foreach (var s in steps)
        {
            switch (s.Op)
            {
                case "WHERE":
                    current = $"SELECT {selectList} {current} WHERE {s.Body}";
                    current = Wrap(current); selectList = "*";
                    break;

                case "SELECT":
                    selectList = s.Body;
                    break;

                case "EXTEND":
                    selectList = $"*, {s.Body}";
                    break;

                case "DROP":
                    selectList = $"* EXCEPT ({s.Body})";
                    break;

                case "JOIN":
                    current = $"SELECT {selectList} {current} JOIN {s.Body}";
                    current = Wrap(current); selectList = "*";
                    break;

                case "AGGREGATE":
                    // Body looks like: "SUM(price) AS total GROUP BY region, product"
                    var (agg, grp) = SplitAggregate(s.Body);
                    string agSelect = string.IsNullOrEmpty(grp) ? agg : $"{grp}, {agg}";
                    current = $"SELECT {agSelect} {current}";
                    if (!string.IsNullOrEmpty(grp))
                        current += $" GROUP BY {grp}";
                    current = Wrap(current); selectList = "*";
                    break;

                case "ORDER BY":
                    current = $"SELECT {selectList} {current} ORDER BY {s.Body}";
                    current = Wrap(current); selectList = "*";
                    break;

                case "LIMIT":
                    current = $"SELECT {selectList} {current} LIMIT {s.Body}";
                    current = Wrap(current); selectList = "*";
                    break;

                default:
                    throw new NotSupportedException($"Unknown pipe op: {s.Op}");
            }
        }
        // Emit final outer SELECT with the accumulated projection.
        return $"SELECT {selectList} {current}";
    }

    private static string Wrap(string sql) => $"FROM ({sql}) AS t";

    private static List<string> SplitOnPipes(string sql)
    {
        // Naive splitter — a real parser handles strings/comments/parentheses.
        // We split on "|>" that is NOT inside parentheses or string literals.
        var result = new List<string>();
        int depth = 0; bool inStr = false; int start = 0;
        for (int i = 0; i < sql.Length - 1; i++) {
            char c = sql[i];
            if (c == '\'') inStr = !inStr;
            else if (!inStr && c == '(') depth++;
            else if (!inStr && c == ')') depth--;
            else if (!inStr && depth == 0 && c == '|' && sql[i+1] == '>') {
                result.Add(sql[start..i]);
                start = i + 2;
                i++;
            }
        }
        result.Add(sql[start..]);
        return result;
    }

    private static PipeStep ParseStep(string raw)
    {
        string s = raw.Trim();
        foreach (var op in Ops)
            if (s.StartsWith(op, StringComparison.OrdinalIgnoreCase))
                return new(op, s[op.Length..].Trim());
        throw new FormatException($"Unknown pipe operator in: {raw}");
    }

    private static (string agg, string grp) SplitAggregate(string body)
    {
        var m = Regex.Match(body, @"^(.*?)\s+GROUP\s+BY\s+(.*)$",
            RegexOptions.IgnoreCase | RegexOptions.Singleline);
        return m.Success ? (m.Groups[1].Value.Trim(), m.Groups[2].Value.Trim())
                          : (body.Trim(), "");
    }
}

//                |> ORDER BY total DESC
//                |> LIMIT 10";

WHERE ...) AS t GROUP BY region, product) AS t WHERE total > 500) AS t ORDER BY total DESC LIMIT 10. What a real production version adds

ZetaSQL's real implementation adds: full tokeniser and Bison-generated LALR parser, complete type system, scope/name resolution with catalog lookups, error messages that point at column offsets, support for all ~20 pipe operators, correct handling of correlated subqueries and window functions, and unit tests asserting that pipe queries produce byte-identical resolved trees to their standard equivalents. Alternative languages that fit this problem well: Rust (used by DataFusion), Go (used by Vitess's parser), OCaml (used by many compilers).

⚖️ Trade-offs, bottlenecks & likely follow-ups

The trade-offs

  • Two syntaxes to maintain. The parser now supports both standard SQL and pipes; grammar test suites double. Google accepted this because forcing a migration would be worse.
  • Tooling lag. Formatters, linters, BI tools (Tableau, Looker), and ORMs don't universally understand |> yet. Adoption inside Google was analyst-first because they hand-write SQL; app developers using ORMs are unaffected.
  • Interop with other dialects. A pipe query is not portable to PostgreSQL/MySQL/Snowflake as of 2026-08. This is the biggest practical drawback — you pick your engine, and you pick it earlier.
  • Standardization is slow. The SQL standard committee moves in years. Until then, pipe syntax remains a GoogleSQL / early-adopter feature.

Failure modes

  • Silently different semantics. None expected — the resolved algebra is identical. But this must be tested rigorously, and ZetaSQL does exactly that.
  • Ambiguous grammar rules. The team validated that |> is not a valid token anywhere in existing SQL, so pipe syntax cannot accidentally activate on legacy queries.
  • Optimizer regressions. The optimizer is unchanged, so pipe queries can't regress compared to their standard equivalent. However, humans writing pipe queries may compose operations in orders the optimizer struggles with (e.g. forgetting to filter early) — but that's a query-quality issue, not a syntax issue.

Likely interview follow-ups

Why |> and not . like a fluent API, or >> like Elixir?

|> is not a valid symbol anywhere in existing SQL — zero ambiguity, no reserved-keyword collision. . would clash with qualified column references; >> would clash with bit shift. It also visually screams "pipe" to anyone who has used F#, Elixir, or R's dplyr.

Is this faster than standard SQL?

Not directly — they produce the same execution plan, so runtime is identical. The productivity win is at authoring/review time. Analysts write correct queries faster, and reviewers catch bugs faster because the flow is linear.

Why didn't Google just make a new language (like Malloy or PRQL)?

Every prior attempt to replace SQL failed on the same shoal: SQL is embedded in JDBC drivers, BI tools, ORMs, dashboards, permissions, audits, and — crucially — 40 years of accumulated user muscle memory. Pipe syntax is an extension that requires zero migration. Its adoption cost is a code review, not a rewrite.

Where does the ZetaSQL front-end run?

It's a shared C++ library linked into each engine's query coordinator process. Engines call ZetaSQL::AnalyzeStatement() to turn SQL text into a resolved algebra tree; from there each engine has its own optimizer and executor. The library is open-sourced at github.com/google/zetasql.

What happens if you mix pipe and standard SQL?

Fully supported. A pipe chain is a valid table expression, so you can wrap it in a standard SELECT. And any standard FROM t can start a pipe chain. This is why incremental adoption works — a team can convert one query, or one clause, at a time.

Will Postgres / Snowflake / Redshift adopt this?

There is an active proposal to the SQL standard committee, and Apache Calcite (which many engines use as their front-end) has a pipe-syntax proposal in flight. As of 2026-08, only GoogleSQL-based engines ship it natively. The transpiler-sidecar pattern above is how you'd bring it to any other engine today.
