Database Sharding & Partitioning

How one big database becomes many — the classic scaling move that every large system eventually makes, and every interviewer eventually asks about.

🎯 Real-world scenario

What we're solving & where it's used

You started with a single PostgreSQL or MySQL box and it served you beautifully — until traffic climbed, tables grew to hundreds of millions of rows, indexes stopped fitting in RAM, backups started taking hours, and a single hot query could freeze the whole application. The classic answer is partitioning (split the data into smaller pieces) and eventually sharding (put those pieces on different physical machines). This is how every large system — Instagram, Discord, Slack, Shopify, Notion, Uber, Pinterest, Figma, YouTube — keeps its database responsive as it grows past what any single server can hold.

The video this page is based on — Database Sharding and Partitioning by Arpit Bhayani — frames it exactly this way: partitioning is logically splitting a big table into smaller pieces (still on one machine), and sharding is physically distributing those pieces across independent database servers so read and write throughput scale horizontally. The distinction is small in wording but massive in operational impact: partitioning is a query-planner optimization; sharding is a distributed-systems commitment.

Interviewers love this topic because a good answer proves you understand the whole ladder — vertical scaling → read replicas → caching → partitioning → sharding — and can articulate when to pull each lever, not just how. The wrong answer is "just shard everything"; the right answer names the shard key, the strategy, the resharding pain, and the cross-shard query trap before the interviewer has to ask.

🧑‍🎓 In laymen terms

Explaining it to someone who's never touched a database

Imagine you run a giant library that started with a single, beautiful room full of books. At first, one librarian at the front desk could handle everyone — someone walks in, asks for "Harry Potter," she walks to the shelf, finds it, hands it over. Simple.

Now imagine your library becomes wildly popular. Fifty people show up every second asking for books. Your one librarian is running around, sweating, dropping things. The room itself is packed floor to ceiling — you literally can't fit more shelves in it. What do you do?

You open more rooms. But now you have a problem: if the books are randomly scattered across ten rooms, every request means checking every room. So instead, you agree on a rule for where each book lives. Maybe: "books whose title starts with A–E go in Room 1, F–J in Room 2, K–O in Room 3…" Now a visitor asking for "Harry Potter" is sent straight to Room 2, and the other nine rooms don't even know the request happened. Each room has its own librarian. Everyone's fast again.

That's sharding. Each "room" is a separate database server, each "rule for where things live" is called a shard key, and the person at the front door who sends you to the right room is a router. Instagram does this with your photos, WhatsApp does this with your chats, Uber does this with rides — the trick is exactly the library trick, just with computers.

The hard parts, in plain English: (1) picking a bad rule means one room gets slammed while the others sit empty (imagine everyone asks for "Harry Potter" — poor Room 2). (2) Some questions can't be answered from one room — "how many books do we have in total?" — so you have to walk to every room and add up. And (3) once you've split things up, merging them back or changing the rule is a nightmare, because you have to physically move millions of books between rooms without closing the library.

Think of it as: one giant filing cabinet → many smaller filing cabinets, each in a different room, with a receptionist who knows exactly which cabinet holds your file. That's the whole idea. Everything else is engineers arguing about the receptionist's algorithm.

📋 Requirements & scale

When sharding is (and isn't) the right answer

Sharding is not a first move — it's the last big lever you pull before you're in true "large-system" territory. Interviewers expect you to name the ladder of cheaper alternatives you'd try first, then justify why sharding is unavoidable.

The scaling ladder (try these before sharding)

RungWhat it doesCeiling
1. Vertical scaleBigger box: more RAM, faster NVMe, more cores.~1–2 TB working set; expensive at the top end.
2. Read replicasAsync replicas serve reads; primary takes writes.Read-heavy only; writes still bottlenecked on primary.
3. CachingRedis / Memcached in front of the DB.Great for hot keys, useless for uncached queries.
4. PartitioningSplit one table into many smaller tables inside one DB.Same machine limits — CPU, RAM, disk I/O.
5. ShardingSplit across many DBs on many machines.Near-infinite; complexity explodes.

Signals it's time to shard

  • Data doesn't fit on one box. Working set exceeds ~1 TB and the index no longer fits in RAM.
  • Writes overwhelm the primary. Read replicas don't help — you need write parallelism.
  • Backups & DDL become impossible. A single table migration takes 12 hours and locks the app.
  • Blast radius is unacceptable. One noisy tenant can freeze all tenants; you need physical isolation.

🏗️ High-level architecture

How the pieces fit together

The core architecture has four moving parts: the application (which knows nothing about physical shards), a shard router / proxy (which knows exactly which shard holds which key), a set of shards (independent DB clusters, each often replicated for HA), and a metadata / config store (which holds the shard map — key ranges or hash-bucket-to-shard assignments). A write for user u42 flows: app → router → hash(u42) → shard 3 → primary → replicas. A cross-user query (e.g. "top posts across the platform") requires scatter-gather: the router fans the query out to every shard, waits for all responses, merges them.

The two axes of splitting to keep separate in your head:

Vertical partitioning

Split a wide table by columns — put hot columns (user_id, name, email) on one server and cold ones (bio, avatar_blob, prefs_json) on another. Reduces row width and I/O per read. Common inside a single DB.

Horizontal partitioning (a.k.a. sharding)

Split a table by rows — users 1–10M on shard 1, users 10M–20M on shard 2, etc. Each shard has the same schema, different subsets. This is what people usually mean by "sharding."

🔍 Component deep-dive

Partitioning vs sharding — the strict definition

Arpit's key clarification (and the one interviewers reward): partitioning is a logical split; sharding is a physical distribution. Partitioning a table into monthly chunks inside one PostgreSQL keeps everything on one machine — the query planner just prunes irrelevant partitions. Sharding takes those partitions and puts them on different boxes with independent CPU, RAM, storage, and network. Sharding is horizontal partitioning, but not all horizontal partitioning is sharding.

The four sharding strategies

1) Range-based sharding

Assign contiguous key ranges to shards: user_id 0–10M → S1, 10M–20M → S2. Perfect for range queries (give me all orders from Jan–Mar) because they hit one or two shards. The killer downside: skew. If new users are always assigned the highest ID, the last shard becomes a hot write shard while shard 1 sees nothing. Time-series data is famously bad at this — the "current day" partition takes every write.

2) Hash-based sharding

shard = hash(shard_key) mod N. This spreads writes evenly and needs no lookup table — the router computes the shard from the key. The trade-off: range queries are broadcast (every shard has some of the requested rows), and changing N is catastrophic because almost every key moves. The fix is consistent hashing, which limits the moved fraction to roughly 1/N.

3) Directory-based sharding

A lookup table maps shard_key → shard_id. Maximum flexibility — you can move any key anywhere, add shards dynamically, target hot users. The cost: the lookup service becomes a hot path on every request and a potential single point of failure. In practice the map is cached aggressively on the router (a "shard cache" in Instagram parlance).

4) Geo-based sharding

Shard key encodes region: EU users on EU shards, US users on US shards. Great for latency (users hit the nearest data center) and compliance (GDPR data residency). It's really just range-based sharding with a geographic dimension. The classic pain is the traveling user — someone flies from Berlin to New York and their data is still on eu-central-1.

Shard key selection — the highest-leverage decision

Nothing you do later can save a bad shard key. Two properties matter:

  • High cardinality. The key must have far more distinct values than the shard count. Sharding by country_code caps you at ~200 shards forever.
  • Even frequency. If 30% of your traffic is one tenant, that tenant creates a permanent hot shard no matter which strategy you use.

The best keys are also request-correlated — the key naturally appears in every query. Instagram shards by user_id because virtually every request is "show me user X's stuff." A payment system might shard by merchant_id. Never shard by an auto-increment ID and never by a low-cardinality enum.

The hot-shard problem

A hot shard is when one shard receives disproportionate traffic — a celebrity user, a viral product, a Black-Friday tenant. Sharding alone doesn't fix it because the hot key by definition maps to one shard. Real defenses: replicate hot keys (fan reads across replicas of that shard), split further (subdivide the hot user's data by another dimension — e.g. per-post shards for a celebrity), or write-buffer and coalesce (batch writes to that key). This is the follow-up interviewers always ask, and "consistent hashing" alone is not a full answer.

Resharding without downtime

The most feared operation. The typical pattern (used by Instagram, Discord, Slack) is double-writes: (1) launch new shards, (2) dual-write every mutation to old and new, (3) backfill historical data online, (4) shadow-read the new shards and compare, (5) cut reads over, (6) stop writing to old. This takes weeks and requires idempotent writes and a killswitch. Consistent hashing dramatically reduces the size of the move but does not eliminate the ceremony.

Cross-shard queries

Any query without the shard key becomes a scatter-gather: fan out to all shards, wait for all responses, merge. Latency = slowest shard, not average. Two mitigations: (a) denormalize / duplicate — maintain a global secondary index in a separate store (Elasticsearch, DynamoDB GSI) so "search all users by email" doesn't need to hit every shard; (b) embrace approximate answers — pre-aggregated counters, sketch data structures (HyperLogLog).

Cross-shard transactions

Multi-key ACID transactions across shards are essentially impossible cheaply. Real systems fall back to Saga pattern (compensating actions), 2PC (slow, blocking, availability-hostile), or outbox + event sourcing (asynchronous eventual consistency). This is one of the biggest costs of sharding, and interviewers ask about it.

🧮 The DSA behind it

Data structures & algorithms that make sharding work

1) Modulo hashing

The naive baseline: shard = hash(key) % N. Beautiful simplicity — O(1) lookup, no memory. But when N changes from 4 to 5, virtually every key remaps: ~80% of your data moves. That's the primary reason large systems don't use plain modulo.

2) Consistent hashing

Place shards on a ring of hash values 0..2³²−1. A key hashes to a point on the ring; it belongs to the next shard clockwise. Adding a shard only takes over the arc between it and the next-clockwise shard — only K/N keys move, not K. Use virtual nodes (each physical shard owns 100–200 points on the ring) to smooth out uneven arcs. Used by DynamoDB, Cassandra, Riak, ElastiCache Redis.

Ring (simplified, 3 shards, hashes 0..99) 0 ─── 33 ─── 66 ─── 99 \ | | [S1] [S2] [S3] keys 34..66 → S2 add S4 at 50 → only keys 34..50 move from S2 to S4

3) Rendezvous (HRW) hashing

For each key, compute hash(key, shard_i) for every shard i and pick the shard with the highest hash. Adds only 1/N movement on shard changes, no ring, no virtual nodes. Simpler correctness proof; used in load balancers and CDN routing.

4) B-Tree indexes (per shard)

Each shard is still a normal database — B-Trees on the primary key, secondary indexes, WAL. Sharding doesn't replace them, it multiplies them. Total index memory across shards grows sub-linearly with data because each shard's index fits in that shard's RAM.

5) Bloom filters for existence checks

Before scattering "does user@example.com exist?" to N shards, ask a Bloom filter maintained per shard (or globally). A Bloom filter says "definitely not on this shard" with zero false negatives, saving expensive fan-out.

A canonical AWS deployment for a self-sharded relational stack: an ECS/EKS fleet running your API with a shard-routing library, an ElastiCache Redis that holds the shard map plus hot-key cache, N × Aurora clusters (each with a writer + 2 read replicas), a small DynamoDB table as the authoritative shard-map source, and DMS ready to spin up whenever a reshard is planned. All traffic enters through ALB → API Gateway. Observability (per-shard QPS, p99, storage) lives in CloudWatch + Managed Grafana. 💻 C# implementation — a minimal shard router

Below is a self-contained C# reference: a consistent-hash ring, a shard resolver that supports both modulo-hash and consistent-hash strategies, and a routing entry-point. It's intentionally small — a real one adds virtual nodes (already included), weight, replica awareness, health checks, and a shard-map store — but this is the code you should be able to sketch on a whiteboard in an interview.

using System;
using System.Collections.Generic;
using System.Linq;
using System.Security.Cryptography;
using System.Text;

// 1) A shard descriptor — in real life this holds a connection string, replica list, region, etc.
public sealed record Shard(string Id, string ConnectionString);

// 2) The abstraction — every strategy answers "which shard owns this key?"
public interface IShardRouter
{
    Shard Resolve(string shardKey);
}

// 3) Naive modulo hashing — great for interviews to explain the "why not this?" case.
public sealed class ModuloRouter : IShardRouter
{
    private readonly List<Shard> _shards;
    public ModuloRouter(IEnumerable<Shard> shards) => _shards = shards.ToList();

    public Shard Resolve(string shardKey)
    {
        var h = Stable64(shardKey);
        var idx = (int)((h & long.MaxValue) % _shards.Count);
        return _shards[idx];
    }

    // SHA-1 → first 8 bytes → long. Deterministic across processes (Object.GetHashCode is NOT).
    internal static long Stable64(string s)
    {
        using var sha = SHA1.Create();
        var b = sha.ComputeHash(Encoding.UTF8.GetBytes(s));
        return BitConverter.ToInt64(b, 0);
    }
}

// 4) Consistent-hash ring with virtual nodes. Adding/removing a shard moves only ~K/N keys.
public sealed class ConsistentHashRouter : IShardRouter
{
    private readonly SortedDictionary<long, Shard> _ring = new();
    private readonly int _vnodes;

    public ConsistentHashRouter(IEnumerable<Shard> shards, int vnodes = 150)
    {
        _vnodes = vnodes;
        foreach (var s in shards) AddShard(s);
    }

    public void AddShard(Shard s)
    {
        for (int i = 0; i < _vnodes; i++)
        {
            var point = ModuloRouter.Stable64($"{s.Id}#{i}");
            _ring[point] = s;
        }
    }

    public void RemoveShard(string shardId)
    {
        var victims = _ring.Where(kv => kv.Value.Id == shardId).Select(kv => kv.Key).ToList();
        foreach (var k in victims) _ring.Remove(k);
    }

    public Shard Resolve(string shardKey)
    {
        if (_ring.Count == 0) throw new InvalidOperationException("No shards registered");
        var h = ModuloRouter.Stable64(shardKey);

        // Walk clockwise: first ring key >= h; wrap around if past the end.
        foreach (var kv in _ring)
            if (kv.Key >= h) return kv.Value;
        return _ring.First().Value;
    }
}

// 5) Usage. In production, wrap this in a decorator that reads shard-map version from
// ElastiCache/DynamoDB so that a live reshard can update the ring without redeploying.
public static class Demo
{
    public static void Main()
    {
        var shards = new[]
        {
            new Shard("s0", "..."), new Shard("s1", "..."),
            new Shard("s2", "..."), new Shard("s3", "..."),
        };
        IShardRouter router = new ConsistentHashRouter(shards);

        var shard = router.Resolve("user:u42");
        Console.WriteLine($"u42 → {shard.Id}");   // consistent across processes
    }
}

Language alternatives. Discord published its version of this in Elixir (Cassandra-backed sharding); Instagram's original was Python calling PostgreSQL with a hand-rolled Python shard_id % N. In Go, look at Vitess (YouTube's MySQL sharding layer). In Java, look at Apache ShardingSphere. All of them have the exact same shape as the code above — a hash function, a shard map, and a router.

⚖️ Trade-offs, bottlenecks & likely follow-ups

The costs you pay the moment you shard

You lose cheap joins — anything crossing shards has to be done in the app layer or via a denormalized secondary index. You lose global unique constraints — no single database can enforce "email must be unique across all users"; you need a separate uniqueness service or a dedicated shard for unique-index tables. You lose auto-increment IDs — you need a distributed ID generator (Snowflake, UUIDv7, KSUID). You lose easy transactions — anything spanning shards is Saga or 2PC. You lose operational simplicity — N times the pagers, N times the disk-full alerts, N times the version-upgrade coordination.

The bottlenecks that persist

Sharding does not fix these on its own: (1) the router or proxy tier can become the new bottleneck if it's synchronous and single-threaded; (2) the shard-map store is read on every request — cache it and expect thundering herds when it invalidates; (3) cross-region latency if shards live in different regions; (4) tail latency — with N shards and slow-tail request rate p, the probability at least one shard is slow is roughly 1 − (1−p)ᴺ, which is why scatter-gather queries have exponentially worse p99 as N grows.

Common interviewer follow-ups (and crisp answers)

"What's the difference between partitioning and sharding?"

Partitioning is a logical split of a table into pieces (usually inside one database, exploited by the query planner). Sharding is a physical split of those pieces across multiple independent database servers. Sharding is horizontal partitioning + operational separation.

"How do you pick a shard key?"

Two properties: high cardinality (so it can support many shards) and even distribution (so no shard gets disproportionate traffic). Ideally the key is also present in nearly every query, so most reads/writes are single-shard. Instagram picks user_id; a marketplace might pick merchant_id.

"Why not just modulo hash?"

Because changing shard count remaps almost every key. Consistent hashing or rendezvous hashing move only ~K/N keys when N changes, which is critical for online resharding.

"What if one shard becomes hot?"

Split it (subdivide by a secondary dimension), replicate hot keys behind a cache like DAX/Redis, and add write coalescing. Sometimes the correct answer is to give the hot tenant a dedicated shard.

"How do you reshard without downtime?"

Dual-write to old and new shards, backfill history in the background, shadow-read to verify, then cut reads over and stop writing to old. Requires idempotent writes and CDC (DMS or DynamoDB Streams).

"How do you handle queries that don't include the shard key?"

Either denormalize into a secondary index (Elasticsearch or a DynamoDB GSI keyed by the alternate field), or scatter-gather across all shards. Fan-out is O(N), latency is set by the slowest shard.

"Cross-shard transactions — how?"

Sagas with compensating actions are the pragmatic answer. 2PC is technically possible but slow and hurts availability. Outbox pattern + event sourcing is common for eventual consistency.

"When would you NOT shard?"

When vertical scaling still has headroom, when the workload is read-heavy (replicas are cheaper), when the data fits in ~1 TB, when the join graph is dense, or when the cost of losing ACID and easy operations outweighs the throughput win.

🗣️ Interview cheat sheet

30-second pitch: "Partitioning is splitting a table logically; sharding is putting those partitions on physically separate databases. Pick a shard key with high cardinality and even distribution — often user_id or tenant_id. Use consistent hashing so adding a shard only moves 1/N keys. Design around single-shard queries: cross-shard fan-out kills p99, cross-shard transactions require sagas, and hot shards need targeted mitigation like key-splitting or caching. Reshard online with dual-writes, CDC, and shadow-reads."

  • Numbers to quote: one Postgres box handles ~10k–50k QPS and ~1 TB; keep each shard's index in RAM; typical fleets are 16/64/256/1024 shards.
  • The four strategies: range, hash (with consistent variant), directory, geo — each with its own hot-shard failure mode.
  • Shard key rules: high cardinality, even frequency, request-correlated. Bad keys are permanent.
  • The three losses on day one: joins, global unique constraints, easy transactions. Plan replacements upfront.
  • The three hardest ops: resharding, hot shards, cross-shard queries. Every senior interviewer will drill into these — have concrete tactics for each.
