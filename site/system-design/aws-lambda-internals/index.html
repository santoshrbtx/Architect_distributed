AWS Lambda Internals

How Lambda actually runs your code: Firecracker microVMs, the execution environment lifecycle, the Runtime API, SnapStart snapshots, and multi-tenant scheduling — the interview answer that separates a user from an operator.

🎯 Real-world scenario

What Lambda is really doing under the hood

You upload a zip or container image. Someone hits an HTTPS endpoint, drops a file into S3, or writes a row to DynamoDB. Milliseconds later a fresh, isolated environment appears out of nowhere, runs your handler, and vanishes when it's no longer needed. You pay for the milliseconds it ran. How is that possible on shared hardware, safely, across millions of untrusted customers, without a fleet of always-on VMs?

That question is the interview. AWS Lambda is not "just a container." It's a compute plane built on top of a Rust-based hypervisor called Firecracker, a control plane that places microVMs onto a bare-metal worker fleet, a strict Init → Invoke → Shutdown execution environment lifecycle, and an HTTP-based Runtime API that lets any language talk to the platform. It's the same substrate that powers AWS Fargate, and the design ideas ripple through Google Cloud Run, Azure Container Apps, Fly.io, and every serious FaaS since 2018.

Interviewers love this topic because it forces you to reason about virtualization vs containerization, cold-start economics, snapshotting, multi-tenant isolation, and the physics of "scale to zero." If you can whiteboard Firecracker, the lifecycle, SnapStart, and the concurrency model, you're demonstrating principal-engineer-level depth in one answer.

🧑‍🎓 In laymen terms

Explain it like I've never opened a terminal

Imagine you own a food-truck kitchen. Some days nobody orders anything. Other days a wedding party of 300 walks up in the same minute. You could rent a giant kitchen "just in case" — but that's expensive and mostly empty. Or you could keep tiny, identical mini-kitchens folded up in a warehouse, and unfold one only when a customer arrives, cook the dish, then fold it back up. That's Lambda.

When you "write a Lambda function," you're writing the recipe. AWS keeps the recipe in a warehouse. The moment a customer places an order — someone visits your website, uploads a photo, sends a message — AWS pops open a fresh mini-kitchen in a fraction of a second, lets your recipe cook one dish, and then either keeps the kitchen open in case another order arrives soon, or folds it away. You are billed for the seconds your kitchen was cooking, not for the empty warehouse hours.

The clever part is that the "mini-kitchen" is actually a very small, very fast virtual computer called a microVM. Think of it as a full kitchen inside a shipping container — sealed off from all other kitchens on the same truck, so if one customer's recipe catches fire (or is malicious), no one else's dish is ruined. AWS invented a lightweight hypervisor called Firecracker just to make these containers boot in milliseconds instead of minutes.

The hard part? Two things. Booting takes time. The first order after a quiet period is called a "cold start" and is slower — the kitchen has to be unfolded. AWS spent years shaving that down to under a second, and their newest trick, SnapStart, is like taking a photograph of an already-warmed-up kitchen and cloning it — the next order arrives to a kitchen that's already got the oven at 400°F. The other hard part is scale: when 10,000 customers show up at once, AWS has to spin up 10,000 kitchens across thousands of physical trucks, load-balance them, isolate them, and bill them separately — all without you doing anything.

Products you already use that run on Lambda-shaped systems: parts of Netflix, Coca-Cola's vending backend, iRobot, Slack's file-upload pipeline, Amazon Alexa, and thousands of "just call this webhook when X happens" glue jobs. Once you see it, you see it everywhere.

📋 Requirements & scale

What the platform has to deliver

Lambda is the platform, so its requirements are what Amazon promises to its customers. Interviewers will expect you to name both the functional and non-functional constraints and to quote the real published numbers.

Functional requirements

  • Run arbitrary customer code from many languages (managed runtimes for Node.js, Python, Java, .NET, Go, Ruby; custom runtimes via the Runtime API).
  • Deliver events from 200+ sources: HTTPS (API Gateway/ALB/Function URLs), S3, DynamoDB Streams, Kinesis, SQS, SNS, EventBridge, MQ, MSK, self-managed Kafka, CloudWatch, IoT, Step Functions.
  • Support synchronous (RequestResponse), asynchronous (Event), and poll-based (Event Source Mappings) invocation.
  • Scale to zero when idle, scale to thousands of concurrent environments in seconds.
  • Bill per millisecond of execution and per configured memory (128 MiB – 10 GiB).

Non-functional requirements

  • Strong isolation between tenants — VM-grade, not just container-grade — because customer code is untrusted by default.
  • High density — thousands of tenants per bare-metal host — to make per-request pricing economically viable.
  • Sub-second cold start for typical code, and < 100 ms warm invoke overhead.
  • Global availability across every AWS region, with retries and DLQs for async paths.

🏗️ High-level architecture

Control plane, data plane, and worker fleet

Lambda is a two-plane system. The control plane handles function definitions, versions, configuration, IAM, and — critically — placement: deciding which physical worker should run the next invocation. The data plane is the hot path: the frontend that accepts Invoke calls, the workers running Firecracker, and the pollers pulling events from queues and streams.

When you call Invoke, the request first lands on the Lambda frontend. The frontend authorizes the call, looks up the function, and asks the Worker Manager for a live execution environment to route to. If a warm environment exists for that (function version, version), the frontend forwards the payload straight to it. If not, the Worker Manager asks the Placement Service to pick a physical worker, spawn a fresh Firecracker microVM, pull the code, run Init, and register the new environment. The request then flows through — this is the "cold start" path. Every subsequent invoke can reuse the now-warm environment for a non-deterministic period.

The control-plane hop is off the hot path. Once the environment exists and the Worker Manager has cached the placement, subsequent invokes route directly frontend → worker. That's why warm invokes add only a few milliseconds of overhead over the code itself.

🔍 Component deep-dive

The execution environment lifecycle

Every Lambda invocation runs inside an execution environment — a sandboxed process tree inside a Firecracker microVM. The lifecycle has three phases (four with SnapStart): Init → Restore (optional) → Invoke → Shutdown. Each phase begins with an event Lambda dispatches to the runtime and to every registered extension, and completes when they signal readiness by issuing a Next request against the Runtime API. Between events, Lambda freezes the environment's processes — that's how it stops billing you and how one worker can hold thousands of dormant environments.

The Init phase does three concrete jobs: Extension init (start every registered extension), Runtime init (bootstrap the language runtime), Function init (execute the static code above your handler — imports, DB pool creation, model loading). For SnapStart-enabled functions, Init also runs beforeCheckpoint hooks. Standard functions get 10 seconds for the whole Init phase; PC, SnapStart, and Managed Instances functions get up to 130 s or the function timeout (max 900 s). On timeout, the standard function retries Init at first invocation using the configured function timeout.

The Invoke phase is what you pay for. It fires when an event arrives. Crucially, each execution environment handles exactly one request at a time in the default runtime — Lambda's fundamental concurrency unit. Six simultaneous API Gateway requests against a function with no warm environments produce six cold starts, because you need six independent environments. AWS keeps environments alive for a non-deterministic period between invokes (in practice, empirical measurements show 5–15 minutes for typical workloads) and proactively recycles them every few hours for patching.

The Shutdown phase gives extensions time to flush before Lambda terminates the process. The window depends on what's registered: 0 ms with no extensions, 500 ms with an internal extension, 2,000 ms with one or more external extensions. Anything that doesn't respond by the deadline gets a SIGKILL.

Firecracker — the isolation primitive

Firecracker is a purpose-built, open-source, Rust-based Virtual Machine Monitor (VMM) that AWS created for Lambda and Fargate. It's a fork of Google's crosvm, aggressively stripped down. It runs each microVM on Linux KVM (hardware virtualization), giving VM-grade isolation between tenants — you're not sharing a kernel with your noisy neighbor, unlike containers. That matters because customer code is untrusted.

The design that makes Firecracker special is minimalism. It exposes only five emulated devices to the guest: virtio-net (network), virtio-block (disk), virtio-vsock (host-guest RPC), a serial console, and a minimal i8042 keyboard controller used only to signal the microVM to stop. No VGA, no USB, no BIOS emulation, no PCI. Fewer devices means less code, less attack surface, and less memory — under 5 MiB of VMM memory overhead per microVM, which is how a single bare-metal host can safely pack thousands of tenants.

Firecracker also hardens the VMM process with thread-specific seccomp filters (each thread has a narrowly scoped syscall allowlist), and it uses a separate binary called the Jailer to set up isolation before launching the VMM: unshare namespaces (mount, PID, optionally network), pivot_root into a chroot, cgroup v1/v2 constraints on CPU and memory, drop to a non-root UID/GID, close inherited file descriptors, clear environment, apply setrlimit ceilings, then exec Firecracker. Every microVM sits inside three layers of defense.

The Runtime API — how your code talks to Lambda

Managed runtimes and custom runtimes both use the Lambda Runtime API, a versioned HTTP interface (current version 2018-06-01). The runtime discovers the endpoint from the AWS_LAMBDA_RUNTIME_API environment variable Lambda injects into the execution environment, and composes URLs like http://$AWS_LAMBDA_RUNTIME_API/2018-06-01/runtime/invocation/next. The core loop is a long-poll GET on /runtime/invocation/next — the runtime process may be frozen for several seconds while waiting for an event. This is the mechanism Lambda uses to cheaply suspend the environment between invokes: everything blocks on that single HTTP call.

Other endpoints on the same API: POST /runtime/invocation/{req_id}/response to return the result, POST /runtime/invocation/{req_id}/error for handler errors, and POST /runtime/init/error for Init-phase failures. Extensions register on /runtime/register and receive lifecycle events on /extension/event/next. That's the entire contract — any language that speaks HTTP can be a Lambda runtime.

Code loading & layers

Container images and zip functions are content-addressed. AWS unpacks images into a flat filesystem and splits it into 512 KiB chunks, hashes each chunk, and stores unique chunks once. Brooker et al.'s USENIX ATC '23 paper reports that roughly 75% of Lambda container images contain less than 5% unique bytes, so this dedup is enormous — the same base Python image, same node_modules, same JVM runtime chunks fan out across millions of functions from a small deduplicated store. Chunks are fetched lazily on demand as the microVM boots.

Lambda Layers are a lighter-weight variant of the same idea for zip functions: attach up to 5 layers per function, each an independently versioned zip. Lambda extracts each layer's contents into /opt inside the environment. Every runtime's search paths (/opt/bin, /opt/lib, /opt/python, /opt/nodejs/node_modules, etc.) already include those directories, so imports "just work" without you knowing a layer was involved.

SnapStart — Init at publish time

Cold starts on JVM-heavy handlers (Java, Spring) are painful — sometimes 2–5 seconds — because class loading, JIT warm-up, and framework initialization dominate. SnapStart cuts that by shifting the Init phase to version-publish time. Here's the mechanic: when you publish a function version with SnapStart on, Lambda spins up a Firecracker microVM, runs Init (including your beforeCheckpoint hooks), and then takes a Firecracker snapshot of the microVM's memory and disk state. That snapshot is encrypted and cached for low-latency access.

On first invoke and on scale-up, instead of starting from scratch, Lambda resumes new environments from the cached snapshot — that's the Restore phase in the lifecycle. Firecracker's snapshot format captures three things: the guest memory file, the microVM state file (both KVM and Firecracker-emulated hardware state), and disk state. Restore uses MAP_PRIVATE so each resumed environment gets its own copy-on-write view of guest memory.

The catch is uniqueness. A single snapshot is shared across many resumed environments — anything that must be per-instance-unique will be duplicated if you baked it into Init. That includes: cryptographic random seeds (yes, the RNG state is snapshotted), ephemeral IDs, cached credentials with a lifetime, and any TCP connection whose server-side state won't tolerate being cloned. The workaround is runtime hooks: use beforeCheckpoint to release stateful resources before the snapshot, and afterRestore to regenerate them on wake. In Java that's Core.getGlobalContext().register(new Resource() {...}).

Fairness & multi-tenancy

The Worker Manager and Placement Service — briefly named in the NSDI '20 and ATC '23 papers, but not otherwise publicly documented — handle placement. They pick which worker gets a new microVM, weighing bin-packing (density) against noisy-neighbor risk. Once placed, the Jailer's cgroup constraints and the Firecracker VMM's own accounting enforce per-tenant limits. Network egress is rate-limited at the vsock/virtio boundary. AWS has published enough at NSDI/ATC to convince security auditors, but the exact scheduling algorithm remains proprietary.

Two things worth highlighting for interviews: Hyperplane ENIs — when your Lambda runs in a VPC, Lambda no longer creates one ENI per environment (that scaling problem was fixed in 2019). Instead, a small pool of shared, multi-tenant ENIs (called Hyperplane) fronts your VPC subnet, so cold-start latency doesn't scale with concurrency. And Lambda Managed Instances — a newer feature that keeps a warm pool of environments and can handle multiple requests per environment concurrently (unlike the default one-request-at-a-time model). It's the escape hatch for interviewers who like to needle you about the "one request per environment" claim.

💻 C# implementation

You don't implement Lambda's internals in your app code — but you can absolutely simulate the pieces that make the interview click. Here's a minimal reference implementation in C# that mirrors what a custom runtime does: long-poll the Runtime API for the next invocation, execute the handler, post the response. This is what AWS's own .NET runtime does under the hood, and writing it out proves you understand the contract.

// Minimal Lambda custom runtime loop in C# — mirrors the AWS Runtime API contract.
// Real code you'd bundle as ./bootstrap in a "provided.al2" runtime zip.

using System;
using System.Net.Http;
using System.Text;
using System.Text.Json;
using System.Threading.Tasks;

public class LambdaRuntime
{
    private static readonly HttpClient Http = new();
    private static readonly string ApiBase =
        $"http://{Environment.GetEnvironmentVariable("AWS_LAMBDA_RUNTIME_API")}/2018-06-01/runtime";

    public static async Task Main()
    {
        // Function init — this runs once per environment, in the Init phase.
        // Static setup goes here: DB pools, DI containers, warmed-up config.
        var handler = BuildHandler();

        // Invoke loop — one iteration = one Invoke phase.
        // The GET blocks (long-poll); Lambda freezes the process here between events.
        while (true)
        {
            using var next = await Http.GetAsync($"{ApiBase}/invocation/next");
            var reqId = next.Headers.GetValues("Lambda-Runtime-Aws-Request-Id").First();
            var deadlineMs = long.Parse(next.Headers.GetValues("Lambda-Runtime-Deadline-Ms").First());
            var payload = await next.Content.ReadAsStringAsync();

            try
            {
                var result = await handler(payload, deadlineMs);
                using var body = new StringContent(result, Encoding.UTF8, "application/json");
                await Http.PostAsync($"{ApiBase}/invocation/{reqId}/response", body);
            }
            catch (Exception ex)
            {
                var err = JsonSerializer.Serialize(new { errorMessage = ex.Message, errorType = ex.GetType().Name });
                using var body = new StringContent(err, Encoding.UTF8, "application/json");
                await Http.PostAsync($"{ApiBase}/invocation/{reqId}/error", body);
            }
        }
    }

    private static Func<string, long, Task<string>> BuildHandler() =>
        async (payload, deadlineMs) =>
        {
            using var doc = JsonDocument.Parse(payload);
            var name = doc.RootElement.TryGetProperty("name", out var n) ? n.GetString() : "world";
            return JsonSerializer.Serialize(new { message = $"Hello, {name}!", remainingMs = deadlineMs - DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() });
        };
}

Two things this snippet reveals that interviewers probe:

  1. The long-poll GET is the entire mechanism for freezing your process between events. There's no magic — just a blocking HTTP call. When Lambda "freezes" you, it's freezing you while you're waiting on this socket. When it thaws you, the socket returns.
  2. The Lambda-Runtime-Deadline-Ms header tells you exactly when you'll be SIGKILLed. Use it to bail out gracefully before the platform kills you mid-write.

Alternative languages: the same 30 lines work in Rust (lambda_runtime crate), Go (aws-lambda-go), Python (awslambdaric — the real AWS-shipped runtime interface client), or a shell script + curl. The Runtime API is the language-neutral contract.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Design tensions Lambda navigates

Isolation vs density. Firecracker gives up some of a container's density (a raw container is measured in KiB of overhead; a microVM in low MiB) in exchange for hardware-enforced isolation. AWS accepted that trade because customer code is untrusted and shared-kernel container escape bugs are catastrophic when your tenant is a stranger from the internet.

Cold start vs cost. The pay-per-ms billing model requires "scale to zero," which requires environments to actually shut down when idle. But shutting down means the next invoke pays for Init. AWS's answers — Provisioned Concurrency (pre-warm N environments, you pay for idle), SnapStart (Init once at publish, restore on invoke), Lambda Managed Instances (multi-request-per-env warm pool) — each pick a different point on the cold-start-vs-cost curve.

One request per environment vs concurrency inside one env. The default "one request at a time" model is dead simple to reason about but wastes CPU on I/O-bound workloads. Managed Instances is the escape hatch. Cloudflare Workers took the opposite extreme (isolate-per-request, thousands per V8 process) and pay for it with a much more restrictive execution model.

Simplicity vs power. Lambda deliberately does not let you SSH into the environment, run background threads that outlive a request, or open a listening socket. Those constraints are what make the platform manageable at millions of tenants.

Likely bottlenecks

  • Container image cold start. A 500 MB container image can add seconds to the first cold start while chunks stream in, even with dedup. Mitigation: keep images small, use Lambda's optimized base images, favor zip + layers for latency-sensitive functions.
  • VPC networking (pre-Hyperplane workloads). Historically each ENI creation was slow; Hyperplane fixed it in 2019, but code that predates it still assumes the old cost.
  • Downstream throughput. Lambda scales faster than most databases. Without connection pooling (RDS Proxy) or asynchronous fan-in, you crush the DB.
  • Per-region account concurrency limit (default 1,000). Easy to forget until a viral event or a Kinesis backfill lights it up.

Interviewer follow-ups & crisp answers

Why Firecracker instead of gVisor or plain containers?

gVisor intercepts syscalls in user-space — great for compatibility but adds latency and can't match hardware-virtualization security guarantees. Plain containers share the host kernel: one kernel bug and one tenant escapes. Firecracker gives VM-grade isolation with < 5 MiB VMM overhead — enough of both to co-locate untrusted tenants at high density.

How does SnapStart handle randomness?

It doesn't — that's on you. The RNG state is inside the snapshot, so if you cache SecureRandom.getInstanceStrong() in Init and reuse it, every resumed environment starts with identical seed state. Fix: reseed in an afterRestore hook. Same rule for anything unique-per-instance (ephemeral IDs, cached tokens).

Why does the Runtime API use HTTP long-polling instead of gRPC or a socket?

HTTP is language-universal, easy to implement in any runtime (Python, Rust, shell, .NET all speak it), and long-polling gives Lambda a natural point to freeze the process cheaply — a blocked recv() is essentially free. The simplicity is the feature.

If each environment handles one request at a time, how do you get 10,000 concurrent invocations?

Ten thousand environments. Scaling rate is 1,000 new environments every 10 seconds per function; the default per-region account concurrency is 1,000. Above that you burst by requesting a service quota increase or by pre-warming via Provisioned Concurrency.

What actually gets snapshotted?

A Firecracker snapshot captures three things: the guest memory file, the microVM state file (both KVM CPU/register state and Firecracker-emulated device state), and the disk state. On restore, guest memory is MAP_PRIVATE-mapped so each resumed environment lazily copies pages it modifies.

Why not just keep every function warm?

Economics. Lambda's business model depends on thousands of dormant tenants per host. Keeping every function warm would collapse density and force AWS to charge for idle time — which is exactly what Provisioned Concurrency does, and why it costs extra.

🗣️ Interview cheat sheet

30-second pitch: Lambda runs your code in a Firecracker microVM — an AWS-built, Rust-based, KVM-backed hypervisor with less than 5 MiB of overhead per instance. Every invocation runs inside an execution environment that follows an Init → Invoke → Shutdown lifecycle (plus Restore for SnapStart). Each environment handles one request at a time, so concurrency equals the number of live environments. A control-plane Worker Manager + Placement Service assigns new microVMs to a bare-metal worker fleet. The runtime talks to Lambda over a versioned HTTP Runtime API by long-polling for the next event. SnapStart short-circuits slow JVM cold starts by snapshotting a pre-initialized Firecracker microVM at publish time and restoring it on invoke.

Numbers to quote

  • Firecracker overhead: < 5 MiB per microVM, exactly 5 emulated devices
  • Cold-start frequency: < 1% of invocations, duration < 100 ms to > 1 s
  • Init cap: 10 s standard, up to 130 s / 900 s for PC/SnapStart/Managed Instances
  • Shutdown: 0 / 500 / 2,000 ms depending on extensions, then SIGKILL
  • Concurrency: 1,000 per region default, +1,000 environments per 10 s per function
  • Container images: 75% of images < 5% unique bytes → massive block-level dedup at 512 KiB granularity

Five talking points that win the round

  • Two-plane architecture — control plane (Worker Manager, Placement) is off the hot path; data plane (frontend → worker) handles the invoke.
  • Firecracker's design is minimalism — 5 devices, seccomp per thread, Jailer sets up cgroups + namespaces + privilege drop before exec.
  • Lifecycle drives the mental model — Init runs once per env, Invoke runs per request, Shutdown gets a small extension-dependent window; SnapStart adds Restore.
  • One request per environment is the concurrency unit (Managed Instances is the exception). Six simultaneous requests = six environments = six cold starts if none warm.
  • SnapStart trades snapshot uniqueness for speed — you must regenerate any per-instance-unique state in afterRestore, or all clones share the same "unique" value.
