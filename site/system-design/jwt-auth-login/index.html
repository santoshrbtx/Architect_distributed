JWT & the User Login Flow

"Design authentication for a service with 100M users." The classic security-design round — access/refresh tokens, sessions, OAuth, rotation, and revocation.

🎯 The interview question

The prompt an architect-level candidate gets

The ask

"Design the authentication and login system for a web + mobile product with ~100 million users. Walk me through what happens when a user logs in, how we keep them logged in across requests without hammering the database, and how we handle logout, token theft, and 'sign out everywhere.'"

The follow-ups they'll drill into

  • Sessions (stateful) vs JWT (stateless) — which and why?
  • Access token vs refresh token — lifetimes, storage, and rotation.
  • If JWTs are stateless, how do you revoke one before it expires?
  • Where do you store tokens in a browser — cookie vs localStorage — given XSS and CSRF?
  • HS256 vs RS256; where does OAuth2 / OpenID Connect / "Login with Google" fit?

This is one of the most common security-flavored system-design rounds at FAANG and senior/architect interviews because it forces you to reason about the CAP-like tension in auth: stateless scalability versus instant revocation. Every real product solves it — Google, GitHub, Netflix, Auth0, Okta, AWS Cognito — and there is no single "right" answer, only well-justified trade-offs. The interviewer is watching whether you (a) know how a JWT is actually verified, (b) understand the token lifecycle end-to-end, and (c) can defend your choices against attack scenarios.

🧑‍🎓 In laymen terms

The festival wristband that every stall trusts

Imagine you've just arrived at a big three-day music festival. At the front gate they check your ID and your ticket very carefully — passport, name, date of birth, the works. Once they're happy, they snap a wristband on you and wave you in. From then on, every food stall, every stage, every bar just glances at your wristband and lets you through. Nobody at the taco truck calls the ticketing office to ask "is Sarah really allowed in?" — the wristband itself carries a special printed pattern that only the festival could have made, and the stall trusts it on sight.

That is exactly what happens when you log into Gmail or Instagram. The very first step — typing your password — is the front-gate check. It's slow and careful. What you get back is a tiny signed slip of paper (the token) that says "this is Sarah, and she's allowed in." Every time your phone opens a new screen or refreshes your feed, it quietly shows this slip. The app's servers can check the signature in a split second, without ever bothering the password database again. That is why apps feel so instant after you log in.

The clever twist is two wristbands, not one. The short one is like a paper day-pass that expires every fifteen minutes — if a pickpocket steals it, they can only misuse it for a few minutes. The longer one is kept safe in a locked drawer (your phone's secure storage) and its only job is to quietly ask for a fresh day-pass when the old one runs out. That's why WhatsApp keeps you logged in for months but is still safe.

The tricky bit? Once a wristband is on your wrist, the stalls don't call home to check — so if you want to kick someone out early, you have to keep a small blacklist somewhere. That is the whole hard problem, in one sentence.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Register / login with email + password; support social login (OAuth2/OIDC — "Login with Google").
  • Authenticated API calls — every downstream microservice must verify identity cheaply.
  • Stay logged in across requests and app restarts without re-entering the password.
  • Logout, "log out of all devices," and forced revocation on password change / suspected theft.
  • MFA hook and account-lockout on brute force.

Non-functional requirements (the hard part)

  • Low latency & horizontal scale — auth is on the critical path of every request; it cannot be a DB bottleneck.
  • Security — protect against credential theft, token replay, XSS, CSRF, and brute force.
  • Statelessness where possible — services should verify a token without a network hop per request.
  • Fast revocation — a compromised session must die in seconds, not "whenever the token expires."

🏗️ The login & token flow

What actually happens when a user logs in

At login the user posts credentials to the Auth Service, which verifies the password hash, then mints a pair: a short-lived access token (JWT) the client attaches to every API call, and a long-lived refresh token persisted server-side. API requests carry the access token in the Authorization: Bearer header; each microservice (or the API gateway) verifies the signature locally against the auth service's public key — no database, no network hop. When the access token expires, the client silently exchanges the refresh token for a new pair (rotation). Logout deletes the refresh token server-side.

synchronous request path token issue / refresh / revoke
  1. Login: client POSTs email+password to the Auth Service, which verifies the argon2/bcrypt hash in the user store (optionally MFA).
  2. Mint tokens: Auth Service returns a signed access JWT (5–15 min) + a refresh token whose jti is stored server-side (Redis/DynamoDB).
  3. Authenticated calls: client sends Authorization: Bearer <jwt>; the gateway/service verifies the signature with the public key and reads claims — no DB lookup.
  4. Refresh: on 401/expiry, client calls /token/refresh; the Auth Service validates the refresh token in the store, rotates it, and issues a new pair.
  5. Logout / revoke: delete (or mark revoked) the refresh token's jti in the store; "logout everywhere" deletes all of the user's refresh tokens.
  6. Social login: for "Login with Google," the Auth Service runs the OAuth2 Authorization Code + PKCE flow with the IdP, then mints its own tokens.

🔍 Component deep-dive

1. What a JWT actually is

A JWT is three Base64URL segments joined by dots: header.payload.signature. The header names the algorithm (e.g. {"alg":"RS256","typ":"JWT"}). The payload holds claims — registered ones like iss (issuer), sub (subject/user id), aud (audience), exp (expiry), iat (issued-at), jti (token id), plus custom claims like roles/scopes. The signature is computed over base64(header) + "." + base64(payload) with a key. Crucially, the payload is signed, not encrypted — anyone can read it, so never put secrets in a JWT. Verification means recomputing/validating the signature and checking exp/aud/iss; if it passes, the claims are trustworthy without a database.

2. Sessions (stateful) vs JWT (stateless) — the core decision

The classic alternative is a server-side session: on login you store a session record and hand the client an opaque session id cookie; every request looks the session up in Redis. This gives instant revocation (delete the row) but adds a store lookup to every request. A JWT flips it: the token is self-describing so any service verifies it locally — perfect for microservices and horizontal scale — but you lose easy revocation because there's no server record to delete. The mature answer is the hybrid you see everywhere: stateless access JWTs for the hot path + a stateful refresh token store for the revocation lever.

3. Access token vs refresh token

The access token is short-lived (5–15 min), sent on every request, and deliberately not checked against a database — its short TTL is what bounds damage if stolen. The refresh token is long-lived (days–weeks), sent only to the /refresh endpoint, and is tracked server-side so it can be revoked. When the access token expires the client quietly swaps the refresh token for a fresh pair, so the user never notices.

4. Refresh token rotation & reuse detection

Best practice (Auth0/OAuth BCP): every refresh issues a brand-new refresh token and invalidates the old one — rotation. The server tracks a token family. If an already-used refresh token is ever replayed, that means someone stole it, so the server invalidates the entire family, forcing re-authentication. This turns a stolen refresh token from a persistent backdoor into a one-shot that trips an alarm.

5. The revocation problem (the #1 follow-up)

"If JWTs are stateless, how do you log someone out immediately?" You can't un-issue a signed token, so you use one of: (a) short access-token TTL so it self-expires in minutes; (b) a denylist — cache the jti of revoked tokens in Redis until their exp, and have the gateway check it (reintroduces a small stateful lookup, but only for the denylist); or (c) revoke at the refresh layer — kill the refresh token so no new access tokens can be minted, and let the current one die within minutes. Most systems combine (a) + (c), adding (b) only for high-security "kill it now" needs.

6. Where to store tokens in the browser

localStorage is convenient but readable by any JavaScript, so an XSS flaw leaks the token. An httpOnly, Secure, SameSite cookie is invisible to JS (defeats XSS token theft) but is auto-sent by the browser, which opens CSRF — mitigated with SameSite=Strict/Lax plus anti-CSRF tokens. The common architect answer: refresh token in an httpOnly cookie; access token in memory (not persisted), refetched via refresh on reload.

7. HS256 vs RS256, and where OAuth/OIDC fits

HS256 uses one shared secret to sign and verify — fine when the same service does both, but every verifier needs the secret (bad for many microservices). RS256 (asymmetric) signs with a private key and lets anyone verify with the public key — so the Auth Service holds the private key and every microservice verifies independently. That's why real fleets use RS256 (or ES256) and publish keys via a JWKS endpoint. OAuth2 is the delegation framework ("let this app act for me"); OpenID Connect layers identity on top and defines the ID token (itself a JWT). "Login with Google" is OIDC Authorization Code + PKCE: you redirect to Google, get a code, exchange it for tokens, verify Google's ID token, then mint your own.

🧮 The DSA & crypto behind it

Data structures, algorithms & primitives

Auth is less about fancy data structures and more about the right cryptographic primitives — but there are concrete complexity trade-offs an interviewer will probe.

Primitive / structureWhere it's usedCost / property
Password hashing (bcrypt / argon2 / scrypt)Store password hashes; verify at login.Deliberately slow & salted (O(2^cost)) to resist brute force / rainbow tables.
HMAC-SHA256 (HS256)Symmetric JWT signing.O(n) over token bytes; single shared secret.
RSA / ECDSA (RS256 / ES256)Asymmetric JWT signing; verify with public key.Sign O(private-key op); verify cheap & distributable via JWKS.
Base64URLEncode header/payload/signature into a URL-safe string.O(n), reversible, not encryption.
Hash map / KV (Redis, DynamoDB)Refresh-token & session store; jti denylist.O(1) lookup/insert; TTL eviction aligned to exp.
Bloom filter (optional)Fast "is this token maybe revoked?" pre-check before hitting the denylist.O(k) probabilistic; no false negatives — never misses a real revocation.
CSPRNGGenerate opaque refresh tokens, jti, PKCE verifiers, CSRF tokens.High-entropy randomness — unguessable.

Why a denylist + Bloom filter combo is elegant: most tokens are not revoked, so you want the common case to cost nothing. A Bloom filter answers "definitely not revoked" in O(k) with zero I/O; only on a "maybe" do you consult Redis. Because Bloom filters have no false negatives, a revoked token can never slip through — exactly the safety property you want here.

💻 C# implementation

The two things worth showing: minting a signed JWT + refresh token at login, and verifying/refreshing with rotation & reuse detection. This is idiomatic ASP.NET Core with System.IdentityModel.Tokens.Jwt.

Issuing the token pair at login

// On successful password check, mint a short-lived access JWT + a stored refresh token.
using System.IdentityModel.Tokens.Jwt;
using Microsoft.IdentityModel.Tokens;

public class TokenService
{
    private readonly SigningCredentials _creds;  // RS256 private key (from KMS/Secrets)
    private readonly IRefreshStore _store;       // Redis / DynamoDB

    public AuthResult IssueTokens(User user)
    {
        var jti = Guid.NewGuid().ToString("N");
        var claims = new[]
        {
            new Claim("sub", user.Id),           // who the user is
            new Claim("role", user.Role),        // custom claim → authz
            new Claim("jti", jti)
        };

        var access = new JwtSecurityToken(
            issuer:   "https://auth.myapp.com",
            audience: "myapp-api",
            claims:   claims,
            expires:  DateTime.UtcNow.AddMinutes(15),  // SHORT TTL — bounds theft
            signingCredentials: _creds);                // RS256 → verifiers use public key

        // Refresh token is opaque + high-entropy, and its jti is stored server-side.
        var refresh = RandomHelper.SecureToken(32);
        _store.Save(refresh, user.Id, TimeSpan.FromDays(30));  // revocable

        return new AuthResult(
            new JwtSecurityTokenHandler().WriteToken(access), refresh);
    }
}

Refresh with rotation + reuse detection

// Exchange a refresh token for a NEW pair. If a used/unknown token appears,
// treat it as theft and nuke the whole family.
public AuthResult Refresh(string presented)
{
    var record = _store.Get(presented);

    if (record == null || record.Used)          // unknown OR already-rotated
    {
        if (record?.UserId != null)
            _store.RevokeAllForUser(record.UserId); // reuse detected → kill family
        throw new SecurityTokenException("Refresh token reuse detected");
    }

    _store.MarkUsed(presented);               // old token can never be used again
    var user = _users.Get(record.UserId);
    return IssueTokens(user);              // brand-new access + refresh (rotation)
}

builder.Services.AddAuthentication().AddJwtBearer(o =>

Other stacks do the same: jsonwebtoken/Passport in Node, Spring Security in Java, PyJWT/Authlib in Python. The primitives (RS256, JWKS, rotation) are identical across languages.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Statelessness vs revocation — the central tension. Pure JWT scales beautifully but can't be revoked before expiry; pure sessions revoke instantly but add a store lookup to every request. The hybrid (short access JWT + stateful refresh) captures most of both, and you should state it as a deliberate choice, not a default.

Token size & over-stuffing. Every request carries the JWT, so cramming roles/permissions bloats headers and can't be updated until the token expires. Keep claims minimal; fetch volatile authorization data separately if needed.

Clock skew & key rotation. exp checks fail across drifting clocks — allow ~30–60s skew. Rotate signing keys via JWKS with overlapping validity so in-flight tokens still verify during a rollover.

The "alg=none" and algorithm-confusion attacks. Historically, libraries could be tricked into accepting alg:none or verifying an RS256 token with the public key as an HS256 secret. Always pin the expected algorithm server-side and reject anything else.

Q: If JWTs are stateless, how do you log a user out instantly?

You can't un-sign a token, so combine short access-token TTL (self-expires in minutes) with revoking the refresh token (no new access tokens can be minted). For hard "kill now," add a Redis jti denylist checked at the gateway until the token's exp.

Q: Why not just use long-lived access tokens and skip refresh tokens?

A long-lived stateless token that's stolen is valid until it expires with no way to revoke it. Short access + rotating refresh bounds the blast radius and keeps a revocation lever, at the cost of a periodic refresh call.

Q: Cookie or localStorage for the token?

httpOnly+Secure+SameSite cookie for the refresh token (immune to XSS reads, CSRF-mitigated by SameSite), access token in memory. localStorage is simplest but any XSS leaks it.

Q: HS256 or RS256?

RS256 for microservices: the auth service signs with a private key; every service verifies with the public key via JWKS, so the secret never spreads. HS256 only when a single service both signs and verifies.

Q: How does "Login with Google" fit?

OIDC Authorization Code + PKCE: redirect to Google, receive a code, exchange it server-side for Google's ID token, verify it, then mint your own access/refresh tokens so the rest of your system is IdP-agnostic.
