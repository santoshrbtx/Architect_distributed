🎯 Real-world scenario

What we're building & where it's used

A load balancer is the single public endpoint that sits in front of a fleet of servers, accepts every incoming request, and decides which backend gets it. It is the piece that lets an application scale beyond one machine, survive machine failures, deploy new versions safely, and terminate TLS in one place. Every large product you use is behind one: Netflix in front of its edge tier, Amazon in front of its retail API, WhatsApp in front of its chat servers, Uber in front of its dispatcher, GitHub in front of its API, your bank in front of its login page.

The load balancer answers three related questions at once. How do we present one address to millions of clients? Give clients one DNS name resolving to the LB. How do we survive a server crash? Health-check every backend and stop sending it traffic within seconds. How do we scale horizontally? Add another backend, register it with the LB, done. It also solves several bonus problems: TLS termination, WAF integration, cross-zone routing, canary/blue-green rollout, and hiding backend IPs from the world.

This is a classic interview question because it touches almost every distributed-systems concept: consistent hashing, health checks, session state, HA/failover, DNS, CAP trade-offs, and the difference between transport-layer (L4) and application-layer (L7) routing. Whether a candidate can whiteboard "here's how one request reaches one server, and here's what happens when that server dies" is a strong signal for senior-level system-design roles.

🧑‍🎓 In laymen terms

Explain it like I've never written code

Imagine a huge, popular restaurant. There's one entrance, one host at the door — and behind them, thirty identical kitchens ready to cook. Every diner walks up to the same host, and the host quietly points them to a table near whichever kitchen has the shortest queue. Diners never see the kitchens. They never know which one cooked their meal. They just see the door, order their food, and eat.

That host is the load balancer. The kitchens are the servers. The magic isn't in the cooking — it's in the calm, invisible dispatch. Because the host spreads customers evenly, no single kitchen gets slammed while others sit idle. If one kitchen catches fire, the host stops sending anyone that way and diverts them to the others — the restaurant keeps serving without anyone noticing.

Now think about the tricky parts:

How does the host know which kitchen is free? They quietly check every few seconds — "you still cooking? still cooking? still cooking?" — and if a kitchen doesn't respond, they mark it "closed" until it recovers. That's a health check.

What if you're mid-meal at kitchen 7 and order dessert? The host remembers you and sends you back to the same kitchen so your table isn't split up. That's session affinity.

What if the host themselves gets sick? A second host is standing right there, watching, ready to take over the exact moment the first one steps away. That's high availability. Without it, the whole restaurant would grind to a halt every time the host sneezes.

Every big website — Netflix, Amazon, WhatsApp, Uber, Instagram, your bank — is really a restaurant with tens of thousands of kitchens and a small army of hosts at the door working together. You just never notice, because they're doing the whole job in about one millisecond, forever.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Accept incoming connections on one virtual IP / DNS name and forward each to a healthy backend server.
  • Support multiple algorithms for target selection: round-robin, weighted, least-connections, IP-hash / consistent-hash.
  • Run active health checks against each backend and remove failing targets from the pool within seconds.
  • Optionally provide session affinity (sticky sessions) so a client keeps hitting the same backend.
  • Terminate TLS at the edge for L7 mode; pass through TCP/UDP for L4 mode.
  • Emit rich metrics and logs for every request/connection: latency, status, target, health-check state.

Non-functional requirements

  • Very high availability. The LB itself must not be a single point of failure — active/active across zones, DNS failover, floating VIP.
  • Extremely low latency added. Sub-millisecond for L4, single-digit ms for L7.
  • Millions of requests per second and tens of millions of concurrent connections at scale.
  • Graceful drain on backend removal so in-flight requests complete.
  • Observability — every routing decision explainable.

🏗️ High-level architecture

How the pieces fit together

A production load balancer is not one box — it's a tier. DNS resolves the LB name to multiple load-balancer node IPs (one per zone). Each node runs the routing logic: parse the request, look up the target group, select a healthy backend using the configured algorithm, forward the packet or the HTTP request, and record the result. A separate health-check subsystem pings each backend on a schedule and updates the routing table when a target flips healthy/unhealthy. A control plane handles configuration updates, TLS certs, and target registration without dropping in-flight traffic.

🔍 Component deep-dive

L4 vs L7 — the fundamental split

A Layer 4 load balancer operates at the transport layer. It sees TCP/UDP packets, not HTTP requests. It picks a backend using a flow hash — a hash of (src_ip, src_port, dst_ip, dst_port, protocol) — and forwards every packet in that flow to the same target for the connection's lifetime. It doesn't parse anything above TCP. This makes it extremely fast (microseconds of added latency), protocol-agnostic (works for anything over TCP/UDP: TLS, MQTT, gRPC-over-TCP, database protocols), and blind to application semantics.

A Layer 7 load balancer terminates the TCP connection itself, parses the HTTP request, and routes based on content: the URL path, host header, cookies, method, query string. This is what lets you say "requests to /api/v2/* go to the v2 fleet" or "requests with cookie canary=1 go to the canary pods." The trade-off is TLS + HTTP parsing add latency (single-digit ms) and expose it to HTTP-level attacks. Modern L7 LBs (envoy, nginx, HAProxy, ALB) also do TLS termination, WebSocket upgrade, HTTP/2 fan-out, and connection multiplexing.

Health checks

Health checks are the LB's truth signal about the fleet. They come in two forms. Active health checks are probes the LB sends on a schedule — a TCP SYN, a TLS handshake, or an HTTP GET /healthz — and grade each backend. Passive checks watch real traffic and eject a backend that starts returning 5xxs or timing out (outlier detection). A well-tuned LB uses both.

Key parameters: interval (how often we probe — 5–30 s), timeout (how long to wait for a response — a few seconds), unhealthy threshold (consecutive failures before ejection — usually 2 or 3), and healthy threshold (consecutive successes before re-admission). Every parameter is a trade-off between false positives and time-to-detect.

Session affinity (sticky sessions)

Sometimes the backend keeps state per user — a shopping cart, a game session, an SSE stream. The LB then needs to send the same user back to the same server. Two approaches: cookie-based stickiness (the LB injects a cookie like AWSALB=<target-id> and honors it) or IP-hash / source-affinity. Cookies are more precise; IP-hash breaks when many clients share an IP (mobile CGNAT, corporate proxies). Both come at the cost of load imbalance — you're overriding the algorithm's judgment. The best answer is often "make the backend stateless and don't need affinity."

High availability of the LB itself

The load balancer is the front door — if it dies, everything dies. Production LBs achieve HA through redundancy at every layer. Multiple LB nodes run in parallel, one per availability zone; the DNS returns all their IPs so clients naturally shard across them. Inside a single VIP, ECMP (equal-cost multi-path routing) or a floating VIP managed by keepalived/VRRP lets a peer take over an address within milliseconds. Managed services like AWS ELB do this transparently; self-hosted setups (HAProxy + keepalived, nginx + Consul + BGP) reproduce the pattern.

TLS termination and connection lifecycle

Terminating TLS at the LB centralises certificate management (one cert, not one per backend), lets the LB inspect HTTP for routing, and offloads crypto from backends. Some architectures prefer re-encryption (mTLS to backends) for defense in depth. Long-lived connections (WebSocket, gRPC streaming) need connection draining: when a backend is deregistered, the LB stops sending new traffic to it but lets existing streams finish for up to 5 minutes.

🧮 The DSA behind it

Data structures & algorithms

Under the hood, a load balancer is a small stack of very classical CS. Every routing decision must be O(1) or O(log N) — millions per second per node.

  • Round-robin counter — a single atomic integer modulo N. O(1) selection; the "hello world" algorithm.
  • Min-heap on active connections — least-connections uses a heap keyed by connection count, giving O(log N) select and O(log N) increment/decrement on connect/disconnect.
  • Consistent hash ring — nodes and keys hashed onto a 32-bit or 64-bit ring; a request finds "the next node clockwise" via binary search on a sorted array of hash points. O(log N) lookup, and adding/removing a backend disturbs only 1/N of keys. Used everywhere from Cassandra to memcached to Envoy's ring-hash LB.
  • Maglev hashing — Google's improvement: a fixed-size lookup table where every entry maps to a backend and each backend gets a near-equal share. O(1) lookup; small disruption on membership changes; symmetric across nodes so any LB gets the same answer for the same 5-tuple.
  • Rendezvous / HRW hashing — for each request key, compute hash(key, node_i) for every backend, take the max. O(N) but stateless and easy to reason about — used in some CDNs and cache tiers.
  • Bloom filter of drained IDs — to answer "is this connection stuck to an old backend?" with a tiny memory footprint during rolling deployments.
  • Ring buffer of health-check results — per backend, the last K probe outcomes. Sliding window O(1) decides "unhealthy" once ≥ threshold in the buffer are failures.
  • Concurrent hash map — flow table mapping 5-tuple → backend, so every packet of an established TCP flow is routed to the same target without recomputing the hash.

Concretely: for a typical web API, put an ALB in front of an EKS or ECS service with WAF attached; front it with Route 53 alias record; deploy the ALB across at least three AZs. For a stateless TCP service (game server, MQTT broker), use an NLB and preserve source IP so backends see real clients. For a global product, add Global Accelerator so users hit the nearest AWS edge and traverse the AWS backbone the rest of the way. NLB and ALB both auto-scale and hide the load-balancer HA plumbing behind a single DNS name.

💻 C# implementation

Below is a small, correct in-process load balancer core: a target pool with health tracking, three algorithms (round-robin, least-connections, consistent hashing), and a request-scoped lease that decrements the counter on Dispose. This is the exact shape you'd pull into a service mesh sidecar or a custom TCP proxy — swap the "pick a target" strategy and you have a real LB.

// A minimal load-balancer core: healthy target list + pluggable strategy + lease pattern.

public sealed record Target(string Id, string Endpoint, int Weight = 1);

public interface ILoadBalancer
{
    Task<TargetLease?> PickAsync(string? flowKey = null, CancellationToken ct = default);
    void MarkHealthy(string id);
    void MarkUnhealthy(string id);
}

// Lease pattern — release decrements the active-connection counter when the caller Dispose()s.
public sealed class TargetLease : IDisposable
{
    public Target Target { get; }
    private readonly Action _release;
    public TargetLease(Target t, Action release) { Target = t; _release = release; }
    public void Dispose() => _release();
}

// Backend state — atomic conn counter, atomic health flag.
internal sealed class TargetState
{
    public required Target Target { get; init; }
    public int ActiveConnections; // Interlocked
    public volatile bool Healthy = true;
}

// ---------- Round Robin ----------
public sealed class RoundRobinBalancer : ILoadBalancer
{
    private readonly TargetState[] _targets;
    private int _cursor = -1;

    public RoundRobinBalancer(IEnumerable<Target> targets)
        => _targets = targets.Select(t => new TargetState { Target = t }).ToArray();

    public Task<TargetLease?> PickAsync(string? _, CancellationToken __)
    {
        // Try each target at most once, starting after the current cursor.
        for (int i = 0; i < _targets.Length; i++)
        {
            int idx = Math.Abs(Interlocked.Increment(ref _cursor)) % _targets.Length;
            var t = _targets[idx];
            if (!t.Healthy) continue;
            Interlocked.Increment(ref t.ActiveConnections);
            return Task.FromResult<TargetLease?>(new TargetLease(t.Target,
                () => Interlocked.Decrement(ref t.ActiveConnections)));
        }
        return Task.FromResult<TargetLease?>(null); // no healthy targets → caller returns 503
    }

    public void MarkHealthy(string id)   => FindById(id).Healthy = true;
    public void MarkUnhealthy(string id) => FindById(id).Healthy = false;
    private TargetState FindById(string id) => _targets.First(t => t.Target.Id == id);
}

// ---------- Least Connections ----------
public sealed class LeastConnectionsBalancer : ILoadBalancer
{
    private readonly TargetState[] _targets;
    public LeastConnectionsBalancer(IEnumerable<Target> targets)
        => _targets = targets.Select(t => new TargetState { Target = t }).ToArray();

    public Task<TargetLease?> PickAsync(string? _, CancellationToken __)
    {
        TargetState? best = null; int bestScore = int.MaxValue;
        foreach (var t in _targets)
        {
            if (!t.Healthy) continue;
            // Weight-aware: lower "conns / weight" wins.
            int score = t.ActiveConnections / Math.Max(1, t.Target.Weight);
            if (score < bestScore) { best = t; bestScore = score; }
        }
        if (best is null) return Task.FromResult<TargetLease?>(null);
        Interlocked.Increment(ref best.ActiveConnections);
        return Task.FromResult<TargetLease?>(new TargetLease(best.Target,
            () => Interlocked.Decrement(ref best.ActiveConnections)));
    }

    public void MarkHealthy(string id)   => _targets.First(t => t.Target.Id == id).Healthy = true;
    public void MarkUnhealthy(string id) => _targets.First(t => t.Target.Id == id).Healthy = false;
}

// ---------- Consistent Hashing ----------
public sealed class ConsistentHashBalancer : ILoadBalancer
{
    private readonly SortedDictionary<uint, TargetState> _ring = new();
    private readonly Dictionary<string, TargetState> _byId = new();
    private const int Replicas = 150; // virtual nodes for balance

    public ConsistentHashBalancer(IEnumerable<Target> targets)
    {
        foreach (var t in targets)
        {
            var state = new TargetState { Target = t };
            _byId[t.Id] = state;
            for (int i = 0; i < Replicas; i++)
                _ring[Hash($"{t.Id}-{i}")] = state;
        }
    }

    public Task<TargetLease?> PickAsync(string? flowKey, CancellationToken _)
    {
        if (string.IsNullOrEmpty(flowKey) || _ring.Count == 0)
            return Task.FromResult<TargetLease?>(null);

        var h = Hash(flowKey);
        // Walk clockwise from h, wrap around, skip unhealthy.
        foreach (var kv in _ring.Where(k => k.Key >= h).Concat(_ring))
        {
            if (!kv.Value.Healthy) continue;
            Interlocked.Increment(ref kv.Value.ActiveConnections);
            return Task.FromResult<TargetLease?>(new TargetLease(kv.Value.Target,
                () => Interlocked.Decrement(ref kv.Value.ActiveConnections)));
        }
        return Task.FromResult<TargetLease?>(null);
    }

    public void MarkHealthy(string id)   => _byId[id].Healthy = true;
    public void MarkUnhealthy(string id) => _byId[id].Healthy = false;

    private static uint Hash(string s)
    {
        using var md5 = System.Security.Cryptography.MD5.Create();
        var b = md5.ComputeHash(System.Text.Encoding.UTF8.GetBytes(s));
        return BitConverter.ToUInt32(b, 0);
    }
}

// A background health-check loop. Real LBs use adaptive intervals and jitter.
public sealed class HealthChecker
{
    private readonly ILoadBalancer _lb;
    private readonly HttpClient _http;
    private readonly Target[] _targets;
    private readonly Dictionary<string, int> _fails = new();
    private const int Threshold = 3;

    public HealthChecker(ILoadBalancer lb, HttpClient http, Target[] targets)
    { _lb = lb; _http = http; _targets = targets; }

    public async Task RunAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await Task.WhenAll(_targets.Select(ProbeAsync));
            await Task.Delay(TimeSpan.FromSeconds(10), ct);
        }
    }

    private async Task ProbeAsync(Target t)
    {
        try
        {
            using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
            var res = await _http.GetAsync($"{t.Endpoint}/healthz", cts.Token);
            if (res.IsSuccessStatusCode) { _fails[t.Id] = 0; _lb.MarkHealthy(t.Id); }
            else RecordFail(t);
        }
        catch { RecordFail(t); }
    }

    private void RecordFail(Target t)
    {
        _fails.TryGetValue(t.Id, out var f);
        _fails[t.Id] = ++f;
        if (f >= Threshold) _lb.MarkUnhealthy(t.Id);
    }
}

In production, you'd use a real hash (SHA-1, xxHash, MurmurHash3), replace the SortedDictionary with a sorted array + binary search for O(log N) with better cache behavior, and add outlier detection to fold passive signal (5xx rates, latency) into ejection decisions. The bones above are what tools like YARP (Microsoft's reverse proxy), Envoy, and HAProxy implement — just faster and in C++/Rust.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Where a load balancer hurts

It's still a bottleneck. Every packet flows through it, so its throughput ceiling is your ceiling. Solution: run many LB nodes and let DNS or ECMP fan out across them. AWS ELB does this transparently; self-hosted needs BGP or Anycast to scale beyond one box.

L7 costs latency. Parsing HTTP and terminating TLS adds ~1–5 ms. If you don't need content-based routing, use L4 and preserve simplicity + speed.

Sticky sessions kill load balance. Once a user is stuck to a warm backend, the algorithm can't rebalance them. Preferred fix: externalize session state (Redis, DynamoDB) and make backends stateless.

Rebalancing is disruptive without consistent hashing. A modulo-N hash sends 100% of traffic to different backends when N changes. Consistent hashing (or Maglev) limits disturbance to 1/N — mandatory for cache tiers.

Health checks lie. A backend can pass /healthz while its downstream DB is broken. Add deep health checks that exercise dependencies, and use passive outlier detection on real traffic to catch what active probes miss.

Thundering herd on backend restart. When a large backend comes back healthy, least-connections routes a burst to it. Mitigate with slow start — the ALB supports this natively — where a new target ramps up over 30–900 s.

Likely interview follow-ups

When would you pick NLB over ALB?

Sub-millisecond latency, non-HTTP protocols (MQTT, gRPC over raw TCP, gaming UDP), static IPs, or you need to expose the service through PrivateLink. Otherwise ALB, because content-based routing and Lambda targets are worth the extra ms.

Why consistent hashing for caches specifically?

Cache hit rate depends on the same key going to the same node. With plain modulo, adding one node invalidates ~(N-1)/N of the cache. Consistent hashing invalidates only ~1/N, keeping hit rates high through fleet changes.

How does the LB avoid being a single point of failure?

Redundant nodes across AZs, DNS with multiple A records, and a floating VIP (VRRP/keepalived) or ECMP so a peer takes the address within milliseconds. Managed LBs (ELB) handle all of this behind one DNS name.

What happens to in-flight requests when you deregister a target?

Connection draining — the LB stops sending new work but lets existing streams finish for up to a configurable timeout (30 s to 5 min). Only then is the target actually torn down.

How do you handle sticky sessions without breaking scale?

Best answer: don't. Push session state to Redis or a signed cookie, keep backends stateless. If you must, use LB-generated cookies (not IP-hash) so you're immune to NAT and can drain cleanly.

Round-robin vs least-connections vs power-of-two — when do they diverge?

Uniform request cost → round-robin is fine. Highly variable request cost (WebSockets, long-poll, mixed API) → least-connections wins. Massive fleets where global state is expensive → power-of-two-choices gives near-least-connections quality with no shared state.

Global Accelerator vs Route 53 latency routing — what's the difference?

Route 53 answers DNS with the closest regional LB's name. Global Accelerator gives you a fixed anycast IP and moves traffic onto the AWS backbone at the nearest edge, reducing internet-path variance. Use Accelerator when clients don't cache DNS well or you need instant regional failover.

🗣️ Interview cheat sheet

The 30-second pitch: "A load balancer is the single-endpoint dispatcher in front of a horizontal fleet. Clients hit one DNS name; the LB picks a healthy backend using an algorithm — round-robin for uniform workloads, least-connections for variable ones, consistent hashing for cache affinity — and forwards the request. It runs continuous health checks to eject failed backends, terminates TLS, supports sticky sessions when needed, and is itself made HA by running redundant nodes across AZs with DNS or floating VIPs. On AWS: ALB for HTTP with content routing, NLB for extreme L4 throughput, GWLB for appliance insertion, Route 53 in front for regional failover."

  • Numbers to quote: NLB ~100 µs added latency, ALB single-digit ms; millions of RPS per LB; ~1M concurrent conns per node; health checks 5–30 s interval, 2–3 fails to eject; drain 30–300 s.
  • Five talking points that win the round:
    1. L4 vs L7: transport-layer flow hashing vs application-layer content routing — pick by latency vs feature need.
    2. Algorithms: RR, weighted RR, least-connections, consistent hash, power-of-two — name them and know which fits which shape of load.
    3. Health checks + connection draining: how a failed node is ejected fast and a deregistered node dies gracefully.
    4. The LB's own HA: multi-AZ nodes, DNS spread, VIP failover — the front door must not be a SPOF.
    5. AWS mapping: ALB / NLB / GWLB / Global Accelerator / Route 53 — which for which job.
  • Words to say: "flow hash", "5-tuple", "consistent hashing ring", "connection draining", "slow start", "outlier detection", "sticky sessions via LB cookie".
  • Trade-offs to volunteer: sticky sessions vs balance; L7 features vs latency; naive modulo vs consistent hash; active vs passive health checks.
