🎯 Real-world scenario

What we're building & where it's used

Multi-tenancy is the discipline of running one software system that serves many independent customers — called tenants — from shared infrastructure while keeping each tenant's data, load, and failures walled off from the others. A tenant is an organization, not a user; a company with 500 employees is one tenant with 500 users. It is the defining architectural pattern of SaaS: without it there is no SaaS, there is only a hosting business that manually clones one stack per customer.

Every product you use for work is multi-tenant. Slack, Salesforce, GitHub, Notion, Stripe, Datadog, Zoom, HubSpot, Shopify — each is one running system serving millions of orgs. Companies build multi-tenant systems because the economics are transformational: a shared stack costs a fraction of a dedicated one, ships features to everyone at once, and lets a two-engineer team run a business with a million customers. The catch is that if you get isolation wrong even once, one customer sees another customer's data — a business-ending event. So multi-tenancy is really a conversation about how much you share and how you enforce the boundaries when you share.

The interview question is almost never "design multi-tenancy" in the abstract. It's usually embedded in a bigger question — "you're building a SaaS analytics platform, walk me through your tenancy model" — and the interviewer is watching whether you reach for the industry taxonomies (silo/pool/bridge, database-per-tenant vs sharded), name the tradeoffs, and handle the follow-ups on noisy neighbours, cost attribution, and blast radius.

🧑‍🎓 In laymen terms

The plain-English version

Imagine you rent apartments for a living. You have a building with many families living in it. All of them share the front door, the elevator, the plumbing, and the roof — but each family has their own locked apartment with their own key. That's multi-tenancy. One building, many families, and no family ever wanders into another family's kitchen.

Now think about a company like Slack. Your company uses Slack. So does the company across the street, and 10 million other companies. Slack didn't build 10 million separate copies of Slack. They built one Slack — one building — and gave each company a "locked apartment" inside it. When you open Slack, some invisible check figures out which company you belong to and only shows you your company's messages. If that check ever failed, you'd see someone else's private messages. That would be the end of Slack. So the check has to be perfect.

The hard parts are what happen when families share things. If one family throws a huge party, does everyone else lose water pressure? If one family calls the elevator constantly, does everyone wait? If the roof leaks, does every family get wet? Real software has the same problems. If one customer runs a giant report at 3am, other customers shouldn't feel it. If one customer's data corrupts, others shouldn't be affected. If one customer gets hacked, others shouldn't spill.

Some customers pay a lot more money. For them, you might build a private house instead of an apartment — dedicated everything. It costs more, but they get all the water pressure to themselves and nobody can hear their music. Big banks and hospitals often get the private house. Small startups happily share the building.

A tiny example: your two-person startup and IBM both use Slack. Your startup lives in a "shared apartment" — cheap, fine. IBM might live in a dedicated wing with its own elevator. Slack's job is to make both of you feel like you're the only tenant on the planet, even though you're technically breathing the same air.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Tenant onboarding — create a new tenant in seconds; provision users, initial config, quotas.
  • Data isolation — a user of tenant A must never read or write data of tenant B, at any layer.
  • Tenant context on every request — every request carries a verifiable tenant_id; every query is scoped to it.
  • Per-tenant quotas / rate limits — noisy tenants must not degrade quiet tenants.
  • Tier-based isolation — free / pro / enterprise get different isolation levels.
  • Cost attribution — cost per tenant is knowable (for pricing, capacity planning, churn analysis).
  • Tenant lifecycle — offboarding (delete all data, GDPR), tier migration (pool → silo), export.

Non-functional requirements

  • Isolation guarantee: zero cross-tenant reads/writes — treated as a P0 breach.
  • Blast radius: one failing tenant / one failing cell must not take down the fleet.
  • P99 fairness: enterprise tenants see stable P99 even during flash-sale-scale spikes from other tenants.
  • Elasticity: onboarding a tenant is O(seconds), not O(days).

🏗️ High-level architecture

How the pieces fit together

The classic multi-tenant SaaS architecture is a shared control plane (identity, onboarding, billing, observability) sitting in front of a tenant-aware data plane whose isolation level varies by pricing tier. On every request the flow is: client → edge (TLS, WAF) → identity (validate JWT, extract tenant_id) → API gateway (per-tenant rate limit, tier lookup) → services (execute business logic scoped to tenant_id) → data (either the shared pool table with row/item-level policies, or the dedicated silo database for enterprise tenants). Async traffic — notifications, exports, ETL — flows through queues that carry the tenant tag so downstream workers can preserve isolation.

The load-bearing decision is which components pool and which silo. Microsoft's Azure Architecture Center calls isolation a continuum, not a binary — you can pool the UI/app tier while siloing the data tier, or the other way around, depending on what actually causes noisy-neighbour pain. In practice, the app tier is almost always pooled (compute is cheap and stateless), while the data tier is where the isolation model lives.

Pool data plane (shared) Silo data plane (dedicated) Cell / control plane Async plane

The three canonical isolation models

🏰 Silo

Dedicated resources per tenant. No noisy neighbours, trivial cost attribution, simple to enforce. But hits account/quota ceilings and costs ~linearly. Best for enterprise / regulated tenants.

🌉 Bridge

Mix per microservice. Regulatory + noisy-neighbour sensitivity pushes a service to silo; agility + cost pushes to pool. Most real SaaS ends up here.

🏢 Pool

Shared everything, keyed by tenant_id. Cheapest, most agile, hardest to isolate. Requires fine-grained IAM / row-level security. Best for free/pro tiers.

🔍 Component deep-dive

1. Tenant identification & routing

Every request must carry a verifiable tenant identity. The industry-standard pattern (from AWS's serverless SaaS reference) is: the identity provider — Amazon Cognito, Auth0, Okta — authenticates the user and issues a JWT with tenant_id and tier as custom claims. Downstream services trust the JWT signature and read the claims from a shared library (a Lambda Layer in AWS-speak). This means the tenant context is attached to the request itself — you never trust a client-supplied header, and you never make a network call to look up who the user's tenant is. Every service downstream — API gateway, business services, workers, background jobs — receives the tenant context and scopes every operation to it.

2. Tenant isolation is not authentication

This is the single most-repeated point in the AWS SaaS Lens, and the point interviewers use to separate strong candidates from weak ones. An authenticated, authorized user can still cross tenant boundaries if you rely on authorization alone. AuthN answers "who are you"; AuthZ answers "what can you do"; isolation answers "which tenant's slice of the world can you touch". You need a separate mechanism — application-layer scoping, row-level security, dynamically minted IAM policies — that binds every resource operation to the request's tenant context. A breach of this boundary is treated as a P0 event: business-ending.

3. Data isolation strategies

Data isolation runs on a spectrum. From most-shared to most-isolated:

  • Shared table + tenant_id column — cheapest. Every query filters by tenant. Bug in one query = cross-tenant leak. Postgres Row-Level Security (RLS) policies push the guard into the database so even a raw query can't escape the tenant. DynamoDB uses dynamodb:LeadingKeys IAM conditions to achieve the same at the storage engine.
  • Shared DB + schema-per-tenant — Postgres schemas, MySQL databases. Cleaner separation, still one DB engine, migrations run N times.
  • Database-per-tenant (in elastic pool) — Azure SQL and RDS both support this. Isolation is at the storage engine, cost sharing is at the pool. Scales to 100 000+ databases per Azure SQL instance.
  • Silo — dedicated DB cluster — enterprise tier. Own VPC, own KMS key, own IAM boundary. Trivial isolation, expensive.

4. Sharding — the real production pattern

Notion runs Postgres in the pooled model but hit the limits of one machine. Their solution — the pattern most large SaaS reach — is application-level sharding on workspace_id (their tenant key) into 480 logical shards across 32 physical databases, colocating all block data for a workspace on one shard to preserve transactional consistency within a tenant while avoiding cross-shard joins. This is the sweet spot between pool and silo: shared engine, but tenant data is physically grouped.

5. Noisy-neighbour mitigation

The whole reason silo exists is to eliminate noisy neighbours. In pool mode you fight it with three tools:

  • Per-tenant token buckets — Stripe's rate limiter runs 4 layers: per-user request rate, per-user concurrent-requests, fleet-wide load shedder, and a burst limiter. Keyed by tenant.
  • Shuffle sharding — assign each tenant a random subset of workers so any two tenants overlap on ≤ 1 worker. A tenant that saturates its subset only affects a tiny fraction of others. AWS's canonical technique from the Builders' Library.
  • Cell-based architecture — divide the fleet into fixed-size cells (say ~2 K tenants each). A cell's failure is confined to its tenants. Slack moved to this after a June 2021 AZ outage; each us-east-1 AZ is now a cell.

6. Blast radius & cellular design

The largest architectural upgrade a maturing SaaS makes is cellular. Instead of one global fleet where a bad deploy breaks everyone, you deploy N identical cells, each serving a bounded set of tenants. Roll out to one cell first, watch it, then the rest. A poison pill from tenant Q blows up cell 3 only; cells 1, 2, 4…N are fine.

7. Cost attribution

Silo makes cost trivial — infrastructure tags per tenant → billing report. Pool makes it hard — you have to instrument every request with the tenant tag and aggregate telemetry back. AWS's Split Cost Allocation Data and per-tenant CloudWatch dimensions are the standard tools; underneath, you're just tagging every metric and log line with tenant_id.

8. Onboarding & tier migration

Onboarding in pool mode is a row in the tenants table — milliseconds. Onboarding a silo tenant is a Terraform / control-plane workflow that spins up a dedicated stack — minutes. The hardest operation is tier migration, e.g. pool → silo when a Standard tenant upgrades to Enterprise. You provision the silo stack, run a background copy of the tenant's data, dual-write for a window, then cut reads over and stop the pool writes. No downtime, no lost writes — this is what shipped-in-production SaaS teams get paid to do right.

Interview-critical: the two data structures interviewers probe most are the tenant → shard router (consistent hashing or range map) and the per-tenant rate limiter (token bucket). Be able to whiteboard both in 90 seconds.

Shuffle sharding — the one clever bit

AWS's foundational multi-tenant idea. If you have W workers and give each tenant S of them at random, then two tenants overlap on all S workers with probability C(S, S) / C(W, S). For W = 8, S = 2 → 1/28. For W = 100, S = 4 → 1/3.9 M. A single bad tenant can only take out its S workers, and every other tenant still has W − S good ones. It's isolation without dedicated hardware — the math does the walling off.

AWS reference flow, in one paragraph

Client hits API Gateway. A Lambda authorizer verifies the Cognito-issued JWT, pulls tenant_id and tier out of custom claims, and generates a short-lived STS credential scoped by a dynamically constructed IAM policy that uses dynamodb:LeadingKeys = tenant_id. That credential is handed to the Lambda business logic, which reads from a shared DynamoDB table where the partition key is the tenant id. If the same JWT had a tier=Platinum claim, the authorizer would route to a dedicated Lambda + DynamoDB + Cognito pool that lives in a tenant-specific VPC and is invisible to pool tenants. Async writes fan out through EventBridge with the tenant tag; downstream workers scope everything to that tag.

💻 C# implementation

Three of the most-asked reference snippets: (1) middleware that extracts the tenant from a JWT and puts it in the request context, (2) per-tenant token-bucket rate limiter backed by Redis, and (3) tenant-scoped repository using EF Core global query filters. Together they cover the request→service→DB path.

1. Tenant context middleware — extract from JWT, fail-closed

// ASP.NET Core middleware. Runs on every request. Extracts tenant_id + tier
// from a verified JWT and stashes it in a scoped ITenantContext. Downstream
// code is REQUIRED to use ITenantContext — never a client header.

public sealed class TenantContext : ITenantContext
{
    public string TenantId { get; init; } = "";
    public string Tier     { get; init; } = "pool";   // pool | silo
}

public sealed class TenantContextMiddleware
{
    private readonly RequestDelegate _next;
    public TenantContextMiddleware(RequestDelegate next) => _next = next;

    public async Task Invoke(HttpContext ctx, ITenantContextAccessor acc)
    {
        // The JWT is already validated by [Authorize] earlier in the pipeline.
        // We just pull the trusted claims. If any are missing, 401 — fail closed.
        var user = ctx.User;
        var tenant = user.FindFirst("tenant_id")?.Value;
        var tier   = user.FindFirst("tier")?.Value ?? "pool";

        if (string.IsNullOrEmpty(tenant))
        {
            ctx.Response.StatusCode = StatusCodes.Status401Unauthorized;
            await ctx.Response.WriteAsync("missing tenant claim");
            return;
        }

        acc.Current = new TenantContext { TenantId = tenant, Tier = tier };

        // Tag every log line for this request so observability aggregates by tenant.
        using (LogContext.PushProperty("tenant_id", tenant))
        using (LogContext.PushProperty("tier", tier))
        {
            await _next(ctx);
        }
    }
}

2. Per-tenant token-bucket rate limiter (Redis-backed)

// Atomic Lua script: refill bucket at rate r, take 1 token, return 0 if empty.
// Runs in Redis under one RTT — safe under contention across service replicas.

public sealed class TenantRateLimiter
{
    private const string LUA = @"
        local key      = KEYS[1]
        local rate     = tonumber(ARGV[1])       -- tokens/sec
        local capacity = tonumber(ARGV[2])
        local now      = tonumber(ARGV[3])       -- ms

        local b   = redis.call('HMGET', key, 'tok', 'ts')
        local tok = tonumber(b[1]) or capacity
        local ts  = tonumber(b[2]) or now

        local delta = math.max(0, now - ts)
        tok = math.min(capacity, tok + (delta * rate / 1000.0))

        local allowed = 0
        if tok >= 1 then tok = tok - 1; allowed = 1 end

        redis.call('HMSET', key, 'tok', tok, 'ts', now)
        redis.call('PEXPIRE', key, 60000)
        return allowed
    ";

    private readonly IDatabase _redis;
    public TenantRateLimiter(IConnectionMultiplexer mux) => _redis = mux.GetDatabase();

    public async Task<bool> TryAcquireAsync(string tenantId, int ratePerSec, int capacity)
    {
        var key = $"rl:{tenantId}";
        var now = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
        var res = (int)(long)await _redis.ScriptEvaluateAsync(
            LUA, new[] { (RedisKey)key },
            new RedisValue[] { ratePerSec, capacity, now });
        return res == 1;
    }
}

3. EF Core global query filter — tenant-scoped repository

// Every entity carries a TenantId. The global query filter appends
// `WHERE TenantId = @current` to EVERY query — so a forgotten filter
// in a repo can't leak. Belt AND suspenders: DB-side RLS on top for depth.

public class AppDb : DbContext
{
    private readonly ITenantContextAccessor _tenant;
    public AppDb(DbContextOptions<AppDb> o, ITenantContextAccessor t) : base(o)
        => _tenant = t;

    public DbSet<Invoice> Invoices => Set<Invoice>();

    protected override void OnModelCreating(ModelBuilder mb)
    {
        mb.Entity<Invoice>().HasQueryFilter(i => i.TenantId == _tenant.Current!.TenantId);
    }

    // Also stamp TenantId on inserts — never trust the caller.
    public override Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        var tid = _tenant.Current!.TenantId;
        foreach (var e in ChangeTracker.Entries<Invoice>())
            if (e.State == EntityState.Added) e.Entity.TenantId = tid;
        return base.SaveChangesAsync(ct);
    }
}

Note on "belt and suspenders": the EF query filter is application-side. It's convenient but a bad LINQ query using IgnoreQueryFilters() can bypass it. In production, pair it with a database-side guarantee — Postgres RLS or DynamoDB LeadingKeys. Two independent walls. Interviewers love this answer.

Other-language notes

Same shapes in other stacks: Spring / Java — Hibernate @FilterDef + @Filter; Django — a tenant-scoped model manager; Node / Prisma — a middleware that injects where: { tenantId } before every query. Redis Lua for the rate limiter is language-agnostic and is what Stripe, GitHub, and Cloudflare all publicly describe.

⚖️ Trade-offs, bottlenecks & likely follow-ups

The one tradeoff that rules them all

Isolation strength vs economies of scale. Every other decision — noisy neighbours, cost attribution, blast radius, onboarding cost — falls out of this. Silo maximises isolation and sacrifices scale economics; pool maximises economics and sacrifices isolation guarantees; bridge picks per microservice.

Common bottlenecks

  • Hot tenant — one tenant is 50× the traffic of the median. In pool mode they'll saturate whatever shard they're on. Cure: shuffle-shard them, or graduate them to silo.
  • Pool DB write hotspot — pool tables with tenant_id as the leading key are fine for reads but a hot tenant creates a hot partition. Cure: composite key (tenant_id + hash-suffix) or move to database-per-tenant.
  • Silo account limits — AWS has quota ceilings on VPCs, IAM roles, RDS instances per account. Hit them at ~1 K silo tenants. Cure: multi-account (AWS Organizations), one account per ~500 silo tenants.
  • Cross-tenant analytics — the CFO wants "total signups this quarter across all tenants". Pool table is easy; silo means fanning out queries to N tenant DBs. Cure: ETL every tenant into a shared analytics warehouse (with tenant tag), never query silos live for cross-tenant analytics.

Failure modes to name unprompted

  • Leak via a forgotten WHERE tenant_id = ? — the classic P0. Answer: RLS at the DB, plus code-review checklist, plus contract tests.
  • Bad deploy blows up all tenants at once — cellular deploy + canary cell.
  • Poison message from tenant Q clogs the queue for everyone — per-tenant DLQ, tenant-aware retry policy.
  • Enterprise tenant's silo DB is slow → looks like the whole product is slow to their execs — silo P99 SLO is per-tenant, not fleet-wide.

Likely interviewer follow-ups (with 30-second answers)

"What if a pool tenant grows so big they need to become a silo tenant — how do you migrate them without downtime?"

Provision the silo stack. Snapshot + streaming replicate the tenant's data into it. Enter a dual-write window where writes go to both. Cut reads over to silo, verify parity. Stop writes to pool, delete pool data. Feature-flag the whole thing so you can roll back at any step.

"How do you rate-limit tenants fairly when quiet tenants can't predict what noisy ones will do?"

Per-tenant token buckets sized to their tier, plus a fleet-wide load shedder that kicks in when aggregate load threatens SLO. Weighted fair queueing between tiers. That's Stripe's public model.

"How do you enforce isolation if a bug in your ORM lets a query drop the tenant filter?"

Never rely on the ORM alone. Two independent walls: application-side (query filter / repository middleware) and database-side (Postgres RLS or DynamoDB LeadingKeys). A single bug breaks one wall, not both.

"How do you know what each tenant costs?"

Silo: tag every resource with tenant_id, use AWS Cost Allocation Tags and Split Cost Allocation Data. Pool: instrument requests with a cost proxy (DB rows read, S3 bytes stored, Lambda ms) tagged per tenant, roll up nightly. It's an approximation, but it's defensible.

"What's your blast-radius story?"

Cellular. Fixed-size cells, deployable independently, tenants pinned to cells. A blast is confined to one cell of ~2 K tenants — that's how Slack survives AZ failures.

🗣️ Interview cheat sheet

30-second pitch: "Multi-tenancy is a spectrum from silo (dedicated per tenant) to pool (shared with tenant_id keys), with bridge as the practical mix. Tenant isolation is separate from authN/authZ — the JWT carries tenant_id + tier as custom claims, every service scopes to it, and I use two independent walls: application-side query filters plus a database-side guarantee like Postgres RLS or DynamoDB LeadingKeys. Small tenants share a pooled Aurora + DynamoDB, enterprise tenants get siloed stacks. I contain blast radius with cellular deploys, contain noisy neighbours with per-tenant token buckets and shuffle sharding, and attribute cost via CloudWatch tenant dimensions."
