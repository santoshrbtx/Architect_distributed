Transactional Outbox Pattern

How to update your database and publish an event atomically — the go-to answer when a FAANG interviewer asks "how do you avoid the dual-write problem?"

🎯 Real-world scenario

What we're building & where it's used

Almost every event-driven system at scale eventually hits the same wall. A service handles a command — say "place order" — and it must do two things: (1) write the new order row to its own database, and (2) publish an OrderPlaced event to a message broker (Kafka, SQS, RabbitMQ) so that downstream services — payments, inventory, notifications, analytics — can react. The interviewer's trap is this: these are two separate systems, and there is no shared transaction across them. If you commit the DB row and then crash before publishing, the rest of the company never learns the order exists. If you publish first and the DB rollback fires, you've told everyone about an order that doesn't exist. This is the famous dual-write problem, and the transactional outbox pattern is the canonical, battle-tested answer.

The core idea is deceptively simple: don't write to two systems — write to one. Inside the same local database transaction that saves your business data, you also insert a row into an outbox table describing the event you want to publish. Because it's one transaction, it's all-or-nothing: the order and its "please publish this" record commit together or roll back together. A separate background process — the message relay — later reads the outbox and forwards those events to the broker, retrying until they land.

This pattern is everywhere in production: it's a first-class feature of Debezium (Red Hat's CDC platform), it underpins how companies like Uber, Netflix, Airbnb, Shopify, and DoorDash keep their microservices consistent, and it's the recommended alternative to distributed transactions in Chris Richardson's Microservices Patterns and Sam Newman's books. If you can whiteboard it and defend the trade-offs, you've demonstrated the single most important reliability pattern in event-driven architecture.

🧑‍🎓 In laymen terms

The waiter's notepad trick

Picture a busy restaurant. You order a paneer tikka. The waiter has to do two things: (1) update the bill on your table, and (2) run to the kitchen and tell the chef. Both have to happen — no bill without a dish, no dish without a bill. But what if the waiter writes the bill, then trips on the way to the kitchen and forgets? You get charged, no food arrives. What if he tells the chef first, then his pen runs out and he never writes the bill? You eat free.

Now here's the clever trick real restaurants actually use. The waiter carries one notepad. On a single page, he writes both: "Table 7: paneer tikka, ₹280" AND "Kitchen: make one paneer tikka." He tears the page — one single action — and drops it in a box. Then a separate helper comes along, picks up the paper, and walks the "make one paneer tikka" half to the kitchen. If the waiter trips, the whole page is either torn or not torn — never half. Either both things happen or neither does.

That's the outbox pattern, and it's how big websites keep their promises. Say you pay for a train ticket on IRCTC. The website has to: (1) mark your seat as booked in the database, and (2) tell the SMS system to text you the PNR. If it tries to do both separately, one might fail — you'd get a seat with no confirmation SMS, or an SMS with no seat. Disaster.

So instead, in one single write, the website scribbles both the booking AND a little sticky note that says "please send an SMS to +91-98…" into the same table. Then a background helper program quietly walks over, picks up the sticky note, and hands it to the SMS system — retrying until the SMS actually sends. If the whole website crashes right after you paid, the sticky note is still safely there, waiting to be delivered when things come back up.

The catch: the SMS might arrive a few seconds late, and if the helper is clumsy it might send the same SMS twice — so the receiving side has to be smart enough to ignore duplicates. But you'll never get "money taken, no seat, no message." That's the whole point.

📋 Requirements & scale

Requirements and back-of-the-envelope math

This is a pattern, not a product, so "requirements" means the reliability properties you must guarantee. The interviewer wants to hear you name them precisely, because each one drives a design decision.

Functional requirements

  • An event is published if and only if the business transaction commits (no phantom events, no lost events).
  • Downstream consumers eventually receive every event — eventual consistency across service boundaries.
  • Events for the same aggregate/entity are delivered in commit order.

Non-functional requirements

  • Durability — a crash of the service, relay, or broker must never drop an event.
  • At-least-once delivery — we accept possible duplicates and make consumers idempotent, rather than paying for true exactly-once.
  • Low added latency — publishing should trail the commit by milliseconds, not minutes.
  • No 2PC — we must not require distributed transactions between DB and broker.

Back-of-the-envelope: does the outbox table become a bottleneck?

Suppose an e-commerce service does 5,000 writes/sec at peak, each producing one event. That's 5,000 extra INSERTs/sec into the outbox — trivial for Postgres/MySQL, which comfortably handle tens of thousands of small inserts per second, especially since they piggyback on an existing transaction (no extra round-trip). The numbers interviewers expect you to reason about:

The only real operational concern is housekeeping: at 5k writes/sec the table would grow ~430M rows/day, so I purge published rows or use a log-only outbox."

🏗️ High-level architecture

How the pieces fit together

The flow has two independent halves connected only through the database. On the write path (solid arrows), the service opens one local transaction, writes the business row and the outbox row, and commits — atomically. On the relay path (dashed arrows), a separate process observes the outbox (by polling it or by tailing the DB's transaction log) and publishes each event to the broker, marking it done only after the broker acknowledges. Consumers read from the broker and apply idempotency to tolerate the duplicates that at-least-once delivery inevitably produces.

write path (one local TX) async relay path (at-least-once) outbox table
  1. Client calls the service (POST /order).
  2. Service opens one local DB transaction and writes both the orders row and an outbox row, then COMMIT. Atomic — no partial state possible.
  3. The message relay observes the new outbox row (polling query, or transaction-log tailing via CDC).
  4. Relay publishes the event to the broker and waits for the broker's ack.
  5. On ack, the relay marks the outbox row published (or deletes it). If it crashed before this step, it republishes on restart → at-least-once.
  6. Consumers read from the broker and deduplicate using the event ID / log offset before applying side effects.

🔍 Component deep-dive

1. The outbox table schema

The outbox is an ordinary table in the same database as your business data — that co-location is the whole point, because it's what makes the shared transaction possible. A typical schema:

CREATE TABLE outbox (
  id             UUID PRIMARY KEY,      -- event id (dedup key for consumers)
  aggregate_type VARCHAR,            -- e.g. 'Order' → routes to a topic
  aggregate_id   VARCHAR,            -- e.g. order id → Kafka partition key (ordering!)
  event_type     VARCHAR,            -- e.g. 'OrderPlaced'
  payload        JSONB,              -- the serialized event
  created_at     TIMESTAMPTZ DEFAULT now(),
  published_at   TIMESTAMPTZ          -- NULL = not yet relayed (polling mode)
);

The aggregate_id is doing double duty: consumers need it, and the relay uses it as the broker partition key so that all events for one order land on the same partition and stay ordered.

2. The message relay — polling vs. log tailing (the key decision)

This is where interviewers push hardest, because it's the real engineering trade-off. There are two ways to get events out of the outbox:

(a) Polling Publisher. A background job runs SELECT * FROM outbox WHERE published_at IS NULL ORDER BY created_at LIMIT N on a timer, publishes each row, then marks it published. Simple, works on any database, easy to reason about. The downsides: it adds constant query load, forces a latency-vs-load trade-off via the poll interval, and — subtly — ordering can be wrong. Because a row is written when a transaction starts its insert but only becomes visible when it commits, two concurrent transactions can commit in a different order than their created_at/sequence suggests, so a naive poller can even skip a row that committed late. You mitigate with SELECT ... FOR UPDATE SKIP LOCKED for safe concurrent workers and careful ordering logic.

(b) Transaction Log Tailing (CDC) — usually preferred. Instead of querying the table, a tool like Debezium reads the database's write-ahead log (Postgres WAL, MySQL binlog). Every committed insert to the outbox appears in the log in exact commit order, so ordering is correct by construction, there's no polling load, and latency drops to two-digit milliseconds. This is what most large-scale deployments use. The cost is operational complexity — you now run and monitor a CDC connector and (often) Kafka Connect.

Interview power move: "I'd start with a polling relay for simplicity, but at scale I'd move to log-based CDC with Debezium — it gives correct ordering for free from the commit log and cuts latency to tens of milliseconds without loading the database."

3. Delivery semantics & idempotent consumers

The relay gives at-least-once delivery: if it publishes to the broker and then crashes before recording success, it will republish on restart. (Brokers deliver at-least-once anyway, so this is rarely a new burden.) Therefore consumers must be idempotent. Two standard techniques:

  • Dedup journal (UUID): the consumer stores the IDs of processed events and drops anything it's seen. Simple, but you must decide how long to retain IDs (too short → miss a late duplicate; too long → the journal bloats).
  • Monotonic watermark (better): store only the highest offset/LSN seen and reject anything ≤ it. Use the transaction-log offset (Postgres LSN, Kafka offset) — not a database sequence, which isn't reliably monotonic across concurrent transactions.

4. Housekeeping

At high write rates the outbox grows fast, so you must prune it: delete rows on successful publish, run a periodic cleanup, or partition by day and drop old partitions. A neat CDC trick: INSERT then DELETE the outbox row in the same transaction — CDC still captures the insert from the log, but the table stays empty. Postgres goes further with pg_logical_emit_message(), writing the event straight to the WAL with no table at all ("log-only outbox").

Data structures & algorithms

The outbox pattern isn't algorithm-heavy, but a strong candidate names the data structures that make it correct and the abstractions each component is really an instance of.

The deepest insight to state out loud: the outbox turns a distributed-transaction problem into a single-node log-ordering problem. Ordering and durability come "for free" from the database's own transaction log — the same mechanism that already guarantees ACID — rather than from an expensive cross-system coordinator like two-phase commit.

☁️ AWS implementation

Mapping the design to AWS

On AWS the pattern maps cleanly, and the relay choice mirrors the polling-vs-CDC decision above. The managed sweet spot is Aurora/RDS → DynamoDB isn't needed → DMS or Lambda relay → SNS/SQS/Kinesis/MSK.

NoSQL variantDynamoDB + DynamoDB StreamsThe "outbox" is the item's change itself; Streams is a built-in log-tailing relay — very popular AWS answer

HousekeepingTTL on DynamoDB / partitioned RDS purge jobAuto-expire relayed rows

The most idiomatic serverless AWS expression of this pattern skips a separate outbox table entirely: write to DynamoDB, enable DynamoDB Streams, and attach a Lambda that forwards each change to EventBridge/SNS. The stream is your ordered, durable, log-tailed outbox — atomicity is guaranteed because the stream record and the item write are the same operation. For SQL shops, Aurora + DMS (or Debezium on MSK Connect) → MSK/Kinesis is the direct analog of the classic Postgres-WAL-to-Kafka design.

💻 C# implementation

The heart of the pattern is one method: save the entity and the outbox record in a single EF Core SaveChanges (one transaction). Then a separate polling relay drains the outbox. This is the correct, idiomatic .NET version.

// ---------- 1. The outbox row ----------
public class OutboxMessage {
    public Guid     Id           { get; set; } = Guid.NewGuid(); // dedup key
    public string   AggregateId  { get; set; } = "";   // partition key → ordering
    public string   EventType    { get; set; } = "";
    public string   Payload      { get; set; } = "";   // serialized JSON
    public DateTime CreatedAt    { get; set; } = DateTime.UtcNow;
    public DateTime? PublishedAt  { get; set; }        // null = pending
}

// ---------- 2. Write path: business row + event in ONE transaction ----------
public async Task PlaceOrderAsync(Order order) {
    _db.Orders.Add(order);

    // Same DbContext → same SaveChanges → same transaction. Atomic!
    _db.Outbox.Add(new OutboxMessage {
        AggregateId = order.Id.ToString(),
        EventType   = "OrderPlaced",
        Payload     = JsonSerializer.Serialize(new { order.Id, order.Total })
    });

    await _db.SaveChangesAsync(); // commit both, or neither — no dual write
}

// ---------- 3. Polling relay: drain the outbox, publish, mark done ----------
public async Task RelayLoopAsync(CancellationToken ct) {
    while (!ct.IsCancellationRequested) {
        // FOR UPDATE SKIP LOCKED lets many relay workers run safely in parallel.
        var batch = await _db.Outbox
            .FromSqlRaw(@"SELECT * FROM outbox WHERE published_at IS NULL
                          ORDER BY created_at
                          LIMIT 100 FOR UPDATE SKIP LOCKED")
            .ToListAsync(ct);

        foreach (var msg in batch) {
            // Event Id is the idempotency key — consumers dedup on it.
            await _broker.PublishAsync(msg.EventType, msg.AggregateId, msg.Payload, msg.Id, ct);
            msg.PublishedAt = DateTime.UtcNow; // crash before this ⇒ republish (at-least-once)
        }
        await _db.SaveChangesAsync(ct);
        if (batch.Count == 0) await Task.Delay(200, ct); // backoff when idle
    }
}

// ---------- 4. Idempotent consumer: watermark / dedup on event Id ----------
public async Task HandleAsync(Guid eventId, string payload) {
    if (await _seen.ExistsAsync(eventId)) return; // already processed → drop duplicate
    // ... apply side effect ...
    await _seen.RecordAsync(eventId);                // mark processed (same TX as side effect)
}

The one bug interviewers look for: publishing inside a different transaction, or publishing before SaveChanges. The whole pattern collapses unless the business write and the outbox write share one commit. In .NET that means: same DbContext, one SaveChangesAsync.

Alternatives worth a sentence: instead of hand-rolling the relay, production teams use Debezium (log-based CDC) or a library like MassTransit, whose built-in Transactional Outbox does exactly this within its message-consumer pipeline.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Why not just use two-phase commit (2PC)? Because the broker often can't participate in an XA transaction (Kafka, SQS don't), 2PC couples the service to the availability of both systems, blocks on the coordinator, and scales poorly. The outbox deliberately trades strong cross-system atomicity for local atomicity plus eventual consistency — the right trade for microservices.

Why accept at-least-once instead of exactly-once? True exactly-once across a DB and a broker requires distributed coordination that's expensive and fragile. At-least-once + idempotent consumers gets you effectively-once results at a fraction of the cost, and brokers already force you to handle duplicates.

Bottlenecks & failure modes

  • Outbox table bloat — the #1 operational issue. Solve with purge-on-publish, partition-drop, or a log-only outbox.
  • Polling load & latency — polling adds DB load and floor latency; CDC removes both but adds infra.
  • Ordering under concurrency — commit order ≠ insert/sequence order; rely on the log (LSN) or a per-aggregate partition key, not created_at.
  • Relay is a moving part — it must be HA; use leader election or SKIP LOCKED so multiple relays don't double-publish or stall.
  • Developer discipline — someone can forget to write the outbox row. Enforce via a repository/UoW abstraction or domain-event dispatch so it's automatic.

Q: How do you guarantee ordering of events?

A: Use the transaction log (WAL/binlog) which is in commit order, and key the broker partition by aggregate_id so all events for one entity stay on one ordered partition. Don't trust a DB sequence or timestamp — they aren't monotonic across concurrent commits.

Q: What if the relay publishes but crashes before marking the row published?

A: On restart it republishes — that's the at-least-once guarantee. Consumers dedup on the event id / offset watermark, so the duplicate is harmless.

Q: Polling vs CDC — which and why?

A: Polling for simplicity and any-DB portability; CDC (Debezium/DynamoDB Streams) for correct ordering from the log, no polling load, and ~10–99 ms latency. I default to CDC at scale.

Q: How is this different from event sourcing?

A: Event sourcing makes the event log the source of truth and rebuilds state from it. The outbox keeps current-state tables as truth and merely uses a table/log to reliably publish events. The outbox is a smaller, additive change; event sourcing is a whole storage philosophy.

Q: How does this relate to the Saga pattern?

A: Sagas coordinate a multi-service business transaction through a chain of local transactions + events. The outbox is how each saga step reliably emits its event/command — sagas are a primary reason the outbox exists.

🗣️ Interview cheat sheet

30-second pitch: "To update my database and publish an event atomically without 2PC, I use the transactional outbox. In the same local transaction that writes the business row, I insert a row into an outbox table. A separate relay — polling, or better, log-based CDC like Debezium — reads the outbox and publishes to the broker with at-least-once delivery, and consumers dedup on the event id. This solves the dual-write problem: the event is published if and only if the transaction commits."
  • Name the enemy: "dual-write problem" — two systems, no shared transaction.
  • One transaction: business row + outbox row commit together or not at all.
  • Relay = polling vs CDC: CDC (WAL/binlog, Debezium, DynamoDB Streams) wins at scale — correct ordering, ~ms latency, no polling load.
  • Delivery = at-least-once + idempotent consumers: dedup by UUID journal or monotonic offset/LSN watermark.
  • Ordering: from the commit log + partition-by-aggregate-id — not from timestamps or DB sequences.
  • Don't forget housekeeping: purge/partition the outbox, or go log-only (pg_logical_emit_message).
  • Numbers to quote: one small INSERT per txn (negligible), CDC latency two-digit ms, table grows ~430M rows/day at 5k writes/s if unpruned.
