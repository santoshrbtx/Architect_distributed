🎯 Real-world scenario

What we're building & where it's used

The design problem: build a distributed version-control system that lets thousands of developers snapshot a directory tree over time, work offline, branch and merge cheaply, and later synchronize their histories with no central authority — while never silently corrupting a byte. That system is Git, and its internals are one of the cleanest real-world examples of a content-addressable store layered into an immutable DAG with a peer-to-peer sync protocol on top.

Git powers essentially all modern software: it's the storage engine behind GitHub, GitLab, and Bitbucket, and it was written by Linus Torvalds in 2005 to manage the Linux kernel after the project lost access to BitKeeper. The design goals were speed, strong integrity guarantees against corruption, and true distributed workflows — any clone is a complete, self-sufficient repository, not a thin checkout.

Why it's a great interview topic: under the friendly porcelain commands (add, commit, push) sits a beautifully small set of primitives. If you can explain how a commit is just a hash of a tree, how a branch is just a 41-byte file, and how push is a want/have negotiation that ships a custom packfile, you're demonstrating content addressing, Merkle DAGs, immutability, and distributed reconciliation — all at once.

🧑‍🎓 In laymen terms

A magical notebook that never loses a page

Imagine you're writing a big novel with your friends. Everyone edits the same chapters, everyone worries about accidentally deleting someone else's work, and everyone would love a big red "undo" button that goes back not just one step, but back to any moment in the past — last Tuesday's version, or the version from before Priya rewrote chapter 4. That's the everyday problem this tool solves for the people who write software (and increasingly, anyone who writes anything at all together).

Think of it like a magical notebook that never loses a page. Every time you tell it "save," it doesn't just save the pages you changed — it silently takes a photograph of the entire novel as it looks right now, staples the photo together, and writes a unique fingerprint on the back like "commit #a3f9." Then it drops that stapled photo into a big box in the corner. The box already has hundreds of earlier photos in it, each one a complete snapshot of the whole novel at some earlier moment. Want to see what the novel looked like on Monday morning? Just pull out that photo. Want to compare two photos and see what changed? Easy — flip them side by side.

The real magic is two more things. First, the photo album is copied in full onto every friend's desk — so if the office burns down, everybody's copy is the whole history, not a fragment. Second, when you and Priya both edit chapter 4 at the same time, the notebook is smart enough to stitch the two versions together, and only asks a human for help on the tiny bit where you both changed the exact same sentence. This is the invisible engine behind GitHub, which is where nearly every piece of software you use — from your banking app to your video game — actually lives.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Snapshot the full state of a directory tree at a point in time (a commit), cheaply and repeatedly.
  • Branch & merge — create divergent lines of history and reconcile them; branching must be O(1).
  • History & diff — walk backwards through parent pointers; compute diffs between any two snapshots.
  • Distributed sync — clone, fetch, and push between repositories with no shared central state.
  • Integrity — detect any corruption or tampering of stored content.

Non-functional requirements (the ones that shape the design)

  • Integrity by construction — the identity of every object is a hash of its content, so corruption is self-evident.
  • Deduplication — identical content stored once, no matter how many commits or files reference it.
  • Offline-first — every operation except sync works against the local object database.
  • Space efficiency — near-identical file versions must not each cost a full copy.
  • Minimal transfer — sync sends only the objects the other side is missing.

🏗️ High-level architecture

How the pieces fit together

Git is two layers. The object database (.git/objects) is a content-addressable key-value store: give it content, it returns the SHA-1 key; give it the key, it returns the content. On top sits the reference layer (.git/refs + HEAD) — tiny mutable pointers that give human names to specific commits. Everything a user does is either (a) adding immutable objects to the store, or (b) moving a mutable pointer.

There are exactly four object types, and they form a Merkle DAG (a directed acyclic graph where every node names its children by their hashes): a blob is file content; a tree is a directory listing that maps names → blob/tree hashes with file modes; a commit points to one top-level tree plus zero-or-more parent commits and carries author/message metadata; and a tag object annotates a commit. Because each node embeds its children's hashes, the commit hash transitively fixes the entire tree state — change one byte in one file and every hash up the chain changes. That's the integrity guarantee.

Refs (mutable pointers) Commit Tree Blob parent edge

What happens on git commit

  1. git add writes a blob for each changed file into the object DB and records it in the index (staging area, .git/index).
  2. On commit, Git builds tree objects from the index — one per directory — snapshotting the whole hierarchy (write-tree).
  3. Git writes a commit object pointing to the top tree, to the current HEAD commit as parent, plus author/committer/message (commit-tree).
  4. Git updates the current branch ref (e.g. refs/heads/main) to the new commit SHA. HEAD symbolically points at that branch, so "you" move forward automatically.

🔍 Component deep-dive

Content addressing: the hash IS the identity

To store content, Git builds a byte string "<type> <size>\0<content>" — e.g. blob 16\0what is up, doc? — and takes the SHA-1 over that whole string. That 40-hex-char digest is the object's key. Crucially the hash is computed on the uncompressed bytes; only afterwards does Git zlib-compress the object for storage. Identical content therefore always yields the identical key, which gives automatic deduplication (the same file in 1,000 commits is stored once) and tamper-evidence (flip a bit on disk and the recomputed hash no longer matches the filename).

The object store on disk

Objects live under .git/objects/. The key is split: the first 2 hex chars name a subdirectory and the remaining 38 name the file — so d670460b… is stored at .git/objects/d6/70460b…. This 2-char sharding keeps any one directory from holding millions of files (a classic filesystem performance killer). You can poke at the raw store with plumbing commands: git hash-object -w writes an object and returns its key; git cat-file -p <sha> pretty-prints it; git cat-file -t shows its type.

References: branches, HEAD, and tags

A branch is literally a file under .git/refs/heads/ containing a commit SHA — git branch x is just update-ref writing that file. HEAD is a symbolic ref (ref: refs/heads/main) telling Git which branch you're on; a "detached HEAD" is when it holds a raw SHA instead. Lightweight tags are refs that never move; annotated tags point to a real tag object carrying a tagger, date, and message. Remote-tracking refs (refs/remotes/origin/main) are read-only bookmarks of what the server had at last contact. The reflog (.git/logs) records every movement of every ref locally — your safety net for recovering "lost" commits after a bad reset or rebase.

Packfiles & delta compression

Storing every file version as a full zlib blob is wasteful when versions are near-identical. So Git periodically (on git gc, on push, or when loose objects pile up) rolls many objects into a single packfile (.pack) with a companion index (.idx) that maps each SHA to a byte offset. Inside the pack, similar objects are delta-compressed: Git stores one version in full and the others as deltas against it, and deltas can chain. A clever twist: it stores the newest version intact and older versions as deltas, since you most often read recent data. This is why .git stays remarkably small even for huge histories.

The distributed sync protocol (push / fetch / clone)

Because no repo is authoritative, syncing two repos means reconciling two object graphs. Git's smart protocol does it in three moves. (1) Ref advertisement: the server lists all its refs with their SHAs and its capabilities. (2) want/have negotiation: the client sends want <sha> for tips it lacks and have <sha> for commits it already owns, so the two sides discover their common ancestor. (3) Packfile transfer: the server computes exactly the objects reachable from the wants but not the haves, packs them on the fly, and streams them. Push is the mirror image (send-pack ↔ receive-pack), with all-zero SHAs signaling ref creation or deletion. This content-addressed, negotiate-the-difference design is precisely what makes Git distributed rather than client-server.

🧮 The DSA behind it

Data structures & algorithms

Git is a small pile of famous data structures used exactly right. The object store is a content-addressable hash map. The history is a Merkle DAG — the same structure behind blockchains and IPFS — giving cryptographic integrity and cheap structural sharing. History traversal (git log, merge-base) is graph search over that DAG. Merges compute a lowest common ancestor. Storage uses delta encoding; sync uses set reconciliation via reachability.

💻 C# implementation

The heart of Git is tiny: hash content with the "<type> <size>\0" header, zlib-compress it, and store it under a 2-char-sharded path. Below is a faithful, idiomatic C# rebuild of hash-object -w and cat-file, plus a commit-object writer — enough to demonstrate the content-addressable store end to end.

using System.IO.Compression;
using System.Security.Cryptography;
using System.Text;

// A minimal Git-style content-addressable object database.
public sealed class ObjectStore
{
    private readonly string _objectsDir;   // e.g. ".git/objects"
    public ObjectStore(string objectsDir) => _objectsDir = objectsDir;

    // hash-object -w : store content, return its 40-char SHA-1 key.
    public string Write(string type, byte[] content)
    {
        // 1. Build the store bytes: "<type> <size>\0<content>"
        var header = Encoding.ASCII.GetBytes($"{type} {content.Length}\0");
        var store  = new byte[header.Length + content.Length];
        Buffer.BlockCopy(header, 0, store, 0, header.Length);
        Buffer.BlockCopy(content, 0, store, header.Length, content.Length);

        // 2. The KEY is SHA-1 of the UNCOMPRESSED store bytes.
        var hash = Convert.ToHexString(SHA1.HashData(store)).ToLowerInvariant();

        // 3. Store path is sharded: objects/<first 2>/<remaining 38>
        var dir  = Path.Combine(_objectsDir, hash[..2]);
        var path = Path.Combine(dir, hash[2..]);
        Directory.CreateDirectory(dir);

        // 4. zlib-DEFLATE the store bytes to disk (idempotent: same content => same file).
        if (!File.Exists(path))
        {
            using var fs   = File.Create(path);
            using var zlib = new ZLibStream(fs, CompressionLevel.Optimal);
            zlib.Write(store, 0, store.Length);
        }
        return hash;
    }

    // cat-file : inflate the object and split off the header.
    public (string Type, byte[] Content) Read(string hash)
    {
        var path = Path.Combine(_objectsDir, hash[..2], hash[2..]);
        using var fs   = File.OpenRead(path);
        using var zlib = new ZLibStream(fs, CompressionMode.Decompress);
        using var ms   = new MemoryStream();
        zlib.CopyTo(ms);
        var bytes = ms.ToArray();

        int nul   = Array.IndexOf(bytes, (byte)0);          // find the \0 separator
        var hdr   = Encoding.ASCII.GetString(bytes, 0, nul);   // "blob 16"
        var type  = hdr.Split(' ')[0];
        var body  = bytes[(nul + 1)..];
        return (type, body);
    }

    // Write a commit object pointing at a tree + parent (the DAG edge).
    public string CommitTree(string treeSha, string? parentSha, string author, string message)
    {
        var sb = new StringBuilder();
        sb.Append($"tree {treeSha}\n");
        if (parentSha is not null) sb.Append($"parent {parentSha}\n");
        sb.Append($"author {author}\n");
        sb.Append($"committer {author}\n\n");
        sb.Append(message).Append('\n');
        return Write("commit", Encoding.UTF8.GetBytes(sb.ToString()));
    }
}

This reproduces Git's exact hash for the same input — echo -n "what is up, doc?" | git hash-object --stdin and Write("blob", …) both yield bd9dbf5aae1a3862dd1526723246b20206e5fc37. Real Git adds packfiles, the index, delta compression, and the transfer protocol on top, but the content-addressable core is exactly this. Note Git is migrating from SHA-1 to SHA-256 for collision resistance — swap SHA1 for SHA256 and the model is unchanged.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Snapshots vs deltas. Git conceptually stores full snapshots (each commit names a complete tree) — unlike older VCSs (SVN, CVS) that store per-file diffs. This makes branching, merging, and history-walking simple and fast, at the cost of apparent redundancy — which packfiles + delta compression then claw back on disk. Interviewers love this: "isn't storing a full tree per commit wasteful?" Answer: no, because unchanged blobs/trees are shared by hash (the DAG dedups), and packfiles delta-compress the rest.

SHA-1 and collisions. Git used SHA-1, which is cryptographically broken (SHAttered, 2017). In practice Git added collision-detection and is migrating to SHA-256, but the design assumption "hash uniquely identifies content" is the load-bearing one — be ready to discuss it.

Large binaries & huge histories. Delta compression works great on text, poorly on large binaries; every clone gets the entire history. Mitigations: Git LFS (store big files out-of-band, keep a pointer in the repo), shallow clones (--depth), and partial/sparse clones. This is the #1 scaling pain for monorepos.

Mutable refs are the only race. Objects are immutable so they never conflict; the only concurrency hazard is two people updating the same branch. Servers resolve this with a compare-and-swap on the ref — the losing push is rejected as a non-fast-forward, and the user must fetch+rebase/merge. That's the whole story behind "! [rejected] (fetch first)".

Q: Does Git store diffs or full snapshots?

Conceptually full snapshots — each commit points to a complete tree. Unchanged files are shared by hash (dedup), and packfiles delta-compress similar blobs on disk. So it's snapshots logically, deltas physically.

Q: Why is creating a branch so cheap?

A branch is just a 41-byte file containing a commit SHA. Creating one writes that file; no objects are copied. That's why repos can carry thousands of branches.

Q: How does push send only the new commits and not the whole repo?

The want/have negotiation: the server advertises its refs, the client says which SHAs it wants and which it already has; the server packs only objects reachable from the wants but not the haves.

Q: What actually guarantees integrity?

Content addressing plus the Merkle DAG. Every object's name is the hash of its bytes, and every parent embeds its children's hashes — so the commit hash fixes the entire tree. Any corruption changes a hash and is detected by git fsck.

🗣️ Interview cheat sheet

30-second pitch: "Git is a content-addressable object store under an immutable Merkle DAG, with a peer-to-peer sync protocol on top. Content is hashed with a type size\0 header into a SHA-1 key, zlib-compressed, and stored sharded under .git/objects. Four object types — blob, tree, commit, tag — form a DAG where each node names its children by hash, so a commit hash fixes the whole tree and integrity is automatic. Refs (branches, HEAD, tags) are tiny mutable pointers into that graph; a branch is a 41-byte file. Packfiles delta-compress similar objects on disk, and push/fetch is a want/have negotiation that ships a custom packfile of exactly the missing objects — which is what makes Git distributed."

  • 4 object types: blob, tree, commit, tag.
  • Branch = 41-byte file (40 hex + newline).
