Distributed File System

Storing exabytes across thousands of failing machines — how GFS, HDFS, Colossus & Ceph split metadata from data to hit high throughput and durability.

🎯 Real-world scenario

What we're building & where it's used

A distributed file system (DFS) presents a single logical namespace of files and directories that is physically spread across thousands of commodity machines. To the application it looks like one giant disk; underneath, every file is chopped into large blocks, replicated or erasure-coded across many servers, and served in parallel. This is the storage substrate that big-data and cloud platforms are built on.

The canonical family: Google File System (GFS, 2003) — the paper that started it all, built to store the web crawl and index for Search. HDFS — the open-source clone at the heart of Hadoop, powering analytics at nearly every large enterprise. Colossus — Google's GFS successor (2010) that removed the single-master bottleneck and now underpins Search, YouTube, Drive, Gmail, and all of Google Cloud (Cloud Storage, BigQuery, Filestore). Ceph — the open-source unified store (object + block + file) used by OpenStack clouds and on-prem fleets. And the cloud managed services: Amazon S3 (object), EFS / FSx (file), and Azure Data Lake Storage.

Companies build these because a single machine — no matter how big — cannot hold petabytes, cannot serve millions of concurrent readers, and will fail. The DFS turns a fleet of cheap, unreliable disks into one reliable, high-throughput, effectively-infinite volume. As the Colossus team puts it: "at Google scale, hardware is failing virtually all the time — not because it's unreliable, but because there's a lot of it." The DFS's whole job is to make that failure invisible.

🧑‍🎓 In laymen terms

A movie studio's giant film archive spread across three warehouses

Old movies were kept on long spools of film in metal cans. If a studio made hundreds of films every year, one warehouse couldn't hold them all — and a single fire could wipe out a century of cinema in one afternoon. So the big studios came up with a smart plan. First, they'd take each long film and cut it into shorter reels that fit into standard-sized cans. Then, for every single can, they'd make three identical copies and store them in three different warehouses across the country. Finally, they kept a master index at the head office — a big book that says "Reel 4 of Casablanca is in Warehouse A shelf 12, Warehouse B shelf 5, and Warehouse D shelf 88."

Now imagine you want to watch a movie. The studio doesn't hand you the whole thing from one warehouse — that would be slow. Instead, the head office tells five delivery trucks to pick up different reels from different warehouses at the same time, and you get the whole film almost instantly because everyone was pulling in parallel. If Warehouse B burns down tomorrow, no problem — the head office sees the gap, and quietly asks a fourth warehouse to make new copies from A and D. You never even notice.

That's exactly the trick behind the storage powering Dropbox, Google Drive, YouTube, and Netflix. Your holiday photo isn't sitting on one hard drive somewhere; it's chopped into small pieces, copied to three different buildings, and any two of them can still give you back the photo perfectly. So even though the hard drives break every single day — thousands of them — you never lose a single picture of your dog.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Create / open / read / write / delete files within a hierarchical namespace (directories).
  • Store very large files (GB → TB) and stream them efficiently.
  • Append (and in GFS, atomic concurrent record append) — the dominant write pattern for logs and datasets.
  • Return the locations of a file's data so clients can read directly from the machines that hold it.

Non-functional requirements (the ones that shape the design)

  • Durability — survive disk, machine, and rack failures with essentially zero data loss (target ~11 nines for S3-class systems).
  • High throughput over low latency — optimized for large sequential scans, "even at the cost of latency" (GFS). Batch/analytics, not interactive random I/O.
  • Availability — no single point of failure in the data path; fast automatic recovery.
  • Horizontal scalability — add machines to add capacity and bandwidth linearly.
  • Consistency — a defined, well-understood model (not necessarily strict POSIX).

🏗️ High-level architecture

How the pieces fit together

The single most important idea in the whole design: separate the control plane (metadata) from the data plane (bytes). A client first asks the metadata service "which machines hold the blocks of this file?" — a small, cheap lookup. It then streams the actual data directly to and from the storage nodes, never routing bulk bytes through the metadata server. This keeps the metadata node off the hot path, so read/write bandwidth scales with the number of storage nodes rather than being throttled by one coordinator.

In GFS/HDFS terms: the Master / NameNode owns the namespace and the block→location map; the Chunkservers / DataNodes store the blocks and talk to clients directly. Storage nodes send periodic heartbeats (every 3s in HDFS) carrying block reports; if the master misses heartbeats for ~2 minutes it declares the node dead and re-replicates its blocks elsewhere. Writes are chained through a replication pipeline so a block flows node→node→node and is only acknowledged once all replicas have it.

Control plane (metadata) Data plane (bytes, direct) Replication pipeline Heartbeat / block report

The read path, step by step

  1. Client asks the metadata service for the block handles and replica locations of /data/logs.txt at a given offset.
  2. Metadata service returns the block IDs and the set of storage nodes holding each replica (sorted by network proximity).
  3. Client connects to the nearest replica and streams bytes directly — the metadata node is now out of the loop.
  4. Client caches the block→location map briefly so subsequent reads skip the metadata round-trip.

The write (append) path

  1. Client asks the metadata service to allocate a new block; it picks replica nodes (rack-aware) and grants one replica a lease making it the primary.
  2. Client pushes the data to all replicas in a pipeline (A→B→C), decoupled from control flow to use full network bandwidth.
  3. Client sends the write request to the primary; the primary assigns a serial order and forwards it to secondaries.
  4. Once all replicas acknowledge, the primary acks the client. Any failure ⇒ client retries; the write is atomic only when all replicas succeed.

🔍 Component deep-dive

Why blocks are huge (64–128 MB)

A giant block size is a deliberate, load-bearing decision. First, it slashes metadata volume: at ~150 bytes of metadata per block, using 128 MB blocks instead of 4 KB OS pages reduces the number of metadata entries by ~30,000×, letting a single master's RAM hold the map for petabytes. Second, it amortizes disk seeks — for a workload of large sequential scans, one seek then a long streaming read is near-optimal disk behavior. Third, it lets a client hold a persistent TCP connection to a chunkserver and do many operations against the same block. The cost: small files waste space and create hot blocks — DFSs are explicitly not built for millions of tiny files.

The metadata bottleneck and how Colossus fixed it

GFS used a single master holding all metadata in memory, with an operation log + periodic checkpoints for durability. This is beautifully simple and keeps metadata operations fast and strongly consistent — but it caps the cluster at whatever one machine's RAM and CPU can serve, and it's a recovery bottleneck. Google hit this wall (notably storing Search metadata). Colossus replaced the single master with a horizontally scalable metadata service: Curators handle control operations and store the file-system metadata in BigTable (itself built on Colossus — a neat bootstrap). This "allowed Colossus to scale up by over 100× over the largest GFS clusters." HDFS took a different route to the same problem: HDFS Federation (multiple independent NameNodes, each owning a slice of the namespace) plus NameNode HA (an active/standby pair sharing an edit log via a quorum journal, with automatic failover).

Replication, rack-awareness, and re-replication

The default is 3 replicas. Placement is rack-aware: HDFS puts two replicas on one rack and a third on a different rack. This balances two forces — keeping two copies close is cheap for the write pipeline's bandwidth, while the off-rack copy survives a whole-rack failure (a failed top-of-rack switch or PDU). When a node dies (missed heartbeats), the master notices its blocks are under-replicated and schedules re-replication from surviving copies to restore the factor of 3 — this background healing is what delivers durability despite constant hardware failure.

Erasure coding for cold data

3× replication costs 200% overhead. For colder data, systems switch to Reed-Solomon erasure coding: split data into k blocks, compute m parity blocks, and store all k+m. A common choice is RS(10,4) (used in Facebook's HDFS): 10 data + 4 parity survives any 4 simultaneous failures at only 1.4× overhead — versus needing 5× replication for the same fault tolerance. The trade-off is reconstruction cost: rebuilding one lost block requires reading k other blocks and doing math, which burns CPU and cross-node network. That's why EC is used for cold/archival data while hot data stays replicated for cheap reads and fast recovery.

Ceph & CRUSH — placement with no lookup table at all

Ceph takes a radically different tack on the metadata bottleneck for data placement: it stores no central block→location map at all. Instead, the CRUSH algorithm (Controlled, scalable, decentralized placement) computes which OSDs (storage daemons) hold an object from the object's ID and a cluster map. Any client can calculate the location independently — zero lookups, no directory to become a chokepoint. Ceph's Monitors maintain the authoritative cluster map; its MDS serves only POSIX filesystem names/inodes for CephFS (not data placement); and everything sits on RADOS, the underlying object store that also exposes S3-compatible object and RBD block interfaces.

Consistency model

These systems deliberately relax POSIX. GFS guarantees that a successful record append is written at least once atomically, but concurrent writes to overlapping regions can leave "consistent but undefined" data — the client is expected to tolerate duplicates and use checksums/record boundaries. HDFS is simpler: write-once, read-many with append; a file has a single writer and readers see data only after a block is fully written/closed. The lesson for interviews: the file-system semantics are co-designed with the workload — append-mostly, large-scan analytics — rather than trying to be a general POSIX disk.

🧮 The DSA behind it

Data structures & algorithms

A DFS is a surprisingly rich bag of data structures. The namespace is a tree (or a flat hash map of full-path → inode, as GFS actually uses to avoid per-directory locking). The block map is a hash table from block-ID → replica set. Durability of metadata comes from a write-ahead log (edit log) plus periodic checkpoints (fsimage) — the same pattern databases use. Data integrity relies on checksums (CRC32C) stored per block sub-chunk so silent disk corruption ("bit rot") is caught on read. And the heart of durability math is Reed-Solomon coding over a Galois field.

💻 C# implementation

The two ideas most worth coding for an interview are (1) the metadata service that maps a file to its blocks and their replica locations, and (2) the durability math of Reed-Solomon-style erasure coding. Here is a compact, idiomatic sketch of a NameNode-style metadata service plus the rack-aware placement and a simple XOR parity (RAID-4 style, the intuition behind Reed-Solomon).

// ---- Metadata service: the control plane (NameNode / Master / Curator) ----
public sealed record BlockId(long Value);

public sealed class BlockInfo
{
    public BlockId Id { get; init; }
    // replica locations, ordered by network proximity to the writer
    public IReadOnlyList<string> Replicas { get; init; } = Array.Empty<string>();
}

public sealed class MetadataService
{
    private const long BlockSizeBytes = 128L * 1024 * 1024;   // 128 MB (HDFS default)
    private const int  ReplicationFactor = 3;

    // path -> ordered list of blocks that make up the file
    private readonly Dictionary<string, List<BlockId>> _fileToBlocks = new();
    // blockId -> where its replicas live
    private readonly Dictionary<BlockId, BlockInfo> _blocks = new();
    private readonly object _lock = new();
    private long _nextBlockId = 1;

    private readonly IPlacementPolicy _placement;
    public MetadataService(IPlacementPolicy placement) => _placement = placement;

    // WRITE control-op: allocate a new block and pick rack-aware replicas.
    public BlockInfo AllocateBlock(string path)
    {
        lock (_lock)
        {
            var id = new BlockId(_nextBlockId++);
            var replicas = _placement.ChooseReplicas(ReplicationFactor);  // e.g. 2 same-rack + 1 off-rack
            var info = new BlockInfo { Id = id, Replicas = replicas };
            _blocks[id] = info;
            (_fileToBlocks.TryGetValue(path, out var list)
                ? list : _fileToBlocks[path] = new()).Add(id);
            return info;   // client now streams bytes DIRECTLY to these nodes
        }
    }

    // READ control-op: return block layout so the client reads direct from storage nodes.
    public IReadOnlyList<BlockInfo> GetBlockLocations(string path)
    {
        lock (_lock)
        {
            if (!_fileToBlocks.TryGetValue(path, out var ids))
                throw new FileNotFoundException(path);
            return ids.Select(id => _blocks[id]).ToList();
        }
    }

    // Heartbeat handler: a dead node's blocks become under-replicated -> schedule repair.
    public IEnumerable<BlockId> OnNodeDead(string node)
    {
        lock (_lock)
            return _blocks.Values
                .Where(b => b.Replicas.Contains(node))
                .Select(b => b.Id)
                .ToList();   // caller re-replicates each from a surviving copy
    }
}

// ---- Durability math: XOR parity (RAID-4) — the intuition behind Reed-Solomon ----
// Store k data blocks + 1 parity block = tolerate ANY 1 lost block for 1/k overhead.
public static class XorParity
{
    public static byte[] ComputeParity(IReadOnlyList<byte[]> dataBlocks)
    {
        int len = dataBlocks[0].Length;
        var parity = new byte[len];
        foreach (var block in dataBlocks)
            for (int i = 0; i < len; i++)
                parity[i] ^= block[i];        // XOR fold across all data blocks
        return parity;
    }

    // Reconstruct the ONE missing block by XOR-ing every surviving block (incl. parity).
    public static byte[] Reconstruct(IReadOnlyList<byte[]> survivingBlocks)
    {
        int len = survivingBlocks[0].Length;
        var rebuilt = new byte[len];
        foreach (var block in survivingBlocks)
            for (int i = 0; i < len; i++)
                rebuilt[i] ^= block[i];        // XOR is its own inverse
        return rebuilt;
    }
}

XOR parity tolerates only a single failure; real systems use Reed-Solomon (e.g. RS(10,4)) over a Galois field to survive m simultaneous losses. In production you'd reach for a battle-tested library rather than hand-rolling the field arithmetic — Jerasure or ISA-L (C/C++), or in .NET wrap ISA-L via P/Invoke; Backblaze also open-sourced a clean Java Reed-Solomon implementation worth reading. The C# above is deliberately the intuition, not the production coder.

⚖️ Trade-offs, bottlenecks & likely follow-ups

The metadata server is the classic bottleneck. A single master (GFS/HDFS) is simple and strongly consistent but caps namespace size at one machine's RAM and is a recovery risk. Fixes: HDFS Federation + HA (active/standby with quorum journal), or Colossus's fully distributed metadata in BigTable. Interviewers love to push here — be ready to explain why the single master survived so long (it's off the data path, so it only handles lightweight control ops) and what finally broke it (block-count growth).

Small-file problem. Huge blocks + per-block metadata means millions of tiny files explode metadata and waste space. Mitigations: pack small files into container formats (HAR, SequenceFile, Parquet), or use an object store with a flat namespace.

Durability vs cost vs recovery speed. 3× replication = fast reads & simple recovery but 200% overhead; erasure coding = ~40% overhead but expensive, network-heavy reconstruction. The standard answer: replicate hot data, erasure-code cold data, and place replicas rack-aware so no single failure domain loses everything.

Consistency vs performance. Strict POSIX (fsync semantics, random overwrite, byte-range locking) is expensive at scale, so DFSs relax to write-once/append-mostly with at-least-once record append. Know the CAP framing: metadata operations are usually CP (consistent, may pause during failover); the data path favors availability and throughput.

Q: Why is the block size so large (64–128 MB) instead of a normal 4 KB page?

To shrink metadata (fewer block entries fit the whole map in the master's RAM) and to amortize disk seeks for large sequential scans. The cost is wasted space and hot blocks for small files — which is why a DFS isn't for millions of tiny files.

Q: How do you avoid the single master being a single point of failure?

Persist metadata with a write-ahead edit log + periodic checkpoint; run active/standby with automatic failover (HDFS HA over a quorum journal); or eliminate the single master entirely — shard metadata across many servers backed by a scalable KV store (Colossus/BigTable) or compute placement algorithmically with no central map (Ceph/CRUSH).

Q: How is data integrity guaranteed against silent disk corruption?

Per-block CRC32C checksums verified on every read; background scrubbing continuously re-verifies replicas. A checksum mismatch triggers repair from a healthy replica or erasure-coded reconstruction.

Q: Why keep the metadata service off the data path?

So aggregate read/write bandwidth scales with the number of storage nodes rather than being throttled by one coordinator. The client does one cheap lookup, then streams bytes directly to storage nodes — GFS scaled reads to 583 MB/s across 342 nodes precisely because the master isn't in the byte stream.

🗣️ Interview cheat sheet

30-second pitch: "A distributed file system stores one logical namespace across thousands of failing machines. The key move is separating the control plane — a metadata service that maps files to large 64–128 MB blocks and their replica locations — from the data plane, where clients stream bytes directly to storage nodes. Blocks are replicated 3× (rack-aware) or erasure-coded ~1.4× for cold data; heartbeats detect failures and trigger background re-replication. GFS pioneered it with a single master; HDFS cloned it; Colossus removed the master bottleneck by sharding metadata into BigTable; Ceph computes placement with CRUSH and needs no central map at all."

Numbers to quote

  • Block size: 64 MB (GFS) / 128 MB (HDFS); metadata ≈ 150 B/block.
  • Replication: 3× (tolerate 2 failures) vs RS(10,4) = 1.4× overhead, tolerate 4 failures.
  • Per-node read ≈ 80–100 MB/s; GFS scaled to 583 MB/s over 342 nodes.
  • Colossus: 100× metadata scaling over GFS; single cluster ≈ exabytes, tens of thousands of machines.
  • Heartbeat every 3s; dead after ~2 min of silence (HDFS).
  • S3 durability target: 11 nines across ≥3 AZs.

5 talking points that win the round

  • Control plane / data plane split — the reason it scales; metadata off the hot path.
  • Large blocks — shrink metadata + amortize seeks; explain the small-file trade-off.
  • Failure is the norm — heartbeats, re-replication, checksums, background scrubbing.
  • Replication vs erasure coding — hot vs cold data; overhead vs reconstruction cost.
  • Evolution — single master (GFS/HDFS) → sharded metadata (Colossus) / CRUSH (Ceph); know why each step happened.
