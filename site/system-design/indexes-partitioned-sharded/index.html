Indexes on Partitioned & Sharded Data

Why one index type makes reads free and writes cheap — and the other flips it. Local Secondary Indexes vs Global Secondary Indexes, scatter-gather, and the trade-offs that decide whether your query touches one shard or a hundred.

🎯 Real-world scenario

What we're building & where it's used

When a dataset outgrows a single machine, we split it — partition by hash or range, then shard those partitions across nodes. The primary key lookup is easy: hash the key, jump to the right shard, done. The interesting problem is secondary access. If a table of 500 million movies is partitioned by movie_id, then a query like WHERE genre = 'Crime' has no idea where the data lives — the partition key isn't in the predicate. What now?

This is one of the most common real-world tension points in distributed databases, and interviewers love it because it forces you to reason about writes, reads, consistency, and latency all at once. The two answers are Local Secondary Index (LSI) and Global Secondary Index (GSI), and picking wrong turns a 5 ms point read into a 200 ms scatter-gather nightmare.

Every serious partitioned system faces this: DynamoDB ships both LSI and GSI as first-class features. Cassandra and ScyllaDB only ship local indexes and warn you about the scatter-gather cost. MongoDB lets you build indexes on any field, but on a sharded collection those are per-shard indexes underneath. PostgreSQL's partitioned tables build one child index per partition — no truly global index. Elasticsearch, Vitess, CockroachDB, Spanner — all have to answer this question. The pattern is universal.

🧑‍🎓 In laymen terms (for a beginner)

Explaining this at a dinner party

Imagine you own a huge library with 500 million books. One building can't hold that many, so you rent 10 warehouses across the city and split the books by their catalog number — books 1 to 50 million go to warehouse 1, 50 to 100 million to warehouse 2, and so on. If someone asks for "book 137,842,301," you look at the catalog number, know instantly it's in warehouse 3, and drive straight there. Easy.

But then a librarian asks: "give me all mystery novels." Uh oh. Mystery novels aren't grouped together — they're scattered across all 10 warehouses. You have two choices, and this is the whole story.

Choice A — the little card catalog in each warehouse. You put a small card index at every warehouse listing only the mysteries in that warehouse. Cheap to keep updated (a new mystery arrives at warehouse 4, you just update warehouse 4's index). But to answer "give me all mysteries," you have to send 10 messengers to 10 warehouses, wait for them all to come back, then combine the answers. Slow.

Choice B — one giant master catalog for mysteries. You build a separate index in its own building, organized by genre. All the mysteries in the world are listed in one place. Now "give me all mysteries" is a single trip — fast. But every time a new book arrives at any warehouse, you must also send an update to the master catalog building. And if you demand this update happens immediately, every book delivery becomes slow.

That's the whole trade-off. Choice A = cheap writes, slow "search everywhere" reads. Choice B = fast reads, expensive writes. Real systems like Amazon's DynamoDB let you pick either one — and if you pick wrong, your app either can't keep up with new orders or takes forever to search.

Concrete example: Netflix has a movies table split across 100 machines by movie_id. If Netflix wants to show you "all Crime movies released in 2024," a local-index setup would ask all 100 machines and merge — maybe 200 ms. A global-index setup keeps a separate table organized by genre, so the same query hits just one machine — 5 ms. But when Netflix adds a new movie, the global-index approach makes that write touch two places instead of one. You're literally trading write speed for read speed.

📋 Requirements & scale

Requirements and back-of-the-envelope math

This isn't a "design a product" question — it's a design decision that every partitioned data store must answer. So the requirements are framed around the query patterns and the write budget you're given.

Functional requirements

  • Support point queries on the primary/partition key with single-partition latency.
  • Support secondary queries on non-partition-key attributes (e.g. genre, email, status) without full-table scans.
  • Support both combined queries (partition key + secondary attr) and pure secondary queries (attr only).
  • Allow the operator to choose the consistency model — strong for financial data, eventual for social feeds.

Non-functional requirements

  • p50 read latency < 10 ms, p99 < 100 ms for indexed lookups.
  • Write amplification bounded — one logical write should not fan out to hundreds of shards synchronously.
  • Index freshness: strong for LSI, ≤ few seconds for GSI (typical eventual replication lag).
  • Horizontal scaling: adding shards must not require rebuilding a global index from scratch.

🏗️ High-level architecture

How the pieces fit together

The base table is hash-partitioned by its primary partition key across N shards. Every shard is a self-contained storage node with its own local B-tree/LSM. A Local Secondary Index (LSI) is another B-tree living inside the same shard, keyed on a non-primary attribute but scoped to that shard's data only. A Global Secondary Index (GSI) is essentially a separate logical table, re-partitioned by the indexed attribute — physically it lives on its own set of nodes (possibly overlapping with the base shards).

A query planner sits in front. When the predicate includes the base partition key, the planner routes to one shard. When the predicate is only on an indexed attribute, the planner either fans out to all shards (LSI) or routes to the single GSI partition that owns that value.

🔍 Component deep-dive

The partition-key contract

The partition key is the only field the router uses to place a row on a shard. If you query with the partition key, the router does hash(pk) mod N and lands on exactly one shard. If you don't, the router has no locality signal and must broadcast — this is the entire origin of the LSI vs GSI question. Some systems (PostgreSQL, DynamoDB) let you add secondary indexes; others (Cassandra pre-3.0) essentially forced a scatter-gather.

Local Secondary Index (LSI) — the co-located index

An LSI is stored inside the same shard as the base row it points to. The index key is (base_partition_key, secondary_attr), so lookups still need the base partition key to find the right shard. In DynamoDB, LSIs share the base table's storage partition — that's why the 10 GB per-partition-key limit applies to the sum of base + LSIs. Because the update happens in the same shard, the write is a local transaction — no distributed commit, no network amplification. Reads that supply the partition key hit one shard and are strongly consistent if you ask.

The catch: an LSI does nothing for a query that only supplies the secondary attribute. That degenerates to scatter-gather, which is what the animation shows above.

Global Secondary Index (GSI) — the re-partitioned index

A GSI is effectively a separate logical table keyed on the indexed attribute and physically distributed across its own partition set. In DynamoDB, the GSI has its own read/write capacity units, its own throughput, its own partitions. A query that filters only on the indexed attribute hashes that attribute's value and jumps directly to one GSI partition — no fanout, no coordinator merge.

The catch: every write to the base table must also flow to the correct GSI partition, which lives on a different node group. Doing this synchronously means every base write becomes a distributed transaction — 2× the latency, coordinator overhead, and a new failure mode where the GSI is down but the base isn't. Almost every production system takes the pragmatic escape hatch: update the GSI asynchronously. The base write commits fast, an internal replicator streams the change into the GSI, and readers accept eventual consistency (typically sub-second, up to minutes under load).

The scatter-gather tax on LSI cross-partition reads

Suppose we have 100 shards and each shard's p99 latency is 20 ms. The mean latency of a scatter-gather is not 20 ms — it's the maximum of 100 independent 20 ms samples. Tail-latency amplification means the actual observed p99 might be 80–120 ms because somebody in the fan-out is always slow. That's before you count coordinator merge time, network jitter, or partial failures forcing retries. This is why big-data engines like Elasticsearch aggressively cap the number of shards you can query in one request.

Sync vs async GSI updates

Synchronous GSI updates give you a globally consistent index but cost every write a 2PC. Async updates give you cheap writes but readers see stale index entries. Most real systems (DynamoDB GSIs, MongoDB sharded secondary indexes, Elasticsearch replicas) pick async. The correctness patch is either read-your-writes stickiness (route the writer's next few reads to the base table, not the GSI) or a hard product decision — "the search index is eventually consistent, the transactional store isn't."

Hot partitions in a GSI

Because a GSI is re-partitioned by the indexed attribute, an attribute with skewed values creates a hot spot in the GSI even if the base table is perfectly balanced. Example: partition a users table by user_id (uniform), then GSI on country_code. If 40% of your traffic is US, one GSI partition eats 40% of index writes and reads. Mitigations: composite index keys (country_code#user_id), sharded counters, or accepting the skew and provisioning the GSI more heavily than the base table.

Where PostgreSQL sits

PostgreSQL partitioned tables are more like the LSI model: a "partitioned index" on the parent is a logical wrapper over N child indexes, one per partition. There is no truly global index. Consequently, a unique constraint on a partitioned table must include every partition key column — the DB can't enforce uniqueness across partitions with only local indexes, so it structurally guarantees uniqueness by making the partition key part of the constraint. That is worth memorizing.

🧮 The DSA behind it

Data structures & algorithms

Under the surface, everything here is either a B-tree/LSM (the index structures), a consistent hash (the router), or a merge algorithm (the coordinator).

Index structures

  • B+ tree — used by PostgreSQL, MySQL, DynamoDB LSIs. O(log n) point + range reads, in-place updates. Good for read-heavy workloads.
  • LSM tree (SSTable + memtable) — used by Cassandra, ScyllaDB, RocksDB, DynamoDB storage. Sequential appends → cheap writes, compaction handles cleanup. Good for write-heavy workloads.
  • Hash index — DynamoDB partition selection. O(1) lookup, no range support.

Routing algorithms

  • Consistent hashing (with virtual nodes) — maps partition keys → shards while minimizing rebalance on add/remove. Foundational to DynamoDB, Cassandra, Redis Cluster.
  • Range partitioning — used by HBase, Bigtable, Spanner. Keeps range scans efficient but is more prone to hot spots.

Scatter-gather merge

When a coordinator receives ordered result streams from N shards, merging is exactly a k-way merge problem — the same one you'd solve with a min-heap of size N. Complexity is O(K · log N) for K total results across N shards. This is why the query planner cares deeply about pushing filters and sorts down into each shard before merging.

Mapping the design to AWS

DynamoDB is the reference implementation of both index types on a partitioned KV store — the terminology on the AWS page literally reads "Local Secondary Index" and "Global Secondary Index," and the design decisions map 1:1 to what we've discussed. For other patterns, you compose with OpenSearch, RDS, or Aurora.

DynamoDB specifics worth quoting in an interview

  • LSI: must share the base table's partition key; can only be defined at table creation; consumes the base table's throughput; supports strong or eventual consistency.
  • GSI: can use any attribute as partition key; created/deleted online; has its own throughput budget; supports eventual consistency only.
  • Size limits: LSI adds to the 10 GB per-partition-key limit; GSIs have no such limit because they re-partition.
  • Projected attributes: GSI queries can only read projected attrs (no base-table fetch); LSI queries can fetch non-projected attrs from the base table on the fly.

💻 C# implementation

Below is a small reference showing how you'd model both index types against DynamoDB using the AWS SDK for .NET. The important part is which query you send: a base-table QueryAsync, an LSI query (same partition key, different sort key), or a GSI query (repartitioned attribute).

// Movie table example — see how LSI vs GSI change the query shape.
// Base table:  PK = MovieId (S), SK = ReleaseDate (S)
// LSI:         PK = MovieId (SAME), SK = Genre       — local, co-located, cheap writes.
// GSI:         PK = Genre,          SK = ReleaseDate — global, own partitions, fast "by genre" reads.

using Amazon.DynamoDBv2;
using Amazon.DynamoDBv2.Model;

public sealed class MovieIndexRepo
{
    private readonly IAmazonDynamoDB _db;
    private const string Table = "Movies";

    public MovieIndexRepo(IAmazonDynamoDB db) => _db = db;

    // 1) POINT READ using the BASE table partition key. One shard. Cheapest read possible.
    public async Task<List<Movie>> GetMovieHistory(string movieId)
    {
        var req = new QueryRequest
        {
            TableName              = Table,
            KeyConditionExpression = "MovieId = :m",
            ExpressionAttributeValues = new() { [":m"] = new(movieId) }
        };
        var res = await _db.QueryAsync(req);
        return res.Items.Select(Movie.From).ToList();
    }

    // 2) LSI query — same partition key as base, but sorted/filtered by Genre.
    //    Still lands on ONE shard because MovieId (base PK) is in the predicate.
    //    Strongly consistent by default (LSIs support strong consistency).
    public async Task<List<Movie>> GetGenresForMovie(string movieId, string genre)
    {
        var req = new QueryRequest
        {
            TableName              = Table,
            IndexName              = "MovieId-Genre-LSI",
            KeyConditionExpression = "MovieId = :m AND Genre = :g",
            ConsistentRead         = true,   // LSI supports it; GSI would refuse.
            ExpressionAttributeValues = new()
            {
                [":m"] = new(movieId),
                [":g"] = new(genre)
            }
        };
        return (await _db.QueryAsync(req)).Items.Select(Movie.From).ToList();
    }

    // 3) GSI query — pure secondary lookup by Genre, no base PK required.
    //    Router jumps to the ONE GSI partition that owns "Crime".
    //    Eventually consistent — reads may lag base writes by ~1 sec.
    public async Task<List<Movie>> GetMoviesByGenre(string genre, DateOnly since)
    {
        var req = new QueryRequest
        {
            TableName              = Table,
            IndexName              = "Genre-ReleaseDate-GSI",
            KeyConditionExpression = "Genre = :g AND ReleaseDate >= :d",
            // ConsistentRead = true would THROW — GSIs are eventual-only.
            ExpressionAttributeValues = new()
            {
                [":g"] = new(genre),
                [":d"] = new(since.ToString("O"))
            }
        };
        return (await _db.QueryAsync(req)).Items.Select(Movie.From).ToList();
    }

    // 4) The anti-pattern: NO index on Genre. This is a scatter-gather Scan.
    //    Reads every partition of the base table. Never do this in production.
    public async Task<List<Movie>> ScatterGatherByGenre_DoNotDoThis(string genre)
    {
        var req = new ScanRequest
        {
            TableName        = Table,
            FilterExpression = "Genre = :g",     // FilterExpression runs AFTER the scan — you pay for every read.
            ExpressionAttributeValues = new() { [":g"] = new(genre) }
        };
        var results = new List<Movie>();
        string? cursor = null;
        do
        {
            req.ExclusiveStartKey = cursor is null ? null : DecodeCursor(cursor);
            var page = await _db.ScanAsync(req);
            results.AddRange(page.Items.Select(Movie.From));
            cursor = page.LastEvaluatedKey?.Count > 0 ? EncodeCursor(page.LastEvaluatedKey) : null;
        } while (cursor is not null);
        return results;
    }
}

Notes worth mentioning verbally in an interview:

  • Same query semantics, three latencies. The only thing that changes across #1–#3 is which index name we pass — but the routing (one shard vs one GSI partition vs scatter-gather) is entirely determined by which attributes are in the KeyConditionExpression.
  • ConsistentRead = true throws on a GSI. The SDK enforces this at request time — a clean interview-friendly example of the eventual-consistency contract.
  • Never Scan with a filter in prod unless you're an admin tool. FilterExpression runs after the read, so you pay full RCU cost for every item scanned. It's the "no index at all" version of scatter-gather.

⚖️ Trade-offs, bottlenecks & likely follow-ups

The core trade-off in one sentence

LSI makes writes cheap and pure-secondary reads expensive (scatter-gather). GSI makes writes expensive (or eventually consistent) and pure-secondary reads cheap. There is no free lunch — you're moving the cost around, not eliminating it.

Failure modes

  • Straggler shards on LSI reads. One slow shard drags the whole query to its p99. Mitigation: hedged requests (send to a replica after 95 ms), circuit-break slow shards, or degrade to partial results with an explicit "incomplete" flag.
  • GSI backfill lag under bursty writes. Async replicators fall behind, and the "1-second lag" turns into a "5-minute lag." Mitigation: rate-limit writes into the GSI, over-provision the GSI's throughput, or read from the base table for read-your-writes.
  • Hot GSI partition. Skewed indexed attribute → one GSI partition eats all traffic. Mitigation: composite key (append a bucket/user hash to the indexed attr), or shard the GSI writes explicitly.
  • Index corruption drift. If a GSI async pipeline drops a message, the index disagrees with the base table silently. Mitigation: periodic reconciliation jobs, an idempotent replayer keyed by base-table version.

Likely interviewer follow-ups

Why is a scatter-gather query on 100 shards slower than 100× a single-shard read?

Because latency is dominated by the slowest shard, not the average. Even if the mean shard responds in 20 ms, the max of 100 samples has a much fatter tail — often 3–5×. Add coordinator merge overhead and network jitter, and the "parallel" fanout is bottlenecked by tail latency.

If GSIs are eventually consistent, when would you ever want an LSI?

When you need strong consistency on a secondary read but always have the partition key in the query. Example: fetching an order's payment attempts by orderId + attemptStatus. The partition key is always known, and you can't afford a stale read of "payment successful" that hasn't propagated to a GSI yet.

Why does PostgreSQL force the unique constraint to include the partition key?

Because PostgreSQL only supports local indexes on partitioned tables. It can enforce uniqueness inside a single partition (its local index will refuse duplicates), but it has no global index to enforce uniqueness across partitions. Forcing the constraint to include the partition key means two duplicate rows would necessarily land on the same partition, where the local index catches the collision.

Could you build a synchronous GSI? What's the cost?

Yes — every base write becomes a distributed 2-phase commit across the base partition and the GSI partition. You get strong consistency but roughly 2× the write latency and a new failure mode: if the GSI is unavailable, the base write blocks. DynamoDB deliberately chose eventual consistency for GSIs to preserve base-table write availability.

How would you handle a query needing multiple indexed attributes — say genre AND year?

Options: (1) build a composite GSI with partition key genre and sort key year — one hop, no fanout. (2) fall back to two lookups + intersection (expensive and pointless if either result set is large). (3) push the workload to a search engine like OpenSearch, which is designed for multi-attribute queries. The rule: if it's a hot query, model the composite key upfront; DynamoDB rewards single-purpose indexes over general-purpose ones.

Where do you see this in Cassandra?

Cassandra's native secondary indexes are effectively LSIs — an index per node covering only that node's data. That's why the community warns against them for high-cardinality attributes: a query without the partition key becomes a coordinator-driven fanout to every node. The preferred pattern is a manual denormalized table keyed on the query attribute — literally hand-building a GSI. SASI and Materialized Views moved the needle but still don't give you a true global index.

🗣️ Interview cheat sheet

The 30-second pitch: Once you partition a table by a primary key, any query that doesn't include that key has no locality. Two answers: Local Secondary Index co-locates a small index inside every shard — cheap writes, but pure secondary queries scatter-gather across all shards. Global Secondary Index re-partitions the table by the indexed attribute onto its own node group — pointed reads, but writes now touch two shards and must be async or 2PC. Pick LSI when writes dominate or the partition key is always in the query; pick GSI when the indexed attribute is your dominant read path.
  • The words that win the round: "scatter-gather," "tail latency amplification," "write amplification," "eventual consistency," "hot partition on the GSI."
  • Numbers to quote: DynamoDB allows 5 LSIs, 20 GSIs per table. LSI adds to the 10 GB per-partition-key limit. Async GSI lag is typically sub-second but can stretch to minutes under stress.
  • The 5 talking points: (1) partition key contract, (2) LSI = local, GSI = repartitioned, (3) scatter-gather cost, (4) sync vs async GSI updates, (5) hot-partition mitigation.
  • The clean escape: when they ask "why not both?" say "you can, and often should — LSIs for strongly-consistent (PK + attr) reads, GSIs for pure-attr reads, and OpenSearch for anything multi-dimensional or full-text."
  • The gotcha to mention proactively: "Postgres partitioned tables don't have a true global index — that's why unique constraints must include the partition key."
