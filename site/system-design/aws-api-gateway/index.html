🎯 Real-world scenario

What we're building & where it's used

Amazon API Gateway is a fully managed service that acts as the "front door" for your APIs — the single entry point that accepts every client request, then handles authentication, authorization, throttling, request/response transformation, caching, and monitoring before and after it forwards the call to your backend (a Lambda function, an HTTP service on EC2/ECS, or another AWS service). It creates and runs REST, HTTP, and WebSocket APIs "at any scale," absorbing up to hundreds of thousands of concurrent calls so you don't build the plumbing yourself.

The API Gateway pattern is a foundational system-design concept: instead of clients talking to dozens of microservices directly (and each service re-implementing auth, rate limiting, logging, TLS, CORS…), you put one gateway in front that owns those cross-cutting concerns. AWS API Gateway is the managed embodiment of that pattern and the app-facing half of the serverless stack (API Gateway + Lambda). Real uses: public REST/JSON APIs for mobile and web apps, serverless backends, internal microservice front doors (private APIs inside a VPC), third-party developer platforms with API keys and usage plans, and real-time apps over WebSockets (chat, live dashboards).

Why it's a strong interview topic: it forces you to explain the gateway/reverse-proxy pattern, the request lifecycle, how throttling protects backends (token bucket), how edge caching and CloudFront reduce latency, and the authorization models — all concepts that transfer to any API gateway (Kong, NGINX, Apigee), not just AWS.

The front-desk receptionist of a giant office building

Picture a huge office tower with hundreds of teams inside — Finance, Legal, HR, the design studio, the engineering floor. If every visitor could walk straight in and wander the hallways, it would be chaos: nobody would know who's a guest, who's supposed to be there, or who's stealing the biscuits. So the building has one busy front desk. Every single person, whether they're delivering pizza or here for a job interview, stops there first. The receptionist checks their ID, signs them in the visitor book, tells them where to sit, and calls upstairs to say "your 3 o'clock is here." That's exactly what this system does for a website's requests.

Now imagine three annoying situations the receptionist quietly handles for you. Some visitors show up a hundred at a time from the same tour bus — the receptionist says "please form a line, I can only send five upstairs a minute, or the elevator will jam." Some visitors don't speak the same language as the teams upstairs — the receptionist quickly translates their form into the format the team uses. And some questions get asked over and over ("what floor is HR on?") — so the receptionist keeps a little cheat sheet under the desk and answers those instantly without bothering anyone upstairs.

You use this every day without noticing. When you open the Uber app or ask Alexa a question, your phone doesn't talk to fifty different teams inside Uber or Amazon directly — it talks to one front desk that decides where the message goes. Amazon's version of this front desk lets a company set it up in an afternoon instead of building the reception area, hiring the guards, and printing the visitor books themselves.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • Route incoming HTTP/WebSocket requests to the right backend based on path + method (resources & methods, or routes).
  • Authenticate/authorize callers — IAM, Cognito/JWT, Lambda authorizers, API keys.
  • Transform requests and responses (mapping templates / parameter mapping) between client and backend formats.
  • Throttle & quota — protect backends from overload and enforce per-client usage plans.
  • Cache responses to cut backend load and latency; monitor/log every call.
  • Support staged deployments (dev/prod/v2) and safe rollouts (canary).

Non-functional requirements (the ones that shape the design)

  • Massive scale — hundreds of thousands of concurrent requests, fully managed, no servers to run.
  • Low latency — edge-optimized via CloudFront POPs for global clients; regional to skip the CloudFront hop for in-Region callers.
  • Availability & isolation — one noisy client or method must not exhaust the whole backend (layered throttling).
  • Security — TLS everywhere, mTLS, WAF integration, private (VPC-only) endpoints.
  • Observability — CloudWatch metrics/logs, X-Ray tracing, access logs.

🏗️ High-level architecture

How the pieces fit together

Every request flows through four internal stages, and understanding them is the crux of "how it works internally." (1) Method Request — the public interface: this is where API Gateway does auth (authorizer/IAM/API key), request validation, and throttling. (2) Integration Request — the internal interface to the backend: a mapping template (VTL) transforms the client's parameters/body into whatever the backend expects, and the call is dispatched to the integration (Lambda, HTTP, AWS service, or mock). (3) The backend runs and returns a result. (4) Integration Response — maps the backend's status/headers/body back toward the client, then (5) Method Response — the public response contract returned to the caller. With proxy integration, stages 2 and 4 are pass-through: the entire request goes to Lambda and its output becomes the HTTP response, no mapping templates needed — the common serverless setup.

In front of all this sits the endpoint type. Edge-optimized routes clients to the nearest CloudFront Point of Presence (best for globally distributed users). Regional targets the Region directly, skipping the CloudFront round-trip for in-Region callers (and enabling latency-based multi-Region routing via Route 53). Private exposes the API only inside a VPC via interface VPC endpoints. The API itself is versioned via stages (dev/prod), each an addressable snapshot of a deployment.

Request (inbound) Response (outbound) Rejected (429/401) Edge (CloudFront)

The request lifecycle, step by step

  1. Client hits the endpoint (edge-optimized → nearest CloudFront POP; regional → straight to the Region).
  2. Method Request: API Gateway authenticates (authorizer/IAM/API key), validates the request, and applies throttling — over the limit ⇒ immediate 429. A cache hit here returns the cached response and skips the backend.
  3. Integration Request: a VTL mapping template transforms the request to the backend's expected shape (skipped for proxy integration), then dispatches to the integration.
  4. Backend (Lambda / HTTP / AWS service / mock) executes and returns a result.
  5. Integration Response → Method Response: map the backend result back to the client contract, cache it if configured, emit CloudWatch metrics/logs, and return to the client.

🔍 Component deep-dive

Resources, methods & the routing model

A REST API is a tree of resources (URL paths like /pets, /pets/{id}), and each resource exposes methods (HTTP verbs: GET, POST, …). Each method binds to exactly one integration. A powerful shortcut is the proxy resource: a greedy path variable {proxy+} combined with the catch-all ANY method routes everything under a path to a single backend — the typical "let my Lambda/framework handle all routing" setup. HTTP APIs use the leaner concept of routes (e.g. GET /items) mapped to integrations.

Integration types

API Gateway supports four ways to reach a backend. Lambda — invoke a function (proxy or custom). HTTP — proxy to any public HTTP endpoint. AWS Service — call another AWS API directly (e.g. drop a message straight into SQS or write to DynamoDB) with no Lambda in between — great for simple passthroughs. Mock — API Gateway returns a canned response with no backend at all (handy for CORS preflight, stubs, and contract-first development). Proxy vs custom is the key axis: proxy passes the whole request/response through untouched (simple, fast to build); custom integration uses mapping templates for fine-grained transformation.

Mapping templates (VTL) & request validation

In custom integrations, mapping templates written in Velocity Template Language (VTL) reshape data between the client's format and the backend's — reading path/query/header params and the body, and referencing context and stage variables. They can be a simple identity passthrough or a full restructuring (e.g. wrap a client JSON into the exact event a legacy service expects). REST APIs can also do request validation against JSON-Schema models, rejecting malformed requests at the gateway before they ever hit your backend — cheap defense and less backend code.

Throttling: the token bucket, layered

API Gateway protects backends with the token bucket algorithm — one token per request, refilled at the rate and capped at the burst (bucket size). Crucially the limits are layered and applied in a specific order: (1) per-client / per-method limits from a usage plan, (2) per-method limits on a stage, (3) the account-level Regional limit (default 10,000 RPS / 5,000 burst), (4) the AWS-wide Regional limit AWS sets and you can't change. A request must pass every applicable layer; the first bucket that's empty returns 429. This lets you give a premium client a bigger slice while still protecting the whole account. Throttles are "best-effort targets," not exact ceilings.

Usage plans & API keys

For monetized or multi-tenant APIs, API keys identify each client app and usage plans attach throttle + quota (e.g. 1M requests/month) limits to those keys. This is how you offer Free/Pro/Enterprise tiers. (Note: API keys and per-client throttling are REST-only — a key reason to pick REST over HTTP APIs.)

Authorization models

Four mechanisms, in rough order of use: IAM (SigV4-signed requests — for AWS-to-AWS or trusted callers); Cognito / JWT authorizers (validate a user-pool or OIDC token — the common choice for user-facing apps); Lambda authorizers (your own function returns an IAM policy allow/deny — for custom/bespoke auth, and the way REST APIs validate JWTs); and API keys + usage plans for identifying app developers. Authorization runs in the Method Request stage, before any backend call, and authorizer results can be cached to avoid re-validating every request.

Caching

REST APIs offer a dedicated response cache (0.5 GB–237 GB) keyed on request parameters, with a configurable TTL (default 300 s). A cache hit is served entirely from the gateway, cutting both latency and backend load — the same win as any read-through cache, but managed at the front door. (HTTP APIs don't have built-in caching; you'd front them with CloudFront.)

REST vs HTTP vs WebSocket

REST APIs are the feature-rich, older product: API keys, per-client throttling, request validation, WAF, private endpoints, mapping templates, caching, mock integrations. HTTP APIs are newer, ~70% cheaper and lower-latency, with a minimal feature set (native JWT authorizers, auto-deploy) — pick them when you don't need REST's extras. WebSocket APIs keep a persistent, stateful connection and route incoming messages to integrations by message content (route keys) — for chat, live feeds, and push. Note the connection is persistent between client and gateway only; backends are invoked per-message.

Data structures & algorithms

A gateway is a routing + policy engine, so the DSA is about fast matching and fair limiting. Path routing uses a prefix/trie-style route table (with greedy {proxy+} wildcards); throttling is the token bucket; authorizer and response caching are hash-map caches with TTL; request validation walks a JSON-Schema.

💻 C# implementation

Two things are worth showing: (1) a Lambda proxy integration handler in C# — the exact request/response envelope API Gateway sends and expects; and (2) a sketch of the token-bucket throttle API Gateway applies in the Method Request stage, to prove you understand what the managed service is doing under the hood.

using Amazon.Lambda.APIGatewayEvents;
using Amazon.Lambda.Core;

// ---- Lambda PROXY integration: API Gateway sends the WHOLE request as this event,
// and turns whatever you return into the HTTP response. No mapping templates needed. ----
public class Handler
{
    public APIGatewayProxyResponse Get(APIGatewayProxyRequest req, ILambdaContext ctx)
    {
        // API Gateway already did auth + throttling in the Method Request stage.
        string id = req.PathParameters?.GetValueOrDefault("id") ?? "unknown";
        string caller = req.RequestContext?.Identity?.SourceIp ?? "?";
        ctx.Logger.LogInformation($"GET pet {id} from {caller}");

        return new APIGatewayProxyResponse
        {
            StatusCode = 200,                       // becomes the Method Response status
            Headers = new Dictionary<string, string>
            {
                ["Content-Type"] = "application/json",
                ["Cache-Control"] = "max-age=300"     // pairs with gateway caching
            },
            Body = $"""{{"id":"{id}","name":"Rex"}}"""
        };
    }
}

// ---- What API Gateway does internally at the Method Request stage: token-bucket throttle.
// (Illustrative — the managed service does this for you, layered per-client/method/account.) ----
public sealed class TokenBucketThrottle
{
    private readonly double _ratePerSec;   // steady-state rate (e.g. 10_000)
    private readonly double _burst;        // bucket capacity (e.g. 5_000)
    private double _tokens;
    private long _lastTicks;
    private readonly object _gate = new();

    public TokenBucketThrottle(double ratePerSec, double burst)
    {
        _ratePerSec = ratePerSec; _burst = burst;
        _tokens = burst; _lastTicks = Stopwatch.GetTimestamp();
    }

    // true = allowed; false = return HTTP 429 Too Many Requests.
    public bool TryAdmit()
    {
        lock (_gate)
        {
            long now = Stopwatch.GetTimestamp();
            double elapsed = (now - _lastTicks) / (double)Stopwatch.Frequency;
            _lastTicks = now;
            _tokens = Math.Min(_burst, _tokens + elapsed * _ratePerSec);  // lazy refill
            if (_tokens >= 1.0) { _tokens -= 1.0; return true; }
            return false;                                            // bucket empty → 429
        }
    }
}

The takeaways: (1) with proxy integration your handler receives the full APIGatewayProxyRequest and returns an APIGatewayProxyResponse that becomes the HTTP response verbatim — this is why proxy integration needs no mapping templates; and (2) the throttle sketch is exactly the token-bucket logic API Gateway runs for you, just layered across per-client, per-method, and per-account buckets. In real deployments you write only the handler; the gateway owns auth, throttling, caching, and transformation.

⚖️ Trade-offs, bottlenecks & likely follow-ups

REST vs HTTP API is the most common follow-up. HTTP APIs are ~70% cheaper and lower latency but lack API keys, per-client throttling, request validation, WAF, caching, mock integrations, and private endpoints. Default to HTTP APIs for simple Lambda/JWT backends; choose REST when you need those enterprise features. Say this trade-off out loud.

The 29-second integration timeout is a real ceiling — API Gateway is for request/response APIs, not long-running jobs. For long work, return 202 Accepted and hand off to Step Functions/SQS + async polling or WebSocket push. Similarly the 10 MB payload cap means large uploads should use S3 pre-signed URLs, not the gateway.

Latency & cold starts. The gateway adds a small hop; edge-optimized adds a CloudFront leg that helps distant users but hurts in-Region ones (use regional there). With Lambda backends, cold starts add latency — mitigate with provisioned concurrency. Caching hot GETs at the gateway removes both the backend call and its variability.

Throttling is best-effort, and layered. Limits are targets, not hard guarantees, and a burst can briefly overrun. Design backends to tolerate some overshoot, and use the layered limits (per-client < per-method < account) so one tenant can't starve others — the classic noisy-neighbor defense.

Cost model. You pay per request (+ data + cache hours). At very high, steady volume a self-managed gateway (ALB + NGINX/Kong on ECS) can be cheaper — the usual managed-vs-DIY trade. API Gateway wins on zero-ops, built-in auth/throttle/cache, and burst scaling.

Q: What's the difference between proxy and custom (non-proxy) integration?

Proxy passes the entire request to the backend and turns its output straight into the HTTP response — no mapping templates, minimal config (the common Lambda setup). Custom integration uses VTL mapping templates to transform request and response between client and backend formats, giving fine control at the cost of complexity.

Q: How does API Gateway rate-limit?

Token bucket, one token per request, refilled at a steady rate up to a burst capacity. Limits are layered and checked in order: per-client/per-method (usage plan) → per-method (stage) → account (default 10k RPS / 5k burst) → AWS Regional. The first empty bucket returns 429.

Q: When would you choose REST API over HTTP API?

When you need API keys and usage plans, per-client throttling, request validation, response caching, AWS WAF, mock integrations, or private VPC endpoints. Otherwise HTTP APIs are cheaper and lower-latency.

Q: Edge-optimized vs regional endpoint?

Edge-optimized routes through the nearest CloudFront POP — best for geographically spread clients. Regional targets the Region directly, skipping the CloudFront round-trip for in-Region callers, and supports Route 53 latency-based multi-Region routing. Private is VPC-only.

🗣️ Interview cheat sheet

30-second pitch: "API Gateway is the managed front door for your APIs. Every request flows through four internal stages: the Method Request does auth (IAM/Cognito-JWT/Lambda authorizer/API key), validation, and token-bucket throttling; the Integration Request transforms it via VTL mapping templates and dispatches to a backend (Lambda, HTTP, AWS service, or mock); then the Integration Response and Method Response map the result back to the client, optionally from cache. With proxy integration those transform stages are pass-through. It comes in REST (feature-rich), HTTP (cheaper/faster), and WebSocket (stateful) flavors, deployed via stages, exposed as edge-optimized (CloudFront), regional, or private endpoints. Default throttle is 10k RPS / 5k burst per Region, layered per-client and per-method, returning 429 on overflow."

Numbers to quote

  • Account throttle default: 10,000 RPS steady, 5,000 burst (per Region, soft).
