Distributed Cache

Millions of ops per second, sub-millisecond reads, and — when a node dies at 3 AM — only 1/N of the keys move, not the whole cluster. The design pattern behind Redis Cluster, Memcached at Facebook, and DynamoDB DAX.

🎯 Real-world scenario

What we're building & where it's used

We're designing a distributed in-memory cache — the fast, forgetful layer that sits between the application and the database. It's the class of system that powers Redis Cluster, Memcached (as used at Facebook, Twitter, Netflix, Reddit, Pinterest), Amazon ElastiCache, Amazon DynamoDB DAX, and TAO's cache tier at Meta. When a service needs to look up a user profile, a session, a feed page, or a hot product listing, the answer should come back in under 1 ms, not the 20–50 ms of a database round trip. A distributed cache lets us keep terabytes of hot data in RAM across dozens of nodes, spread the load evenly, survive individual node failures, and add or remove nodes at 2 AM without moving 99% of the keys.

Interviewers reach for this scenario because it forces you to defend the two hardest ideas in distributed systems in one conversation: partitioning (how do you split N keys across M servers?) and fault tolerance (what happens when one of those servers dies?). The right answer — consistent hashing with virtual nodes, plus replication and gossip-based failure detection — is the same pattern that underpins Amazon Dynamo, Cassandra, Riak, Discord's chat routing, and Akamai's CDN. Nail it here and you can defend it everywhere.

🧑‍🎓 In laymen terms

The whole thing, without any jargon

Imagine a giant library that gets so busy that every question — "where's the biography section?" "what time do you close?" — takes three minutes for a librarian to answer because they have to walk to the archive every single time. So the library builds a whiteboard right at the front desk and writes down the most-asked answers. When someone asks a common question, the receptionist just glances at the whiteboard and answers in two seconds. That whiteboard is a cache.

Now imagine the library grows to ten million visitors a day. One whiteboard isn't enough — even reading it becomes a queue. So we buy twenty whiteboards, line them up along the wall, and split up the answers: whiteboard 1 holds anything about music, whiteboard 2 holds anything about history, whiteboard 3 holds cookbooks, and so on. Now twenty receptionists can answer twenty questions at the same time. This is partitioning — splitting the data so each server only handles its slice.

Here's the tricky part. What if we simply said "take the question, count the letters, divide by 20, use the remainder to pick a whiteboard"? It works — until one whiteboard breaks, or we buy a new one. Suddenly the formula changes to "divide by 19" or "divide by 21", and almost every answer is now on the wrong whiteboard. All the librarians spend the whole night rewriting everything. Chaos.

The clever fix is to arrange the whiteboards in a circle around the room, and give each question a spot on that circle based on its name. When someone asks a question, they just walk clockwise from their spot until they hit a whiteboard — that one holds their answer. If a whiteboard breaks, only the questions that pointed to that whiteboard have to move; they simply walk one more step clockwise to the next one. If we add a whiteboard, it only takes over a little slice of the circle. This trick — the hash ring — means node changes only move a small fraction of the data, never the whole library.

Two more tricks. First, we write each answer on three whiteboards in a row, so if one dies mid-shift the next one already knows. That's replication. Second, the whiteboards constantly whisper to each other — "still here! still here!" — and if one goes silent for a few seconds, the others agree it's out and someone else takes over its slice. That's failure detection. Put it all together and you get the cache behind WhatsApp's contact lookups, Netflix's viewer sessions, Instagram's feed, and Uber's driver locations — all served from RAM in about a millisecond.

📋 Requirements & scale

Requirements and back-of-the-envelope math

Functional requirements

  • GET(key), PUT(key, value, ttl), DELETE(key) — the classic three.
  • Values up to a few MB (typically KB); millions of keys per node.
  • TTL-based expiration + eviction policy (LRU, LFU, or TinyLFU).
  • Add/remove nodes online without downtime.
  • Optional: pub/sub, transactions, scripting, atomic counters (Redis-shaped) vs pure KV (Memcached-shaped).

Non-functional requirements

  • Latency: p99 GET < 1 ms within a datacenter, p999 < 5 ms.
  • Throughput: 100K – 1M ops/sec per node; cluster scales linearly.
  • Availability: 99.99% — survive single-node failures without losing recent writes (with replication).
  • Rebalancing cost: adding/removing a node moves ~1/N of keys, not all of them.
  • Consistency: usually eventual (cache is by nature a best-effort projection of the database).

🏗️ High-level architecture

How the pieces fit together

The client library (or a proxy) holds the hash ring — a sorted structure mapping positions on a 232 or 264 ring to physical nodes, with each node placed at ~100–200 virtual positions. When the app calls GET(user:42), the client hashes the key (MurmurHash3 / xxHash), walks the ring clockwise, and finds the first virtual node — that's the primary. The next N-1 unique physical nodes clockwise are the replicas. The client sends the request straight to the primary (one network hop). Writes go to the primary and are replicated to the followers either synchronously (strong-ish) or asynchronously (fast).

A background gossip protocol (Redis Cluster's approach) or a central configuration store like ZooKeeper (Memcached-mcrouter's approach) keeps everyone's view of "which nodes are alive" in agreement. When a node dies, gossip flags it "PFAIL → FAIL", the cluster elects one of its replicas as the new primary, and the ring position transparently switches over. When you add a node, it slots into the ring at 100–200 virtual positions and pulls in the small slice of keys that now belong to it — a bounded, background migration.

🔍 Component deep-dive

1. Partitioning — why modulo hashing fails

The naïve approach is node = hash(key) % N. It's dead simple and O(1). It also utterly breaks the moment N changes: going from 10 nodes to 11 causes roughly 10/11 of all keys to relocate. Every ounce of hot cache goes cold in one autoscale event. That's why every real distributed cache uses consistent hashing: nodes and keys both hash onto a large ring (typically 232 or 264 positions), and each key is owned by the first node clockwise. Adding or removing a node touches only the arc between the neighbour and the affected node — statistically K/N keys vs modulo's ~K.

2. Virtual nodes — smoothing the ring

Placing a physical node at a single ring position gives you terrible variance: one node might own 30% of the keyspace, another 3%. The fix is to hash each physical node's identity multiple times (e.g. hash("n2#0"), hash("n2#1"), ..., hash("n2#199")) and place all those virtual positions on the ring. Two benefits: (1) load smooths out — with ~100–200 vnodes per physical, the largest node owns roughly 1.05× the average vs 2–3× without vnodes; (2) when a node dies, its arc is broken into ~200 pieces which get absorbed by many neighbours instead of doubling the load on a single unlucky one.

3. Replication — what happens when a node dies

Each key is stored on the primary and the next N-1 unique physical nodes clockwise (walking past virtual duplicates). With N=3 you survive one full node loss without data loss and any single-node loss without unavailability. Replication can be:

  • Async (Redis default) — write acknowledged after primary; replicas catch up in ~ms. Small window of data loss on primary crash, but sub-ms writes.
  • Sync — write acknowledged only after M replicas ack (WAIT M timeout in Redis). Safe but slower.
  • Quorum (Dynamo-style, N/W/R) — the client picks W (write quorum) and R (read quorum). If W + R > N you get read-your-writes; typical picks are N=3, W=R=2.

On failure, gossip detects the dead node in ~5 s. One of its replicas is elected primary (via a mini-Raft or gossip vote), the ring's owner-of-that-slot flips to the new primary, and clients transparently retry through the client library. Meanwhile the cluster spawns a hinted handoff or a fresh replica to restore N=3.

4. Rebalancing — the migration protocol

When you add node N6, it registers on the ring at ~200 vnode positions. Each of those positions "steals" the arc between itself and the counter-clockwise neighbour. The cluster runs a slot migration in the background: for each stolen slot, N6 pulls keys from the old owner (Redis Cluster uses CLUSTER SETSLOT + MIGRATE). During migration the old node keeps serving while the new one is filling up; when the arc is fully moved, a single atomic slot handoff switches ownership. This is why cluster resize is a bounded, background operation — the app never sees a stampede.

5. Fault tolerance — gossip, quorum, and self-healing

Every node picks a few random peers every second and exchanges a heartbeat table (Cassandra, Redis Cluster, Dynamo all do this). If node A hasn't seen a heartbeat from B in timeout, A marks B "PFAIL" (probably failed) and gossips this. When a quorum of nodes agree, B is marked "FAIL" and failover triggers. This decentralised approach avoids the single-point-of-failure of a central coordinator, at the cost of a few-second detection window. For tighter windows you use ZooKeeper or etcd to hold the membership authoritative — that's what Memcached-mcrouter and Twemproxy do.

6. Cache patterns — the four you have to know

  • Cache-aside (lazy loading) — app checks cache; on miss, reads DB, writes back. Simplest, most common. Downsides: cold-start latency and thundering herd on cache expire.
  • Read-through — cache library owns the "on miss, fetch from DB" logic. Cleaner abstraction, but couples cache and DB.
  • Write-through — writes hit cache and DB synchronously. Strong consistency, slower writes.
  • Write-back / write-behind — writes hit cache; async flush to DB. Blazing writes, risk of data loss on crash.

7. Hot keys, thundering herd, and stampedes

Two failure modes that always come up:

  • Hot key — e.g. a viral tweet's like-count. Every request slams one physical node. Fix: replicate hot keys to multiple nodes (client picks randomly), or use request coalescing — the first miss fetches, everyone else waits.
  • Thundering herd on TTL expiry — a hot key expires; 10K threads simultaneously miss and hit the DB. Fixes: probabilistic early recomputation (refresh at expected miss time − ε), lease-based single-flight (Facebook's Memcached leases — first miss gets a lease token, everyone else waits), or stale-while-revalidate (return stale data while asynchronously refreshing).

8. Eviction policies

When RAM fills up, something has to go. The classics:

  • LRU — evict the least-recently-used. O(1) with a hashmap + doubly-linked list. Good general default.
  • LFU — evict the least-frequently-used. Better for stable working sets, worse for changing ones.
  • TinyLFU / W-TinyLFU (Caffeine's default) — sketch-based frequency admission + LRU eviction. State-of-the-art hit ratio.
  • TTL — evict on time, not on space. Complementary to the others.
  • Random / FIFO — trivial, surprisingly close to LRU for uniform workloads (Redis allkeys-random).

💻 C# implementation

A minimal, correct consistent-hash client in C#. It maintains a sorted map of virtual node positions → physical nodes, looks up "the first vnode ≥ hash(key)" with a binary search, and supports adding/removing nodes online. This is the trickiest part of a real client library — the network I/O is the easy bit.

// ConsistentHashRing.cs — virtual-node ring with binary-search lookup
using System.Collections.Concurrent;
using System.Security.Cryptography;
using System.Text;

public sealed class ConsistentHashRing<TNode> where TNode : notnull
{
    private readonly int _vnodesPerNode;
    private readonly SortedDictionary<uint, TNode> _ring = new();
    private uint[] _sortedHashes = Array.Empty<uint>();
    private readonly ReaderWriterLockSlim _lock = new();

    public ConsistentHashRing(int vnodesPerNode = 150) =>
        _vnodesPerNode = vnodesPerNode;

    public void AddNode(TNode node)
    {
        _lock.EnterWriteLock();
        try
        {
            for (int i = 0; i < _vnodesPerNode; i++)
                _ring[Hash($"{node}#{i}")] = node;
            _sortedHashes = _ring.Keys.ToArray();      // already sorted (SortedDictionary)
        }
        finally { _lock.ExitWriteLock(); }
    }

    public void RemoveNode(TNode node)
    {
        _lock.EnterWriteLock();
        try
        {
            for (int i = 0; i < _vnodesPerNode; i++)
                _ring.Remove(Hash($"{node}#{i}"));
            _sortedHashes = _ring.Keys.ToArray();
        }
        finally { _lock.ExitWriteLock(); }
    }

    // The primary owner of `key` = first vnode clockwise from hash(key)
    public TNode GetNode(string key)
    {
        _lock.EnterReadLock();
        try
        {
            if (_sortedHashes.Length == 0) throw new InvalidOperationException("empty ring");
            var h  = Hash(key);
            var ix = Array.BinarySearch(_sortedHashes, h);
            if (ix < 0) ix = ~ix;                            // insertion point
            if (ix == _sortedHashes.Length) ix = 0;           // wrap around
            return _ring[_sortedHashes[ix]];
        }
        finally { _lock.ExitReadLock(); }
    }

    // The next N unique physical nodes clockwise — for replication.
    public List<TNode> GetNodesForReplication(string key, int replicationFactor)
    {
        _lock.EnterReadLock();
        try
        {
            var result = new List<TNode>(replicationFactor);
            var seen   = new HashSet<TNode>();
            var h  = Hash(key);
            var ix = Array.BinarySearch(_sortedHashes, h);
            if (ix < 0) ix = ~ix;

            for (int step = 0; step < _sortedHashes.Length && result.Count < replicationFactor; step++)
            {
                var node = _ring[_sortedHashes[(ix + step) % _sortedHashes.Length]];
                if (seen.Add(node)) result.Add(node);           // skip virtual-duplicate
            }
            return result;
        }
        finally { _lock.ExitReadLock(); }
    }

    // Fast, well-distributed 32-bit hash. MurmurHash3 would be even better; MD5 is used for clarity.
    private static uint Hash(string key)
    {
        Span<byte> buf = stackalloc byte[16];
        MD5.HashData(Encoding.UTF8.GetBytes(key), buf);
        return BitConverter.ToUInt32(buf);
    }
}

// ---- Wiring it up as a cache client ----
public sealed class DistributedCacheClient
{
    private readonly ConsistentHashRing<string> _ring = new();
    private readonly ConcurrentDictionary<string, ICacheNode> _connections = new();
    private const int N = 3;

    public async Task<string?> GetAsync(string key)
    {
        var nodes = _ring.GetNodesForReplication(key, N);
        foreach (var id in nodes)                             // try primary, fall through on failure
        {
            try { return await _connections[id].GetAsync(key); }
            catch (NodeUnavailableException) { continue; }
        }
        return null;                                          // all replicas down
    }

    public async Task PutAsync(string key, string value, TimeSpan ttl, int writeQuorum = 2)
    {
        var nodes = _ring.GetNodesForReplication(key, N);
        var tasks = nodes.Select(id => _connections[id].PutAsync(key, value, ttl)).ToList();
        int acked = 0;
        while (tasks.Count > 0 && acked < writeQuorum)
        {
            var done = await Task.WhenAny(tasks);
            tasks.Remove(done);
            if (done.IsCompletedSuccessfully) acked++;
        }
        if (acked < writeQuorum) throw new QuorumException(acked, writeQuorum);
    }
}

What to point out in an interview when walking through this: (1) GetNodesForReplication skips virtual-node duplicates via the seen set — otherwise you'd "replicate" the key to the same physical node three times; (2) writes use a WhenAny quorum loop so the call returns as soon as W replicas ack, not after all N; (3) reads try replicas in ring order so a single dead node just adds a few microseconds; (4) the ReaderWriterLockSlim keeps GET lock-free-ish under load — writes to the ring (rare) block; reads (billions) don't. In production you'd swap MD5 for MurmurHash3/xxHash and use ImmutableSortedDictionary for lock-free reads.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Scaling bottlenecks

The first bottleneck is hot keys — no amount of consistent hashing helps if 40% of all requests target one key on one shard. The fix is hot-key replication (put the same key on multiple shards, client picks randomly) or request coalescing in the client. The second is network — a single Redis shard on a c7g.4xlarge can push ~2 Gbps; beyond that you're fanning out across shards. The third is memory fragmentation — Redis's jemalloc allocator can end up with 20–30% wasted RAM under heavy churn; sizing needs a safety margin.

Consistency trade-off

Cache is fundamentally an AP system (CAP). We accept eventual consistency: a write may take a few ms to propagate to replicas, and cross-region replication is asynchronous. If your app needs read-your-writes, you either use tunable quorum (W=R=2, N=3, so W+R>N) or read from the primary only. The trickiest bug in this space is cache-DB consistency — updating both non-atomically causes stale reads. The idiomatic fix is write-through or delete-then-DB-write (invalidate first) rather than update-then-update.

Follow-ups you should expect

Why consistent hashing and not just hash(k) % N?

Modulo hashing moves almost all keys when N changes (going from 10→11 relocates ~10/11 of the ring). Consistent hashing moves only ~K/N. That's the difference between "add a node in the afternoon" and "add a node at 2 AM Sunday."

Why virtual nodes? Doesn't one hash per node work?

One point per node gives you dreadful variance — the largest shard can end up 2–3× the average. With ~100–200 virtual points per physical, the largest shard is only ~1.05× average. Vnodes also spread the recovery load: on a failure, the dead node's arcs get absorbed by many neighbours instead of doubling one.

What happens when a cache node dies mid-request?

Gossip flags PFAIL → FAIL in ~5 s. A replica is promoted primary via a mini-election. Client library retries the in-flight request against the next replica in the ring. Meanwhile a fresh replica is spun up to restore N=3. All told, availability blip is a few seconds and no data is lost (assuming N ≥ 3 with quorum writes).

How do you keep the cache in sync with the source DB?

Two patterns. Write-through — every DB write goes through the cache client, keeping them coupled. Invalidation — the DB (via CDC / Kafka / Debezium) emits change events; a consumer deletes affected cache keys. Facebook's mcsqueal does the second at scale. The rule to memorise: delete, don't update — an invalidation is idempotent, an update-write can race.

What's the thundering-herd fix for a hot key expiring?

Three viable answers: (1) single-flight / lease — first miss gets a "recomputing" lease, everyone else waits; (2) probabilistic early refresh — some fraction of requests before TTL trigger a background refresh; (3) stale-while-revalidate — return stale data instantly, refresh in background.

Alternatives to a hash ring?

Jump consistent hashing (Google, 2014) — O(1) memory, O(log N) time, arithmetic-only, no data structure. Downside: buckets are 0..N-1, not arbitrary. Rendezvous hashing (HRW) — hash(k, node) for every node, take the max. Slightly better distribution, O(N) per lookup. Maglev (Google) — populates a fixed table with permutations; O(1) lookup, minimal disruption. Pick based on cluster size and lookup budget.

How do you handle a cache-DB consistency race?

Classic race: thread A reads DB, thread B writes DB and deletes cache, thread A writes stale value to cache. Fixes: (1) double-delete pattern (invalidate before AND after DB write, with a small delay); (2) versioned writes (only overwrite cache if incoming version > stored); (3) Facebook's lease tokens — cache hands out a lease on miss; only a client with the current lease can populate that key.

🗣️ Interview cheat sheet

30-second pitch: "I'd partition keys with consistent hashing on a 2³² ring using ~150 virtual nodes per physical node — that gives smooth distribution and moves only ~K/N keys on any scale event, versus 100% for modulo. Each key is replicated to the next N-1 unique physical nodes clockwise, with tunable N/W/R quorum. A gossip protocol detects node failures in ~5 s, promotes a replica, and rebalances only the affected arc. Cache-DB consistency uses delete-on-write invalidation via a CDC stream. Hot keys get single-flight leases to prevent stampedes. On AWS this is ElastiCache Redis Cluster or DAX in front of DynamoDB."

Numbers to quote

  • Read QPS ~1M/s cluster-wide; p99 < 1 ms in-DC; single-node ~100K–1M ops/sec.
  • ~150 vnodes per physical node; K/N keys move on rebalance vs ~K for modulo.
  • N=3 replicas with W=R=2 gives read-your-writes and 1-node fault tolerance.
  • Gossip: heartbeat every 1s, fail after ~5s, failover ~15s (ElastiCache).

5 talking points that win the round

  • Consistent hashing + vnodes — the pair, not just one. Vnodes are what make it actually work.
  • K/N keys move — quote this fraction; it's the whole reason for the technique.
  • Quorum N/W/R — W+R>N gives read-your-writes; picks are workload-dependent.
  • Failure detection is gossip, not a coordinator — no SPOF, ~5s convergence.
  • Delete-on-write for DB consistency — never "update cache after update DB"; delete or version.
