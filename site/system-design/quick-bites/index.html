Part 1 · Foundational Building Blocks

1 Client & Server Fundamentals

Gist: Client asks, server answers. Communication over a network via a protocol (usually HTTP/HTTPS).
  • Client = anything initiating a request (browser, mobile app, IoT, another service).
  • Server = a machine/process listening on a port, serving responses.
  • Request/response cycle: DNS lookup → TCP handshake → TLS → HTTP request → server processes → response.
  • Stateless (REST) — each request is self-contained. Stateful (WebSockets, gRPC streams) — connection keeps state.

Latency = network + server processing. Servers can also be clients (service-to-service calls).

2 Database Fundamentals

Gist: Persistent, queryable storage. Choice depends on data shape and access pattern — not religion.
TypeUse whenExample
Relational (SQL)Structured data, ACID, joins, complex queriesPostgreSQL, MySQL
DocumentFlexible schema, nested JSONMongoDB, DynamoDB

ACID (SQL): Atomicity, Consistency, Isolation, Durability. BASE (NoSQL): Basically Available, Soft state, Eventual consistency.

Interview tip: justify by access pattern first, not "SQL vs NoSQL".

3 Vertical vs Horizontal Scaling Fundamentals

Gist: Bigger box vs more boxes.

⬆️ Vertical (scale up)

Add CPU/RAM/SSD to one server. Simple, no code change, but has a hardware ceiling, single point of failure, and gets expensive at the top.

➡️ Horizontal (scale out)

Add more servers behind a load balancer. Near-infinite scale and resilient, but needs stateless design, distributed coordination, and often data partitioning.

Rule of thumb: start vertical, move horizontal when cost or reliability demands it.

4 Load Balancer Fundamentals

Gist: Traffic cop that distributes requests across multiple servers.
  • Layer 4 (Transport) — TCP/UDP, super fast, IP+port routing. (AWS NLB)
  • Layer 7 (Application) — HTTP-aware, routes by path/header/cookie. (AWS ALB, Nginx, HAProxy)
  • Algorithms: Round Robin, Least Connections, IP Hash, Weighted, Latency-based.
  • Also gives you: high availability, SSL termination, health checks.
  • Sticky sessions — route same user to same server. Needed if server holds session state, but prefer stateless.

Watch out for the LB itself becoming a SPOF → use redundant LBs with DNS failover.

5 Database Sharding Core

Gist: Split ONE database horizontally into pieces (shards) across multiple machines.

Why: single DB can't hold the data or handle the write throughput.

Shard key: the field used to route data (e.g. user_id). Choose wisely — hard to change later.

  • Range-based: user_id 1–1M → shard A. Simple, but risks hotspots.
  • Hash-based: hash(user_id) % N. Even distribution, painful to reshard.
  • Consistent hashing: minimizes data movement when adding/removing shards.
  • Geo/Directory-based: route by location or a lookup table.

Costs: no cross-shard joins, harder transactions, rebalancing pain.

6 Database Replication Core

Gist: Copy data across multiple DB nodes for read scale and durability.
  • Leader-Follower: writes to leader, reads from followers. Async replication → replication lag → stale reads.
  • Multi-Leader: multiple write nodes (multi-region). Needs conflict resolution.
  • Leaderless (Dynamo): any node accepts writes; quorum reads/writes (R+W>N). Cassandra, DynamoDB.
  • Sync = safer but slower. Async = fast, risk of data loss on leader crash.

Sharding splits data; replication copies it. Real systems do BOTH.

7 Cache Core

Gist: Store frequently accessed data in fast memory (RAM) to skip slow storage or computation.

Where caches live

  • Client (browser) → CDN (edge) → App-level (Caffeine, Guava) → Distributed (Redis, Memcached) → DB (query cache, buffer pool)

Write policies

  • Write-through: write to cache + DB together. Consistent, slower.
  • Write-back: write cache, flush to DB later. Fast, risk of loss.
  • Write-around: write to DB directly, cache on read miss.

Eviction: LRU, LFU, FIFO, TTL. Cache invalidation is one of the two hardest problems in CS — stale data is often worse than a miss.

Beware: thundering herd, cache stampede, cold start. Fix with request coalescing or stale-while-revalidate.

8 Content Delivery Network (CDN) Core

Gist: Geographically distributed cache for static (and increasingly dynamic) content.
  • Push CDN: you upload assets in advance. Rare, small sites.
  • Pull CDN: CDN fetches from origin on first request, caches with TTL. Most common.
  • Use for: images, JS/CSS, video, downloads, API responses (edge compute).
  • Players: CloudFront, Akamai, Cloudflare, Fastly.

Key concept: Cache-Control headers, ETag, purge/invalidation on deploy.

9 Monolith vs Microservices Core

Gist: One big app vs many small independent services.
MonolithMicroservices
DeployOne artifactIndependent per service
ScaleWhole app scalesScale bottleneck services only
ComplexitySimple ops, complex codeComplex ops, simpler code per service
TeamOne team OKNeeds multiple autonomous teams
FailureAll or nothingPartial failure (need circuit breakers)

Start monolithic; extract services when boundaries and pain are clear. Watch out for the distributed monolith — worst of both worlds.

10 Message Queue Core

Gist: Async, durable buffer between producers and consumers. Decouples systems.
  • Queue (point-to-point): one consumer processes each message. SQS, RabbitMQ.
  • Pub/Sub (topic): every subscriber gets a copy. Kafka, SNS, Google Pub/Sub.
  • Delivery: at-most-once, at-least-once (most common — need idempotent consumers), exactly-once (hard; Kafka approximates).
  • Kafka special: distributed log, partitions, replayable, high throughput. Not just a queue — a streaming platform.

Adds latency + operational complexity. Debugging async flows is harder.

11 API Gateway Core

Gist: Single entry point for clients to reach backend services.

Responsibilities: routing, auth (JWT/OAuth/API keys), rate limiting, request/response transform, SSL termination, logging/metrics/tracing, caching, circuit breaking.

Why: clients don't need to know microservice topology; cross-cutting concerns live in one place.

Examples: AWS API Gateway, Kong, Envoy, Nginx, Zuul.

BFF (Backend for Frontend): separate gateway per client type (web, mobile) tailoring the API.

Watch out for gateway becoming SPOF/bottleneck — deploy HA, keep it lean.

Part 2 · Important / Advanced Concepts

12 CAP Theorem Advanced

Gist: In a distributed system, during a network Partition, you must choose between Consistency and Availability. You always tolerate P.
  • CP: rejects requests during partition to stay consistent (HBase, MongoDB default).
  • AP: serves requests but may return stale data (Cassandra, DynamoDB, Couchbase).
  • CA: only when no partition exists — i.e., single node. Not realistic in distributed systems.

PACELC: extension — if Partitioned pick A/C; Else pick Latency vs Consistency.

13 Consistency Models Advanced

Gist: How "fresh" and "ordered" your reads are across replicas.
  • Strong: every read sees the latest write. Expensive, high latency.
  • Eventual: replicas converge over time. Fast, may return stale reads.
  • Read-your-writes: you always see your own writes (session consistency).
  • Monotonic reads: data never appears to go "backwards" in time.
  • Causal: related events seen in order; unrelated may reorder.
  • Linearizability: strongest — as if operations happen instantly in a global order.

14 ACID vs BASE Advanced

Gist: Transaction guarantees on either end of the spectrum.
ACIDBASE
WhereSQL / RDBMSNoSQL

15 Rate Limiting Advanced

Gist: Throttle requests to protect systems from abuse or overload.
  • Token Bucket: tokens refill at rate R; request consumes 1. Allows bursts.
  • Leaky Bucket: fixed drain rate — smooths traffic.
  • Fixed Window: N requests per minute. Simple, but has burst-at-boundary problem.
  • Sliding Window: rolling count. Smoother and more accurate.

Where: API gateway, LB, or per-service (Redis with atomic counters). HTTP 429 Too Many Requests — include Retry-After.

16 Circuit Breaker Advanced

Gist: Stop calling a failing downstream service to prevent cascading failure.
  • States: Closed (normal) → Open (fail fast) → Half-Open (test recovery).
  • Trip on: error rate, latency threshold, timeout count.
  • Pair with: retries (exponential backoff + jitter), timeouts, bulkheads.
  • Libraries: Hystrix (deprecated), Resilience4j, Polly (.NET), Envoy built-in.

17 Idempotency Advanced

Gist: Same operation, called multiple times, has the same effect as once.

Why: retries are unavoidable in distributed systems. Non-idempotent retry = double-charge.

  • Send an idempotency key in the header; server dedupes on it.
  • Use PUT / DELETE (idempotent by HTTP spec) over POST where possible.
  • Design operations as "set state," not "increment."

Classic example: payments — client sends a UUID, server dedupes.

18 Consistent Hashing Advanced

Gist: Hash keys AND nodes onto a ring. Minimizes reshuffling when nodes are added/removed.
  • Naive hash(key) % N breaks everything when N changes.
  • Virtual nodes: each physical node owns many ring positions → smoother distribution.
  • Used in: Cassandra, DynamoDB, Memcached client, CDNs, load balancers.

19 Bloom Filter Advanced

Gist: Probabilistic set — "definitely not in set" or "probably in set." No false negatives; some false positives.
  • Space-efficient — bits, not full data.
  • Uses: "already crawled?" checks, "key exists?" before disk hit (Cassandra, HBase), spam filters, Chrome's malicious-URL check.
  • Trade-off: more hashes / larger bitmap → fewer false positives.

20 Leader Election Advanced

Gist: Cluster picks one node to coordinate (writes, scheduling, config).
  • Why: avoid split-brain; single writer for consistency.
  • Algorithms: Raft, Paxos, ZAB (ZooKeeper), Bully.
  • Tools: ZooKeeper, etcd, Consul, Kubernetes control plane.
  • Election triggered on heartbeat timeout.

21 Distributed Consensus Advanced

Gist: Get multiple nodes to agree on a value despite failures.
  • Raft: understandable — used in etcd, Consul, CockroachDB.
  • Paxos: original but notoriously hard — Google Chubby, Spanner.
  • Quorum: majority (N/2 + 1) must agree. R+W>N gives strong reads.

22 Event-Driven Architecture Advanced

Gist: Services communicate by emitting and consuming events (facts about what happened).
  • Event Sourcing: store events, not state. Rebuild state by replaying.
  • CQRS: command (write) and query (read) models separated. Optimized independently.
  • Saga: long-running distributed transaction — chain of local transactions + compensating actions. Replaces 2PC in microservices.

Trade-off: eventual consistency and harder debugging, but great scalability + auditability.

23 Two-Phase Commit vs Saga Advanced

Gist: Two ways to make multiple services agree on a transaction.

2PC

Coordinator asks all nodes to "prepare," then "commit." Blocks on failure — rare in modern microservices.

Saga

Series of local transactions; if one fails, run compensating transactions. Better fit for distributed systems.

25 Data Partitioning Strategies Advanced

Gist: Different ways to split data across storage.
  • Vertical: split table by columns (rarely-used cols to another table).
  • Horizontal (Sharding): split rows across nodes.
  • Functional: split by feature/service (users DB, orders DB).
  • Directory-based: lookup service maps key → shard.

26 Indexing Advanced

Gist: Extra data structure to speed up reads — at the cost of writes and space.
  • B-Tree: default for relational DBs, great for range queries.
  • Hash index: O(1) equality lookup, no ranges.
  • LSM Tree: write-optimized (Cassandra, RocksDB, LevelDB).
  • Inverted index: full-text search (Elasticsearch, Lucene).
  • Composite index: multi-column — order matters.

Rule: index columns in WHERE, JOIN, ORDER BY. Don't over-index writes.

27 Batch vs Stream Processing Advanced

Gist: Process data at rest vs in motion.
  • Batch (Hadoop, Spark): process large data at rest — high throughput, high latency.
  • Stream (Kafka Streams, Flink, Spark Streaming): process data in motion — low latency, real-time.
  • Lambda architecture: batch + stream layer. Complex.
  • Kappa architecture: stream only, batch as replay. Simpler, modern preference.

28 Backpressure Advanced

Gist: Slow consumer signals fast producer to slow down. Prevents OOM/collapse.
  • Mechanisms: bounded queues, reactive streams (Project Reactor, RxJava), TCP flow control, Kafka consumer-lag as signal.

29 Observability Advanced

Gist: The 3 pillars — you can't fix what you can't see.
  • Logs: discrete events (structured JSON). ELK, Loki, Splunk.
  • Metrics: numeric time-series. Prometheus + Grafana, Datadog.
  • Traces: follow request across services. Jaeger, Zipkin, OpenTelemetry.
  • RED method: Rate, Errors, Duration (services).
  • USE method: Utilization, Saturation, Errors (resources).

30 SLA · SLO · SLI Advanced

Gist: Reliability targets you actually measure and commit to.
  • SLI: what you measure (e.g., p99 latency).
  • SLO: internal target (p99 < 200ms 99.9% of the time).
  • SLA: contract with customers, with penalties.
  • Error budget: 1 − SLO. Spend on risk (deploys, experiments).

Availability math: 99.9% ≈ 8.76 hrs/year down; 99.99% ≈ 52 min; 99.999% ≈ 5 min.

31 Security Essentials Advanced

Gist: Bare-minimum you should mention when the interviewer asks "what about security?"
  • AuthN vs AuthZ: who you are vs what you can do.
  • OAuth 2.0 / OIDC: delegated auth — access tokens (short) + refresh tokens.
  • JWT: self-contained token. Stateless but hard to revoke — keep TTL short.
  • TLS everywhere, even inside your VPC (zero trust).
  • Secrets: Vault, AWS Secrets Manager. Never in code.
  • OWASP Top 10: SQLi, XSS, CSRF, SSRF, IDOR, broken auth.
  • Encryption: at rest (KMS) + in transit (TLS).
  • DDoS: CDN + WAF + rate limiting.

32 Networking Basics Advanced

Gist: The wires and rules under everything.
  • DNS: name → IP. TTLs matter. Recursive → root → TLD → authoritative.
  • HTTP versions: 1.1 (keep-alive), 2 (multiplexing), 3 (QUIC/UDP).
  • TCP vs UDP: reliable/ordered vs fast/lossy. UDP for gaming, DNS, video.
  • Cloud infra: CIDR, VPC, subnets, NAT, security groups.

33 Storage Classes Advanced

Gist: Different storage for different access patterns.
  • Block storage: low-latency, mountable (EBS). For DBs, VMs.
  • Object storage: HTTP API, infinite scale, cheap (S3, GCS). Blobs, backups.
  • File storage: POSIX-compliant (EFS, NFS). Shared file systems.
  • Cold storage: Glacier — archival, cheap, retrieval in minutes/hours.

34 Concurrency Control Advanced

Gist: How multiple writers avoid stepping on each other.
  • Optimistic locking: assume no conflict; check on write (version number/ETag). Great for low-contention.
  • Pessimistic locking: lock row while updating. Blocks others.
  • MVCC: multi-version — readers don't block writers (Postgres, Oracle).

35 GeoDNS & Multi-Region Advanced

Gist: How you serve users globally and survive an entire region going down.
  • GeoDNS / Anycast: route users to nearest region.
  • Active-Active: all regions serve traffic. Complex data replication.
  • Active-Passive: standby region for failover. Simpler, wastes capacity.
  • RPO / RTO: Recovery Point (data loss tolerance) / Recovery Time (downtime tolerance).

36 Feature Flags & Progressive Delivery Advanced

Gist: Ship safely by decoupling release from deploy.
  • Feature flag: toggle features without redeploy.
  • Canary: roll out to 1% → 10% → 100%.
  • Blue-Green: two environments; instant cutover, easy rollback.
  • Shadow traffic: mirror prod traffic to new version, don't return response.

🗣️ Interview cheat sheet — say this out loud

30-second framework (memorize the order):
1. Clarify requirements — functional + non-functional (scale, latency, consistency).
2. Estimate scale — QPS, storage, bandwidth.
3. API design — endpoints, request/response.
4. Data model — schema, DB choice.
5. High-level architecture — client → LB → services → DB / cache / queue.
6. Deep dive on the 1–2 hardest parts (sharding, caching, consistency).
7. Bottlenecks + trade-offs — what breaks at 10× scale? How to fix?

One-liners you can drop verbatim

  • "Read-heavy?" — Add cache + read replicas. "Write-heavy?" — Shard + async processing.
  • "Always ask:" QPS, data size, read/write ratio, latency SLO, consistency needs.
  • "CAP under partition:" pick Consistency or Availability. You always tolerate P.
  • "Retries are mandatory," so consumers must be idempotent (idempotency key).
  • "Cache invalidation is one of the two hardest problems in CS" — mention TTL, write-through, or stale-while-revalidate.
  • "Start monolithic;" extract microservices when boundaries and pain are clear.
  • "Add a message queue" to smooth traffic spikes and decouple services.
  • "Deploy the LB and API gateway in HA;" they can otherwise become the SPOF.
