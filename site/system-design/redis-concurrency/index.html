How Redis Handles Concurrency

The single-threaded event loop that serves millions of ops/sec — plus the MULTI/WATCH transactions, Lua atomicity, and Redlock/single-node distributed locks for coordinating across many processes.

🎯 Real-world scenario

What we're building & where it's used

Redis is famous for being fast — millions of operations per second on a single node — and yet it's single-threaded for command execution. That sounds like a contradiction: how does one thread serve thousands of concurrent clients without any locks, mutexes, or race conditions? And once you scale beyond one node, how do you coordinate across processes when Redis itself has no atomic cross-node primitive? That's what "how Redis handles concurrency" is really asking, and it splits cleanly into two questions.

Within a single Redis instance, concurrency is solved by not having any — the event loop processes one command at a time, so every command is inherently atomic. Between commands, clients coordinate with server-side primitives: MULTI/EXEC transactions, WATCH for optimistic locking (CAS), Lua scripts as atomic units, and single atomic commands like INCR and SET NX PX. Across many Redis nodes or many application processes, you need distributed coordination — a single-node lock via SET NX PX for the common case, or the Redlock algorithm across a quorum of Redis nodes for safety under failover (though Redlock is famously controversial — Martin Kleppmann argues it's still unsafe for correctness locks without fencing tokens).

Real uses: this pattern is behind rate limiters (Stripe, AWS API Gateway), caching layers (Twitter, GitHub, Instagram), session stores, leaderboards, distributed job queues (Sidekiq, Bull), and countless "prevent double-processing" locks. In an interview, "how does Redis handle concurrency" tests whether you understand event loops, atomicity, optimistic locking, and the CAP-flavored trade-offs of a leader-based cache — a rich topic in a compact system.

🧑‍🎓 In laymen terms

One incredibly fast bank teller and a shared clipboard

Picture a small village bank on a Friday afternoon. Everyone in the village wants to withdraw money at once, and things could get ugly. One approach is to hire twenty tellers — but then they start arguing: "Wait, I already gave Maya her cash!" "But her account said she still had 500 rupees!" The tellers keep stepping on each other. So the bank tries a different trick: they hire one incredibly fast teller, put everyone into a single line, and say — this teller finishes each customer in a blink, and because there's only one, nobody can argue about who did what first. The line looks long, but it moves so quickly that customers barely notice. That's the whole idea behind this system's speed.

Now zoom out. In the modern world, a company like Instagram or Uber doesn't have one bank — it has hundreds of little "bank branches" scattered around the world, and hundreds of ticket-issuing machines (their apps) all sending requests at once. Sometimes two machines send the same request at the same instant: "Book this concert seat for me." Both can't win. So they use a clever second trick: a shared clipboard on the wall that anyone can grab, but only one person at a time. Whoever grabs the clipboard first gets to book the seat; everyone else sees the clipboard is taken and waits their turn. To make sure a forgetful person doesn't hold the clipboard forever, it comes with a tiny sand timer glued to it — after 30 seconds the clipboard automatically pops back onto the wall.

That's why when you tap "buy" on the last concert ticket, or "like" on a photo the exact millisecond your friend does, you never end up double-charged and the like count never goes wrong. One super-fast teller, one shared clipboard with a sand timer — and the whole internet stays civilised.

📋 Requirements & scale

Requirements and back-of-the-envelope math

The two concurrency problems Redis has to solve

  • Intra-server concurrency — many clients hitting one Redis node concurrently. Redis must serialize command execution while sustaining high throughput and sub-ms latency.
  • Inter-process coordination — many client processes wanting to acquire the same lock, run the same critical section once, or perform "check-then-set" atomically. Redis must offer primitives (transactions, WATCH, Lua, SET NX) so applications can build correct concurrency on top.
  • Distributed correctness — coordination that must survive a Redis node failing and a replica being promoted (Redlock territory).

Non-functional requirements that shape the design

  • Sub-microsecond command execution for common ops (GET/SET/INCR) — the whole point of Redis.
  • Predictable latency: no other client's command should delay yours beyond the current command's own runtime.
  • No lock overhead — no coarse GIL to fight; the event loop eliminates the concept of a race between concurrent commands.
  • Well-defined semantics under contention — WATCH/MULTI/EXEC must abort the transaction when a watched key was touched, so lost updates are impossible.
  • Safety under failover for distributed locks — the harder property, and where Redlock is proposed (and debated).

🏗️ High-level architecture

How the pieces fit together

Redis's concurrency architecture has three layers, from bottom to top: (1) the event loop inside one Redis process, (2) client-side primitives (transactions, WATCH, Lua, atomic commands) that let apps coordinate within one node, and (3) distributed coordination across nodes and application processes via patterns like SET NX PX and Redlock.

The event loop uses I/O multiplexing (epoll on Linux, kqueue on macOS): a single thread waits on many client sockets simultaneously and wakes up whenever any of them is readable. It then reads the command, executes it in memory (dictionary lookup, list push, whatever), writes the reply back to the socket, and returns to the wait. Nothing runs in parallel with the command — no other client can observe a partial state, and no lock is needed. This is exactly like Node.js's design, and it's why "single-threaded" is not a scaling weakness for the type of workload Redis targets.

Client → server data flow I/O threads (Redis 6+, parallel sockets only) Single-threaded event loop (serializes execution) Distributed coordination layer

What happens when 1,000 clients send commands at the same instant

  1. The kernel wakes the Redis process via epoll with a list of readable sockets (all 1,000 of them).
  2. Redis reads command bytes from each socket — with Redis 6+, this parsing step is parallelized across I/O threads, up to 8. Command execution is not.
  3. Parsed commands enter the main thread's queue. The event loop executes them one at a time in receive order. Each is atomic — no other client sees a partial state.
  4. Replies are written back to sockets (again optionally via I/O threads).
  5. Slow commands (a big SUNION, a KEYS scan, an expensive Lua script) block all other clients until they finish. This is the one big trade-off — hence the standing advice to avoid slow commands or run them on a replica.

🔍 Component deep-dive

The single-threaded event loop — where the concurrency "vanishes"

Redis's own docs describe it as "mostly single-threaded" using multiplexing: one process serves every client request by cycling through them, but never blocks on syscalls (Redis uses non-blocking I/O with epoll/kqueue for readiness notification). Because a single thread does all command execution, two commands never truly run at the same time — the concept of a race between them doesn't exist. This is why Redis has no user-visible locks and yet safely supports thousands of concurrent clients. The elegant consequence: every individual Redis command is atomic by definition, so a single INCR counter under contention from a million clients never loses an increment.

Why is it fast, then? Two reasons: (1) data lives in RAM, so each operation is sub-microsecond; and (2) the loop never blocks on I/O — epoll_wait returns readiness events for many sockets, and Redis handles each in turn. In fact this is exactly the Node.js model. The catch, as Redis docs stress explicitly: "when a request is slow to serve, all the other clients will wait." So KEYS * or a huge SUNION stalls everyone. The mitigation is to avoid slow commands (use SCAN-family, run heavy queries on a replica) and use pipelining so many small commands amortize the network round-trip.

Redis 6+ multi-threaded I/O — a subtle addition, not a rewrite

Redis 6 added I/O threads (io-threads config, up to 128) that parallelize reading from and writing to client sockets. Command parsing can also happen on these threads. But command execution stays single-threaded on the main event loop — the atomicity guarantee is unchanged. This is a targeted fix for the case where the bottleneck was syscall overhead on the sockets (large deployments with many clients), and it delivers real throughput gains (multiple × RPS on network-bound workloads) without breaking the mental model.

Atomic commands: the simplest coordination primitive

Because every command is atomic, many "concurrency problems" have a trivial one-command solution:

  • INCR counter — atomic increment. Used for rate limiter tokens, ID generation, page views.
  • GETSET key value — get old value, set new one, atomically.
  • SETNX key value (aliased SET key value NX) — set only if key does not exist. The building block for locks.
  • SET key value NX PX 10000 — set only if absent, expire in 10 s. The safe single-node distributed lock idiom (auto-release on crash).
  • LPUSH / RPOPLPUSH — atomic list moves for queues.
  • ZADD / ZINCRBY — atomic sorted-set updates for leaderboards.

MULTI / EXEC / DISCARD — batching commands atomically

Redis's version of a transaction is optimistic and simple: MULTI starts a queue, subsequent commands are stashed (not run), and EXEC runs them all as one indivisible unit — no other client can interleave. DISCARD throws the queue away. Two important non-obvious properties:

  • No rollback. If a command inside EXEC fails at runtime (say, INCR on a non-numeric string), the failed command errors out and the rest still execute. Redis's rationale: runtime failures are programmer bugs, not something to auto-heal. Handle them at the client.
  • Isolation is trivial because the event loop runs the whole batch before any other command. There's no partial visibility.

What MULTI/EXEC alone can't do is a read-then-write that depends on the read (like "if x > 100, decrement it"). For that you need WATCH.

WATCH — optimistic concurrency control (CAS)

WATCH key tells Redis: "keep an eye on this key; if any client modifies it before my EXEC, abort my transaction." Combined with MULTI/EXEC, this is optimistic locking — a check-and-set equivalent that never blocks. The client reads the current value, decides what to write, and executes; if someone else got there first, EXEC returns nil and the client retries.

# Classic conditional decrement — subtract 10 if balance ≥ 10, else fail.
WATCH balance
val = GET balance
if val < 10: UNWATCH; abort
MULTI
  DECRBY balance 10
EXEC   # returns nil if someone else touched `balance` between WATCH and EXEC

WATCH is the piece that lets Redis handle contended write patterns correctly without pessimistic locking. It's the same optimistic-concurrency pattern used by ETag / If-Match in HTTP and by CAS in relational databases.

Lua scripting (EVAL) — atomic multi-step logic

A Redis Lua script runs on the server as one atomic step. While the script executes, no other command runs — same guarantee as a single command. This makes Lua the tool for logic that can't be expressed as one command and doesn't fit MULTI/EXEC (because it needs conditional reads). Classic examples: the atomic token-bucket rate limiter (refill, check, decrement, return in one shot); a reliable RPOPLPUSH-style dequeue with acknowledgement; a fair semaphore. Interviewer follow-up: "how would you implement rate limiting on Redis?" The best answer is a Lua script — it's the pattern Stripe and countless others actually use.

Single-node distributed lock: SET NX PX

The idiomatic way to get a lock is:

SET lock:job42  NX PX 10000   # set-if-absent, 10 s TTL

NX makes it a check-and-set. PX auto-releases if the holder crashes (no orphaned lock). The unique token is critical for release safety: to unlock you must run a Lua script that checks GET lock:job42 == token and only then deletes — otherwise a slow client whose lease already expired could delete a lock that another holder now owns.

# Safe release: check-and-delete atomically via Lua.
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

This is the safe, simple, single-node lock — good enough for the vast majority of "make sure this cron job only runs once at a time" cases.

Redlock — a lock across N independent Redis masters

Single-node SET NX PX fails safety under Redis failover: replication is asynchronous, so if the master accepts a lock, then dies before replicating, the replica promoted in its place has no record of the lock — two clients can now hold it. To close that gap, Redlock (proposed by Redis creator Salvatore Sanfilippo) requires the client to acquire the lock on a majority of N independent Redis masters (N is typically 5, so 3 acquisitions needed):

  1. Client generates a unique random token.
  2. Client records the current time T₀, then attempts SET NX PX on each of the N Redis instances with a short per-instance timeout.
  3. Client computes elapsed time Δ = now − T₀. Success requires: (a) it got the lock on ≥ ⌊N/2⌋+1 nodes, AND (b) Δ < the TTL.
  4. Effective lock validity = TTL − Δ − clock-drift-factor (typically ~1% of TTL). If validity is not positive, the lock is not held.
  5. To release, run the safe check-and-delete Lua on every node.

The Kleppmann critique — and when Redlock is NOT enough

The industry debate: Martin Kleppmann's essay "How to do distributed locking" argues Redlock is unsafe for correctness locks (where a failure = data corruption) because it doesn't defend against process pauses (a client GCs for 30 s during its lease and wakes up thinking it still holds the lock), clock jumps (Redis uses non-monotonic time), or network delays. His prescription: use a real consensus system (ZooKeeper, etcd, Chubby) and, most importantly, enforce fencing tokens — the lock service issues a monotonically increasing token on each acquisition, and the protected resource rejects any write with a smaller token. Redlock has no fencing tokens.

The practical takeaway: for efficiency locks (avoiding duplicate work, e.g. "only one cron runs the report at a time"), single-node SET NX PX is fine — an occasional double-run is annoying, not catastrophic. For correctness locks (financial transactions, unique constraints), don't rely on Redis locks alone — pair them with fencing tokens the storage layer validates, or use ZooKeeper/etcd for the lock itself.

Redis Cluster — the multi-node story

Redis Cluster shards data across up to 1,000 nodes via 16,384 hash slots (a key's slot = CRC16(key) mod 16384). Each master owns a range of slots and replicates to one or more replicas. Concurrency implications: each node is still single-threaded, so individual commands remain atomic. Multi-key transactions require the keys to hash to the same slot — use {tag}-style hash tags (e.g. user:{42}:profile and user:{42}:sessions) to force co-location when you need cross-key atomicity. Replication is asynchronous (fast but eventually consistent), so a write acked on the master can be lost if it fails before replicating — the same trade-off behind Redlock's motivation.

🧮 The DSA behind it

Data structures & algorithms

The primitives that make Redis's concurrency model work are a small set of classic techniques applied precisely. Concurrency is achieved by serialization on the event loop, not locks; contention is resolved via optimistic concurrency (WATCH) and compare-and-swap (SET NX + unique token); distributed safety uses quorum consensus; hot-key protection uses lazy TTL + probabilistic sampling.

💻 C# implementation

Three canonical patterns using StackExchange.Redis, the standard .NET Redis client: (1) a safe single-node distributed lock with unique-token release, (2) a WATCH-based optimistic transaction for conditional decrement, and (3) an atomic token-bucket rate limiter in Lua — the pattern used in production by Stripe et al.

using StackExchange.Redis;

// ---- (1) Single-node distributed lock: SET NX PX + unique-token safe release ----
public sealed class RedisLock : IAsyncDisposable
{
    private readonly IDatabase _db;
    private readonly RedisKey _key;
    private readonly RedisValue _token;   // unique per acquisition
    private bool _held;

    private const string ReleaseLua = @"
      if redis.call('GET', KEYS[1]) == ARGV[1] then
          return redis.call('DEL', KEYS[1])
      else
          return 0
      end";

    public RedisLock(IDatabase db, string key)
    {
        _db = db; _key = key;
        _token = Guid.NewGuid().ToString();  // unique token guards against expired-lease deletes
    }

    // SET key token NX PX ttl — atomic acquire-if-absent with auto-release TTL.
    public async Task<bool> TryAcquireAsync(TimeSpan ttl)
    {
        _held = await _db.StringSetAsync(_key, _token, ttl, When.NotExists);
        return _held;
    }

    // Safe release: check token == mine, then DEL (atomic Lua).
    public async ValueTask DisposeAsync()
    {
        if (!_held) return;
        await _db.ScriptEvaluateAsync(ReleaseLua,
            new RedisKey[] { _key },
            new RedisValue[] { _token });
        _held = false;
    }
}

// ---- (2) WATCH-based optimistic transaction: conditional decrement ----
// "if balance ≥ amount, subtract amount". Retries if someone else raced us.
public async Task<bool> TryDebitAsync(IDatabase db, RedisKey key, int amount)
{
    for (int attempt = 0; attempt < 5; attempt++)
    {
        // StackExchange.Redis exposes optimistic tx via CreateTransaction() with AddCondition().
        var current = (int)await db.StringGetAsync(key);
        if (current < amount) return false;                       // insufficient

        var tx = db.CreateTransaction();
        tx.AddCondition(Condition.StringEqual(key, current));         // WATCH-equivalent CAS
        _ = tx.StringDecrementAsync(key, amount);
        if (await tx.ExecuteAsync()) return true;                 // EXEC succeeded
        // else: someone raced; loop & retry
    }
    throw new Exception("debit contention: gave up after 5 retries");
}

// ---- (3) Atomic token-bucket rate limiter (single Lua call) ----
private const string RateLimitLua = @"
  local key      = KEYS[1]
  local rate     = tonumber(ARGV[1])       -- tokens per second (r)
  local capacity = tonumber(ARGV[2])       -- bucket size (b)
  local now      = tonumber(ARGV[3])       -- caller's clock (seconds)
  local cost     = tonumber(ARGV[4])

  local b = redis.call('HMGET', key, 'tokens', 'ts')
  local tokens = tonumber(b[1]) or capacity
  local ts     = tonumber(b[2]) or now
  tokens = math.min(capacity, tokens + (now - ts) * rate)   -- lazy refill
  local ok = tokens >= cost
  if ok then tokens = tokens - cost end
  redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', key, math.ceil(capacity / rate) + 1)
  return ok and 1 or 0
";

public async Task<bool> TryAdmitAsync(IDatabase db, string user, int rate, int burst)
{
    try
    {
        var res = (long)await db.ScriptEvaluateAsync(RateLimitLua,
            new RedisKey[] { $"rl:{user}" },
            new RedisValue[] { rate, burst, DateTimeOffset.UtcNow.ToUnixTimeSeconds(), 1 });
        return res == 1;
    }
    catch (RedisException) { return true; }  // FAIL OPEN: limiter must not become the outage
}

Three takeaways: (1) The lock uses a unique token so a slow client whose lease expired can't accidentally delete another holder's lock — that's the safety property. (2) The optimistic transaction uses AddCondition as a WATCH — the transaction only commits if the key still has the value we read. (3) The rate limiter is a single Lua call; Redis's atomicity guarantees the read-modify-write is race-free, regardless of how many app servers concurrently invoke it. For Redlock across N nodes you'd use a library like RedLock.net (or roll it yourself) — but for most workloads the single-node lock above is enough.

⚖️ Trade-offs, bottlenecks & likely follow-ups

Single-threaded = beautifully simple, but slow commands hurt everyone. Because one command executes at a time, a big KEYS * or a huge SUNION blocks every other client. Redis's docs explicitly call this out. Mitigations: avoid slow commands (use SCAN, SSCAN, HSCAN, ZSCAN), run analytics queries on a replica, and profile with SLOWLOG.

MULTI/EXEC has no rollback. If a queued command errors at runtime, the rest still execute. That surprises people coming from SQL. The Redis philosophy: runtime errors are programmer bugs; don't hide them with rollback. Handle them at the client.

Async replication ⇒ Redlock trade-off. A single-node lock is unsafe under failover; Redlock closes that gap with a majority quorum but adds latency and is still not safe for correctness locks (per Kleppmann) without fencing tokens on the resource. For efficiency locks, single-node is enough; for correctness, use fencing tokens or a real consensus system.

Cluster mode restricts multi-key ops. In Redis Cluster, transactions and Lua scripts can only touch keys that live in the same slot — otherwise you get a CROSSSLOT error. Use {tag}-style hash tags to co-locate related keys.

WATCH under high contention can starve. Optimistic concurrency retries on conflict; if a hot key gets constant writes, WATCH-based transactions may repeatedly abort. For truly hot counters, prefer INCR/DECRBY directly or a Lua script.

Q: If Redis is single-threaded, how does it handle 100,000 concurrent clients?

The network is concurrent — one thread polls thousands of sockets via epoll and services them in turn. Commands are cheap (sub-microsecond in RAM), so the queue drains fast. In-flight parallelism is not the goal; low latency and simple atomicity are.

Q: What's the difference between MULTI/EXEC and Lua?

Both run as a single atomic step. MULTI/EXEC batches pre-declared commands with optional WATCH-based CAS but can't include conditional logic. Lua lets you branch, loop, and read intermediate values on the server — the right tool when you need "if X then do Y else do Z" in one atomic step.

Q: Is SET NX PX enough for a distributed lock?

For efficiency locks (avoid duplicate work) — yes, plus a unique-token Lua release. For correctness locks (double-charging must not happen), no — replication is async so failover can lose the lock. Use Redlock (majority quorum) or, if the workload truly demands safety, a consensus system with fencing tokens the resource validates.

Q: How do Redis 6 I/O threads relate to concurrency?

They parallelize socket reads/writes and parsing across multiple threads, so network-bound workloads get more RPS. Command execution remains single-threaded, so the atomicity model is unchanged — you don't need to worry about new race conditions.
